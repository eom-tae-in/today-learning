## 📌 오늘 학습 계획

1. **Swagger 기반 API 명세 확인**
    - 연동할 API의 경로, HTTP 메서드, 파라미터 전달 위치, 필수값을 확인한다.
    - 응답 데이터 구조와 상태 코드를 살펴보고, 기존 프론트에서 기대하는 형식과 비교한다.
2. **기존 프론트엔드와 백엔드 연결**
    - 프론트의 API 호출 주소·메서드·전달값을 백엔드 Controller의 요청 매핑에 맞춘다.
    - 브라우저에서 요청을 보내고, 서버 응답이 프론트의 데이터 처리와 화면 표시로 이어지는지 확인한다.
3. **CORS 발생 조건 확인과 설정 개선**
    - 실제 프론트와 백엔드 주소의 스킴·호스트·포트를 비교하여 출처가 어떻게 구분되는지 확인한다.
    - 브라우저의 요청·응답 헤더와 서버의 CORS 설정을 대조하여 허용 출처와 적용 경로를 점검한다.
    - 확인한 원인에 맞춰 설정을 조정하고 같은 요청을 다시 실행한다.
4. **연동 결과 검증과 정리**
    - 실제 응답 상태 코드와 본문을 Swagger 명세 및 화면에 표시되는 값과 대조한다.
    - CORS 개선 전후의 요청 결과를 비교하고, 원인·수정한 설정·확인 결과를 정리한다.

## 🔄 복습할 부분

- 같은 검색 조건을 쿼리·폼 본문·JSON 본문으로 각각 표현하고, Controller의 수신 애노테이션과 대조한다. 데이터 전달 위치가 동기·비동기를 결정하지 않는 이유도 설명한다.
- `GET /products/10`을 기준으로 Controller → Service → Mapper → SQL → DTO → JSON 흐름을 추적하고, Mapper의 `namespace`, SQL의 `id`, `@Param`, `resultType`이 연결되는 지점을 코드에서 확인한다.
- `mybatis-config.xml`과 Mapper XML의 역할을 비교하고, `product_name`을 `productName`으로 매핑하는 설정과 각 파일을 읽어 들이는 위치 설정을 찾아 확인한다.
- 상품 조회의 200·404 명세를 정상 조회와 대상이 없는 경우의 실제 반환 분기에 대조한다.
- `@RequestParam`, `@Param`, `@Parameter`, `@Qualifier`를 기존 코드에서 찾아 요청 수신·SQL 파라미터 연결·문서화·빈 선택의 역할로 구분한다.

## 🤔 예상되는 어려움

- 요청 데이터의 전달 위치나 응답 필드명이 맞지 않아 통신 오류와 데이터 처리 오류를 혼동할 수 있다.
- Swagger에서 성공한 요청이 프론트에서는 실패할 때, API 자체의 문제와 출처 차이에 따른 CORS 문제를 구별하기 어려울 수 있다.
- Mapper 인터페이스·XML·공통 설정의 연결 지점을 놓쳐 SQL 파라미터 전달과 결과 매핑 과정을 혼동할 수 있다.
- Swagger 문서에 작성한 설명이나 상태 코드가 실제 요청 처리와 반환 동작까지 결정한다고 오해할 수 있다.
