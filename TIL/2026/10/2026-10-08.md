오늘은 Users Microservice에 로그인 기능을 연결하고, 인증에 성공한 사용자에게 JWT를 발급한 뒤 API Gateway에서 토큰을 검증하는 흐름을 학습했다. 이어 여러 서비스에 흩어진 설정을 Spring Cloud Config로 외부화하고, 실행 중인 서비스가 Spring Boot Actuator를 통해 변경된 설정을 다시 읽는 과정까지 살펴봤다.

학습 범위는 Section 7 전체와 Section 8의 Spring Boot Actuator까지다. 아래 코드는 강의 자료의 클래스와 처리 흐름을 바탕으로 구성했으며, 원문을 그대로 옮긴 코드는 별도로 표시하고 나머지는 설명용 예제로 구분한다. 개인 실습 결과나 오류 해결 이력은 제공되지 않았으므로, 실행 예시는 확인 방법으로 설명한다.

> 로그인은 사용자를 확인하는 과정이고, JWT 검증은 이후 요청이 유효한 인증 증명을 가지고 있는지 확인하는 과정이다. Config Server는 그 과정에 필요한 설정을 공급하고, refresh는 실행 중인 서비스가 설정을 다시 읽도록 한다.

- Git 저장소, Config Server, Config Client의 역할과 Actuator refresh의 적용 범위를 구분할 수 있다.

### 1. Spring Security로 로그인 요청 인증하기

회원가입으로 사용자 정보를 저장했다면, 다음에는 요청자가 그 계정의 실제 소유자인지 확인해야 한다. 이메일이 존재하는지만 확인해서는 부족하고, 입력한 비밀번호가 저장된 비밀번호 해시와 일치하는지도 검증해야 한다.

강의에서는 별도의 로그인 Controller 대신 Spring Security의 **인증 필터**를 사용한다. 필터는 Controller에 도달하기 전 요청을 처리할 수 있으므로, 로그인 처리와 일반 비즈니스 요청 처리를 분리할 수 있다.

#### 1.1 인증과 인가는 서로 다른 질문에 답한다

**인증(Authentication)**은 “누구인가?”를 확인하는 작업이다. **인가(Authorization)**는 “이 작업을 할 권한이 있는가?”를 판단하는 작업이다.

|구분|확인하는 내용|예시|
|---|---|---|
|인증|요청자의 신원|이메일과 비밀번호가 일치하는지 확인한다.|
|인가|특정 자원에 대한 접근 권한|일반 회원이 관리자 기능을 사용할 수 있는지 확인한다.|
|로그인|최초 자격 증명 검증|비밀번호를 확인한 뒤 토큰을 발급한다.|
|토큰 검증|이후 요청의 인증 증명 검증|서명과 만료 시각을 확인한다.|

유효한 토큰을 가지고 있다는 사실만으로 모든 사용자 정보에 접근할 권한이 생기는 것은 아니다. 자신의 정보만 조회할 수 있는지, 관리자 권한이 필요한지는 별도의 인가 규칙으로 판단해야 한다.

#### 1.2 Gateway 외부 경로와 서비스 내부 경로를 나눈다

강의의 로그인 API는 Gateway 사용 여부에 따라 요청 경로가 달라진다.

|기능|Gateway 요청 경로|User Service 내부 경로|메서드|
|---|---|---|---|
|회원가입|`/user-service/users`|`/users`|`POST`|
|로그인|`/user-service/login`|`/login`|`POST`|
|회원 목록 조회|`/user-service/users`|`/users`|`GET`|
|강의 상태 확인|`/user-service/health-check`|`/health-check`|`GET`|

Gateway가 `/user-service` 접두사를 제거해야 User Service의 경로와 맞아진다. 외부 URL과 내부 URL을 혼동하면, 정상적으로 로그인 필터를 등록했어도 요청이 필터의 처리 경로에 도달하지 않을 수 있다.

다음은 로그인 요청을 나타내는 설명용 예제다. 이메일은 이 서비스에서 로그인 식별자로 사용된다.

```
POST /user-service/login HTTP/1.1
Host: localhost:8000
Content-Type: application/json

{
  "email": "member@example.com",
  "password": "example-password"
}
```

`RequestLogin`은 이 JSON 본문을 Java 객체로 읽기 위한 요청 모델이다. 회원가입 모델과 달리 로그인에 필요한 이메일과 비밀번호만 담으면 된다.

#### 1.3 각 인증 객체의 책임을 구분한다

강의의 중심 클래스는 `AuthenticationFilter`, `WebSecurity`, `UserService`, `UserServiceImpl`, `UserRepository`다. 이 클래스들은 Spring Security가 정한 인증 계약과 연결된다.

|구성 요소|역할|중요한 입력 또는 출력|
|---|---|---|
|`AuthenticationFilter`|로그인 요청을 읽고 인증을 요청한다.|JSON 본문을 자격 증명으로 변환한다.|
|`UsernamePasswordAuthenticationToken`|인증에 필요한 정보 또는 인증 결과를 표현한다.|로그인 식별자, 비밀번호, 권한을 담는다.|
|`AuthenticationManager`|적절한 인증 제공자에게 처리를 위임한다.|인증 성공 결과 또는 인증 예외를 반환한다.|
|`DaoAuthenticationProvider`|사용자 정보와 비밀번호를 검증한다.|`UserDetailsService`와 `PasswordEncoder`를 사용한다.|
|`UserDetailsService`|인증에 필요한 사용자 정보를 조회한다.|`loadUserByUsername()`이 `UserDetails`를 반환한다.|
|`UserRepository`|DB에서 회원을 조회한다.|강의에서는 `findByEmail()`을 사용한다.|
|`PasswordEncoder`|입력 비밀번호와 저장된 해시를 비교한다.|`matches()`가 일치 여부를 반환한다.|
|`SecurityFilterChain`|요청별 보안 규칙과 필터를 연결한다.|허용 경로, 인증 요구, 필터 순서를 설정한다.|

`UsernamePasswordAuthenticationToken`의 “Token”은 JWT를 의미하지 않는다. Spring Security 내부에서 인증 정보를 운반하는 Java 객체이며, 클라이언트에 보내는 JWT 문자열과 역할이 다르다.

#### 1.4 로그인 요청부터 인증 성공까지의 호출 순서

```
AuthenticationFilter가 로그인 JSON을 읽는다
    ↓ 이메일과 비밀번호를 자격 증명 객체에 담는다
AuthenticationManager에 authenticate를 요청한다
    ↓ 적절한 인증 제공자가 처리를 맡는다
DaoAuthenticationProvider가 사용자 정보를 조회한다
    ↓ UserDetailsService가 Repository에서 이메일로 회원을 찾는다
UserDetails에 저장된 비밀번호 해시와 계정 상태를 전달한다
    ↓ PasswordEncoder가 입력 비밀번호를 검증한다
인증된 Authentication 객체를 반환한다
    ↓ 로그인 성공 처리를 실행한다
AuthenticationFilter의 successfulAuthentication을 호출한다
```

여기서 `UserDetailsService`는 사용자 정보를 **조회**하는 역할을 맡는다. 비밀번호의 최종 비교는 일반적인 DAO 인증 흐름에서 `DaoAuthenticationProvider`가 `PasswordEncoder`를 사용해 수행한다.

회원이 없으면 `UsernameNotFoundException` 같은 인증 예외로 실패를 전달한다. 비밀번호가 다르거나 계정 상태가 인증을 허용하지 않아도 성공 처리로 넘어가지 않는다.

#### 1.5 attemptAuthentication은 인증을 요청하는 입구다

강의의 `AuthenticationFilter`는 `UsernamePasswordAuthenticationFilter`를 상속하고 `attemptAuthentication()`을 재정의한다. 기본 폼 로그인 방식 대신 JSON 본문을 읽기 위한 것이다.

다음은 강의 코드의 호출 구조를 보여주는 설명용 발췌다. 메서드 선언과 예외 처리는 생략했다.

```
RequestLogin login = new ObjectMapper().readValue(
    request.getInputStream(), RequestLogin.class
);

UsernamePasswordAuthenticationToken credentials =
    new UsernamePasswordAuthenticationToken(
        login.getEmail(), login.getPassword(), new ArrayList<>()
    );

return getAuthenticationManager().authenticate(credentials);
```

`readValue()`는 요청 본문을 `RequestLogin`으로 역직렬화한다. `authenticate()`는 인증을 직접 완료했다고 선언하는 코드가 아니라, 인증 관리자에게 검증을 요청하는 코드다.

이 호출이 정상적으로 인증된 객체를 반환하면 성공 처리로 이어진다. JSON 파싱 실패와 비밀번호 불일치는 서로 다른 실패이므로, 실제 구현에서는 요청 형식 오류와 인증 오류를 구분해 응답하도록 구성한다.

#### 1.6 UserDetailsService는 회원 엔티티를 인증용 정보로 변환한다

강의에서는 기존 `UserService`가 `UserDetailsService`를 확장하고, `UserServiceImpl`에서 `loadUserByUsername()`을 구현한다. 이름은 `username`이지만 실제로 전달되는 값은 이메일이다.

다음은 강의의 사용자 조회 흐름을 설명하기 위해 정리한 예제다. `User`는 회원 엔티티가 아니라 Spring Security의 인증용 구현 클래스다.

```
@Override
public UserDetails loadUserByUsername(String email) {
    UserEntity entity = userRepository.findByEmail(email);
    if (entity == null) {
        throw new UsernameNotFoundException(email);
    }
    return new org.springframework.security.core.userdetails.User(
        entity.getEmail(), entity.getEncryptedPwd(),
        true, true, true, true, new ArrayList<>()
    );
}
```

네 개의 `true`는 순서대로 활성화 여부, 계정 만료 여부, 자격 증명 만료 여부, 계정 잠금 여부에 관한 허용 상태를 의미한다. 강의에서는 모두 인증 가능한 상태로 넣지만, 실제 상태 관리가 필요하면 저장된 값과 연결해야 한다.

비어 있는 권한 목록은 역할 기반 권한을 부여하지 않았다는 뜻이다. 권한이 비어 있어도 사용자 인증 자체는 가능하지만, 특정 역할을 요구하는 인가에는 별도 권한 정보가 필요하다.

#### 1.7 BCrypt는 복호화하지 않고 비밀번호를 검증한다

강의의 `BCryptPasswordEncoder`는 비밀번호를 **해시**로 저장하고 비교한다. 저장된 값을 원래 비밀번호로 되돌리는 양방향 암호화 도구가 아니다.

다음은 회원가입과 로그인에서 사용하는 동작을 구분하는 설명용 예제다. 로그인 때의 `matches()` 호출은 인증 제공자가 수행할 수 있다.

```
String storedHash = passwordEncoder.encode(rawPassword);
boolean matched = passwordEncoder.matches(inputPassword, storedHash);
```

BCrypt는 솔트를 사용하므로 같은 비밀번호를 두 번 `encode()`해도 문자열이 달라질 수 있다. 따라서 로그인 때 새로 만든 해시 문자열과 DB 해시를 `equals()`로 비교하는 방식은 적절하지 않다.

|구분|입력|결과|
|---|---|---|
|회원가입의 `encode()`|원문 비밀번호|DB에 저장할 해시|
|로그인의 `matches()`|입력 비밀번호와 저장된 해시|일치 여부|
|JWT의 서명|토큰 내용과 서명 키|위변조 검증에 사용하는 서명|

엔티티 필드가 `encryptedPwd`라는 이름이어도, BCrypt로 생성했다면 실제 값의 성격은 비밀번호 해시다. 필드 이름과 암호학적 개념을 동일하게 보면 안 된다.

#### 1.8 WebSecurity가 인증 관리자와 로그인 필터를 연결한다

강의의 `WebSecurity`는 `SecurityFilterChain` 빈을 구성하고, 사용자 서비스와 BCrypt 인코더를 인증 관리자에 연결한다. 이어 해당 인증 관리자를 사용하는 커스텀 로그인 필터를 등록한다.

아래는 강의의 핵심 연결을 보여주는 설명용 발췌다. 완성된 보안 설정 클래스가 아니며, 경로 접근 규칙과 import 등은 생략했다.

```
AuthenticationManagerBuilder builder =
    http.getSharedObject(AuthenticationManagerBuilder.class);
builder.userDetailsService(userService)
       .passwordEncoder(bCryptPasswordEncoder);
AuthenticationManager manager = builder.build();

AuthenticationFilter loginFilter =
    new AuthenticationFilter(userService, env, manager);
http.authenticationManager(manager);
http.addFilter(loginFilter);
```

핵심은 인증 필터가 호출하는 인증 관리자에 실제 사용자 조회 로직과 비밀번호 인코더가 연결되어 있어야 한다는 점이다. 필터 클래스만 만들어 놓고 보안 체인에 등록하지 않으면 요청 처리에 사용되지 않는다.

> [!NOTE]  
> Spring Security 설정 API는 버전에 따라 달라진다. 강의는 `SecurityFilterChain`과 `AuthenticationManagerBuilder`를 사용하며, 오래된 `WebSecurityConfigurerAdapter` 예제를 그대로 섞어 쓰지 않는다.

강의에서는 H2 콘솔 허용, 프레임 옵션, Gateway IP 접근 조건도 함께 설정한다. H2 콘솔과 프레임 허용은 개발 도구 접근을 위한 설정이며, 사용자 로그인 인증 자체와는 별개다.

> 로그인 필터는 입력을 인증 관리자에게 전달하고, 인증 제공자는 사용자 정보와 비밀번호를 검증한다. 사용자 조회, 비밀번호 비교, 성공 후 처리를 구분하면 로그인 흐름을 따라가기 쉽다.

### 2. JWT로 로그인 이후의 인증 증명 전달하기

앞 장에서 비밀번호를 검증했더라도, 이후의 모든 API 요청에 비밀번호를 다시 보내는 것은 바람직하지 않다. 로그인 성공을 나타내는 증명을 발급하고, 이후 요청에서는 그 증명을 제출하도록 구성한다.

강의에서는 이 증명으로 **JWT(JSON Web Token)**를 사용한다. JWT는 토큰의 데이터 형식이며, `Authorization: Bearer ...`는 그 토큰을 HTTP 요청에 전달하는 방식이다.

#### 2.1 세션 방식과 토큰 방식은 로그인 상태를 확인하는 기준이 다르다

세션 방식에서는 서버가 로그인 상태를 저장하고, 클라이언트는 주로 쿠키로 세션 ID를 보낸다. 서버는 받은 ID로 저장된 상태를 찾아 사용자를 확인한다.

강의의 서명 JWT 방식에서는 토큰에 사용자 식별 정보와 만료 시각을 담고 서명한다. 서버는 요청마다 해당 토큰의 서명과 유효 조건을 검증한다.

|비교 항목|세션 방식|강의의 서명 JWT 방식|
|---|---|---|
|클라이언트가 보내는 증명|세션 ID|JWT 문자열|
|기본 확인 방법|서버의 세션 상태를 조회한다.|서명과 클레임을 검증한다.|
|다중 서버 구성|세션 공유나 요청 고정 등을 고려한다.|검증 키와 검증 정책을 일치시킨다.|
|즉시 무효화|서버의 세션을 제거할 수 있다.|만료 전 무효화에 별도 상태 관리가 필요할 수 있다.|
|데이터 응답 형식|JSON과 HTML 모두 가능하다.|JSON과 HTML 모두 가능하다.|

강의 자료의 “모바일에서는 쿠키·세션을 사용할 수 없다”는 표현은 일반적인 기술적 제한으로 이해하면 안 된다. 모바일 클라이언트도 쿠키·세션을 사용할 수 있고, 세션 인증 API도 JSON을 반환할 수 있다.

토큰 방식의 핵심은 모바일 지원 여부가 아니라 **인증 상태를 확인하는 구조**다. JWT의 자체 검증 방식은 서버 간 세션 공유 부담을 줄일 수 있지만, DB나 모든 서버 상태가 사라진다는 뜻은 아니다.

#### 2.2 서명 JWT의 세 부분과 클레임을 읽는다

강의처럼 서명된 JWT는 점으로 구분된 세 부분으로 표현된다.

```
header.payload.signature
```

|부분|들어가는 정보|역할|
|---|---|---|
|Header|알고리즘 등 메타데이터|토큰 처리 정보를 표현한다.|
|Payload|사용자 식별자, 발급 시각, 만료 시각 등|전달할 클레임을 담는다.|
|Signature|토큰 내용과 키로 만든 서명|내용의 위변조를 검증한다.|

**클레임(Claim)**은 토큰에 담는 정보 항목이다. 강의에서는 회원의 이메일로 인증한 뒤, 회원의 `userId`를 `sub`에 넣어 토큰의 사용자 식별자로 사용한다.

|클레임|의미|강의에서의 용도|
|---|---|---|
|`sub`|Subject, 대상 식별자|회원의 `userId`를 표현한다.|
|`iat`|Issued At, 발급 시각|토큰을 발급한 시간을 기록한다.|
|`exp`|Expiration Time, 만료 시각|해당 시각 이후 토큰을 거부한다.|

> [!WARNING]  
> 강의의 서명 JWT는 암호화된 비밀 문서가 아니다. Header와 Payload는 디코딩해 읽을 수 있으므로 비밀번호나 서명 비밀키를 넣지 않는다. 내용이 보이는 것과 서명 검증에 성공하는 것은 서로 다르다.

#### 2.3 successfulAuthentication에서 사용자 식별자를 찾아 토큰을 만든다

로그인이 성공하면 `successfulAuthentication()`이 실행된다. 이때 `authResult.getPrincipal()`에서 인증된 사용자의 정보를 꺼내고, 강의의 `getUserDetailsByEmail()`로 회원 DTO를 조회한다.

`loadUserByUsername()`은 인증에 필요한 `UserDetails`를 반환한다. `getUserDetailsByEmail()`은 토큰의 `sub`로 사용할 회원 식별자 등 애플리케이션 정보를 얻기 위한 메서드다.

다음은 강의의 흐름을 보여주는 설명용 발췌다. `User`는 Spring Security의 인증용 클래스이며, `token`은 아래 JWT 생성 과정에서 얻은 문자열이다.

```
String email = ((User) authResult.getPrincipal()).getUsername();
UserDto user = userService.getUserDetailsByEmail(email);

response.addHeader("token", token);
response.addHeader("userId", user.getUserId());
```

강의는 로그인 응답의 `token` 헤더로 토큰을 전달한다. 이후 요청의 `Authorization` 헤더와는 이름과 방향이 다르다.

|헤더|전달 방향|의미|
|---|---|---|
|`token`|서버의 로그인 응답|새로 발급한 JWT|
|`userId`|서버의 로그인 응답|회원 식별자|
|`Authorization`|클라이언트의 보호 API 요청|해당 요청에서 사용할 인증 증명|

브라우저가 다른 출처의 응답에서 `token` 같은 커스텀 헤더를 JavaScript로 읽으려면 CORS의 노출 헤더 설정도 맞아야 한다. Postman에서 헤더가 보인다는 사실과 브라우저 코드에서 읽을 수 있다는 사실은 다르다.

#### 2.4 발급 키와 만료 시간을 설정에서 읽는다

강의의 `token.secret`은 서명에 사용하는 비밀키이고, `token.expiration_time`은 발급 시각에 더할 유효 기간이다. 자료의 `86400000`은 밀리초 단위이며 24시간에 해당한다.

다음은 자료에 제시된 JJWT 0.12.3 계열 생성 API를 바탕으로 정리한 설명용 예제다. `user`, `env`와 관련 import는 주변 코드에서 준비된 것으로 가정한다.

```
byte[] secretBytes = env.getProperty("token.secret")
    .getBytes(StandardCharsets.UTF_8);
SecretKey secretKey = Keys.hmacShaKeyFor(secretBytes);
Instant now = Instant.now();
long ttlMillis = Long.parseLong(
    env.getProperty("token.expiration_time")
);
String token = Jwts.builder()
    .subject(user.getUserId())
    .issuedAt(Date.from(now))
    .expiration(Date.from(now.plusMillis(ttlMillis)))
    .signWith(secretKey)
    .compact();
```

`signWith()`는 토큰에 서명을 붙이고, `compact()`는 전송할 문자열을 생성한다. `plusMillis()`로 유효 기간을 더하지만 JWT의 시간 클레임은 라이브러리가 규격에 맞게 직렬화한다.

HMAC 계열 서명은 발급자와 검증자가 같은 비밀키를 사용한다. 양쪽의 설정 이름만 같고 실제 키 바이트가 다르면 검증에 실패한다.

> [!WARNING]  
> HS256의 키는 최소 256비트, 즉 32바이트가 필요하며 충분한 무작위성도 갖춰야 한다. 짧은 예제 문자열을 운영 비밀키로 쓰지 않는다. JWT를 Base64URL로 표시하는 것과 설정 키를 Base64로 저장·해석하는 것은 별개이므로, 발급과 검증에서 키 해석 방식을 일치시킨다.

#### 2.5 Bearer는 가진 사람이 사용할 수 있는 인증 증명이다

다음은 보호 API 요청의 설명용 예제다. `발급받은_JWT`는 실제 로그인 응답에서 얻은 문자열로 대체한다.

```
GET /user-service/users HTTP/1.1
Host: localhost:8000
Authorization: Bearer 발급받은_JWT
```

`Bearer`는 토큰의 형식이 아니라 인증 방식이다. JWT 이외의 토큰도 Bearer 방식으로 전달할 수 있으며, Bearer 헤더를 사용한다고 OAuth 전체 흐름을 구현한 것은 아니다.

토큰이 유출되면 획득한 사람이 만료 전까지 사용할 수 있다. 전송 시 HTTPS를 사용하고, 토큰을 로그에 남기지 않으며, 클라이언트 저장 방식과 유효 기간을 함께 고려해야 한다.

JWT가 CSRF를 자동으로 없애는 것도 아니다. 쿠키에 저장한 인증 증명이 브라우저에서 자동으로 전송되면 CSRF를 고려해야 하고, JavaScript에서 토큰을 관리하면 XSS와 탈취 위험도 고려해야 한다.

> 비밀번호 해시는 비밀번호 검증에 사용하고, JWT 서명은 토큰의 위변조 검증에 사용한다. JWT는 인증 증명의 형식이고 Bearer는 전달 방식이다.

### 3. API Gateway에서 보호 경로와 토큰 검증 연결하기

토큰을 발급했다면 다음 요청에서 이를 확인하는 지점이 필요하다. 강의에서는 서비스 앞에 있는 API Gateway에 `AuthorizationHeaderFilter`를 추가해 보호 경로의 요청을 검사한다.

모든 경로를 일괄적으로 막으면 회원가입과 로그인까지 토큰을 요구하게 된다. 먼저 공개 요청과 보호 요청을 나누고, 필요한 라우트에 검증 필터를 연결한다.

#### 3.1 같은 경로라도 HTTP 메서드에 따라 인증 요구가 달라진다

`POST /user-service/users`는 회원가입이고, `GET /user-service/users`는 회원 조회다. URL만 보고 같은 접근 규칙을 적용하면 안 된다.

|강의 요청|인증 요구|이유|
|---|---|---|
|`POST /user-service/users`|토큰을 요구하지 않는다.|처음 가입하는 사용자는 토큰이 없다.|
|`POST /user-service/login`|토큰을 요구하지 않는다.|자격 증명을 검증하고 토큰을 발급하는 입구다.|
|`GET /user-service/users`|토큰을 요구한다.|회원 정보 조회를 보호한다.|
|`GET /user-service/health-check`|토큰을 요구한다.|강의에서는 보호된 GET 라우트에 포함한다.|

강의의 `/health-check`는 직접 만든 서비스 API다. 뒤에서 배우는 Actuator의 `/actuator/health`와 같은 경로가 아니며, 접근 정책도 각각 구성해야 한다.

#### 3.2 Route의 Predicate와 Filter가 처리 대상을 결정한다

Gateway의 `Path`와 `Method` Predicate는 요청을 어떤 라우트에 연결할지 결정한다. 라우트의 Filter는 선택된 요청에 경로 변환과 토큰 검증 등을 적용한다.

아래는 강의의 공개 POST 라우트 두 개와 보호 GET 라우트를 한곳에 정리한 설명용 YAML이다. `RewritePath`는 외부 접두사를 제거해 User Service 내부 경로로 전달한다.

```
spring:
  cloud:
    gateway:
      routes:
        - id: user-service-register
          uri: lb://USER-SERVICE
          predicates:
            - Path=/user-service/users
            - Method=POST
          filters:
            - RewritePath=/user-service/(?<segment>.*), /$\{segment}
        - id: user-service-login
          uri: lb://USER-SERVICE
          predicates:
            - Path=/user-service/login
            - Method=POST
          filters:
            - RewritePath=/user-service/(?<segment>.*), /$\{segment}
        - id: user-service
          uri: lb://USER-SERVICE
          predicates:
            - Path=/user-service/**
            - Method=GET
          filters:
            - RemoveRequestHeader=Cookie
            - RewritePath=/user-service/(?<segment>.*), /$\{segment}
            - AuthorizationHeaderFilter
```

`lb://USER-SERVICE`는 Discovery에 등록된 서비스 이름을 기반으로 실제 인스턴스를 선택하도록 한다. `AuthorizationHeaderFilter`는 클래스 이름에서 `GatewayFilterFactory` 접미사를 생략한 형태로 등록하는 커스텀 필터 이름이다.

`RemoveRequestHeader=Cookie`는 전달되는 요청에서 쿠키 헤더를 제거한다. 토큰 검증을 대신하거나 세션을 자동으로 종료시키는 기능은 아니다.

이 예제의 보호 범위는 GET 라우트다. 나중에 수정·삭제 API를 추가하면 `PUT`, `PATCH`, `DELETE`에 해당하는 보호 규칙도 따로 연결해야 한다.

#### 3.3 AuthorizationHeaderFilter의 apply는 요청용 필터를 반환한다

강의의 클래스는 `AbstractGatewayFilterFactory<AuthorizationHeaderFilter.Config>`를 상속한다. `apply(Config config)`는 라우트 설정을 받아 `GatewayFilter`를 만들고, 반환된 필터가 실제 요청마다 실행된다.

|객체 또는 메서드|의미|처리 시점|
|---|---|---|
|`Config`|커스텀 필터의 설정 객체|라우트 필터 구성에 사용한다.|
|`apply()`|실행할 필터를 생성한다.|라우트 필터를 구성할 때 호출된다.|
|`exchange`|현재 HTTP 요청과 응답을 묶는다.|요청을 처리할 때 사용한다.|
|`chain.filter(exchange)`|다음 처리 단계로 넘긴다.|검증 성공 후 호출한다.|
|`response.setComplete()`|응답을 완료한다.|요청을 더 전달하지 않고 끝낼 때 사용한다.|

Gateway의 `ServerHttpRequest`와 `ServerHttpResponse`는 WebFlux 타입이다. User Service 로그인 필터의 `HttpServletRequest`와 `HttpServletResponse`는 Servlet 타입이므로 서로 같은 메서드를 제공한다고 가정하면 안 된다.

`Mono<Void>`는 응답 본문 데이터 없이 비동기 처리의 완료를 표현한다. 동기 메서드의 `void`처럼 즉시 아무것도 반환하지 않는다는 뜻으로만 이해하면 요청 체인을 따라가기 어렵다.

#### 3.4 토큰이 없거나 유효하지 않으면 다음 서비스로 전달하지 않는다

```
보호된 GET 라우트가 선택된다
    ↓ 요청의 Authorization 헤더를 확인한다
Bearer 형식에서 JWT 문자열을 추출한다
    ↓ 발급 시 사용한 키와 동일한 방식으로 검증한다
서명과 만료 시각 및 사용자 식별자를 검사한다
    ↓ 성공한 경우에만 chain.filter를 실행한다
User Service로 요청을 전달한다
```

위 흐름의 어느 검증 단계에서든 실패하면, 강의의 필터는 `401 Unauthorized`로 응답을 종료한다. `chain.filter(exchange)`를 호출하지 않아 User Service로 넘어가지 않는다.

다음은 강의의 분기 구조를 보완한 설명용 예제다. `isJwtValid()`와 `onError()`는 각각 토큰 검증과 오류 응답을 담당하는 별도 메서드라고 가정한다.

```
return (exchange, chain) -> {
    String header = exchange.getRequest().getHeaders()
        .getFirst(HttpHeaders.AUTHORIZATION);
    if (header == null || !header.startsWith("Bearer ")) {
        return onError(exchange, "Missing bearer token",
            HttpStatus.UNAUTHORIZED);
    }
    String jwt = header.substring(7).trim();
    if (jwt.isEmpty() || !isJwtValid(jwt)) {
        return onError(exchange, "Invalid token",
            HttpStatus.UNAUTHORIZED);
    }
    return chain.filter(exchange);
};
```

이 예제는 이해를 위해 정확한 `Bearer` 접두사를 검사한다. HTTP 인증 스킴 이름 자체는 대소문자를 구분하지 않으므로, 범용 구현에서는 그 규칙도 처리해야 한다.

강의 코드의 `replace("Bearer", "")`는 접두사만 제거하는 전용 연산이 아니라 해당 문자열을 치환하는 연산이다. 검증 전에 헤더 형식을 확인하고, 토큰 부분을 명확히 추출하는 편이 처리 의도가 분명하다.

#### 3.5 JWT 검증은 문자열 해독보다 많은 조건을 확인한다

Payload를 디코딩해 `userId`를 읽었다는 이유만으로 토큰을 신뢰할 수 없다. 공격자가 작성한 Payload일 수 있으므로, 서명 검증과 만료 검사 후에 정보를 사용해야 한다.

다음은 JJWT 0.12.3 계열 API로 발급 예제와 검증 방식을 맞춘 설명용 예제다. `secretKey`는 발급 예제와 동일한 설정 및 바이트 해석으로 만든 키다.

```
try {
    Claims claims = Jwts.parser()
        .verifyWith(secretKey)
        .build()
        .parseSignedClaims(jwt)
        .getPayload();
    String subject = claims.getSubject();
    return subject != null && !subject.isBlank();
} catch (JwtException | IllegalArgumentException e) {
    return false;
}
```

서명이 다르거나 토큰이 만료되면 파싱·검증 과정에서 예외가 발생한다. 검증이 성공하더라도 강의는 `sub`가 비어 있으면 유효한 사용자 증명으로 처리하지 않는다.

자료에는 최신 발급 API와 오래된 `setSigningKey()`·`parseClaimsJws()` 검증 코드가 함께 등장한다. 위 예제는 호출 형태를 통일한 것이며, 사용하는 라이브러리 버전에 맞춰 API를 선택해야 한다.

|실패 상황|판단|강의의 처리|
|---|---|---|
|헤더 누락|인증 증명이 없다.|`401`로 종료한다.|
|Bearer 형식 오류|토큰을 올바르게 추출할 수 없다.|`401`로 종료한다.|
|서명 불일치|토큰을 신뢰할 수 없다.|`401`로 종료한다.|
|만료|유효 기간이 지났다.|`401`로 종료한다.|
|사용자 식별자 누락|사용자 증명에 필요한 정보가 없다.|`401`로 종료한다.|
|검증 성공|보호 경로의 인증 조건을 통과했다.|다음 체인으로 전달한다.|

#### 3.6 Gateway 인증과 서비스의 접근 통제는 함께 설계한다

강의의 User Service 보안 설정에는 Gateway IP를 허용하는 조건이 등장한다. 이는 “허용된 네트워크 경로를 통해 요청이 왔는가?”를 확인하는 조건이며, “어떤 사용자가 요청했는가?”와는 다른 질문이다.

Gateway에서만 토큰을 검사한다면, 외부 사용자가 User Service로 직접 접근해 검사를 우회하지 못하도록 네트워크와 서비스 접근 정책을 구성해야 한다. 프록시를 거치면 서비스가 보는 원격 IP가 달라질 수 있으므로 IP 조건만으로 사용자 인증을 대체하지 않는다.

강의의 `AuthorizationHeaderFilter`는 요청 통과 여부를 판단하는 커스텀 필터다. 유효한 토큰을 통과시켰다는 사실만으로 모든 다운스트림 서비스에 Spring Security의 인증 객체가 자동으로 생기는 것은 아니다.

> [!WARNING]  
> `userId` 응답 헤더나 클라이언트가 임의로 보낸 사용자 ID만으로 권한을 결정하지 않는다. 검증된 토큰의 식별자와 실제 요청 대상·권한을 연결해야 한다.

#### 3.7 강의의 테스트 순서를 실제 요청으로 연결한다

자료에서 제시한 확인 순서는 회원가입, 로그인, 토큰 없는 조회, 토큰을 포함한 조회다. 아래 표는 수행했다고 주장하는 결과가 아니라, 같은 흐름을 확인할 때의 기준이다.

|확인 요청|전달 정보|확인할 항목|
|---|---|---|
|회원가입|회원 JSON|공개 POST 라우트로 처리되는지 확인한다.|
|로그인|이메일과 비밀번호|응답의 `token`·`userId` 헤더를 확인한다.|
|보호 API 무토큰 호출|인증 헤더 없음|Gateway가 `401`로 종료하는지 확인한다.|
|보호 API 정상 토큰 호출|`Authorization: Bearer ...`|검증 후 서비스로 전달되는지 확인한다.|
|보호 API 잘못된 토큰 호출|잘못된 서명 또는 만료 토큰|서비스로 전달하지 않는지 확인한다.|

Postman의 “No Auth”는 요청에 인증 정보를 추가하지 않는 설정이다. “Inherit auth from parent”는 상위 설정을 상속하므로, 상위에 인증이 있으면 실제 요청에도 포함될 수 있다.

“Bearer Token”을 선택하면 토큰 입력칸에는 보통 JWT 문자열만 넣는다. 도구가 `Bearer` 접두사를 붙이므로 실제 전송된 `Authorization` 헤더를 확인하면 중복 입력을 피할 수 있다.

> Gateway는 공개 경로와 보호 경로를 먼저 구분하고, 보호 요청에만 토큰 검증을 적용한다. 인증 통과와 자원 접근 권한은 별도로 판단해야 한다.

### 4. Spring Cloud Config로 설정을 외부에서 관리하기

JWT를 발급하는 User Service와 검증하는 Gateway는 같은 키와 일관된 정책을 사용해야 한다. 설정을 각 프로젝트에 따로 복사하면 일부 서비스만 바뀌거나, 값을 바꾸기 위해 프로젝트를 다시 빌드하는 문제가 생긴다.

**Spring Cloud Config**는 설정을 애플리케이션 바깥에서 관리하고 여러 서비스에 공급한다. 오늘은 그중 로컬 Git 저장소를 연결한 Config Server와 User Service의 Config Client 구성을 학습했다.

#### 4.1 Git 저장소와 Config Server와 Config Client의 역할

|구성 요소|관리하는 대상|역할|
|---|---|---|
|로컬 Git 저장소|`ecommerce.yml` 등 설정 파일|설정 값과 변경 이력을 보관한다.|
|Config Server|설정 제공 API|저장소의 설정을 읽어 클라이언트에 제공한다.|
|Config Client|서비스가 사용할 설정|서버에서 설정을 받아 환경에 추가한다.|
|`Environment`|애플리케이션의 유효 설정|코드가 이름으로 설정 값을 읽게 한다.|

Config Server는 사용자 회원 정보를 저장하는 DB가 아니다. Config Client는 User Service 같은 애플리케이션에 들어가는 설정 조회 기능이며, 클라이언트 브라우저를 뜻하지 않는다.

자료에 DEV·UAT·PROD가 등장하는 이유는 실행 환경에 따라 다른 설정이 필요하기 때문이다. 개발, 인수 테스트, 운영 환경을 구분한다는 배경만 다루고, Profiles 적용 방식은 오늘 범위에 포함하지 않는다.

#### 4.2 설정 파일을 Git에 커밋한다

강의에서는 `git-local-repo`를 만들고 `ecommerce.yml`을 생성한 뒤 커밋한다. Git을 사용하는 이유는 설정의 현재 값뿐 아니라 변경 이력과 특정 버전을 관리하기 위해서다.

다음은 강의의 절차를 사용자별 경로에 의존하지 않도록 정리한 설명용 명령이다. 파일 내용은 Git 명령을 실행하기 전에 작성한다.

```
mkdir -p git-local-repo
cd git-local-repo
git init -b main
# ecommerce.yml 파일 작성 후 실행
git add ecommerce.yml
git commit -m "Add ecommerce configuration"
```

아래는 `ecommerce.yml`의 구조를 설명하는 예제다. `${JWT_SECRET}`는 의도적으로 실제 비밀키를 적지 않은 자리이며, 이 예제를 사용할 경우 클라이언트 실행 환경에서 해당 값을 제공해야 한다.

```
token:
  expiration_time: 86400000
  secret: ${JWT_SECRET}

gateway:
  ip: 127.0.0.1
```

`token.expiration_time`과 `token.secret`은 YAML 계층을 점으로 이어 코드에서 조회하는 이름이다. 설정 파일을 바꾸는 작업과 Git에 변경을 커밋하는 작업은 구분해야 하며, 강의의 갱신 흐름은 커밋을 기준으로 설명한다.

#### 4.3 EnableConfigServer와 저장소 주소를 연결한다

Config Server에는 `spring-cloud-config-server` 의존성을 추가하고, 시작 클래스에 `@EnableConfigServer`를 붙인다. 이 애너테이션으로 애플리케이션이 설정을 제공하는 서버 역할을 하도록 활성화한다.

아래는 강의의 시작 클래스 구조를 보여주는 설명용 예제다.

```
@SpringBootApplication
@EnableConfigServer
public class ConfigServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(ConfigServiceApplication.class, args);
    }
}
```

다음 설정은 자료의 `8888` 포트를 기준으로 정리한 설명용 예제다. `/absolute/path/git-local-repo`는 앞서 만든 실제 Git 저장소의 절대 경로로 대체한다.

```
server:
  port: 8888
spring:
  application:
    name: config-service
  cloud:
    config:
      server:
        git:
          uri: file:///absolute/path/git-local-repo
          default-label: main
```

`file:///...`는 HTTP API 주소가 아니라 로컬 파일 시스템의 저장소 위치다. `default-label`은 Config Server가 기본으로 읽을 Git 브랜치 등의 라벨을 지정한다.

강의 자료는 `default-label: master`를 사용한다. 예제는 Git 초기화에서 `main`을 만들었으므로 `main`으로 맞췄으며, 실제 저장소의 브랜치 이름을 기준으로 설정해야 한다.

#### 4.4 설정 조회 URL은 애플리케이션 이름과 프로파일로 구성한다

대표적인 설정 조회 경로는 `/{application}/{profile}`이다. Git 브랜치 등 라벨을 명시하려면 `/{application}/{profile}/{label}` 형태를 사용할 수 있다.

자료의 `http://127.0.0.1:8888/ecommerce/default`를 나누면 다음과 같다.

|URL 요소|예제 값|의미|
|---|---|---|
|서버 주소|`127.0.0.1:8888`|Config Server가 실행되는 주소다.|
|application|`ecommerce`|가져올 설정 이름이다.|
|profile|`default`|기본 프로파일의 설정을 요청한다.|
|label|생략|서버의 기본 라벨을 사용한다.|

설정 조회는 파일의 문자열만 그대로 보내는 것과 다르다. 응답에는 설정 이름, 프로파일, Git 버전 정보, 실제 설정을 담은 `propertySources` 등이 포함된다.

아래는 응답에서 볼 항목을 설명하는 축약 예제다. 실제 실행 결과를 복사한 것이 아니며, 값과 `version` 표기는 설명용이다.

```
{
  "name": "ecommerce",
  "profiles": ["default"],
  "label": "main",
  "version": "커밋_SHA",
  "propertySources": [
    {
      "name": "ecommerce.yml",
      "source": { "token.expiration_time": 86400000 }
    }
  ]
}
```

`propertySources`는 설정 값의 출처를 표현한다. 값이 예상과 다를 때에는 파일 이름만 보지 말고, 응답이 어느 저장소 버전과 설정 이름을 기준으로 만들어졌는지 확인해야 한다.

#### 4.5 Config Client가 부팅 초기에 원격 설정을 가져온다

User Service에는 `spring-cloud-starter-config`를 추가한다. 강의의 연결 방식은 `bootstrap.yml`을 사용하며, 부트스트랩 처리를 활성화하기 위해 `spring-cloud-starter-bootstrap`도 추가한다.

아래는 강의 방식의 설명용 예제다. Config Server 포트는 앞의 예제와 같은 `8888`로 통일했다.

```
spring:
  cloud:
    config:
      uri: http://127.0.0.1:8888
      name: ecommerce
```

`spring.cloud.config.name`은 가져올 원격 설정의 이름이다. 따라서 서비스의 Discovery 이름이 `USER-SERVICE`여도 원격의 `ecommerce.yml`을 가져올 수 있다.

자료의 서버 설정은 `8888`이지만 클라이언트 `bootstrap.yml` 화면에는 `8012`도 등장한다. 어느 숫자가 정답인지 외우는 대신, **클라이언트 URI가 실제 Config Server의 주소와 일치해야 한다**는 관계를 확인한다.

```
User Service의 초기 설정을 읽는다
    ↓ Config Server의 주소와 설정 이름을 확인한다
Config Client가 ecommerce/default 설정을 요청한다
    ↓ 서버가 지정된 Git 저장소에서 설정을 읽는다
응답의 PropertySource를 Environment에 추가한다
    ↓ 이후 빈과 서비스 코드가 설정을 사용한다
User Service가 조회한 값으로 동작한다
```

부팅 초기부터 필요한 값을 가져와야 하므로 `bootstrap.yml`에 연결 정보가 들어간다. Config Server 주소를 Config Server에서만 얻으려고 하면, 접속하기 위한 주소부터 알 수 없다는 순환 문제가 생긴다.

> [!NOTE]  
> Spring Boot 2.4 이후의 Config Data 방식에서는 `spring.config.import: configserver:http://127.0.0.1:8888`를 사용하며, 그 방식에는 `bootstrap.yml`이 필수는 아니다. 오늘은 자료의 bootstrap 방식을 중심으로 이해하고 서로 다른 연결 방식의 설정을 무작정 섞지 않는다.

#### 4.6 Environment는 이름으로 유효한 설정을 읽는 통로다

강의의 Controller는 주입받은 `Environment`에서 `env.getProperty()`로 값을 읽는다. 같은 방식으로 JWT 발급 코드도 `token.secret`과 `token.expiration_time`을 읽는다.

다음은 비밀키를 노출하지 않고 설정 조회 구조만 확인하는 설명용 예제다. 실제 강의의 상태 응답을 그대로 복사한 코드는 아니다.

```
@GetMapping("/health-check")
public String status() {
    return "User Service is running"
        + ", token expiration="
        + env.getProperty("token.expiration_time");
}
```

이 코드는 메서드가 호출될 때 설정을 읽는다. 생성자에서 값을 한 번 읽어 필드에 저장하는 코드와 달리, 호출 시점의 `Environment` 값을 사용한다는 차이가 있다.

자료의 확인용 응답에는 `token.secret`도 포함되어 있다. 원리를 확인하기 위한 코드라도 실제 서비스의 상태 응답이나 로그에 비밀키를 그대로 출력하면 안 된다.

#### 4.7 설정의 구체성과 전체 우선순위를 구분한다

Config 저장소에서는 공통 설정과 특정 애플리케이션 설정을 함께 관리할 수 있다. 자료에 나온 파일 이름은 개별 서비스 설정을 찾는 기준을 나타낸다.

|설정 파일|적용 대상|역할|
|---|---|---|
|`application.yml`|여러 애플리케이션의 공통 설정|공통 기본값을 제공한다.|
|`ecommerce.yml`|`ecommerce` 설정을 요청한 클라이언트|애플리케이션별 값을 제공한다.|
|`ecommerce-<profile>.yml`|특정 프로파일|환경별 값을 구분한다.|

같은 원격 저장소 안에서는 애플리케이션별·프로파일별 설정처럼 더 구체적인 설정이 공통 값을 덮어쓰는 구조로 이해할 수 있다. 다만 마지막 행의 실제 Profiles 구성은 오늘 범위 이후다.

이 파일 관계만으로 “원격 Git 설정이 모든 환경변수와 명령행 옵션보다 항상 우선한다”고 결론 내리면 안 된다. 전체 우선순위는 bootstrap 또는 Config Data 연결 방식, 속성 소스와 override 설정에 영향을 받는다.

> Config Server는 설정을 공급하고, Config Client는 그 설정을 서비스의 Environment에 가져온다. 저장소 경로, 설정 이름, 서버 주소, Git 라벨을 서로 구분해야 원하는 값을 읽을 수 있다.

### 5. Spring Boot Actuator로 상태 확인과 설정 갱신하기

설정을 외부로 옮겨도 이미 실행 중인 서비스가 자동으로 모든 변경을 적용하는 것은 아니다. 저장소의 새 값을 가져오는 단계와, 기존 객체가 그 값을 다시 사용하는 단계가 필요하다.

오늘은 Spring Boot Actuator로 운영용 엔드포인트를 제공하고, Spring Cloud의 refresh 기능을 통해 대상 서비스의 설정을 다시 읽는 흐름까지 학습했다.

#### 5.1 Actuator는 애플리케이션의 운영 상태를 확인하는 기능이다

**Spring Boot Actuator**는 상태, 빈 구성, 메트릭 등 애플리케이션을 운영할 때 필요한 정보를 엔드포인트로 제공한다. 일반적인 사용자 API와 목적이 다르다.

|엔드포인트|주된 역할|구분할 점|
|---|---|---|
|`/actuator/health`|애플리케이션과 연결 자원의 상태를 확인한다.|직접 만든 `/health-check`와 다르다.|
|`/actuator/info`|구성된 애플리케이션 정보를 제공한다.|설정과 contributor에 따라 내용이 달라진다.|
|`/actuator/beans`|등록된 Spring 빈 정보를 제공한다.|비즈니스 데이터 목록이 아니다.|
|`/actuator/metrics`|등록된 메트릭을 확인한다.|오늘 노출 예제에는 포함하지 않는다.|
|`/actuator/refresh`|설정 재조회와 갱신 처리를 요청한다.|Spring Cloud Context가 제공하는 기능이다.|

`refresh`를 Actuator 단독 기능으로 외우면 안 된다. Actuator는 엔드포인트를 제공하는 기반이고, 설정 갱신 동작은 Spring Cloud Context와 연결된다.

자료의 “HTTP Endpoint를 통해 Metric 수집”은 상태 데이터를 수집 도구가 읽을 수 있다는 의미다. Actuator 자체가 모든 대시보드와 장기 저장까지 대신한다는 뜻은 아니다.

#### 5.2 의존성과 노출 설정과 접근 허용은 각각 필요하다

User Service에 `spring-boot-starter-actuator`를 추가한다. Config Client를 구성했다면 Spring Cloud Context와 연결된 refresh 기능도 사용할 수 있는 구성을 갖추게 된다.

아래는 강의의 의존성을 나타낸 XML 조각이다. Spring Boot와 Spring Cloud 버전 관리는 프로젝트의 BOM 등 기존 의존성 관리에 맞춘다.

```
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

강의에서 노출하는 엔드포인트는 `refresh`, `health`, `beans`, `info`다. 아래 YAML은 자료의 설정을 같은 의미의 목록으로 옮긴 것이다.

```
management:
  endpoints:
    web:
      exposure:
        include:
          - refresh
          - health
          - beans
          - info
```

**엔드포인트 노출**은 HTTP로 접근할 수 있도록 등록하는 설정이다. **보안 허용**은 그 엔드포인트에 누가 접근할 수 있는지 결정하는 설정이다.

|단계|필요한 구성|빠졌을 때의 판단|
|---|---|---|
|기능 제공|Actuator와 관련 Cloud 의존성|해당 기능이 제공되는지 확인한다.|
|HTTP 노출|`management.endpoints.web.exposure.include`|웹 엔드포인트로 노출되는지 확인한다.|
|접근 허용|Spring Security와 네트워크 규칙|노출된 경로에 접근이 허용되는지 확인한다.|
|올바른 호출|주소, 경로, 메서드|실제 대상 서비스로 요청했는지 확인한다.|

강의의 `WebSecurity`는 `/actuator/**`에 `permitAll()`을 설정한다. 이는 학습 중 접근 확인을 단순화하기 위한 구성으로 이해하고, 실제 운영에서는 관리 경로에 인증·권한과 접근 제한을 적용한다.

> [!WARNING]  
> `beans`는 내부 구성을 보여주고, `refresh`는 실행 중인 설정에 영향을 주는 관리 기능이다. 모든 관리 경로를 공개하는 방식으로 운영하지 않으며, 노출 목록을 설정하는 것만으로 접근 통제가 생기지는 않는다.

#### 5.3 설정 변경은 커밋과 서비스 갱신까지 이어져야 한다

자료에서 설정 갱신을 위해 제시하는 선택지는 서버 재기동, Actuator refresh, Spring Cloud Bus다. 오늘 다루는 것은 대상 서비스를 직접 refresh하는 방식이다.

```
Git 저장소의 ecommerce.yml을 수정한다
    ↓ 변경 내용을 Git에 커밋한다
Config Server가 제공할 설정 버전이 바뀐다
    ↓ 대상 User Service의 refresh 엔드포인트를 호출한다
Config Client가 원격 설정을 다시 조회한다
    ↓ Environment 갱신과 관련 빈의 갱신 처리가 이어진다
대상 서비스의 다음 요청에서 새 설정을 확인한다
```

설정 변경을 반영하려면 **Config Server**와 **설정을 사용하는 서비스**를 구분해야 한다. User Service 설정을 갱신하고 싶다면 User Service의 `/actuator/refresh`를 호출한다.

아래는 확인 절차를 보여주는 설명용 명령이다. 첫 두 줄은 설정 Git 저장소에서 실행하고, 마지막 주소의 `USER_SERVICE_PORT`는 실행 중인 User Service의 실제 포트로 대체한다.

```
git add ecommerce.yml
git commit -m "Update ecommerce configuration"
curl -X POST http://127.0.0.1:USER_SERVICE_PORT/actuator/refresh
```

`POST`를 사용하는 관리 요청이므로 브라우저 주소창에서 단순히 여는 GET 요청과 다르다. `server.port: 0`으로 실행한 서비스는 실제로 할당된 포트를 시작 로그 등에서 확인해야 한다.

Gateway 경유 호출은 해당 관리 경로의 라우트, 접두사 제거, 보안 규칙이 준비되어 있어야 한다. 강의의 직접 호출과 Gateway 경유 호출을 같은 주소로 취급하지 않는다.

#### 5.4 refresh 응답은 변경된 속성 이름을 보여준다

자료의 응답에는 `token.secret`과 `config.client.version`이 등장한다. 아래는 그 형태를 옮긴 응답 예시이며, 사용자의 실행 결과를 의미하지 않는다.

```
[
  "token.secret",
  "config.client.version"
]
```

응답 배열은 변경을 감지한 속성 이름이다. 새 비밀키 값 전체를 반환하는 목록도 아니고, 모든 기능이 정상 동작한다는 테스트 결과도 아니다.

`config.client.version`은 Config Client가 가져온 설정 버전과 관련된다. 실제 변경 내용과 환경에 따라 응답 키 목록은 달라질 수 있다.

설정 갱신은 세 가지를 나눠 확인해야 한다. 새 커밋이 Config Server 응답에 나타나는지, 대상 서비스의 설정이 갱신되는지, 해당 설정을 소비하는 기능이 새 값으로 동작하는지를 구분한다.

#### 5.5 Environment 갱신과 빈의 재생성은 같은 일이 아니다

설정 저장소가 바뀌어도 이미 Java 필드에 복사된 값이 저절로 바뀌는 것은 아니다. 값을 언제 읽고 어떤 객체에 저장하는지에 따라 갱신 방식이 달라진다.

|설정 사용 방식|읽는 시점|갱신 시 확인할 점|
|---|---|---|
|메서드 안의 `env.getProperty()`|메서드 호출 때|Environment가 갱신되면 다음 조회에서 새 값을 읽는다.|
|일반 빈의 `@Value` 필드|보통 빈 생성 때|Environment만 바꿔도 이미 주입된 필드가 자동으로 바뀌지는 않는다.|
|`@RefreshScope` 빈|스코프 대상 객체 생성 때|refresh로 대상 캐시를 비우고 다음 사용 시 재생성할 수 있다.|
|`@ConfigurationProperties`|설정 바인딩 때|재바인딩 가능한 형태인지와 갱신 지원 조건을 확인한다.|
|시작 시 결정되는 서버 설정|서버 시작 때|refresh가 서버 재시작을 대신한다고 가정하지 않는다.|

자료의 JWT 발급 코드는 성공 처리에서 `Environment`를 조회한다. 환경이 갱신되고 다음 로그인 성공 처리가 실행되면 그 시점의 설정을 다시 읽는 구조다.

다음은 필드에 주입한 값을 사용하는 경우를 비교하기 위한 설명용 예제다. 강의에서 실제 작성한 클래스라는 뜻은 아니다.

```
@Component
@RefreshScope
public class TokenSettings {
    @Value("${token.expiration_time}")
    private long expirationTime;

    public long expirationTime() {
        return expirationTime;
    }
}
```

`@RefreshScope`는 모든 객체를 즉시 일괄 수정하는 애너테이션이 아니다. 대상 객체의 캐시를 무효화해 이후 사용 시 새 설정으로 만들어질 수 있게 하는 방식으로 이해한다.

> [!NOTE]  
> 모든 빈이 refresh 대상이 되는 것은 아니다. 불변 객체, 특정 설정 바인딩 형태, 서버 시작 시 사용하는 값 등은 제약이 있으므로 “재빌드 없이 설정을 읽는다”와 “모든 실행 상태가 바뀐다”를 구분한다.

#### 5.6 한 인스턴스의 refresh는 전체 서비스의 일괄 갱신이 아니다

User Service가 여러 인스턴스로 실행 중이라면 각 인스턴스는 자신의 `Environment`와 빈을 가진다. 한 인스턴스의 refresh를 호출했다고 다른 인스턴스까지 자동으로 갱신되는 것은 아니다.

|갱신 방법|동작|오늘 범위에서의 의미|
|---|---|---|
|서비스 재기동|시작 과정에서 설정을 다시 읽는다.|재빌드와 재기동은 다른 작업이다.|
|개별 refresh|요청한 인스턴스가 설정을 갱신한다.|인스턴스별 반영 여부를 확인한다.|
|Spring Cloud Bus|이벤트를 여러 서비스에 전달한다.|반복 호출의 불편함을 해결하는 다음 학습 주제다.|

Gateway가 여러 인스턴스 중 하나로 요청을 보낸다면 같은 URL을 반복 호출해도 모든 인스턴스를 갱신했다고 보장할 수 없다. 갱신 대상으로 어떤 인스턴스를 호출했는지 구분해야 한다.

중앙 저장소의 설정이 같다는 사실과 현재 실행 중인 모든 서비스의 설정이 같다는 사실도 다르다. 저장소의 일관성만으로 각 프로세스의 반영 시점까지 일치하는 것은 아니다.

#### 5.7 JWT 비밀키 변경은 발급자와 검증자에 함께 영향을 준다

비밀키를 바꾸면 새 키로 발급한 토큰과 이전 키로 발급한 토큰의 검증 관계가 달라진다. Config Server에서 설정을 바꿨다는 이유만으로 기존 토큰이 새 키로 다시 서명되는 것은 아니다.

|현재 상태|예상되는 검증 관계|
|---|---|
|User Service와 Gateway가 모두 이전 키를 사용한다.|이전 키로 발급한 토큰을 검증할 수 있다.|
|User Service만 새 키를 사용한다.|새 토큰을 이전 키의 Gateway가 검증하지 못한다.|
|Gateway만 새 키를 사용한다.|이전 키로 발급한 토큰을 새 키로 검증하지 못한다.|
|양쪽 모두 새 키만 사용한다.|새 토큰은 검증할 수 있으나 이전 토큰은 실패한다.|

이 표는 단일 HMAC 비밀키를 사용하는 강의 구조를 전제로 한다. 별도의 키 교체 전략 구현은 오늘 범위 밖이며, 여기서는 설정 반영 시점이 인증 동작에 직접 영향을 준다는 관계를 이해한다.

운영에서는 어떤 설정을 재시작 없이 바꿔도 되는지 판단해야 한다. 특히 비밀키 변경은 단순 문구 변경과 달리, 이미 발급한 토큰과 서비스 간 검증 호환성에 영향을 준다.

> Config 변경은 저장소 수정으로 끝나지 않는다. 대상 서비스가 설정을 다시 읽고, 그 값을 사용하는 객체와 요청이 갱신 조건에 맞게 동작해야 실제 반영이 완료된다.

## 🧠 오늘 이해한 핵심

1. **로그인과 보호 API 요청은 서로 다른 인증 흐름을 가진다.** 로그인은 이메일과 비밀번호를 검증해 JWT를 발급하고, 이후 요청은 그 JWT를 제출해 검증받는다. Spring Security 내부 자격 증명 객체와 클라이언트에 전달하는 JWT도 구분해야 한다.
2. **인증에 성공한 사실만으로 모든 접근 권한이 생기지는 않는다.** Gateway의 토큰 검증은 인증 증명을 확인하는 단계이고, 회원 본인 여부나 관리자 권한 같은 인가는 별도의 정책으로 연결해야 한다.
3. **중앙 설정 관리와 실행 중인 설정 반영은 별개의 단계다.** Config Server가 Git의 새 값을 제공하더라도, 각 인스턴스가 다시 읽고 해당 값을 사용하는 객체가 갱신 조건을 충족해야 동작이 바뀐다.
4. **설정 값은 서비스를 연결하는 동작 조건이다.** JWT 발급자와 검증자의 키가 다르면 정상 토큰도 실패하므로, 설정 이름뿐 아니라 실제 값·키 해석 방식·반영 시점까지 일치해야 한다.
