오늘은 Docker를 배우기 위한 실행 환경부터 첫 컨테이너를 다루는 방법까지 연결해서 학습했다. VMware에 Ubuntu를 설치하고 네트워크와 SSH 접속을 준비한 뒤, 리눅스 명령어와 `vi`로 파일을 다루고 Docker Engine을 설치하는 흐름을 살펴봤다.

핵심은 명령어를 외우는 것보다 지금 어느 컴퓨터에서 무엇을 실행하고 있는지 구분하는 데 있다. 가상머신과 컨테이너, 이미지와 실행 중인 프로그램, 호스트 포트와 컨테이너 포트를 구분하면 Nginx 실행과 컨테이너 종료 현상도 하나의 흐름으로 이해할 수 있다.

> 이미지는 실행에 필요한 파일을 담은 준비물이고, 컨테이너는 그 준비물로 만든 실행 환경이다. 컨테이너가 계속 실행되는지는 그 안의 주 프로세스가 계속 동작하는지에 달려 있다.

## 🎯 오늘의 학습 목표

- 호스트·가상머신·게스트 운영체제·컨테이너의 관계를 설명하고, 이미지와 컨테이너를 구분할 수 있다.
- Ubuntu 실습 환경의 IP·서브넷 마스크·게이트웨이·DNS·SSH 설정이 각각 어떤 역할을 하는지 설명할 수 있다.

- Docker 설치 과정을 이해하고, 컨테이너의 생성·실행·접속·중지·삭제와 포트 연결을 구분할 수 있다.

### 1. 실행 환경을 이해하는 출발점과 가상머신·컨테이너

강의는 VMware 설치부터 시작하지만, 먼저 왜 별도의 Ubuntu 환경이 필요한지 이해하면 뒤의 설정이 연결된다. Docker 명령을 실행할 컴퓨터를 준비하고, 그 위에서 프로그램을 격리해 실행하는 것이 오늘 학습의 큰 구조다.

이 장에서는 [Docker 개념 자료](https://lgcns-docker-container-edu.oopy.io/docker05)의 내용을 바탕으로 컴퓨터·운영체제·프로세스의 관계부터 정리한다.

#### 1.1 프로그램 파일과 실행 중인 프로그램은 다르다

프로그램을 실행하려면 프로그램 파일뿐 아니라 필요한 라이브러리·설정·실행 도구도 맞아야 한다. 같은 코드가 다른 컴퓨터에서 실행되지 않는 이유 중 하나가 이런 **실행 환경**의 차이다.

**프로세스**는 실행 중인 프로그램을 뜻한다. 디스크에 있는 웹 서버 파일과, 그 파일을 실행해 실제 요청을 받는 웹 서버 프로세스는 구분해야 한다.

| 구분 | 쉬운 의미 | 오늘의 예시 |
| --- | --- | --- |
| 프로그램 | 실행할 수 있는 파일과 기능 | Nginx 웹 서버 |
| 라이브러리 | 프로그램이 동작할 때 사용하는 공통 기능 | 프로그램 실행에 필요한 시스템 라이브러리 |
| 운영체제 | 파일·메모리·프로세스·장치 등을 관리하는 시스템 | Ubuntu |
| 프로세스 | 프로그램을 실제로 실행한 상태 | 요청을 기다리는 Nginx 프로세스 |

Docker는 애플리케이션과 필요한 파일을 이미지로 묶고, 이를 바탕으로 격리된 실행 환경을 만든다. 다만 CPU 아키텍처·커널·외부 설정 등의 조건까지 모두 사라지는 것은 아니다.

#### 1.2 Linux·Ubuntu·커널의 관계를 먼저 구분한다

**커널**은 운영체제에서 CPU·메모리·장치 같은 자원을 관리하는 핵심 부분이다. 프로그램이 파일을 읽거나 네트워크를 사용할 때도 커널의 기능을 이용한다.

Ubuntu는 Linux 커널에 설치 프로그램·기본 도구·패키지 관리 체계 등을 묶은 리눅스 배포판이다. Ubuntu와 Rocky Linux처럼 배포판이 달라져도 리눅스의 많은 기본 명령은 비슷하지만, 패키지 관리 도구와 기본 설정에는 차이가 있다.

오늘 Ubuntu에서 사용하는 `apt`·`apt-get`은 패키지를 설치하고 관리하는 도구다. 배포판이 달라지면 같은 목적의 작업을 다른 패키지 관리 명령으로 수행할 수 있다.

#### 1.3 가상머신은 컴퓨터 환경을, 컨테이너는 프로세스 환경을 나눈다

**가상머신**은 CPU·메모리·디스크 등의 가상 하드웨어 위에 별도의 운영체제를 설치한 환경이다. VMware 같은 하이퍼바이저가 이를 만들고 관리한다.

**리눅스 컨테이너**는 호스트의 Linux 커널을 공유하면서 프로세스·파일 시스템·네트워크 등을 격리한 환경이다. 컨테이너마다 별도의 커널을 부팅하는 방식과는 다르다. [Docker 공식 문서의 VM과 컨테이너 비교](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/)

| 비교 기준 | 가상머신 | 리눅스 컨테이너 |
| --- | --- | --- |
| 구분하는 대상 | 가상 하드웨어와 게스트 운영체제 | 프로세스의 실행 환경 |
| 커널 | 게스트 운영체제가 자체 커널 사용 | 실행 호스트의 커널 공유 |
| 준비하는 파일 | 게스트 운영체제와 애플리케이션 등 | 애플리케이션과 필요한 사용자 공간 파일 등 |
| 실행 방식 | 운영체제를 부팅한 뒤 프로그램 실행 | 준비된 환경에서 주 프로세스 실행 |
| 자원 부담 | 운영체제 실행에 필요한 부담 포함 | 별도 커널 부팅 부담이 없어 대체로 가벼움 |

강의의 “컨테이너는 성능 손실이 없다”는 표현은 절대적인 보장으로 읽지 않는다. 저장 장치·네트워크·격리 설정·실행하는 작업에 따라 추가 비용이 생길 수 있다.

> [!NOTE]
> 컨테이너의 격리는 Linux의 네임스페이스와 cgroup 같은 기능을 이용한다. 네임스페이스는 프로세스가 보는 범위를 나누고, cgroup은 자원을 집계·제어한다. 컨테이너마다 CPU와 메모리가 자동으로 고정 배분되는 것은 아니며, 필요한 제한은 별도로 설정한다. [Docker의 격리와 자원 제어](https://docs.docker.com/engine/security/)

#### 1.4 Ubuntu는 VMware의 게스트이면서 Docker의 호스트다

**호스트**는 어떤 환경을 실행해 주는 쪽이고, **게스트**는 그 위에서 실행되는 쪽이다. 무엇을 기준으로 보느냐에 따라 같은 Ubuntu의 역할 이름이 달라진다.

| 기준 | 실행해 주는 쪽 | 그 위에서 실행되는 쪽 |
| --- | --- | --- |
| VMware | 실제 컴퓨터의 운영체제 | Ubuntu 가상머신 |
| Ubuntu 안의 Docker | Ubuntu 가상머신 | Nginx·Ubuntu 컨테이너 |

따라서 강의에서 Docker의 “호스트 포트”라고 하면 보통 실제 노트북의 포트가 아니라 **Docker Engine이 설치된 Ubuntu VM의 포트**를 가리킨다. 이 구분은 마지막 장의 웹 서버 접속에서 중요하다.

VM과 컨테이너는 함께 사용할 수 있다. 오늘처럼 VM 안에 Docker를 설치하는 구조도 자연스러운 구성이다.

#### 1.5 이미지 배포와 여러 컨테이너 관리는 서로 이어지는 단계다

이미지는 실행에 필요한 파일을 담은 읽기 전용 패키지이고, 컨테이너는 그 이미지로 만든 개별 실행 환경이다. 같은 이미지에서 컨테이너를 여러 개 만들 수 있다.

강의가 물리 서버·가상화·Docker·Kubernetes 순으로 설명하는 이유는 배포와 관리의 범위가 넓어지기 때문이다. 다만 앞의 기술이 모두 사라지고 뒤의 기술로 교체된다는 뜻은 아니다.

Kubernetes는 여러 컨테이너의 배치와 원하는 상태 유지 등을 관리하는 도구다. 오늘의 첫 컨테이너를 실행하는 데 반드시 필요하지는 않다.

> 가상머신은 별도 운영체제를 실행하는 환경이고, 컨테이너는 호스트 커널을 이용하는 격리된 프로세스 환경이다. 오늘은 Ubuntu VM을 Docker 호스트로 사용한다.

### 2. Ubuntu 설치에서 네트워크와 SSH 접속까지

실행 환경의 큰 구조를 알았으므로 실제로 Docker를 설치할 Ubuntu 컴퓨터를 준비한다. 이 단계의 목표는 Ubuntu가 켜지는 것뿐 아니라, 패키지를 내려받고 다른 터미널에서 접속할 수 있는 상태를 만드는 것이다.

설치 흐름과 주소는 [VMware 환경 구성 자료](https://lgcns-docker-container-edu.oopy.io/docker00)와 [Ubuntu 설치 자료](https://lgcns-docker-container-edu.oopy.io/docker01)를 따른다. 자료의 VMware Workstation 화면은 해당 실습 환경 기준이며, 다른 가상화 도구의 메뉴 이름과는 구분한다.

#### 2.1 가상 하드웨어를 만든 다음 Ubuntu를 설치한다

가상머신을 생성하는 것과 운영체제를 설치하는 것은 다른 단계다. 빈 컴퓨터를 준비했다고 운영체제가 저절로 설치되는 것은 아닌 것과 같다.

강의의 설치 흐름은 다음과 같다.

1. VMware Workstation에서 `Create a New Virtual Machine`을 선택한다.
2. `Typical` 구성에서 Ubuntu 24.04 설치 ISO 파일을 지정한다.
3. 가상 디스크·메모리·CPU 등 VM의 실행 자원을 확인한다.
4. Ubuntu 설치 화면에서 사용자 계정과 컴퓨터 이름을 설정한다.
5. 설치를 마친 Ubuntu를 부팅하고 네트워크를 설정한다.

**ISO**는 운영체제 설치 매체의 내용을 담은 파일이다. 컨테이너 이미지와 둘 다 파일로 배포할 수 있지만, ISO는 운영체제 설치에, Docker 이미지는 컨테이너 생성에 사용한다.

Ubuntu Desktop은 기본적으로 그래픽 화면을 제공하고, Server는 서버 운영을 위한 구성을 중심으로 제공한다. Server가 “외부 접속으로만 사용할 수 있는 운영체제”라는 뜻은 아니며, 로컬 콘솔에서도 명령어를 사용할 수 있다.

사용자 이름·컴퓨터 이름·VMware 화면의 VM 이름도 다르다. 예를 들어 로그인 계정이 `ubuntu`이고 컴퓨터 이름이 `k8s-master`여도, 이름만으로 Kubernetes가 설치되거나 마스터 역할이 생기지는 않는다.

#### 2.2 NAT와 Host-only는 통신할 수 있는 범위가 다르다

가상머신에는 가상 네트워크 연결도 필요하다. 강의는 VMware의 기본 NAT 네트워크인 `VMnet8`을 사용한다.

| 연결 방식 | 쉬운 의미 | 기본 네트워크 이름 |
| --- | --- | --- |
| Bridged | VM을 실제 LAN에 연결하는 방식 | 보통 `VMnet0` |
| Host-only | 실제 컴퓨터와 VM들 사이의 사설망 | 보통 `VMnet1` |
| NAT | VM이 실제 컴퓨터의 네트워크를 이용해 외부로 통신 | 보통 `VMnet8` |

Host-only를 “아무 네트워크도 연결되지 않은 상태”로 이해하면 안 된다. 호스트와 VM 간 통신은 가능하지만 기본 구성에서는 외부 인터넷으로 나가는 연결을 제공하지 않는다. [VMware 네트워크 방식 설명](https://knowledge.broadcom.com/external/article/309842/understanding-networking-types-in-hosted.html)

NAT는 주소를 변환해 VM의 외부 통신을 돕는다. 같은 물리 컴퓨터에서는 가상 어댑터를 통해 VM에 직접 접근할 수 있지만, 외부 컴퓨터가 VM으로 들어오는 연결은 별도의 포워딩이나 접근 경로가 필요할 수 있다.

#### 2.3 IP·서브넷·게이트웨이·DNS를 하나의 주소 체계로 맞춘다

IP 주소는 컴퓨터의 네트워크 주소이고, 포트는 그 컴퓨터 안에서 통신할 프로그램을 구분하는 번호다. 서브넷 마스크는 같은 네트워크로 판단할 주소 범위를 정한다.

강의에서 설정하는 값은 다음과 같다.

| 설정 위치 | 항목 | 강의 값과 역할 |
| --- | --- | --- |
| VMware VMnet8 | 서브넷 | `10.0.2.0/24` 사설망 |
| VMware NAT 설정 | 게이트웨이 | `10.0.2.2`, 외부 네트워크로 나가는 통로 |
| VMware DHCP 설정 | 자동 할당 범위 | `10.0.2.128`~`10.0.2.254` |
| Ubuntu IPv4 수동 설정 | IP 주소 | `10.0.2.10`, 이 VM에 부여한 주소 |
| Ubuntu IPv4 수동 설정 | 네트마스크 | `255.255.255.0`, `/24`와 같은 범위 |
| Ubuntu IPv4 수동 설정 | 게이트웨이 | `10.0.2.2`, VMware NAT 설정과 일치 |
| Ubuntu IPv4 수동 설정 | DNS | `10.0.2.2`, 강의의 NAT DNS 프록시 사용 |

`10.0.2.0/24`에서 `10.0.2.0`은 네트워크 자체를 나타내는 주소이므로 VM의 개별 주소로 쓰지 않는다. 이 범위의 `10.0.2.255`는 브로드캐스트 주소다.

**DHCP**는 주소를 자동으로 나눠 주는 기능이고, **DNS**는 도메인 이름을 IP 주소로 찾는 기능이다. 둘은 다른 역할이다. 강의의 수동 주소 `.10`은 DHCP 범위 밖에 두어 자동 할당 주소와 겹치지 않게 구성한다.

DNS가 게이트웨이와 같은 `.2`인 것은 이 실습의 NAT 장치가 DNS 요청을 중계하기 때문이다. 다른 네트워크에서도 DNS와 게이트웨이를 무조건 같은 주소로 적는 규칙은 아니다. [VMware Virtual Network Editor와 NAT DNS 설명](https://knowledge.broadcom.com/external/article/339371/using-the-virtual-network-editor-in-vmwa.html)

#### 2.4 주소가 맞아도 경로와 이름 조회를 따로 확인한다

주소를 저장한 뒤 연결을 다시 적용하고, 실제 인터페이스와 기본 경로를 확인한다. 네트워크 연결을 다시 적용하는 작업과 패키지 목록을 갱신하는 `apt-get update`는 전혀 다른 작업이다.

다음은 Ubuntu VM 안에서 실행할 수 있는 설명용 확인 명령이다. 실행 성공 결과를 기록한 것은 아니다.

```bash
ip -br addr
ip route
getent hosts download.docker.com
```

| 확인 명령 | 확인하는 것 |
| --- | --- |
| `ip -br addr` | 네트워크 인터페이스에 원하는 주소가 있는가? |
| `ip route` | 기본 경로가 적절한 게이트웨이를 향하는가? |
| `getent hosts download.docker.com` | Docker 저장소의 이름을 주소로 찾을 수 있는가? |

IP 주소가 있어도 기본 경로가 없으면 외부 통신이 되지 않을 수 있다. 외부 주소로는 통신하지만 도메인만 찾지 못하면 DNS 쪽을 나눠 확인한다.

#### 2.5 기본 도구를 설치하고 패키지 명령의 의미를 읽는다

강의는 Ubuntu 설치 후 SSH 서버와 파일 작업용 도구를 준비한다. 아래는 일반 사용자가 `sudo`를 붙여 실행하는 형태로 정리한 강의 명령이다.

```bash
sudo apt-get update
sudo apt-get install -y openssh-server curl vim tree
```

`update`는 저장소에서 설치 가능한 패키지의 **목록**을 갱신한다. 이미 설치된 프로그램을 모두 새 버전으로 바꾸는 `upgrade`와는 다르다.

| 도구 | 역할 | 필요한 이유 |
| --- | --- | --- |
| `openssh-server` | Ubuntu에서 SSH 접속을 받는 서버 | 다른 터미널에서 VM에 접속 |
| `curl` | URL로 요청을 보내고 응답을 받는 도구 | 파일 다운로드·HTTP 응답 확인 |
| `vim` | 터미널에서 사용하는 텍스트 편집기 | 설정 파일 편집 |
| `tree` | 디렉터리 구조를 트리로 표시 | 파일 위치와 구조 확인 |

`install`은 지정한 패키지를 설치하고, `-y`는 설치 확인 질문에 자동으로 동의하는 옵션이다. Vim은 vi에서 발전한 편집기이며, `vi`라는 명령이 어떤 구현을 실행하는지는 시스템 설정에 따라 달라질 수 있다.

#### 2.6 SSH 접속은 원격 Ubuntu에서 명령을 실행하는 연결이다

SSH는 암호화된 원격 접속 방식이다. XShell은 SSH 클라이언트 프로그램이고, Ubuntu의 OpenSSH 서버는 접속을 받는 쪽이다. XShell 자체가 Ubuntu나 Docker는 아니다.

강의의 직접 접속 기준은 호스트 `10.0.2.10`, 포트 `22`, 사용자 이름 `ubuntu`다. 같은 설정을 명령줄 클라이언트로 표현한 설명용 예시는 다음과 같다.

```bash
ssh ubuntu@10.0.2.10
```

명령을 입력하는 곳은 Ubuntu에 접속하려는 쪽의 터미널이다. 접속이 끝난 뒤 입력하는 리눅스 명령은 원격 Ubuntu에서 실행된다. [Ubuntu OpenSSH 서버 설명](https://ubuntu.com/server/docs/how-to/security/openssh-server/)

자료의 접힌 참고 부분에는 `127.0.0.1`의 `101`~`104` 포트를 쓰는 다른 구성도 나온다. 이는 호스트 포트를 VM의 SSH 포트로 전달하는 규칙이 있을 때 사용하는 방식이다.

| 접속 방식 | 클라이언트가 지정할 주소 | 필요한 조건 |
| --- | --- | --- |
| VM에 직접 접속 | `10.0.2.10:22` | 해당 VM 주소로 통신 가능 |
| 호스트의 포트로 우회 | 예시 `127.0.0.1:101` | 그 포트를 VM의 `22`로 전달하는 규칙 |

`127.0.0.1`은 항상 명령을 실행하는 환경 자신을 가리킨다. 포워딩 설정 없이 주소와 포트 숫자만 바꾼다고 같은 VM에 접속되는 것은 아니다.

첫 접속의 호스트 키 확인은 “이 서버가 이전에 알고 있던 서버인가”를 확인하는 절차다. 서버 신원을 확인하고 저장하는 것과 사용자 계정의 비밀번호를 저장하는 것은 다른 일이다.

#### 2.7 일반 사용자·root·현재 위치를 구분한다

관리 작업은 높은 권한이 필요할 수 있다. `sudo 명령`은 해당 명령을 관리자 권한으로 실행하고, `sudo -i`는 관리자 로그인 셸로 전환한다.

아래는 접속한 Ubuntu에서 사용자와 컴퓨터·위치를 구분하는 설명용 명령이다.

```bash
whoami
hostname
pwd
sudo -i
whoami
pwd
exit
```

관리자 셸로 바꾸면 홈 디렉터리도 보통 `/root`로 바뀐다. `~/`는 현재 사용자의 홈을 뜻하므로, 일반 사용자의 `~`와 root의 `~`가 같은 위치라고 생각하면 안 된다.

프롬프트의 `$`는 일반 사용자, `#`는 root를 나타내는 관례가 있다. 다만 프롬프트는 바꿀 수 있으므로 실제 계정은 `whoami`로 확인한다. 예제 명령을 복사할 때 프롬프트 기호까지 입력하지 않는다.

#### 2.8 스냅샷과 복제는 서로 다른 목적이다

**스냅샷**은 설정을 바꾸기 전 상태로 돌아가기 위한 기준점이고, **복제**는 비슷한 VM을 별도로 만드는 작업이다. 자료의 Full Clone은 원본과 별개의 가상 디스크를 가진 VM을 만드는 방식이다.

복제한 VM을 동시에 사용하려면 IP 주소를 서로 다르게 정해야 한다. 강의의 참고 예시는 `k8s-master`에 `.10`, Worker들에 `.11`·`.12`·`.13`을 사용한다.

> [!NOTE]
> 자료의 여러 VM 복제는 이후 Kubernetes 구성을 위한 참고 내용이다. Docker 기본 실행에 여러 VM이 필수인 것은 아니며, 오늘 구성의 목표는 우선 한 Ubuntu 환경에서 접속과 Docker 실행을 연결하는 것이다.

> Ubuntu 설치, IP 설정, 외부 통신, SSH 접속은 각각 확인해야 하는 단계다. 접속한 뒤에는 사용자·컴퓨터·현재 경로를 구분해야 이후 명령의 실행 위치를 잃지 않는다.

### 3. 리눅스 명령어와 vi로 파일 다루기

Ubuntu에 접속했다면 이제 파일을 찾아서 읽고 고칠 수 있어야 한다. Docker 설치 파일을 옮기거나 설정을 편집하는 작업도 결국 파일과 디렉터리를 다루는 작업이다.

이 장은 [Ubuntu 주요 명령어](https://lgcns-docker-container-edu.oopy.io/docker02)와 [vi 사용 자료](https://lgcns-docker-container-edu.oopy.io/docker03)의 내용을 하나의 파일 작업 흐름으로 연결한다. 명령 예시는 Ubuntu 터미널 기준이며, 설명용으로 연결한 예제를 실제 수행 기록과 구분한다.

#### 3.1 현재 위치를 알아야 같은 명령도 올바른 대상을 가리킨다

**디렉터리**는 파일을 담는 폴더다. 터미널의 현재 작업 디렉터리는 명령에서 상대 경로를 해석하는 출발점이다.

| 명령 | 하는 일 | 구분할 점 |
| --- | --- | --- |
| `pwd` | 현재 작업 디렉터리의 경로 출력 | 내가 어느 폴더에 있는지 확인 |
| `ls` | 현재 디렉터리의 항목 조회 | 기본적으로 숨김 파일은 제외 |
| `ls -al` | 숨김 항목까지 자세히 조회 | 이름·권한·소유자 등 확인 |
| `cd /tmp` | `/tmp`로 이동 | `/`에서 시작하는 절대 경로 |
| `cd ..` | 상위 디렉터리로 이동 | 현재 위치를 기준으로 이동 |
| `cd ~` | 현재 사용자의 홈으로 이동 | root로 바꾸면 홈도 달라짐 |
| `cd -` | 직전 작업 디렉터리로 이동 | 상위 폴더로 가는 `..`와 다름 |

`/home/ubuntu/file.txt`처럼 루트 `/`에서 시작하면 **절대 경로**다. `./test/file.txt`처럼 현재 위치를 기준으로 적으면 **상대 경로**다.

리눅스에서 파일 이름의 대소문자는 일반적으로 구분된다. `File.txt`와 `file.txt`는 서로 다른 파일일 수 있고, 이름 중간의 공백은 따옴표로 감싸야 하나의 인자로 전달된다.

#### 3.2 생성·복사·이동·삭제를 하나의 예제로 연결한다

다음은 새로운 연습 폴더에서 강의의 파일 명령을 연결한 설명용 예제다. `docker-study`라는 이름의 연습 폴더가 비어 있다고 가정한다.

```bash
mkdir -p ~/docker-study
cd ~/docker-study
mkdir test
touch file.txt
cp file.txt file2.txt
mv file.txt file2.txt ./test/
ls ./test/
rm ./test/file2.txt
```

`cp`는 원본을 두고 복사본을 만든다. `mv`는 파일을 다른 위치로 옮기거나 이름을 바꾼다. 예제의 `mv`는 두 파일을 이미 존재하는 `test` 디렉터리 안으로 옮기는 명령이다.

| 명령 형태 | 의미 |
| --- | --- |
| `mkdir test` | 디렉터리 생성 |
| `rmdir test` | 비어 있는 디렉터리 삭제 |
| `touch file.txt` | 없으면 빈 파일 생성, 있으면 수정 시각 등 갱신 |
| `cp 원본 대상` | 파일 복사 |
| `mv 원본 새이름` | 파일 이름 변경 |
| `mv 파일 디렉터리/` | 파일을 해당 디렉터리로 이동 |
| `rm 파일` | 파일 삭제 |

위 예제 마지막에는 `test/file.txt`가 남으므로 바로 `rmdir test`를 하면 비어 있지 않아 삭제되지 않는다. 파일의 내용을 읽으려면 `cat ./test/file.txt`처럼 대상 경로를 지정한다.

> [!WARNING]
> 터미널의 `rm`은 보통 휴지통으로 이동시키지 않는다. 삭제 전 `pwd`와 대상 이름을 확인하고, 복사·이동도 같은 이름의 기존 파일을 덮어쓸 수 있다는 점을 구분한다.

#### 3.3 vi는 현재 모드에 따라 같은 키의 의미가 달라진다

`vi`는 키보드로 조작하는 편집기다. 메모장처럼 열자마자 모든 키가 글자로 입력되는 방식이 아니므로, 먼저 **모드**를 알아야 한다.

| 모드 | 하는 일 | 진입과 복귀 |
| --- | --- | --- |
| 일반 모드 | 이동·삭제·복사 등 편집 명령 | 처음 열었을 때, 또는 `Esc` |
| 입력 모드 | 파일에 글자 입력 | 일반 모드에서 `i`·`a`·`o` 등 |
| 명령줄 모드 | 저장·종료·설정 등 실행 | 일반 모드에서 `:` 후 명령과 Enter |

강의의 “명령 모드”는 위 표의 일반 모드를 가리킨다. 명령을 실행하려고 하는데 글자가 입력된다면 먼저 `Esc`로 일반 모드에 돌아온다.

`i`는 현재 커서 앞에서 입력하고, `a`는 커서 다음에서 입력한다. 소문자 `o`는 아래에 새 줄을 만들고 입력 모드로 들어간다.

#### 3.4 이동 명령에서 숫자 0과 소문자 o를 구분한다

| 키 | 의미 |
| --- | --- |
| `0` | 현재 줄의 맨 앞으로 이동 |
| `$` | 현재 줄의 끝으로 이동 |
| `1G` | 파일의 첫 번째 줄로 이동 |
| `G` | 파일의 마지막 줄로 이동 |
| `gg` | Vim에서 파일 첫 줄로 이동 |
| `/검색어` 후 Enter | 앞으로 검색 |
| `n` | 같은 검색 방향의 다음 결과 |
| `N` | 반대 검색 방향의 다음 결과 |

자료의 “파일 끝으로 `1G`”는 첫 줄 이동으로 바로잡아야 한다. 줄 맨 앞 이동도 알파벳 `o`가 아니라 숫자 `0`이다. 대문자 `G`는 보통 Shift를 누르고 `g`를 눌러 입력한다. [Vim 이동 명령 설명](https://vimhelp.org/motion.txt.html)

#### 3.5 복사·삭제는 명령 앞의 숫자로 범위를 정한다

| 키 | 의미 | 기억할 관계 |
| --- | --- | --- |
| `yy` | 현재 줄 복사 | `2yy`는 두 줄 복사 |
| `p` | 버퍼 내용을 뒤에 붙이기 | 줄 단위 복사라면 현재 줄 아래 |
| `dd` | 현재 줄 삭제하고 버퍼에 보관 | 이어서 `p`로 옮길 수 있음 |
| `3dd` | 현재 줄부터 세 줄 삭제 | 숫자가 반복 범위 지정 |
| `x` | 커서 위치 문자 삭제 | 한 글자 편집 |
| `dw` | 다음 단어 경계까지 삭제 | 단어 단위 편집 |
| `u` | 직전 편집 취소 | 잘못 지운 내용을 되돌릴 때 사용 |
| `:set nu` | 줄 번호 표시 | 명령 뒤 Enter |

`dd`와 `yy`는 이동 명령이 아니라 편집 명령이다. `:%d`는 파일의 모든 줄을 삭제하는 명령이므로 단순 조회 명령처럼 입력하지 않는다.

#### 3.6 저장하지 않은 수정이 있으면 q만으로는 종료되지 않는다

편집 중인 내용은 먼저 메모리의 버퍼에 반영된다. 저장 명령을 실행해야 디스크 파일에 기록된다.

| 입력 | 동작 | 주의할 점 |
| --- | --- | --- |
| `:w` | 저장 | 편집기는 계속 열림 |
| `:q` | 종료 | 저장하지 않은 수정이 있으면 거부될 수 있음 |
| `:wq` | 저장 후 종료 | 수정 내용을 파일에 남김 |
| `:x` | 필요한 경우 저장 후 종료 | 수정이 없으면 다시 쓰지 않음 |
| `:q!` | 마지막 저장 이후 수정 버리고 종료 | 이미 저장한 변경을 되돌리는 명령은 아님 |

자료의 “잘못 수정했으면 `:q`”는 수정이 있는 상황에서 충분하지 않다. 저장하지 않은 변경을 버리고 끝내려면 `Esc`를 누른 뒤 `:q!`와 Enter를 입력한다. [Vim 저장·종료 안내](https://vimhelp.org/quickref.txt.html#Q_wq)

`!`를 붙인다고 모든 문제가 해결되는 것도 아니다. `:wq!`는 일부 보호 확인을 강제로 넘기지만, 운영체제의 파일 쓰기 권한까지 만들어 주지는 않는다.

#### 3.7 파일을 열고 입력한 뒤 저장 결과를 읽는 흐름으로 익힌다

앞의 연습 폴더에서 파일을 편집하는 설명용 예제다. 명령과 편집기에 입력하는 키를 구분한다.

```bash
cd ~/docker-study
vi ./test/file.txt
```

1. 편집기가 열리면 `i`를 눌러 입력 모드로 들어간다.
2. 설명용 문장 `linux test`를 입력한다.
3. `Esc`를 눌러 일반 모드로 돌아온다.
4. `:wq`를 입력하고 Enter를 눌러 저장 후 종료한다.
5. 터미널에서 다음 명령으로 파일 내용을 읽는다.

```bash
cat ./test/file.txt
```

의도대로 저장했다면 입력한 문장이 파일에 남아 있어야 한다. `vi`에서 빠져나왔다는 사실만으로 저장됐다고 판단하지 않고 실제 파일 내용을 확인한다.

> 리눅스 파일 작업은 현재 위치와 대상 경로를 확인하는 데서 시작한다. vi에서는 모드를 구분하고, 저장과 종료가 별개의 동작이라는 점을 기억해야 한다.

### 4. Docker Engine을 설치하고 실행 상태 확인하기

파일과 명령줄 조작을 익혔으므로 Ubuntu에 컨테이너 관리 도구를 설치할 수 있다. 여기서 설치하는 Docker Engine은 명령을 받아 이미지·컨테이너·네트워크 등을 관리하는 실행 기반이다.

[Docker 엔진 설치 자료](https://lgcns-docker-container-edu.oopy.io/docker04)는 단계별 설치와 전달받은 스크립트 실행을 함께 소개한다. 설치가 무엇을 준비하는지 이해한 뒤, Ubuntu 24.04에 맞는 공식 저장소 방식으로 연결한다.

#### 4.1 docker 명령은 데몬에 작업을 요청하는 클라이언트다

터미널에서 `docker run`을 입력하면 명령줄 클라이언트가 Docker 데몬에 컨테이너 실행을 요청한다. 데몬은 이미지와 컨테이너 등의 실제 관리 작업을 담당한다.

| 구성 요소 | 역할 | 오늘의 위치 |
| --- | --- | --- |
| Docker CLI | 사용자의 명령을 API 요청으로 전달 | Ubuntu의 `docker` 명령 |
| Docker 데몬 | 이미지·컨테이너·네트워크 등 관리 | Ubuntu에서 동작하는 `dockerd` |
| 컨테이너 런타임 | 컨테이너 실행을 뒷받침 | `containerd`·`runc` 등 |
| 이미지 레지스트리 | 이미지를 저장하고 배포 | Docker Hub 등 |

기본적인 로컬 설치에서는 CLI와 데몬이 같은 Ubuntu에 있다. 하지만 다른 곳의 데몬에 접속할 수도 있으므로, Docker 명령을 입력하는 위치와 실제 컨테이너가 실행되는 위치는 원래 별개의 개념이다. [Docker의 클라이언트·서버 구조](https://docs.docker.com/get-started/docker-overview/)

#### 4.2 저장소 등록과 GPG 키는 서로 다른 역할이다

패키지 **저장소**는 설치할 프로그램을 내려받는 출처이고, **서명 키**는 그 출처의 패키지 정보를 검증할 때 사용한다. 저장소 주소만 적는 것과 신뢰할 키를 연결하는 작업을 함께 해야 한다.

| 설치 단계 | 목적 |
| --- | --- |
| 사전 도구 설치 | HTTPS 통신과 파일 다운로드 준비 |
| Docker 서명 키 저장 | 저장소 서명 검증 기준 준비 |
| Docker 저장소 등록 | 배포판·아키텍처에 맞는 패키지 출처 지정 |
| 패키지 목록 갱신 | 새 저장소의 설치 가능 목록 읽기 |
| Docker 패키지 설치 | 데몬·CLI·런타임 등 설치 |
| 실행 확인 | 명령줄과 데몬이 모두 동작하는지 확인 |

강의의 `apt-key add`와 `apt-key fingerprint`는 구형 키 관리 방식이다. 현재 공식 안내는 키를 별도 파일에 두고 해당 저장소의 `Signed-By`로 연결한다.

자료의 저장소 출력 예시에는 `focal`도 나오지만 Ubuntu 24.04의 코드명은 `noble`이다. 실행할 Ubuntu 버전을 기준으로 저장소를 선택하며, 예시 출력의 코드명을 그대로 복사하지 않는다.

#### 4.3 Ubuntu 24.04에서는 공식 키와 저장소를 등록한다

다음은 새 Ubuntu 환경에 Docker 공식 저장소를 등록하는 설명용 예제다. 설치 명령을 정리한 것이며 이 문서를 작성하면서 VM에 실행한 결과는 아니다. 기존 Docker·containerd 패키지가 있는 환경에서는 [공식 설치 문서의 충돌 패키지 확인](https://docs.docker.com/engine/install/ubuntu/)도 먼저 적용한다.

**서명 키 준비**

```bash
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
```

`ca-certificates`는 HTTPS 서버 인증서 검증에 필요한 인증서 목록을 제공한다. 여기서 `install -d`는 디렉터리를 만드는 명령이고, `chmod a+r`은 저장한 공개 키 파일을 읽을 수 있도록 권한을 설정한다.

**패키지 저장소 등록**

```bash
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
```

`Suites`는 현재 배포판 코드명을, `Architectures`는 시스템의 CPU 아키텍처를 사용한다. 따라서 강의의 `amd64`를 모든 컴퓨터에 고정하는 방식과 구분한다.

`<<EOF`부터 마지막 `EOF`까지는 셸이 여러 줄을 하나의 입력으로 전달하는 문법이다. 마지막 `EOF`도 포함해 실행해야 하며, `Signed-By`가 앞에서 저장한 키 파일을 가리킨다.

**Docker 구성 패키지 설치**

```bash
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

`docker-ce`는 Engine, `docker-ce-cli`는 명령줄 도구, `containerd.io`는 런타임 구성을 제공한다. Buildx와 Compose 플러그인은 각각 빌드와 여러 컨테이너 구성에 쓰이며, 오늘은 설치 구성 요소로만 구분한다.

#### 4.4 서비스 상태와 Client·Server 응답을 함께 본다

설치 명령이 끝났다는 사실과 데몬이 실행 중이라는 사실은 별개다. 아래는 설치 후 사용할 설명용 확인 명령이다.

```bash
sudo systemctl status docker
sudo docker version
sudo docker run hello-world
```

| 확인 항목 | 무엇을 확인하는가? |
| --- | --- |
| `systemctl status docker` | Docker 서비스의 실행 상태 |
| `docker version`의 Client | 명령줄 클라이언트 정보 |
| `docker version`의 Server | 접속한 Docker 데몬 정보 |
| `docker run hello-world` | 이미지 확보·컨테이너 생성·프로그램 실행의 연결 |

`systemctl status` 뒤에 `docker`를 적어야 특정 Docker 서비스 상태를 확인할 수 있다. 실행되지 않았다면 `sudo systemctl start docker`로 시작한 뒤 상태를 다시 확인한다.

`hello-world`는 확인 메시지를 출력하고 종료하는 프로그램이다. 정상 실행 뒤 컨테이너가 `Exited`가 되는 것은 실패를 뜻하지 않는다. 실제 성공 여부는 출력과 종료 상태를 함께 확인한다.

#### 4.5 전달받은 설치 스크립트의 이름만으로 내용을 추정하지 않는다

강의의 간편 설치는 `install-docker.sh`를 Xftp로 Ubuntu에 전송하고 실행 권한을 준 뒤 실행하는 흐름이다. `chmod u+x`는 파일 소유자에게 실행 권한을 추가하는 명령이지, 설치 자체를 수행하는 명령은 아니다.

자료에 스크립트의 전체 내용이 제공되지 않아 어떤 저장소·버전·설정을 적용하는지 파일명만으로 확정할 수 없다. 따라서 설치 과정을 다시 이해할 때는 앞 소주제의 공개된 단계별 절차와 비교한다.

강의의 `sudo usermod -a -G docker ubuntu`는 기존 그룹을 유지하면서 `ubuntu` 사용자를 `docker` 그룹에 추가하는 명령이다. 적용한 경우 새 로그인 세션이 필요하며, 그룹 추가가 Docker를 다시 설치하는 작업은 아니다.

> [!WARNING]
> 기본 root 데몬 구성에서 `docker` 그룹은 사실상 관리자 수준의 권한을 제공한다. `sudo`를 생략하기 위한 단순 편의 옵션으로만 보지 말고, 접근 권한을 구분한다. 이 문서의 일반 사용자용 Docker 예시는 `sudo`를 붙여 표기한다. [Docker 설치 후 권한 안내](https://docs.docker.com/engine/install/linux-postinstall/)

Docker Hub 로그인은 설치 성공의 필수 조건이 아니다. 공개 이미지도 접근 정책·다운로드 제한 등에 따라 인증이 필요할 수 있지만, 개인 저장소를 쓰는 것과 로컬 Docker 데몬이 동작하는 것은 별도로 확인한다.

> Docker 설치는 패키지만 내려받는 일이 아니다. 현재 Ubuntu에 맞는 저장소와 키를 등록하고, 클라이언트가 실행 중인 데몬에 요청할 수 있는지까지 확인해야 한다.

### 5. 이미지로 컨테이너를 만들고 서비스에 접속하기

이제 설치한 Docker를 이용해 이미지에서 컨테이너를 만들 수 있다. 이때 무엇이 준비물이고 무엇이 실행 대상인지, 웹 요청이 어느 포트로 전달되는지, 왜 어떤 컨테이너는 바로 종료되는지를 구분해야 한다.

[Docker 설치 자료의 Nginx 예제](https://lgcns-docker-container-edu.oopy.io/docker04)와 [Docker 개념 자료의 Ubuntu 예제](https://lgcns-docker-container-edu.oopy.io/docker05)를 연결해 읽는다. 아래 실행 명령은 원리를 설명하기 위한 재구성 예제이며, 사용자의 별도 실행 결과나 성공 기록을 뜻하지 않는다.

#### 5.1 이미지는 준비된 파일이고 컨테이너는 그 파일로 만든 개별 환경이다

이미지에는 실행 파일·라이브러리·설정 같은 재료가 들어 있다. 컨테이너를 만들면 읽기 전용 이미지 위에 그 컨테이너만의 쓰기 가능한 계층이 마련된다.

같은 Nginx 이미지로 `webserver`와 `webserver2`를 만들 수 있다. 각 컨테이너의 파일 변경은 기본적으로 개별 쓰기 계층에 기록되며 원본 이미지 자체를 고치지는 않는다. [Docker 이미지 설명](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/)

| 구분 | 이미지 | 컨테이너 |
| --- | --- | --- |
| 역할 | 생성에 사용할 실행 파일 묶음 | 이미지로 만든 실행 환경 |
| 실행 여부 | 이미지 자체는 프로세스가 아님 | 생성만 된 상태·실행 중·중지 상태 등이 있음 |
| 변경 | 기존 이미지 내용을 직접 바꾸지 않음 | 개별 쓰기 계층에 변경 기록 가능 |
| 관계 | 하나로 여러 컨테이너 생성 가능 | 각각 이름·ID·설정·상태를 가짐 |

컨테이너를 “실행 중인 것만” 뜻한다고 생각해서도 안 된다. 주 프로세스가 멈춘 뒤에도 컨테이너 객체와 파일 변경은 삭제 전까지 남을 수 있다.

#### 5.2 이미지 이름에서 저장 위치와 태그를 읽는다

이미지 참조는 레지스트리·네임스페이스·저장소·태그로 나눠 읽을 수 있다. 다음은 공식 Nginx 이미지의 기본 표기를 풀어 쓴 설명용 예시다.

```text
docker.io/library/nginx:latest
```

| 부분 | 의미 | 예시 |
| --- | --- | --- |
| 레지스트리 | 이미지를 내려받는 서버 | `docker.io` |
| 네임스페이스 | 사용자·조직 또는 공식 이미지 구분 | `library` |
| 저장소 이름 | 이미지의 이름 | `nginx` |
| 태그 | 버전이나 변형을 구분하는 이름표 | `latest` |

일반적인 기본 설정에서 `nginx`만 적으면 Docker Hub의 공식 이미지와 `latest` 태그를 사용한다. 강의의 `powermvp/marvel-collection:latest`에서는 `powermvp`가 사용자·조직 구분 부분이고, `marvel-collection`이 저장소 이름이다. [Docker 이미지 이름 구조](https://docs.docker.com/reference/cli/docker/image/tag/)

`latest`는 “현재 존재하는 모든 버전 중 가장 최신을 계산해서 선택하라”는 뜻이 아니다. 지정된 태그 이름이며, 로컬에 이미지가 있으면 기본 `docker run`이 원격의 새 이미지를 매번 다시 확인해 내려받는 것도 아니다.

강의의 `ubuntu:focal`은 Ubuntu 20.04 계열의 사용자 공간을 담은 이미지다. Ubuntu 24.04 VM에서 이 컨테이너를 실행하더라도 VM의 커널이 20.04 커널로 바뀌지 않는다. 컨테이너는 Docker 호스트의 커널을 공유한다.

#### 5.3 run은 이미지를 확보하고 새 컨테이너를 만들어 시작한다

다음은 강의의 첫 Nginx 실행 명령을 일반 사용자 기준으로 표현한 것이다. 같은 이름의 컨테이너가 없는 상태를 전제로 한다.

```bash
sudo docker run -d --name webserver -p 80:80 nginx
```

| 부분 | 의미 |
| --- | --- |
| `docker run` | 새 컨테이너 생성 후 실행 |
| `-d` | 현재 터미널에 붙어 있지 않는 분리 실행 |
| `--name webserver` | 컨테이너 이름 지정 |
| `-p 80:80` | Docker 호스트의 80번 포트를 컨테이너의 80번으로 연결 |
| `nginx` | 생성에 사용할 이미지 |

이 명령을 요청받은 데몬은 다음 흐름으로 동작한다.

```text
Docker CLI가 데몬에 새 컨테이너 실행을 요청한다
    ↓ 기본 정책에서 로컬 이미지가 없으면 레지스트리에서 가져온다
컨테이너를 만들 이미지가 준비된다
    ↓ 개별 쓰기 계층과 네트워크·포트 설정을 구성한다
webserver라는 새 컨테이너가 생성된다
    ↓ 이미지에 정해진 기본 실행 명령을 시작한다
Nginx 주 프로세스가 웹 요청을 기다린다
```

이미지를 준비하는 `pull`, 컨테이너를 만드는 `create`, 실행하는 `start`를 구분하면 강의의 “run은 pull + create + start”라는 표현을 이해할 수 있다. 단, 이미지를 매번 내려받는다는 뜻은 아니다. [Docker run 동작과 이미지 선택 정책](https://docs.docker.com/reference/cli/docker/container/run/)

Nginx 이미지에는 웹 서버가 계속 요청을 기다리도록 하는 기본 명령이 있다. `-d`가 컨테이너를 영원히 살려 두는 것이 아니라, 실행한 주 프로세스가 계속 동작하기 때문에 유지되는 것이다.

#### 5.4 포트는 왼쪽이 Docker 호스트이고 오른쪽이 컨테이너다

**포트 공개**는 Docker 호스트의 특정 포트로 들어온 요청을 컨테이너 안의 포트로 전달하는 설정이다. IP가 어느 컴퓨터로 갈지 정한다면, 포트는 그 안의 어느 서비스로 갈지 정한다.

Nginx 기본 HTTP 설정의 컨테이너 포트는 `80`이다. 따라서 두 번째 웹 서버를 호스트의 `8080`으로 열려면 다음처럼 연결한다.

```bash
sudo docker run -d --name webserver2 -p 8080:80 nginx
```

| 표기 | 요청을 받는 호스트 포트 | 전달할 컨테이너 포트 |
| --- | --- | --- |
| `-p 80:80` | 80 | 80 |
| `-p 8080:80` | 8080 | 80 |
| `-p 8080:8080` | 8080 | 8080 |

> [!WARNING]
> 자료의 두 번째 Nginx 명령에는 `8080:8080`이 나오지만, 기본 Nginx가 80번에서 요청을 받는 상태라면 목적지가 맞지 않는다. 호스트 8080으로 접근하려면 `8080:80`을 사용하거나 컨테이너 내부 Nginx 설정을 실제로 8080으로 바꿔야 한다. 포트 연결 옵션이 서버의 수신 포트 설정을 바꾸지는 않는다. [공식 Nginx 이미지 사용법](https://hub.docker.com/_/nginx)

오늘 구조에서 `8080`은 Docker가 설치된 Ubuntu VM의 포트다. VM 내부에서는 아래 설명용 명령으로 접근할 수 있다.

```bash
curl http://localhost:8080/
```

실제 컴퓨터의 브라우저에서는 VM 주소로 통신이 가능하다는 전제 아래 `http://10.0.2.10:8080/`에 접근한다. 실제 컴퓨터에서 `localhost:8080`을 여는 것은 그 컴퓨터 자신의 포트에 접근하는 것이므로 VMware 쪽 포워딩이 없다면 같은 요청이 아니다.

```text
실제 컴퓨터의 브라우저가 10.0.2.10:8080에 요청한다
    ↓ VMnet8 경로로 Ubuntu VM에 도착한다
Docker 호스트인 Ubuntu의 8080번 포트로 요청이 들어온다
    ↓ Docker가 공개한 포트 연결 규칙을 적용한다
컨테이너 안의 80번 포트에 요청이 전달된다
    ↓ Nginx가 요청을 처리한다
웹 응답이 브라우저로 돌아온다
```

주소를 생략한 `-p`는 기본적으로 호스트의 여러 인터페이스에 포트를 공개한다. `docker ps`에 `80/tcp`만 보이는 것과 `0.0.0.0:8080->80/tcp`처럼 호스트 연결이 보이는 것은 구분해야 한다. [Docker 포트 공개 설명](https://docs.docker.com/get-started/docker-concepts/running-containers/publishing-ports/)

#### 5.5 images는 준비물을, ps는 컨테이너 상태를 보여 준다

| 명령 | 확인하는 대상 |
| --- | --- |
| `docker images` | 로컬에 있는 이미지 목록 |
| `docker ps` | 현재 실행 중인 컨테이너 목록 |
| `docker ps -a` | 중지 상태 등을 포함한 전체 컨테이너 목록 |
| `docker ps -aq` | 전체 컨테이너의 ID만 출력 |
| `docker inspect 이름` | 지정한 객체의 상세 설정과 상태 |
| `docker logs 이름` | 컨테이너 주 프로세스의 표준 출력·오류 로그 |

자료의 `docker images`는 “생성된 컨테이너 목록”이 아니라 이미지 목록이다. 컨테이너가 `docker ps`에서 사라져도 `docker ps -a`에 중지 상태로 남아 있을 수 있다.

다음은 앞의 Nginx 예제를 확인할 때 사용할 설명용 명령이다.

```bash
sudo docker images
sudo docker ps
sudo docker ps -a
sudo docker inspect webserver2
sudo docker logs webserver2
```

`Up`은 주 프로세스가 실행 중이라는 뜻이지 웹 응답이 정상이라는 보장은 아니다. 로그·포트 설정·HTTP 응답을 함께 확인해야 웹 서버의 상태를 판단할 수 있다.

#### 5.6 Ubuntu 컨테이너가 바로 종료되는 이유는 주 프로세스에 있다

가상머신과 달리 컨테이너는 운영체제를 부팅한 채 무조건 대기하는 환경이 아니다. 컨테이너의 **주 프로세스**가 끝나면 컨테이너 실행도 끝난다.

강의의 다음 예시는 기본 셸을 분리 실행하지만, 대화형 입력을 유지할 조건이 없어 셸이 종료될 수 있다.

```bash
sudo docker run -d --name app ubuntu:focal
```

자료에 나온 `Exited (0)`은 주 프로세스가 종료 코드 0으로 끝났다는 뜻이다. 컨테이너가 멈췄다는 이유만으로 프로그램 오류라고 단정할 수 없다.

직접 셸에 입력하려면 다음처럼 표준 입력과 터미널을 준비한다.

```bash
sudo docker run -it --name app3 ubuntu:focal /bin/bash
```

| 옵션·동작 | 의미 |
| --- | --- |
| `-i` | 표준 입력을 열린 상태로 유지 |
| `-t` | 가상 터미널 할당 |
| `/bin/bash` | 컨테이너의 주 프로세스로 실행할 셸 |
| 셸에서 `exit` | 주 셸을 끝내므로 이 컨테이너도 종료 |
| 기본 분리 키 `Ctrl+p`, 이어서 `Ctrl+q` | 주 셸을 종료하지 않고 터미널만 분리 |

분리 키는 Ctrl을 누른 채 `p`와 `q`를 한꺼번에 누르는 조합이 아니라 순서대로 보내는 두 키 입력이다. Docker의 기본 대화형 터미널 설정을 전제로 하며 분리 키는 설정에 따라 달라질 수 있다.

다음 강의 예제는 셸에 입력을 받을 터미널을 두면서 처음부터 분리 실행한다.

```bash
sudo docker run -dit --name app5 ubuntu:focal /bin/bash
```

`-dit`는 세 옵션을 묶은 표기다. 셸을 연습할 때와 실제 웹 서버·DB의 주 프로세스를 실행할 때의 목적은 다르므로, 모든 서비스에 `-it`가 필수라고 일반화하지 않는다. [컨테이너 실행과 터미널 옵션](https://docs.docker.com/engine/containers/run/)

#### 5.7 exec는 실행 중인 컨테이너에 새 프로세스를 추가한다

실행 중인 컨테이너 안에서 명령을 확인하고 싶을 때는 `docker exec`를 사용한다. 새 컨테이너를 만드는 명령이 아니다.

아래는 `app5`가 실행 중이라는 전제의 설명용 명령이다.

```bash
sudo docker exec -it app5 /bin/bash
```

이 명령으로 실행한 두 번째 셸에서 `exit`를 입력하면 그 셸만 끝난다. 컨테이너의 원래 주 프로세스가 계속 실행 중이라면 컨테이너는 유지된다. [Docker exec 설명](https://docs.docker.com/reference/cli/docker/container/exec/)

| 실행한 것 | exit가 끝내는 대상 | 컨테이너에 미치는 영향 |
| --- | --- | --- |
| `docker run -it ... /bin/bash` | 주 프로세스인 셸 | 주 프로세스가 끝나므로 컨테이너 중지 |
| `docker exec -it ... /bin/bash` | 추가로 실행한 셸 | 주 프로세스가 살아 있다면 실행 유지 |

이미지에 `/bin/bash`가 반드시 있는 것은 아니다. 사용하는 이미지에 들어 있는 실행 파일을 선택해야 하며, 중지된 컨테이너에는 `exec`로 명령을 실행할 수 없다.

#### 5.8 새로 만들기·다시 시작하기·중지하기·삭제하기를 구분한다

| 명령 | 대상과 동작 | 이미지에서 새 컨테이너를 만드는가? |
| --- | --- | --- |
| `docker run 이미지` | 새 컨테이너 생성 후 실행 | 그렇다. |
| `docker create 이미지` | 새 컨테이너만 생성 | 생성하지만 아직 실행하지 않음 |
| `docker start 이름` | 기존 컨테이너의 주 프로세스 시작 | 아니다. |
| `docker stop 이름` | 실행 중인 컨테이너 중지 | 아니다. |
| `docker rm 이름` | 컨테이너 객체 삭제 | 아니다. |
| `docker rmi 이미지` | 로컬 이미지 참조·이미지 제거 | 컨테이너 삭제와 다름 |

`create`와 `start`를 나누는 설명용 예제는 다음과 같다. 여기서도 같은 이름의 기존 컨테이너가 없다고 가정한다.

```bash
sudo docker create --name web-pending -p 8081:80 nginx
sudo docker ps -a
sudo docker start web-pending
```

`create` 직후에는 생성만 된 상태이고, `start`가 기존 컨테이너의 주 프로세스를 시작한다. `start`는 컨테이너를 만든 당시의 설정을 사용하므로 새 포트 연결을 추가하는 명령이 아니다. [Docker create 설명](https://docs.docker.com/reference/cli/docker/container/create/)

중지한 컨테이너를 살리려고 같은 이름으로 `run`을 반복하면 새 객체를 만들려 하므로 이름 충돌이 발생할 수 있다. 기존 객체를 다시 시작할 때는 [docker start](https://docs.docker.com/reference/cli/docker/container/start/)를 사용한다.

다음은 앞에서 만든 `web-pending`만 정리하는 설명용 명령이다.

```bash
sudo docker stop web-pending
sudo docker rm web-pending
```

> [!WARNING]
> 자료의 `docker rm -f $(docker ps -a -q)`는 모든 컨테이너를, `docker rmi -f $(docker images -q)`는 여러 로컬 이미지를 한꺼번에 삭제하는 범위다. `$()`는 안쪽 명령의 결과를 바깥 명령의 인자로 전달하는 셸 문법이므로, 연습용 객체 하나를 정리하는 명령과 구분한다.

Docker에도 재시작 정책이 있어 중지된 컨테이너의 자동 재시작을 설정할 수 있다. 따라서 “Docker는 종료되면 항상 새로 만들어야 하고 Kubernetes만 다시 실행할 수 있다”는 설명은 정확하지 않다. Kubernetes의 원하는 상태 유지와 Docker의 재시작 정책은 관리 범위가 다르다. [Docker 재시작 정책](https://docs.docker.com/engine/containers/start-containers-automatically/)

#### 5.9 추가 자료의 DB 예제로 프로세스와 데이터를 구분한다

개념 자료 하단에는 `2026년 10월 23일 추가사항`으로 표시된 레이어·MySQL 예시도 있다. 이는 오늘의 수행 결과로 합치지 않고, 앞에서 설명한 이미지·프로세스·저장 위치를 구분하는 보충 사례로 읽는다.

MySQL 컨테이너의 주 프로세스는 DB 서버다. 실행 중인 DB 컨테이너에서 `docker exec`로 MySQL 클라이언트나 셸을 추가 실행하더라도, 그 클라이언트를 종료하는 것과 DB 서버를 종료하는 것은 다른 일이다.

컨테이너 내부 파일을 바꿔도 원본 이미지가 바뀌는 것은 아니다. 하지만 마운트로 호스트 경로나 다른 저장 공간을 연결했다면 그 공유 데이터에는 영향을 줄 수 있으므로 “컨테이너 내부 변경은 호스트에 절대 영향을 주지 않는다”라고 단정하지 않는다.

또한 주 프로세스를 중지하는 것과 쓰기 계층을 삭제하는 것은 다르다. 컨테이너의 쓰기 계층에만 저장한 데이터는 컨테이너 삭제 시 사라지지만, 별도 볼륨 등은 독립적으로 유지될 수 있다. [Docker의 저장 계층과 데이터 보존](https://docs.docker.com/engine/storage/)

자료의 `/var/lib/docker/containers/`를 이미지 전체의 저장 경로로 일반화하지 않는다. 저장 위치는 Docker 설정과 저장 백엔드에 따라 달라지며, 우선 `docker image inspect`·`docker inspect`로 이미지와 컨테이너의 정보를 구분해서 확인한다.

#### 5.10 실행 확인은 컨테이너 상태에서 실제 HTTP 응답까지 이어진다

다음은 Nginx 예제를 점검하는 기준이다. 실제로 발생한 오류를 해결했다는 기록이 아니라, 어느 구간을 확인할지 연결한 설명이다.

| 확인 상황 | 먼저 볼 것 | 구분할 기준 |
| --- | --- | --- |
| Docker 명령에 응답하지 않음 | 서비스 상태와 `docker version` | CLI 존재와 데몬 연결은 별개 |
| `docker ps`에 없음 | `docker ps -a` | 생성되지 않았는지 중지됐는지 구분 |
| 생성 직후 종료 | 종료 코드·기본 명령·로그 | 정상 완료와 실행 실패를 구분 |
| Nginx는 Up인데 접속 안 됨 | 실제 수신 포트와 `-p` 연결 | 호스트 포트와 컨테이너 포트 확인 |
| VM 안에서만 접속됨 | VM IP·호스트에서의 경로·방화벽 | 실제 컴퓨터와 VM의 localhost는 다름 |
| 같은 이름으로 새 실행 실패 | 전체 컨테이너 목록 | 기존 객체 시작과 새 객체 생성을 구분 |

조회 결과를 읽을 때마다 “어느 환경에서 실행한 명령인지, 어느 객체를 보고 있는지”로 돌아오면 된다. 가상머신·이미지·컨테이너·프로세스를 구분하는 첫 장의 개념이 마지막 확인 단계에서도 그대로 사용된다.

> 컨테이너를 실행한다는 것은 이미지에서 개별 환경을 만들고 주 프로세스를 시작한다는 뜻이다. 실행 유지 여부는 프로세스로, 외부 접근 여부는 IP와 포트 연결로, 데이터 보존 여부는 저장 위치로 판단한다.

## 🧠 오늘 이해한 핵심

1. **호스트와 게스트는 무엇을 기준으로 보느냐에 따라 달라진다.** Ubuntu는 VMware 위의 게스트이면서 Docker 컨테이너를 실행하는 호스트다. 이 관계를 알아야 명령 실행 위치와 포트의 주인을 구분할 수 있다.
2. **환경 준비는 설치·통신·권한·파일 작업이 연결되는 과정이다.** Ubuntu가 켜지는 것, 인터넷에 연결되는 것, SSH 접속이 되는 것, Docker 데몬에 요청할 수 있는 것은 각각 다른 확인 단계다.
3. **이미지의 존재와 컨테이너의 실행 상태는 다른 사실이다.** 이미지는 준비된 실행 파일 묶음이고, 컨테이너는 개별 설정과 쓰기 계층을 가진 객체다. 생성·실행·중지·삭제를 구분해야 명령을 올바른 대상에 사용할 수 있다.
4. **컨테이너의 종료·접속·데이터 문제는 서로 다른 기준으로 읽는다.** 주 프로세스가 끝나면 실행이 멈추고, 웹 접속에는 올바른 IP와 포트 전달이 필요하며, 파일 보존은 컨테이너 쓰기 계층과 별도 저장 공간을 구분해야 판단할 수 있다.
