오늘은 컨테이너 이미지를 준비하고 Kubernetes에 배포하는 과정을 출발점으로, Git에 기록한 배포 설정을 Argo CD가 클러스터에 반영하는 GitOps 흐름을 연결한다. VM·클러스터 준비, 이미지 버전 관리, GitHub 저장소와 인증, Argo CD 설치, Application 생성, 변경 반영과 롤백까지 하나의 배포 과정으로 정리한다.

아래 코드는 강의 01~15번을 다시 따라 하기 위한 학습용 예제이며 실제 실행 결과를 기록한 것은 아니다. 반복되는 환경 구축 설명은 묶고, 강의에 섞인 온프레미스·AWS 예제는 실행 환경에 따라 구분한다. 예제의 `yourdockerid`와 `yourgithubid`는 자신의 계정으로 바꾸며, 공개·비공개 앱을 동시에 다룰 때 충돌하지 않도록 배포 네임스페이스를 분리했다.

> 이미지는 레지스트리에, 원하는 배포 상태는 Git에 저장한다. Argo CD는 Git과 클러스터의 차이를 확인하고, 동기화 정책에 따라 그 상태를 반영한다.

### 1. 배포 구조와 실습 환경 준비하기

수동 배포에서는 이미지를 빌드하고 서버에 접속해 실행 상태를 바꾼다. 서버와 애플리케이션이 늘어나면 현재 설정이 무엇인지, 누가 어떤 버전을 배포했는지 계속 맞추기 어렵다. 오늘의 자동화는 그 목표 상태를 Git에서 관리하는 데서 시작한다.

[기본 개념 01번](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/argocd01), [관리대장 02번](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/argocd02), [구성도 03번](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/argocd03)은 이 흐름에 필요한 구성요소와 서버 환경을 설명한다.

#### 1.1 이미지·설정·실행 상태는 서로 다른 곳에 있다

음식점으로 비유하면 이미지는 준비된 요리 키트, 배포 YAML은 “어떤 메뉴를 몇 개 준비할지” 적은 주문서, Kubernetes는 실제 주방이다. Argo CD는 Git의 주문서와 주방의 현재 상태를 비교하는 관리자에 해당한다.

| 구성요소 | 보관하거나 담당하는 것 | 오늘 예제 |
| --- | --- | --- |
| 애플리케이션 소스 | 프로그램·웹 페이지·Dockerfile | `index.html`, `dockerfile` |
| 이미지 레지스트리 | 실행할 컨테이너 이미지 | Docker Hub의 `nginxweb:v1.0`·`v2.0` |
| Git 저장소 | 원하는 배포 설정과 변경 이력 | Deployment·Service YAML |
| Kubernetes | 실제 Pod 실행과 자원 관리 | Deployment·ReplicaSet·Pod·Service |
| Argo CD | Git의 선언과 실제 상태 비교·동기화 | Application 단위 배포 관리 |

일반 GitHub 코드 저장소에 YAML을 올리는 것과 컨테이너 이미지를 올리는 것은 다른 작업이다. 강의의 `powermvp/nginxweb:v1.0` 같은 주소는 Docker Hub 이미지다. GitHub에도 GHCR이라는 별도 레지스트리가 있지만, 일반 Git 저장소와 같은 저장 방식으로 취급하지 않는다.

#### 1.2 Kubernetes와 Argo CD는 서로 다른 목표 상태를 관리한다

Kubernetes는 Deployment에 적힌 Pod 템플릿과 복제본 수를 유지한다. Argo CD는 그 Deployment 자체가 Git에 적힌 선언과 맞는지를 확인한다. 따라서 “Pod 하나를 지웠을 때 다시 생김”과 “직접 바꾼 replicas가 Git 값으로 돌아감”은 담당하는 계층이 다르다.

| 구성요소 | 맡은 일 |
| --- | --- |
| kube-apiserver·etcd | API 요청을 처리하고 클러스터 관리 상태 저장 |
| kube-scheduler | 실행 노드가 정해지지 않은 Pod의 노드 선택 |
| Kubernetes 컨트롤러 | Deployment·ReplicaSet 등 선언과 실제 상태 조정 |
| kubelet·containerd | 할당된 노드에서 컨테이너 실행 상태 관리 |
| CNI·CoreDNS·Service 전달 구성 | Pod 네트워크·이름 조회·서비스 접속 지원 |
| Argo CD 컨트롤러 | Git의 선언과 클러스터 객체의 상태 비교·동기화 |

컴포넌트들은 API를 통해 관련 상태를 관찰하고 결과를 반영한다. API 서버가 모든 구성요소를 동기 함수처럼 차례로 직접 호출한다고 이해하지 않는다. Docker로 빌드한 이미지를 containerd가 실행할 수 있으며, Kubernetes가 반드시 Docker Engine에 직접 실행을 요청하는 것도 아니다.

#### 1.3 VM의 이름·IP·네트워크 대역부터 맞춘다

[Ubuntu 설치 04번](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/argocd04)과 [VM 설정 05번](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/argocd05)은 상당 부분 같은 준비 작업이다. 오늘은 관리대장의 Ubuntu Server 24.04 LTS·containerd·단일 컨트롤 플레인 구성을 기준으로 읽고, 05번의 22.04 화면을 별도의 필수 설치 단계로 더하지 않는다.

| 역할 | 호스트 이름 | 노드 IP 예시 | CPU·메모리 예시 |
| --- | --- | --- | --- |
| 컨트롤 플레인 | `k8s-master` | `10.0.2.10` | 2코어·4GB |
| 워커 1 | `k8s-worker1` | `10.0.2.11` | 2코어·2GB |
| 워커 2 | `k8s-worker2` | `10.0.2.12` | 2코어·2GB |
| 워커 3 | `k8s-worker3` | `10.0.2.13` | 2코어·2GB |

VMware 실습망은 `10.0.2.0/24`, 게이트웨이는 `10.0.2.2`, DHCP 범위는 `10.0.2.128–254`다. 표의 고정 IP는 DHCP 범위 밖에서 사용한다. VMnet8은 수업의 NAT 네트워크이며, VMnet1은 보통 호스트 전용이므로 “어떤 통신도 불가능한 네트워크”라는 뜻은 아니다.

재현 순서는 Ubuntu ISO 설치 → 기본 도구·SSH 준비 → VM 종료 → full clone → 복제 VM마다 IP·호스트 이름 변경 → 서로 통신 확인이다. Kubernetes에 이미 참가한 노드를 그대로 복제해 이름만 바꾸는 것과 구분한다.

```bash
sudo apt-get update
sudo apt-get install -y openssh-server curl vim tree git
sudo systemctl enable --now ssh
ip -br addr
ip route
hostnamectl
```

각 VM에서 자신의 호스트 이름을 설정한다. 다음은 워커 1의 예이며, 다른 VM에서는 이름을 바꿔야 한다.

```bash
sudo hostnamectl set-hostname k8s-worker1
sudoedit /etc/hosts
ping -c 3 10.0.2.2
ping -c 3 k8s-master
```

`/etc/hosts`에는 노드 IP와 해당 호스트 이름을 대응시킨다. SSH는 `ssh ubuntu@10.0.2.11`처럼 접속할 수 있으며, Xshell·Xftp는 그 접속과 파일 전송을 도와주는 도구다. 서버 자체의 역할이나 Kubernetes 구성요소는 아니다.

#### 1.4 노드·Pod·Service의 주소 대역을 섞지 않는다

| 주소 범위 | 대상 | 확인할 점 |
| --- | --- | --- |
| 노드 네트워크 | VM의 IP | 관리자·노드 간 통신 경로 |
| Pod 네트워크 | Pod의 IP | 선택한 CNI와 일치하는 설정 |
| Service 네트워크 | ClusterIP | kubeadm·API 서버 설정과 일치 |

관리대장의 Pod CIDR `10.0.0.0/16`에는 노드 대역 `10.0.2.0/24`가 포함된다. 이 두 값을 그대로 조합해 새로 설치하면 주소 범위가 겹치므로, 실제 노드망·VPN망·Service 대역과 겹치지 않는 Pod 대역을 선택하고 CNI 설정까지 맞춰야 한다. **CNI는 네트워크 인터페이스 규약이며 모든 플러그인이 VXLAN 방식인 것도 아니다.**

이미 정상 동작하는 클러스터는 관리대장에 맞추겠다는 이유로 주소 대역을 임의 변경하지 않는다. 03번의 여러 컨트롤 플레인·HAProxy·MetalLB·DB 이중화·AWS ECR 구성은 확장 사례이며, 이 모든 구성을 오늘의 기본 클러스터에서 구축했다는 뜻은 아니다. [kubeadm의 Pod 네트워크 조건](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/)

#### 1.5 클러스터 설치는 모든 노드·마스터·워커 작업을 구분한다

이미 구성한 클러스터가 있다면 설치를 반복하지 않고 마지막 상태 조회부터 진행한다. 새로 재현할 때의 공통 준비는 고유한 노드 이름·IP, swap 정책, 런타임 CRI, kubelet과 런타임의 cgroup 방식, 네트워크 전달 설정이다.

| 실행 위치 | 준비·작업 | 확인 기준 |
| --- | --- | --- |
| 모든 노드 | 수업 구성에서는 swap 비활성화·재부팅 후 유지 | `swapon --show`, `/etc/fstab` |
| 모든 노드 | 브리지 처리·IPv4 전달 설정 | `br_netfilter`, `net.ipv4.ip_forward=1` |
| 모든 노드 | containerd의 CRI와 systemd cgroup 확인 | 런타임·kubelet 방식 일치 |
| 모든 노드 | 같은 계열의 kubeadm·kubelet·kubectl 설치 | 버전과 패키지 저장소 확인 |
| 마스터 | init·관리자 kubeconfig·CNI 배포 | API·네트워크·DNS 정상 |
| 각 워커 | 자신의 마스터가 출력한 join 실행 | 준비한 노드가 목록에 나타남 |

강의의 패키지 저장소는 `v1.32` 계열이다. 새 환경에서는 지원·호환 버전을 확인하고, 그 계열의 `pkgs.k8s.io` 저장소와 서명 키를 준비한 뒤 설치한다. `apt-get install`은 설치 명령이고 패키지 목록 갱신은 `apt-get update`다.

containerd의 `SystemdCgroup = true`는 해당 버전의 설정 경로에 반영한다. Docker의 `/etc/docker/daemon.json`만 수정한다고 containerd 설정도 바뀌지는 않는다. 원문의 containerd 설정 파일 삭제나 방화벽 전체 중지를 모든 환경의 필수 절차로 취급하지 않는다.

마스터 초기화와 관리자 설정의 기본 형태는 다음과 같다. CNI가 Pod 대역 지정을 요구하면 초기화 전에 그 대역과 옵션을 정한다.

```bash
sudo kubeadm init --apiserver-advertise-address=10.0.2.10 \
  --cri-socket=unix:///var/run/containerd/containerd.sock
```

이후 kubeconfig는 kubectl을 사용할 일반 사용자 셸에서 준비한다. root의 홈과 `ubuntu` 사용자의 홈을 섞지 않는다.

```bash
mkdir -p "$HOME/.kube"
sudo cp /etc/kubernetes/admin.conf "$HOME/.kube/config"
sudo chown "$(id -u):$(id -g)" "$HOME/.kube/config"
```

선택한 CNI의 호환 매니페스트를 배포한 뒤 워커에서 자신의 `kubeadm join` 명령을 실행한다. 원문의 Weave Net `v2.8.1`은 오래된 구성 예이므로 새 환경에서는 해당 프로젝트의 유지 상태와 이미지 가용성까지 확인한다. 수업 자료의 토큰·인증서 해시를 자신의 클러스터에 복사하지 않는다.

```bash
kubectl config current-context
kubectl get nodes -o wide
kubectl get pods -n kube-system -o wide
```

준비한 노드의 `Ready`, CNI·CoreDNS와 컨트롤 플레인 상태를 확인하면 앱 배포 준비 단계다. `Ready`는 애플리케이션 접속 성공까지 뜻하지 않으므로 다음 장에서 실제 앱을 검증한다.

> 배포 자동화의 기반은 정상 동작하는 클러스터와 명확한 저장 위치다. 노드 네트워크, 이미지 저장소, Git의 선언, 실제 실행 상태를 나누면 각 단계의 책임이 보인다.

### 2. 이미지와 Kubernetes 배포 선언 만들기

Argo CD가 배포하려면 먼저 실행 가능한 이미지와 그 이미지를 가리키는 YAML이 있어야 한다. [Docker 실습 06번](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/argocd06), [Kubernetes 실습 07번](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/argocd07), [이미지 준비 11번](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/argocd11)을 하나의 앱 준비 과정으로 묶는다.

#### 2.1 Docker는 이미지를 만드는 도구이고 런타임 준비와는 별개다

강의는 제공한 `install-docker.sh`를 모든 VM에 전달해 실행한다. 다음은 해당 파일을 실제로 제공받고 내용을 확인한 환경에서의 절차다. 이 TIL이 설치 스크립트 자체를 제공하는 것은 아니다.

```bash
cd /home/ubuntu
less install-docker.sh
chmod +x install-docker.sh
sudo ./install-docker.sh
sudo systemctl status docker --no-pager
sudo docker version
```

오늘 예제의 Docker 명령은 권한 혼동을 줄이기 위해 `sudo docker`로 통일한다. 로그인도 같은 방식으로 수행한다. containerd를 사용하는 Kubernetes의 컨테이너는 `docker ps`만으로 모두 조회할 수 있는 것이 아니므로, 클러스터 앱은 kubectl로 확인한다.

#### 2.2 웹 페이지를 이미지에 넣고 v1.0을 만든다

강의의 `nginxweb` 폴더에는 `dockerfile`과 `index.html`을 둔다. 먼저 `mkdir -p /home/ubuntu/nginxweb`로 폴더를 준비하고 그 안에 두 파일을 저장한다. 다음은 강의 파일을 바탕으로 정리한 설명용 Dockerfile이다. 소문자 파일명을 확실히 지정하기 위해 빌드 명령에 `-f dockerfile`을 붙인다.

```dockerfile title="dockerfile"
FROM nginx:1.14-alpine
COPY ./index.html /usr/share/nginx/html/index.html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

`COPY`는 호스트의 페이지를 이미지의 Nginx 문서 경로로 넣는다. `EXPOSE`는 포트 정보를 표시하며 호스트 포트를 실제로 여는 명령은 아니다. 강의의 `nginx:1.14-alpine`은 재현용 구버전 태그이므로 새 운영 서비스의 기본 선택으로 받아들이지 않는다. 원문의 `MAINTAINER`는 현재 사용이 권장되지 않는 지시문이다. [Dockerfile 공식 참조](https://docs.docker.com/reference/dockerfile/)

페이지는 강의처럼 제목에 `ArgoCD-V1.0`, 배경에 빨간색을 사용하면 버전 구분에 도움이 된다. HTML 문구는 확인을 위한 표식이며, 이 단계에서 Argo CD가 이미 배포를 수행했다는 뜻은 아니다.

```bash
cd /home/ubuntu/nginxweb
sudo docker build -f dockerfile -t nginxweb:v1.0 .
sudo docker run -d --name mynginx -p 8088:80 nginxweb:v1.0
curl http://127.0.0.1:8088
sudo docker stop mynginx
sudo docker rm mynginx
```

위는 강의의 호스트 80 대신 8088을 사용한 확인용 예제다. `8088:80`은 호스트 8088을 컨테이너 80에 연결한다. `localhost`는 명령을 실행한 머신 자신이므로, VM에서 실행했다면 다른 PC의 localhost와 구분한다.

#### 2.3 v1.0과 v2.0을 서로 다른 태그로 업로드한다

Docker Hub 계정과 사용할 이미지 저장소를 준비하고, 자신의 계정명을 변수에 넣는다. 비밀번호나 액세스 토큰은 로그인 프롬프트에 입력한다.

```bash
DOCKERHUB_USER=yourdockerid
sudo docker login -u "$DOCKERHUB_USER"
sudo docker tag nginxweb:v1.0 "$DOCKERHUB_USER/nginxweb:v1.0"
sudo docker push "$DOCKERHUB_USER/nginxweb:v1.0"
```

이어서 `index.html`의 버전 표기를 `ArgoCD-V2.0`, 배경을 파란색으로 바꾸고 빌드한다. v1 화면을 보관하려면 v1을 먼저 빌드·업로드한 후 파일을 수정해야 한다.

```bash
vi index.html
sudo docker build -f dockerfile -t nginxweb:v2.0 .
sudo docker tag nginxweb:v2.0 "$DOCKERHUB_USER/nginxweb:v2.0"
sudo docker push "$DOCKERHUB_USER/nginxweb:v2.0"
```

v2 페이지로 바꾼 뒤 v1과 v2를 연달아 빌드하면 두 태그가 같은 페이지를 담을 수 있다. 빌드 캐시는 이전 단계의 조건이 같을 때 재사용되며, “두 번째 빌드라서 무조건 빠르다”는 보장은 아니다.

새 이미지 push만으로 Git의 Deployment나 실행 중인 Pod가 바뀌지는 않는다. 오늘은 배포 YAML의 `image`를 다른 태그로 바꾸어 변경을 명확히 한다. 같은 태그의 이미지만 덮어쓰면 Git diff가 없고 노드의 캐시·imagePullPolicy까지 개입하므로 버전 확인이 어려워진다.

#### 2.4 공개 앱은 Deployment로 복제본을 관리한다

매니페스트는 `mkdir -p /home/ubuntu/k8s`로 준비한 디렉터리에 저장하고, 이후 적용 명령도 그 안에서 실행한다. 다음은 07번의 이름·레이블·자원 설정을 사용한 `nginx-deploy.yaml` 예제다. 이미지 계정만 자신의 것으로 바꾼다. 처음에는 복제본 3개와 v1.0을 사용하고, 뒤에서 Git을 통해 5개·v2.0으로 변경한다.

```yaml title="nginx-deploy.yaml" {6,17}
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-app-deploy
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx-app
  template:
    metadata:
      labels:
        app: nginx-app
    spec:
      containers:
      - name: nginx-app
        image: yourdockerid/nginxweb:v1.0
        ports:
        - containerPort: 80
        resources:
          limits:
            cpu: 200m
            memory: 256Mi
          requests:
            cpu: 100m
            memory: 128Mi
```

강조한 `replicas`는 원하는 Pod 수, `image`는 실행할 버전이다. Deployment는 ReplicaSet을 통해 Pod 수를 관리한다. `spec.selector.matchLabels`와 `spec.template.metadata.labels`도 일치해야 한다.

`100m`은 CPU 0.1코어 요청량이며 request는 배치 판단에 쓰는 설정이다. limit은 실행 자원 한도로, CPU는 throttling이 발생할 수 있고 메모리는 한도 초과 시 OOM 종료가 발생할 수 있다. request·limit은 `kubectl top`의 실제 사용량과 다르다.

복제본 3개는 노드 3대에 하나씩 배치한다는 뜻이 아니다. 또한 복제본 수를 늘리는 것은 수평 확장이지, 한 Pod의 CPU·메모리를 키우는 수직 확장과 같은 작업이 아니다.

#### 2.5 Service의 selector를 Deployment와 맞춘다

오늘의 로컬 VM 예제에서는 `nginx-nodePort.yaml`을 사용한다. 11번의 일부 Service 예시는 selector가 `app: nginx`이고 Deployment는 `app: nginx-app`이어서 그대로 조합하면 연결 대상이 생기지 않는다. 다음은 일치하도록 정리한 설명용 Service다.

```yaml title="nginx-nodePort.yaml" {7,12}
apiVersion: v1
kind: Service
metadata:
  name: nginx-app-nodeport
spec:
  selector:
    app: nginx-app
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80
    nodePort: 30080
  type: NodePort
```

강조한 selector는 연결할 Pod를 고르고, `nodePort: 30080`은 접근 가능한 노드 IP와 함께 사용할 포트다. Service의 `port: 80`과 Pod의 `targetPort: 80`은 노드 포트와 역할이 다르다.

| 접속 방식 | 용도 | 실습에서 구분할 점 |
| --- | --- | --- |
| ClusterIP | 클러스터 내부의 안정적인 접속 지점 | 내부 IP를 외부 공개 주소로 생각하지 않음 |
| NodePort | 노드 IP와 지정 포트로 접속 | VM 경로·방화벽·NAT에 따라 외부 접근 결정 |
| LoadBalancer | 외부 LB 주소로 접속 | 클라우드 연동·MetalLB 등 별도 구현 필요 |
| port-forward | 관리자 머신에서 임시로 연결 | kubectl을 실행한 머신의 로컬 터널 |

AWS NLB·ACM 인증서 annotation과 Route 53 도메인은 AWS 구성 예에 해당한다. 로컬 VM에 그 annotation과 타인의 인증서 ARN을 복사한다고 외부 로드밸런서나 HTTPS가 준비되지는 않는다.

#### 2.6 GitOps로 넘기기 전에 매니페스트와 앱을 확인한다

관리자 셸에서 학습용 네임스페이스를 만든다. 이미 있다면 생성 대신 조회한다. 파일에 `metadata.namespace`를 넣지 않은 이유는 배포 대상 네임스페이스를 Application에서 선택하기 위해서다.

```bash
kubectl create namespace gitops-public
kubectl apply --dry-run=server -n gitops-public -f nginx-deploy.yaml
kubectl apply --dry-run=server -n gitops-public -f nginx-nodePort.yaml
kubectl apply -n gitops-public -f nginx-deploy.yaml
kubectl apply -n gitops-public -f nginx-nodePort.yaml
kubectl get deploy,rs,pods,svc -n gitops-public
kubectl rollout status deployment/nginx-app-deploy -n gitops-public
```

실제 노드 IP를 확인하고 그 주소에 도달할 수 있는 머신에서 `curl http://10.0.2.11:30080`으로 응답을 확인한다. 실패하면 Pod 준비 상태·Service selector·targetPort·노드까지의 통신 경로 순서로 나눈다.

뒤의 첫 Argo CD 배포를 빈 상태에서 확인하려면, **방금 만든 두 예제 객체만** 다음처럼 정리한다. 이 명령은 로컬 YAML 파일을 삭제하지 않는다. 다른 작업 자원을 일괄 삭제할 필요도 없다.

```bash
kubectl delete -n gitops-public -f nginx-deploy.yaml
kubectl delete -n gitops-public -f nginx-nodePort.yaml
```

07번의 `/tmp/mem`에 `dd`를 무한 반복하는 예는 순수한 메모리 부하 명령이 아니다. 파일과 쓰기 I/O를 계속 증가시켜 디스크·임시 저장 공간에도 영향을 준다. 메모리 사용량을 이해하기 위한 필수 단계로 그대로 실행하지 않는다.

> 빌드·push·YAML 수정·실제 배포는 별도 단계다. GitOps를 연결하기 전에 이미지 주소, selector, 포트, 실행 자원 설정이 서로 맞는지 확인한다.

### 3. Argo CD 설치하고 접속하기

이미지와 YAML을 준비했으면 Git의 선언을 읽어 클러스터에 반영할 관리 도구가 필요하다. [Argo CD 소개 08번](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/argocd08)과 [설치 09번](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/argocd09)을 기준으로 설치와 접속을 나눈다.

#### 3.1 GitOps는 Git을 원하는 상태의 기준으로 삼는다

**GitOps**는 원하는 시스템 상태를 선언으로 표현하고 버전 관리하며, 에이전트가 그 선언을 가져와 실제 상태와 지속적으로 맞추는 운영 방식이다. GitHub는 Git 저장소를 제공하는 서비스 중 하나다. GitOps가 반드시 GitHub에만 종속되거나, GitHub Actions를 설치해야만 성립하는 것은 아니다. [OpenGitOps의 원칙](https://opengitops.dev/)

**Argo CD**는 Kubernetes를 위한 GitOps CD 도구다. 애플리케이션 이미지를 기본 기능으로 빌드하는 CI 도구는 아니며, Git의 매니페스트를 읽어 배포하는 역할을 한다.

| Argo CD 구성요소 | 담당 역할 |
| --- | --- |
| `argocd-server` | 웹 UI·CLI가 사용하는 API, 로그인과 권한 처리 |
| `argocd-repo-server` | 저장소를 읽고 지정한 revision·path에서 매니페스트 준비 |
| `argocd-application-controller` | 원하는 상태와 실제 상태 비교·동기화 수행 |
| Redis 등 보조 구성 | 캐시 등 설치 구성에 필요한 기능 |

Argo CD API 서버와 Kubernetes API 서버는 다른 프로그램이다. UI에 접속하는 경로와 Argo CD가 Kubernetes에 배포하는 경로도 구분한다. [Argo CD 구성요소](https://argo-cd.readthedocs.io/en/stable/operator-manual/architecture/)

#### 3.2 설치 버전과 클러스터 호환성을 먼저 맞춘다

강의의 `stable`과 `releases/latest`는 실행할 때 다른 버전을 가리킬 수 있다. 현재 공식 테스트 표에서는 Argo CD 3.4 계열에 Kubernetes 1.32가 포함되고, 3.5 계열의 표는 1.33부터다. 표에 없다는 사실만으로 실행 불가능이라고 단정할 수는 없지만, 수업의 1.32 환경에 최신 버전을 무조건 적용하는 근거로 삼지도 않는다. [공식 설치·테스트 조합](https://argo-cd.readthedocs.io/en/stable/operator-manual/installation/)

다음은 버전을 고정하는 방법을 보여 주는 **신규 실습 설치 예제**다. 확인 가능한 `v3.4.0` 태그를 사용했으며, 실제 재구축에서는 사용할 릴리스의 보안 패치와 지원 범위까지 확인해 버전 값을 정한다. 이미 Argo CD가 있으면 먼저 설치 상태를 조회하고 중복 설치하지 않는다.

```bash
ARGOCD_VERSION=v3.4.0
kubectl create namespace argocd
kubectl apply -n argocd --server-side --force-conflicts \
  -f "https://raw.githubusercontent.com/argoproj/argo-cd/${ARGOCD_VERSION}/manifests/install.yaml"
kubectl get deploy,statefulsets,pods,svc -n argocd
kubectl rollout status deployment/argocd-server -n argocd --timeout=300s
```

현재 공식 설치 안내는 큰 CRD의 client-side annotation 크기 제한을 피하도록 server-side apply를 사용한다. `--force-conflicts`는 충돌한 필드의 관리권도 가져올 수 있으므로, 기존 설치의 사용자 수정 사항을 확인하지 않고 재적용하는 옵션으로 취급하지 않는다. [공식 설치 명령과 의미](https://argo-cd.readthedocs.io/en/stable/getting_started/)

#### 3.3 CLI는 관리자 머신에 설치하고 서버 버전과 맞춘다

다음은 Ubuntu VM이 `x86_64`인 경우다. ARM64면 다운로드 파일을 `argocd-linux-arm64`로 바꾼다. CLI는 모든 워커에 반드시 설치해야 하는 에이전트가 아니다.

```bash
uname -m
curl -fL -o argocd \
  "https://github.com/argoproj/argo-cd/releases/download/${ARGOCD_VERSION}/argocd-linux-amd64"
chmod +x argocd
sudo mv argocd /usr/local/bin/argocd
argocd version --client
```

`ARGOCD_VERSION`은 앞에서 정한 값이며 새 셸에서는 다시 설정해야 한다. 서버를 고정 버전으로 설치하고 CLI만 `latest`로 받는 것보다 같은 버전을 기준으로 맞추는 편이 재현하기 쉽다.

#### 3.4 NodePort·LoadBalancer·port-forward 중 접속 방식을 고른다

강의는 Argo CD 서버의 HTTP·HTTPS Service 포트에 각각 NodePort `30070`·`30071`을 지정한다. 다음 패치는 강의의 포트 구성을 읽기 좋게 정리한 예제다.

```bash
kubectl patch service argocd-server -n argocd --type=strategic -p \
  '{"spec":{"type":"NodePort","ports":[{"name":"http","port":80,"targetPort":8080,"nodePort":30070},{"name":"https","port":443,"targetPort":8080,"nodePort":30071}]}}'
kubectl get svc argocd-server -n argocd
kubectl get pods -n argocd -o wide
```

TLS를 유지한 기본 구성에서는 **`https://10.0.2.11:30071`**처럼 HTTPS 포트를 기준으로 접속한다. 실제 노드 주소와 Service 출력으로 확인하며, 원문의 `http:10.0.2.11:30070`은 올바른 URL 표기가 아니다. HTTP 포트가 있다고 서버의 TLS가 자동으로 꺼지는 것도 아니다.

| 방식 | 접속 예시 | 조건 |
| --- | --- | --- |
| NodePort | 노드 IP와 `30071` | 노드 접근 경로·포트 허용 |
| port-forward | `https://localhost:8080` | 터널을 실행한 머신에서 접속 |
| LoadBalancer | 할당된 외부 주소 | 실제 LB 제공 환경 필요 |

port-forward를 선택한다면 별도 터미널에서 다음을 유지한다. NodePort 변경 없이도 사용할 수 있는 대안이다.

```bash
kubectl port-forward -n argocd svc/argocd-server 8080:443
```

LoadBalancer 방식은 `kubectl patch svc argocd-server -n argocd -p '{"spec":{"type":"LoadBalancer"}}'`로 타입을 바꾼다. 로컬 환경에 LB 구현이 없다면 외부 주소가 `Pending`에 머물 수 있으며, 타입 변경만으로 인터넷 공개 구성이 완성되는 것은 아니다.

09번의 `nodeSelector` 패치는 Argo CD API 서버 Pod를 워커 1에 고정하는 선택 사항이다. NodePort 접속을 위해 필수인 것은 아니고, 해당 노드가 사용 불가능하거나 레이블이 다르면 Pod가 배치되지 않을 수 있다.

#### 3.5 초기 비밀번호·CLI 로그인·서버 TLS 설정을 구분한다

초기 관리자 이름은 `admin`이고, 초기 비밀번호는 자신의 설치에서 생성된 Secret으로 확인한다. 아래는 조회 방법이며, 강의 화면에 보인 비밀번호를 자신의 비밀번호로 사용하지 않는다.

```bash
kubectl get secret argocd-initial-admin-secret -n argocd \
  -o jsonpath='{.data.password}' | base64 -d
printf '\n'
```

다음은 기본 자체 서명 인증서를 사용하는 격리된 실습 환경의 로그인 예제다. 비밀번호는 프롬프트에 입력하며, 운영 환경에서는 신뢰할 수 있는 인증서와 클라이언트 신뢰 설정을 준비한다.

```bash
argocd login 10.0.2.11:30071 --username admin --insecure
argocd account update-password
```

port-forward를 사용했다면 로그인 주소를 `localhost:8080`으로 바꾼다. 서버 Pod 안에 들어가야만 비밀번호를 변경할 수 있는 것은 아니다. 초기 비밀번호 Secret은 비밀번호 변경 후 새 비밀번호를 알려 주는 저장소가 아니며, 초기 값이 더 필요 없다면 공식 안내에 따라 해당 초기 Secret을 정리한다.

> [!WARNING]
> CLI의 `--insecure`는 접속 대상의 인증서 검증을 생략하는 옵션이다. `argocd-server --insecure`는 서버의 TLS를 비활성화하는 별도 설정이다. 저장소 연결의 “Skip server verification”도 또 다른 구간의 검증 옵션이므로 서로 같은 조치로 취급하지 않는다.

> Argo CD 설치, 관리자 접속, Git 저장소 인증, 실제 앱 배포는 각각 별도 단계다. UI가 열린다고 저장소 연결과 배포까지 끝난 것은 아니다.

### 4. GitHub 저장소와 인증 연결하기

Argo CD가 사용할 Git 저장소에는 배포 YAML을 두고, 읽을 권한을 준비한다. 강의의 [13번 GitHub 저장소 준비](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/034de383-d1a1-82b3-8e41-81a211448b80)와 [14번 Argo CD 연동](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/235de383-d1a1-834d-8ff1-01833bf0e53f)을 기준으로 한다.

#### 4.1 누가 어디에 접근하는 인증인지 먼저 구분한다

| 접근 주체와 대상 | 필요한 권한·인증 | 다른 인증과의 차이 |
| --- | --- | --- |
| 개발자 → GitHub push | 해당 저장소 쓰기 권한·PAT 또는 SSH 등 | Git 작성자 이름 설정과 다름 |
| Argo CD → Git 저장소 | 배포 설정을 읽을 권한 | Argo CD의 admin 비밀번호와 다름 |
| 빌드 도구 → 이미지 레지스트리 | 이미지 push 권한 | Git 저장소 읽기 권한과 다름 |
| Kubernetes 런타임 → 레지스트리 | 이미지 pull 권한 | Argo CD 저장소 인증이 대신하지 않음 |

비공개 Git 저장소에 공개 이미지 주소를 적을 수도 있고, 공개 Git 저장소에 비공개 이미지 주소를 적을 수도 있다. **저장소의 공개 여부와 이미지 공개 여부는 독립적**이다. ECR 이미지라면 해당 노드의 IAM 연동 또는 같은 네임스페이스의 `imagePullSecrets` 등 적절한 pull 인증이 별도로 필요하다.

#### 4.2 공개·비공개 예제의 저장소와 배포 범위를 나눈다

GitHub에서 `kubernetes-public`은 Public, `kubernetes-private`은 Private으로 만들고 README를 추가해 기본 브랜치를 준비한다. 예제는 브랜치 `main`을 기준으로 하며 실제 기본 브랜치가 다르면 Application의 revision과 push 대상도 맞춘다.

```text
kubernetes-public/
├─ README.md
├─ nginx-deploy.yaml
└─ nginx-nodePort.yaml

kubernetes-private/
├─ README.md
└─ nginx-pod.yaml
```

공개 저장소는 Deployment·Service, 비공개 저장소는 단독 Pod를 배포한다. 두 Application이 동일한 네임스페이스의 같은 객체를 함께 관리하지 않도록 공개 앱은 `gitops-public`, 비공개 앱은 `gitops-private`에 배포한다.

다음은 비공개 저장소의 `nginx-pod.yaml` 설명용 예제다. 강의 Pod 예제를 두 앱의 이름·레이블이 겹치지 않도록 조정했다.

```yaml title="nginx-pod.yaml"
apiVersion: v1
kind: Pod
metadata:
  name: nginx-private-pod
  labels:
    app: nginx-private
spec:
  containers:
  - name: nginx-app
    image: yourdockerid/nginxweb:v1.0
    ports:
    - containerPort: 80
    resources:
      requests:
        cpu: 100m
        memory: 128Mi
      limits:
        cpu: 200m
        memory: 256Mi
```

이 Pod는 private Git 연결을 확인하는 예제다. Deployment가 아니므로 Pod 객체를 삭제했을 때 같은 복제 관리가 자동 적용되는 것은 아니다. 이미지 필드의 태그 변경 등 일부 갱신과, 모든 Pod 필드의 변경이 허용되는 것도 구분한다.

#### 4.3 파일을 GitHub에 올리는 과정과 로그인은 다르다

다음은 공개 저장소에 앞 장의 두 파일을 올리는 절차다. 명령은 자신의 실습 저장소에서 실행하며, 작성자 정보는 해당 저장소에 설정하는 예시다.

```bash
GITHUB_USER=yourgithubid
git clone "https://github.com/$GITHUB_USER/kubernetes-public.git"
cd kubernetes-public
git config user.name "자신의 이름"
git config user.email "자신의 이메일"
cp /home/ubuntu/k8s/nginx-deploy.yaml .
cp /home/ubuntu/k8s/nginx-nodePort.yaml .
git add nginx-deploy.yaml nginx-nodePort.yaml
git commit -m "Add nginx deployment manifests"
git push origin main
```

2장에서 YAML을 다른 위치에 저장했다면 `cp`의 원본 경로도 바꾼다. `git config user.name`·`user.email`은 커밋 작성자 정보이며 GitHub 인증을 대신하지 않는다. HTTPS push에서 인증을 요청하면 GitHub 사용자 이름과 해당 권한을 가진 PAT를 사용한다.

비공개 저장소도 자신의 계정으로 clone한 뒤 `nginx-pod.yaml`을 복사해 add·commit·push한다. **clone해 파일을 수정했더라도 commit과 push가 없으면 Argo CD가 보는 원격 브랜치는 바뀌지 않는다.** GitHub 웹에서 파일을 생성·편집하고 커밋하는 방법도 같은 원격 상태를 만드는 대안이다.

#### 4.4 HTTPS와 PAT는 공개 저장소 전용 방식이 아니다

익명 읽기가 가능한 공개 저장소는 Argo CD에 PAT 없이 연결할 수 있다. 다음은 공개 저장소 읽기 연결 예제다. Argo CD CLI에는 앞 장의 관리자 로그인이 먼저 되어 있어야 한다.

```bash
argocd repo add "https://github.com/$GITHUB_USER/kubernetes-public.git"
argocd repo list
```

PAT 인증을 학습하거나 비공개 저장소를 HTTPS로 연결하려면 UI의 Settings → Repositories → Connect Repo에서 다음 값을 사용한다.

| 입력 항목 | 값 |
| --- | --- |
| 연결 방식·종류 | HTTPS·git |
| Repository URL | 연결할 저장소의 HTTPS URL |
| Username | GitHub 사용자 이름 |
| Password | 저장소 읽기 권한을 가진 PAT |
| Project | 예제에서는 `default`와 일관되게 설정 |

Username은 Argo CD의 `admin`이 아니다. PAT는 일반 GitHub 로그인 비밀번호와 다르며, 무조건 `ghp_`로 시작하는 종류만 존재하는 것도 아니다. 가능하면 사용할 저장소와 읽기 권한으로 제한하고 만료 기간을 정한다. 원문의 classic PAT `repo` 전체·무기한 설정을 필수 조건으로 받아들이지 않는다. [PAT 종류와 권한](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)

정상적인 GitHub HTTPS 연결에서 서버 검증 생략을 기본값으로 고를 이유는 없다. 인증 실패라면 저장소 URL·계정·권한·만료·조직 정책을 먼저 확인한다.

#### 4.5 SSH는 공개키와 비공개키의 위치가 핵심이다

다음은 Argo CD 전용 키를 생성하는 강의 방식이다. 같은 이름의 파일이 이미 있다면 덮어쓰지 말고 기존 키의 용도를 확인하거나 새 파일명을 정한다.

```bash
mkdir -p ~/.ssh
ssh-keygen -t ed25519 -f ~/.ssh/argocd-ssh-key -N "" -C "argocd-readonly"
chmod 600 ~/.ssh/argocd-ssh-key
cat ~/.ssh/argocd-ssh-key.pub
```

| 파일 | 둘 곳 | 역할 |
| --- | --- | --- |
| `argocd-ssh-key.pub` | GitHub 저장소 Settings → Deploy keys | 상대에게 등록하는 공개키 |
| `argocd-ssh-key` | Argo CD의 비공개 저장소 인증 | 클라이언트가 보관하는 비공개키 |

GitHub Deploy key에는 출력한 공개키를 등록하고 **Allow write access는 끈다**. Argo CD는 매니페스트 읽기만 필요하다. 이 키는 passphrase 없이 자동 연결하는 예이므로 비공개키 파일의 접근과 보관을 제한하고 Git에는 넣지 않는다. [Deploy key의 범위와 권한](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys)

```bash
argocd repo add "git@github.com:$GITHUB_USER/kubernetes-private.git" \
  --ssh-private-key-path ~/.ssh/argocd-ssh-key
argocd repo list
argocd cert list --cert-type ssh
```

강의의 `argocd-deploy-key`와 `argocd-ssh-key`라는 이름은 문단마다 섞여 있다. 실제 생성한 파일명을 등록·연결 단계에서 끝까지 사용한다. SSH 서버의 host key와 자신의 인증 키도 다르며, host key 문제가 있다면 공식 지문과 Argo CD의 known hosts를 확인한다. [Argo CD 저장소 인증과 host 검증](https://argo-cd.readthedocs.io/en/stable/user-guide/private-repositories/)

#### 4.6 AppProject와 GitHub 저장소 이름은 다른 설정이다

**AppProject**는 Argo CD에서 허용할 저장소·대상 클러스터·네임스페이스 등의 경계를 묶는 객체다. GitHub 리포지토리를 Public으로 만들었다고 이름이 `public`인 AppProject가 자동 생성되는 것은 아니다.

오늘 예제는 `default` 프로젝트로 통일한다. 저장소를 특정 프로젝트에 묶어 등록했다면 Application의 project도 일치해야 하며, 별도 프로젝트를 쓰려면 그 프로젝트가 먼저 존재하고 source·destination을 허용해야 한다. [프로젝트와 저장소 범위](https://argo-cd.readthedocs.io/en/stable/user-guide/projects/)

> Argo CD의 Git 인증은 배포 설정을 읽는 권한이다. 개발자의 push 권한과 노드의 이미지 pull 권한을 따로 준비하고, 연결 URL·키 파일·프로젝트를 일관되게 맞춘다.

### 5. Application으로 Git과 클러스터 연결하기

저장소 연결 성공은 “읽을 수 있다”는 의미다. 실제 배포에는 어느 저장소의 어느 경로를 어떤 클러스터에 반영할지 지정하는 **Application**이 필요하다. [파이프라인 설정 10번](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/argocd10)과 [자동 배포 실습 15번](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/argocd15)을 연결한다.

#### 5.1 source와 destination을 하나의 배포 단위로 묶는다

| 설정 | 예제 | 의미 |
| --- | --- | --- |
| Application 이름 | `nginx-public` | Argo CD에서 관리할 앱 이름 |
| Project | `default` | 허용 범위를 묶은 AppProject |
| Repository URL | `kubernetes-public.git`의 전체 URL | 선언을 읽을 저장소 |
| Revision | `main` | 추적할 브랜치·태그·커밋 |
| Path | `.` | 매니페스트가 있는 저장소 내부 디렉터리 |
| Destination server | `https://kubernetes.default.svc` | Argo CD가 설치된 클러스터의 API 주소 |
| Destination namespace | `gitops-public` | 실제 앱 자원을 만들 네임스페이스 |

`argocd`는 Argo CD와 Application 객체가 있는 네임스페이스이고, `gitops-public`은 배포할 앱의 네임스페이스다. Application 이름과 Deployment 이름도 달라도 된다. 같은 클러스터를 대상으로 할 때는 강의의 내부 API 주소를 사용하며, 외부 클러스터를 관리하려면 별도의 등록과 권한이 필요하다.

#### 5.2 Path는 Git 저장소 안에서 YAML이 실제로 있는 위치다

오늘 예제는 저장소 루트에 두 YAML을 두므로 `path: .`이다. 10번처럼 `k8s/` 디렉터리에 넣었다면 Path를 `k8s`로 바꾼다. 관리자 VM의 `/home/ubuntu/k8s`를 Application path로 쓰는 것이 아니다.

일반 디렉터리 방식은 기본적으로 그 경로의 매니페스트를 읽는다. 하위 폴더까지 읽으려면 별도 재귀 설정을 고려해야 하므로, YAML을 하위 폴더에 넣어 두고 루트 `.`만 지정해도 모두 자동 검색된다고 생각하지 않는다. 파일명도 `nginx-loadbalance.yaml`·`nginx-loadbalancer.yaml`처럼 혼용하지 않고 실제 저장한 이름을 기준으로 관리한다.

#### 5.3 공개·비공개 Application을 우선 수동 모드로 만든다

이미 만든 `gitops-public`은 조회하고, 비공개 앱용 네임스페이스도 준비한다. 원문의 `default` 대신 예제별 범위를 분리하는 보완이다.

```bash
kubectl get namespace gitops-public
kubectl create namespace gitops-private
```

다음은 공개 앱의 CLI 생성 예제다. UI의 Applications → New App에 같은 값을 입력하는 것과 같은 목적이며, 자동 동기화 옵션을 지정하지 않아 처음에는 수동 모드다.

```bash
argocd app create nginx-public \
  --repo "https://github.com/$GITHUB_USER/kubernetes-public.git" \
  --revision main --path . \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace gitops-public \
  --project default
```

비공개 앱은 등록한 SSH URL을 그대로 사용한다. HTTPS 주소와 SSH 주소를 임의로 섞으면 기대한 저장소 인증 설정과 연결되지 않을 수 있다.

```bash
argocd app create nginx-private \
  --repo "git@github.com:$GITHUB_USER/kubernetes-private.git" \
  --revision main --path . \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace gitops-private \
  --project default
```

Argo CD는 Application이라는 사용자 정의 Kubernetes 리소스로 이 설정을 저장한다. 다음은 공개 앱의 선언형 표현이며, 위 CLI 생성과 비교하는 설명용 예제다. 이미 CLI로 생성했다면 같은 앱을 별도 방식으로 중복 생성할 필요는 없다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nginx-public
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/yourgithubid/kubernetes-public.git
    targetRevision: main
    path: .
  destination:
    server: https://kubernetes.default.svc
    namespace: gitops-public
```

이 YAML에는 `syncPolicy.automated`가 없으므로 생성만으로 자동 동기화가 켜지는 것은 아니다. [Application 생성과 옵션](https://argo-cd.readthedocs.io/en/stable/user-guide/commands/argocd_app_create/)

#### 5.4 첫 생성과 첫 배포 사이에는 Sync가 있다

강의 15번은 처음 정책을 Manual로 선택한다. 이 경우 Argo CD는 저장소를 읽고 차이를 보여 줄 수 있지만, 새 Application을 만들었다는 이유만으로 배포가 끝난다고 해석하지 않는다.

```bash
argocd app get nginx-public --refresh
argocd app diff nginx-public
argocd app sync nginx-public
argocd app wait nginx-public --sync --health --timeout 180
kubectl get deploy,rs,pods,svc -n gitops-public
```

`diff`는 차이를 보여 주며 차이가 있을 때 0이 아닌 종료 코드를 반환할 수 있다. 그 사실만으로 명령 실행 자체가 실패했다고 판단하지 않는다. UI에서는 앱 선택 → Diff·대상 revision 확인 → Sync → Synchronize 순서다.

비공개 앱도 `argocd app sync nginx-private`를 실행하고 `kubectl get pods -n gitops-private`로 확인한다. Git의 비공개 설정은 컨테이너가 인터넷에 공개되는지와는 별개의 문제다.

#### 5.5 Sync 상태와 Health 상태를 따로 읽는다

| 표시 | 답하는 질문 | 의미 |
| --- | --- | --- |
| `Synced` | 원하는 선언과 현재 설정이 맞는가? | 비교 대상에서 차이가 없음 |
| `OutOfSync` | 원하는 선언과 현재 설정이 다른가? | 동기화할 차이가 있음 |
| `Healthy` | 관리 자원이 정상 상태인가? | 자원별 health 기준 충족 |
| `Progressing` | 상태가 아직 준비되는 중인가? | 배포·준비 진행 중 |
| `Degraded` | 자원이 비정상 상태인가? | 정상 기준 미충족 |
| `Missing` | 필요한 자원이 존재하는가? | 기대한 자원이 없음 |

`Synced`면서 Pod가 제대로 시작되지 않아 `Degraded`일 수 있다. 반대로 현재 앱은 정상 실행 중이지만 Git에 새 버전이 올라와 `OutOfSync`일 수도 있다. Sync 작업 성공, 자원 health, 브라우저의 실제 응답까지 세 단계로 확인한다. [Argo CD 자원 health 기준](https://argo-cd.readthedocs.io/en/stable/operator-manual/health/)

#### 5.6 Automatic·self-heal·prune는 서로 다른 옵션이다

처음 수동 배포의 흐름을 확인한 다음, 공개 앱을 자동 관리하도록 바꿀 수 있다. 다음은 10번의 자동 설정과 연결되는 예제다.

```bash
argocd app set nginx-public --sync-policy automated --auto-prune --self-heal
argocd app get nginx-public
```

| 옵션 | 주된 역할 | 혼동하지 않을 점 |
| --- | --- | --- |
| Automated sync | 감지한 목표 상태의 변경을 자동 반영 | 이미지 빌드를 자동 수행하는 기능 아님 |
| `selfHeal: true` | 클러스터에서 직접 변경한 관리 설정의 차이 복구 | Git과 다른 설정을 계속 유지하는 옵션 아님 |
| `prune: true` | Git의 선언에서 빠진 관리 자원도 동기화 때 삭제 | 클러스터의 모든 미등록 자원을 지우지 않음 |
| `CreateNamespace=true` | 대상 namespace가 없으면 생성하도록 요청 | 잘못된 destination 이름까지 바로잡지 않음 |
| `allowEmpty` | 목표 자원이 비어 있는 상태의 자동 반영 허용 | 기본 보호를 이해하고 선택할 옵션 |

다음은 Application의 `spec` 아래에 넣는 **동기화 설정 부분 발췌**다. 완성된 Application 전체를 대신하는 파일이 아니다.

```yaml
syncPolicy:
  automated:
    prune: true
    selfHeal: true
  syncOptions:
  - CreateNamespace=true
```

`allowEmpty`의 기본 보호가 있더라도 일부 파일을 잘못 삭제하는 등 모든 실수를 막아 주는 것은 아니다. prune을 켜면 배포 설정 삭제가 실제 자원 삭제로 연결될 수 있으므로 diff의 삭제 대상도 확인한다. [자동 동기화와 복구·정리의 조건](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/)

> Application은 저장소 접근을 실제 배포 대상으로 연결한다. 먼저 어느 revision·path·namespace를 관리하는지 확인하고, 생성·변경 감지·동기화·정상 실행을 각각 확인한다.

### 6. 변경 반영과 롤백 및 운영 상태 확인하기

이제 이미지를 직접 교체하는 대신 Git의 Deployment를 바꾸어 배포를 진행한다. [동작 확인 12번](https://lgcnd-argocd-kubernetes-cicd-edu.oopy.io/argocd12)과 15번의 실습은 변경 감지, Sync, Kubernetes의 rollout, 사용자 응답을 차례로 연결하는 과정이다.

#### 6.1 Git에서 replicas와 image를 바꾼다

공개 저장소의 `nginx-deploy.yaml`에서 `replicas: 3`을 `5`로, `image`의 `v1.0`을 `v2.0`으로 바꾼다. 다음은 변경할 위치를 보여 주는 **Deployment 부분 발췌**이며 기존 selector·labels·ports·resources는 유지한다.

```yaml
spec:
  replicas: 5
  template:
    spec:
      containers:
      - name: nginx-app
        image: yourdockerid/nginxweb:v2.0
```

실제 공개 저장소의 작업 디렉터리에서 확인하고 push한다. UI에서 직접 파일을 편집해 커밋했다면 같은 변경을 로컬에서 또 만들 필요는 없다.

```bash
git diff -- nginx-deploy.yaml
git add nginx-deploy.yaml
git commit -m "Deploy nginx v2.0 with five replicas"
git push origin main
```

이미지는 앞 장에서 v2.0으로 먼저 push해 둔 상태여야 한다. 존재하지 않는 이미지 태그를 Git에 반영하면 Argo CD가 YAML을 동기화하더라도 새 Pod의 이미지 다운로드는 실패할 수 있다.

#### 6.2 Refresh·Sync·rollout·실제 응답을 차례로 확인한다

```text
원격 main 브랜치의 Deployment 변경
    ↓ Argo CD가 대상 revision을 다시 확인
Git의 원하는 상태와 현재 상태의 차이 감지
    ↓ Manual이면 Sync 요청, Automatic이면 정책에 따라 동기화
Kubernetes의 Deployment 설정 갱신
    ↓ 템플릿 변경을 Deployment 컨트롤러가 반영
새 ReplicaSet과 Pod를 통한 버전 교체
    ↓ 준비 상태와 접속 경로 확인
Service를 통한 새 버전 응답 검증
```

Manual이어도 변경 감지는 계속할 수 있다. “Manual이므로 변경을 전혀 감지하지 않는다”와 “변경을 감지해도 자동 적용하지 않는다”는 다른 설명이다. **Refresh는 비교 정보를 갱신하고 Sync는 실제 자원을 반영한다.**

```bash
argocd app get nginx-public --refresh
argocd app diff nginx-public
argocd app sync nginx-public
argocd app wait nginx-public --sync --health --timeout 180
kubectl rollout status deployment/nginx-app-deploy -n gitops-public
kubectl get deploy,rs,pods -n gitops-public
```

위 `sync`는 수동 모드에서 적용하거나 직접 동기화를 요청할 때 쓰는 명령이다. Automatic이 이미 반영했다면 상태 확인만 하면 된다. 변경을 실시간으로 보고 싶으면 별도 터미널에서 다음을 유지한다.

```bash
kubectl get pods -n gitops-public -l app=nginx-app -o wide --watch
```

다른 터미널에서는 실제 적용된 이미지와 사용자 응답을 확인한다. 확인 후 watch는 `Ctrl+C`로 종료한다.

```bash
kubectl get deployment nginx-app-deploy -n gitops-public \
  -o jsonpath='{.spec.template.spec.containers[*].image}{"\n"}'
curl http://10.0.2.11:30080
```

replicas 변경은 개수 조정이고, 이미지 변경은 Pod 템플릿 변경에 따른 rollout이다. 둘을 함께 수정한 실습이라도 같은 동작으로 합쳐 이해하지 않는다. RollingUpdate가 사용되더라도 여유 자원·준비 상태·전략에 따라 가용성은 달라지며, 언제나 무중단이 보장되는 것은 아니다.

#### 6.3 Pod 보충과 self-heal을 다른 계층에서 관찰한다

| 실습 상황 | 주로 동작하는 관리 계층 | 관찰할 내용 |
| --- | --- | --- |
| Deployment의 Pod 한 개 삭제 | Kubernetes ReplicaSet | 원하는 Pod 수를 맞추도록 대체 Pod 생성 |
| Git과 다르게 replicas를 직접 수정 | Argo CD의 자동 self-heal | 관리 설정을 Git의 선언으로 다시 맞춤 |
| Git의 YAML에서 자원 제거 | Argo CD의 prune 정책 | 관리 중인 해당 자원의 삭제 반영 |

다음은 자동 동기화와 self-heal이 켜진 공개 앱에서만 진행하는 설명용 변경이다. Git에 5개가 선언되어 있다면 직접 2개로 바꾼 상태가 계속 유지되지 않고 다시 조정되는지 관찰한다.

```bash
kubectl scale deployment nginx-app-deploy -n gitops-public --replicas=2
kubectl get deployment nginx-app-deploy -n gitops-public --watch
```

이 실습의 결론은 “자동화가 임의의 올바른 수를 판단한다”가 아니다. **원격 Git에 남아 있는 선언이 계속 적용할 목표**라는 것이다. 유지할 변경이라면 Git을 바꾼다. 장애를 수습하는 임시 직접 변경은 자동 동기화와 충돌할 수 있으므로 정책과 Git 상태를 함께 고려한다.

#### 6.4 롤백은 Git의 기준 상태까지 되돌려야 지속된다

가장 명확한 GitOps 롤백은 배포 설정을 이전의 정상 이미지·설정으로 되돌리는 새 커밋을 만들고 Sync하는 방식이다. 해당 배포 변경만 포함한 커밋이라면 GitHub의 Revert나 `git revert`를 사용할 수 있다. 여러 변경이 섞였다면 되돌릴 파일·필드를 먼저 확인한다.

| 방식 | 바꾸는 곳 | GitOps에서의 의미 |
| --- | --- | --- |
| Git에서 v1.0으로 되돌려 커밋 | 원하는 상태의 기준 | 다음 동기화에서도 이전 버전 유지 가능 |
| Argo CD History and Rollback | 앱의 과거 배포 상태 | 자동 동기화 상태와 Git의 현재 선언을 함께 고려 |
| `kubectl rollout undo` | 클러스터의 Deployment 템플릿 | Git은 그대로여서 다음 동기화 때 다시 바뀔 수 있음 |

Argo CD의 자동 동기화가 켜진 Application에는 직접 rollback을 수행할 수 없으므로, History and Rollback을 학습할 때는 자동 동기화를 먼저 해제하고 대상 이력을 선택한다. 이후 Git을 새 버전에 둔 채 자동 동기화를 다시 켜면 Git의 상태가 재적용될 수 있다.

`argocd app history nginx-public`로 이력을 확인할 수 있다. 롤백은 데이터베이스의 데이터나 외부 시스템까지 자동 복구하는 기능이 아니며, 애플리케이션 기능 오류가 발생했다고 Argo CD가 항상 자동으로 이전 버전을 선택하는 것도 아니다.

#### 6.5 변경 감지는 정확히 180초마다 실행되는 작업이 아니다

공식 기본 설명은 `timeout.reconciliation: 120s`와 최대 `60s`의 jitter다. jitter는 여러 앱이 동시에 확인 작업을 시작하는 것을 분산하기 위한 추가 지연이다. 따라서 “모든 변경이 정확히 3분 뒤 배포된다”는 의미가 아니다. [변경 확인 주기와 Manual·Automatic 차이](https://argo-cd.readthedocs.io/en/stable/faq/)

배포 지연에는 Git 재확인뿐 아니라 매니페스트 준비, Sync, 이미지 다운로드, 스케줄링, readiness 대기도 포함된다. 빨리 비교하고 싶을 때의 수동 Refresh와 자동 적용 여부도 나눈다. 웹훅은 변경 확인을 촉진하는 방법이며, 자동 Sync가 꺼진 앱을 그 이유만으로 자동 배포하게 만드는 것은 아니다.

다음은 `argocd-cm`의 관련 **설정 부분 발췌**다. 현재 설정을 조회한 뒤 필요할 때만 변경한다. 강의의 `1M` 대신 분을 뜻하는 `1m`처럼 유효한 duration 형식을 사용한다.

```yaml
data:
  timeout.reconciliation: 30s
  timeout.reconciliation.jitter: 10s
```

```bash
kubectl get configmap argocd-cm -n argocd -o yaml
kubectl edit configmap argocd-cm -n argocd
kubectl rollout restart deployment/argocd-repo-server -n argocd
kubectl rollout restart statefulset/argocd-application-controller -n argocd
```

기본 설치의 application-controller는 StatefulSet이다. 다른 형태로 설치했다면 실제 자원 종류에 맞춘다. 현재 공식 설정 안내는 관련 값 변경 후 repo-server와 application-controller의 재시작을 요구하므로, 자동으로 모두 반영되거나 repo-server만 재시작하면 된다고 단정하지 않는다. [설정과 적용 대상](https://argo-cd.readthedocs.io/en/stable/operator-manual/argocd-cm-yaml/)

폴링을 짧게 하면 저장소 확인과 매니페스트 처리 부담이 커질 수 있다. 30초를 모든 환경의 권장 최소값으로 고정하지 않고 앱 수·저장소 규모·허용 지연에 맞춰 선택한다. 원문의 비슷한 이름의 설정 키를 검증 없이 모두 추가하지 않는다.

#### 6.6 CI와 CD를 연결하면 무엇이 자동화되는지 설명할 수 있다

오늘의 실습은 사람이 이미지를 빌드·push하고 Git의 배포 YAML을 바꾸는 흐름을 포함한다. Argo CD의 Automatic을 켰다고 테스트·이미지 빌드·push까지 자동화된 것은 아니다. 08·10번의 GitHub Actions·ECR·EKS 흐름은 다음처럼 역할을 나누어 읽는다.

| 단계 | 담당 | 전달하는 결과 |
| --- | --- | --- |
| 코드 변경·테스트 | 개발자와 CI 워크플로 | 검증할 소스 revision |
| 이미지 빌드·push | GitHub Actions 등의 CI | 레지스트리의 버전별 이미지 |
| 배포 선언 갱신 | CI 또는 승인된 변경 과정 | 새 이미지 태그·digest가 적힌 Git 커밋 |
| 선언 비교·동기화 | Argo CD | Kubernetes API에 원하는 자원 반영 |
| 이미지 pull·실행 | 노드 런타임과 Kubernetes | 실제 Pod 실행 |
| 정상 여부 확인 | Argo CD·kubectl·애플리케이션 확인 | Sync·Health·실제 응답 |

CI는 Continuous Integration으로 코드 통합·빌드·테스트를 자동화한다. CD는 승인된 배포 준비까지 자동화하는 Continuous Delivery 또는 운영 반영까지 자동화하는 Continuous Deployment라는 의미로 쓰인다. 어떤 승인 단계가 있는지까지 봐야 정확히 구분할 수 있다.

GitHub Actions가 ECR을 사용할 때의 AWS 인증, Git에 배포 선언을 push할 권한, Argo CD의 저장소 읽기 인증, 클러스터의 ECR pull 권한은 각각 준비한다. 자료에 나온 AWS 액세스 키·PAT를 같은 비밀번호처럼 재사용하지 않는다. 이 문서가 실제 Actions 워크플로 실행이나 EKS 구축 완료를 기록한 것은 아니다.

#### 6.7 멈춘 단계를 먼저 찾아 필요한 정보를 조회한다

다음은 실제 발생한 장애 기록이 아니라 재현 과정에서 사용할 확인 기준이다.

| 증상 | 먼저 확인할 것 | 구분 기준 |
| --- | --- | --- |
| Repository 연결 실패 | URL·계정·PAT 만료·Deploy key·host 검증 | Argo CD 로그인 실패와 Git 읽기 실패를 구분 |
| 매니페스트를 찾지 못함 | revision·path·원격 파일 위치 | 로컬 파일 존재와 원격 저장 여부를 구분 |
| Application 생성 후 자원이 없음 | Manual 정책·첫 Sync·프로젝트·destination | 앱 등록과 자원 배포를 구분 |
| 계속 `OutOfSync` | Git의 최신 commit·diff·자동 정책·오류 | 변경 감지·적용·설정 충돌을 구분 |
| `Synced`지만 앱 비정상 | Health·Pod Events·컨테이너 로그 | 설정 일치와 정상 실행을 구분 |
| `ImagePullBackOff` | 레지스트리 주소·태그·pull 인증·통신 | Git 인증이 아닌 이미지 준비 문제 확인 |
| Service에 대상이 없음 | selector·Pod 레이블·namespace·readiness | 포트보다 대상 선택부터 확인 |
| NodePort 접속 불가 | 노드 IP·Service 포트·NAT·방화벽 | 앱 실패와 외부 경로 실패를 구분 |
| LoadBalancer 주소가 `Pending` | 실제 LB 제공 환경 | 타입 지정과 LB 제공을 구분 |
| 수동 변경이 되돌아감 | Git 선언·self-heal·관리 Application | 유지할 설정을 Git에서 변경 |

argocd repo list

kubectl get applications -n argocd

특정 Pod를 조사할 때는 목록에서 실제 이름을 확인한 후 `kubectl describe pod 실제Pod이름 -n gitops-public`과 `kubectl logs 실제Pod이름 -n gitops-public -c nginx-app`을 사용한다. describe는 이벤트와 상태, logs는 컨테이너 출력이다. CPU·메모리 사용량을 보는 `kubectl top pods -n gitops-public`에는 정상 동작하는 Metrics Server가 별도로 필요하다.

실습 자원을 정리할 때도 Git과 자동 정책부터 확인한다. Git에 선언이 남고 자동 복구가 켜진 상태에서 앱 자원만 삭제하면 다시 만들어질 수 있다. Application 삭제 시 자원을 함께 지울지 남길지도 확인하며, 이를 클러스터 초기화나 VM 삭제와 같은 작업으로 취급하지 않는다.

> 배포 성공은 Git의 변경, Argo CD의 동기화, Kubernetes의 정상 실행, 사용자의 실제 응답이 연결되어야 판단할 수 있다. 롤백과 임시 수정도 Git에 남은 목표 상태를 함께 봐야 지속된다.

## 🧠 오늘 이해한 핵심

1. **GitOps에서는 실행 결과물과 원하는 배포 상태를 별도로 관리한다.** 이미지는 레지스트리에 저장하고, Git의 YAML은 어떤 이미지와 설정을 사용할지 선언하며, Argo CD와 Kubernetes가 각자의 계층에서 상태를 맞춘다.
2. **저장소 연결과 Application 생성은 실제 배포와 다른 단계다.** source·revision·path·destination을 맞춘 뒤 Sync와 Health, 실제 응답을 나누어 확인해야 한다.
3. **자동 동기화·self-heal·prune는 각각 다른 변경을 다룬다.** Git 변경 반영, 클러스터의 직접 수정 복구, 선언에서 빠진 관리 자원 정리를 구분하면 자동화가 무엇을 바꾸는지 예측할 수 있다.
4. **운영의 기준을 Git에 두면 변경과 롤백의 책임이 명확해진다.** 유지할 설정을 Git에 반영하고 CI·CD·이미지 인증·접속 경로를 분리해서 확인해야 수동 변경과 자동화의 충돌을 줄일 수 있다.
