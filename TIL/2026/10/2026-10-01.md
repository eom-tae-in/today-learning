# 📚 학습 내용

## 1. 아키텍처를 이해하고 모놀리식과 MSA를 비교하기

기능이 동작하는 것만으로 서비스가 안정적으로 운영되지는 않는다. 사용자가 늘어날 때 어떻게 확장할지, 일부 기능을 수정할 때 어디까지 다시 배포할지, 장애가 발생하면 어떤 영역까지 영향을 받을지 결정해야 한다. 이 판단의 바탕이 아키텍처다.

### 1.1 소프트웨어 아키텍처의 역할

**소프트웨어 아키텍처**는 시스템의 구성요소와 요소 사이의 관계를 정의하는 전체 설계다. 건물의 방과 복도, 출입구를 계획하듯이 기능과 데이터, 실행 환경의 연결을 정한다.

|설계 대상|확인할 질문|쇼핑몰 예시|
|---|---|---|
|구성요소|어떤 기능과 저장소가 필요한가?|회원, 상품, 주문, 데이터베이스|
|포함 관계|어떤 기능이 어떤 프로그램에 속하는가?|주문 기능이 하나의 백엔드에 포함되는가?|
|호출 관계|누가 누구에게 요청하는가?|주문 기능이 상품 정보를 어떻게 가져오는가?|
|배포 관계|무엇을 어느 환경에 배포하는가?|주문 서비스만 따로 배포할 수 있는가?|
|운영 구조|부하와 장애에 어떻게 대응하는가?|상품 조회가 증가하면 무엇을 늘리는가?|

아키텍처는 개발자만 보는 설계가 아니다. 업무 담당자, 개발자, 운영자가 시스템의 책임과 영향을 함께 이해하는 도구다.

자료의 **4+1 View**는 하나의 시스템을 여러 관점으로 설명한다.

|관점|초점|
|---|---|
|Logical View|기능과 객체의 논리적 구조|
|Implementation View|코드와 모듈의 구성|
|Process View|실행 중 작업, 동시성, 통신|
|Deployment View|실행 환경과 프로그램의 배치|
|Use Case View|사용자 시나리오를 통한 구조 확인|

**UML**은 이러한 구조와 관계를 표현하는 표준 모델링 언어다. 아키텍처 스타일이 구성의 큰 방향이라면, 패턴은 반복되는 설계 문제에 사용할 수 있는 해결 방법이다. 자료의 Peer-to-Peer는 참여자 간 직접 협력을, Event-Bus는 이벤트 전달 통로를 통한 협력을 보여준다.

같은 주문 시스템을 보더라도 업무 담당자는 “주문 취소가 가능한가?”를, 개발자는 “취소 로직이 어느 모듈에 있는가?”를, 운영자는 “어느 서버가 실패했는가?”를 궁금해한다. 관점을 나누는 이유는 이처럼 **서로 다른 관심사를 빠뜨리지 않고 같은 시스템을 설명하기 위해서**다.

Peer-to-Peer에서는 참여자들이 직접 연결되어 협력한다. Event-Bus에서는 이벤트를 발행한 쪽과 이를 받아 처리하는 쪽이 전달 통로를 통해 연결된다. 예를 들어 “주문 완료”를 발행하고 알림 기능이 받아 처리하는 방식은 이후 비동기 통신 설명과 연결된다.

### 1.2 모놀리식과 MSA의 차이

**모놀리식**은 여러 업무 기능을 하나의 애플리케이션 배포 단위로 묶는 구조다. **MSA**는 업무 능력 중심으로 나눈 서비스들을 독립적인 실행·배포 단위로 구성하고 API나 메시지로 협력하게 하는 구조다.

|비교 기준|모놀리식|MSA|
|---|---|---|
|배포 단위|여러 업무를 하나로 배포|서비스별 독립 배포를 지향|
|기능 변경|일반적으로 전체 애플리케이션 재배포|변경한 서비스 중심으로 배포 가능|
|통신|내부 메서드 호출 중심|서비스 간 네트워크 통신 필요|
|확장|애플리케이션 전체를 확장|부하가 큰 서비스만 선택적으로 확장|
|데이터 처리|한 DB 트랜잭션으로 묶기 쉬운 경우가 많음|여러 서비스에 걸친 정합성 설계 필요|
|기술 선택|전체 애플리케이션의 제약을 받기 쉬움|서비스별 선택 가능, 운영 비용 증가|
|문제 추적|한 실행 흐름 안에서 비교적 추적하기 쉬움|로그와 분산 추적으로 여러 경로를 연결해야 함|
|초기 운영 부담|비교적 단순|배포·통신·관찰 기반이 늘어남|

예를 들어 상품 조회 요청만 크게 증가한다면, MSA에서는 상품 서비스 인스턴스만 늘리는 선택이 가능하다. 반면 모놀리식에서는 상품 기능을 포함한 전체 애플리케이션을 함께 확장하는 경우가 많다.

MSA는 선택적 확장과 독립 배포에 유리하지만, 개별 요청이 항상 빨라지는 것은 아니다. 내부 호출이 네트워크 호출로 바뀌면서 지연과 통신 실패가 추가될 수 있다.

#### 주문 기능만 수정한다면?

모놀리식에서 상품·회원·주문은 논리적으로 구분되어 있어도 하나의 배포 단위에 들어갈 수 있다. 주문 취소 규칙 하나를 바꾸더라도 수정된 버전의 전체 애플리케이션을 빌드하고 배포하는 것이 일반적이다.

MSA에서는 주문 취소를 담당하는 주문 서비스만 새 버전으로 배포할 수 있다. 다만 주문 서비스의 API 계약을 바꾸면 이를 사용하는 다른 서비스도 수정해야 할 수 있다. 독립 배포를 유지하려면 **기존 계약과의 호환성**이 중요하다.

#### 상품 조회만 급증한다면?

|상황|모놀리식에서의 대응 예|MSA에서의 대응 예|
|---|---|---|
|상품 조회만 증가|전체 백엔드 인스턴스를 추가|상품 서비스 인스턴스를 추가|
|주문 취소 규칙 변경|전체 애플리케이션의 새 버전을 배포|주문 서비스의 새 버전을 배포|
|추천 기능 장애|같은 프로세스의 자원에 영향이 생길 수 있음|별도 서비스로 제한할 수 있지만 호출 의존은 점검해야 함|

모놀리식도 여러 인스턴스로 수평 확장할 수 있다. 차이는 “확장이 가능한가?”보다 **필요한 업무만 따로 확장할 수 있는가?**에 있다.

#### 어떤 부담을 어디에서 치르는가?

모놀리식은 초기 배포와 디버깅이 단순한 대신, 내부 결합이 커지면 변경의 영향 범위가 넓어진다. MSA는 업무 경계를 분리하는 대신, 통신·배포·관찰·데이터 처리의 복잡성을 감당해야 한다.

따라서 규모가 작고 독립 배포 요구가 약하면 모놀리식이나 모듈러 모놀리스가 합리적인 선택이 될 수 있다. 변경 주기와 확장 요구가 뚜렷하게 다르고 운영 기반을 갖출 수 있다면 MSA의 편익을 검토할 수 있다. 구조 선택은 우열보다 **요구사항과 비용의 판단**이다.

### 1.3 프론트·백엔드 분리, 모듈러 모놀리스와 구분하기

|구조|나누는 기준|배포 관점|
|---|---|---|
|프론트·백엔드 분리|화면과 서버의 책임|백엔드 내부는 하나의 배포 단위일 수 있음|
|모듈러 모놀리스|하나의 앱 안에서 업무 모듈 경계를 구분|배포는 하나로 유지|
|MSA|독립성이 필요한 업무 책임|업무 서비스별 독립 배포를 지향|

프론트엔드와 백엔드 저장소가 따로 있다는 사실만으로 MSA라고 판단할 수 없다. DB의 개수나 서버 대수만으로도 판정하기 어렵다. **업무 경계, 배포 단위, 의존 관계, 데이터 소유권**을 함께 봐야 한다.

예를 들어 React 화면과 Spring Boot 서버를 따로 배포하더라도, Spring Boot 서버 한 개 안에 회원·상품·주문이 모두 들어 있다면 백엔드는 여전히 모놀리식일 수 있다. 저장소를 분리하는 결정과 업무 서비스를 분리하는 결정은 서로 다른 설계다.

### 1.4 SOA와 MSA의 강조점

**SOA(Service Oriented Architecture)**와 MSA는 모두 서비스로 업무를 구성한다. 자료는 두 접근의 지향점을 다음처럼 비교한다.

|비교 기준|SOA의 대표적인 강조점|MSA의 대표적인 강조점|
|---|---|---|
|목표|공통 서비스 공유와 재사용|서비스 독립성과 변화 대응|
|업무 구성|기업 시스템 통합과 서비스 조합|응집된 작은 업무 책임|
|책임|업무·기술·운영 조직이 나뉘는 구성을 만날 수 있음|담당 팀이 서비스 개발·운영 책임을 가짐|
|연결 방식|ESB를 통한 중앙 연계가 대표 예시|경량 API와 메시지 기반 협력이 대표 예시|

**ESB(Enterprise Service Bus)**는 여러 시스템 사이의 메시지 전달, 변환, 연계를 돕는 기반이다. 여러 부서의 전달 규칙을 중앙에서 맞춰주는 창구에 비유할 수 있다.

SOA가 반드시 SOAP이나 ESB만 쓰는 것은 아니며, MSA도 REST만 쓰는 것은 아니다. 통신 기술 이름보다 **공유·재사용과 독립성 중 무엇을 강조하는지**가 비교의 핵심이다.

자료의 “서비스 공유 최소화”도 서비스 호출을 금지한다는 의미가 아니다. 여러 서비스가 하나의 공통 구현이나 내부 데이터 구조에 지나치게 의존하면 변경 시 함께 움직여야 한다. MSA는 이런 결합을 줄이면서 필요한 협력을 계약으로 유지하려는 접근이다.

> MSA를 선택하는 이유는 서비스를 많이 만들기 위해서가 아니라, 필요한 업무를 독립적으로 변경·배포·확장하기 위해서다.

## 2. 서비스 경계를 정하고 데이터와 통신까지 설계하기

독립 배포가 필요하다는 판단 다음에는 “어디까지를 하나의 서비스로 묶을 것인가?”를 결정해야 한다. 이 경계가 잘못되면 서비스를 분리하고도 함께 수정하고 함께 배포해야 할 수 있다.

### 2.1 좋은 마이크로서비스의 조건

|조건|의미|판단 기준|
|---|---|---|
|작은 서비스|명확한 업무 책임을 가진 배포 단위|코드 줄 수보다 책임의 범위가 적절한가?|
|독립된 서비스|다른 서비스 내부 구현에 과하게 묶이지 않음|다른 서비스를 모두 수정하지 않고 변경할 수 있는가?|
|응집된 서비스|같은 목적의 기능이 모여 있음|기능들이 하나의 업무 책임으로 설명되는가?|
|자율적 서비스|담당 팀이 개발부터 운영까지 책임짐|의사결정과 운영 책임이 명확한가?|

**높은 응집도**는 관련 기능이 잘 모여 있는 상태이고, **낮은 결합도**는 다른 서비스의 변경에 덜 의존하는 상태다. 예를 들어 주문 생성·조회·취소는 주문이라는 업무 책임으로 묶을 수 있다.

독립성은 통신하지 않는다는 뜻이 아니다. 필요한 계약을 통해 협력하면서 서로의 내부 코드나 테이블에 과하게 묶이지 않는다는 뜻이다.

#### 응집도와 결합도를 주문 기능으로 이해하기

주문 생성·조회·취소는 주문 상태와 업무 규칙을 함께 다룬다. 이 기능들을 주문 서비스 안에 묶으면 관련 변경을 한곳에서 이해하기 쉬워진다. 이것이 응집도를 높이는 방향이다.

반대로 주문 취소를 위해 회원 서비스의 내부 클래스와 상품 DB의 테이블 구조까지 알아야 한다면, 회원·상품의 변경이 주문 기능에 영향을 준다. 이 의존을 줄이고 공개된 계약으로 필요한 정보만 받는 것이 결합도를 낮추는 방향이다.

작다는 이유만으로 좋은 서비스가 되지는 않는다. 조회·취소·상태 변경을 무조건 각각 분리하면 주문 규칙 하나를 바꿀 때 여러 서비스를 조율해야 할 수 있다. **같은 업무 이유로 함께 바뀌는 기능은 함께 두는 것이 유리할 수 있다.**

### 2.2 Bounded Context와 공통 업무 언어

**Bounded Context**는 업무 용어와 데이터 모델이 일관된 의미를 갖는 경계다.

같은 “고객”이라도 회원 영역에서는 로그인과 개인정보가 중요하고, 배송 영역에서는 수령인과 배송지가 중요하다. 서로 다른 의미를 억지로 하나의 모델에 담으면 변경 영향이 커질 수 있다.

**Ubiquitous Language**는 해당 업무 영역에서 개발자와 업무 담당자가 함께 사용하는 공통 용어다. “주문 완료”와 “결제 완료”를 구분했다면 코드, API, 대화에서도 그 의미를 일관되게 사용해야 한다.

Bounded Context는 서비스 경계를 정하는 기준이지만, 항상 마이크로서비스 하나와 정확히 1:1로 대응하지는 않는다.

|같은 표현|회원 영역의 의미|배송 영역의 의미|
|---|---|---|
|고객|가입 계정과 이용자 정보의 주체|물건을 받는 수령인|
|주소|회원이 저장한 주소 정보|해당 주문에서 사용할 실제 배송지|
|정보 변경|현재 계정 정보 갱신|이미 생성한 배송 업무의 변경 규칙 적용|

예를 들어 회원이 주소를 수정했다고 이미 배송 중인 주문의 수령지가 자동으로 바뀌어야 하는 것은 아니다. 두 업무가 같은 필드 이름을 사용해도 의미와 변경 규칙은 다를 수 있다. 경계를 정하면 이런 차이를 모델과 계약에 반영하기 쉽다.

### 2.3 서비스 식별 절차와 선택 기준

```text
도메인·요구사항·조직 이해
    ↓ 사용자, 핵심 업무, 제약조건을 파악한다
분할 원칙 수립
    ↓ 업무 경계, 크기, 책임 기준을 정한다
기능·데이터·호출 관계 분석
    ↓ 함께 바뀌는 부분과 독립시킬 부분을 확인한다
서비스 후보 식별
    ↓ 독립성이 필요한 업무와 담당 팀을 정한다
우선순위 결정
    ↓ 영향도와 비용을 보고 Pilot·MVP로 검증한다
분리 범위 조정
```

Pilot은 제한된 범위의 시범 적용이고, MVP는 핵심 가치를 검증하기 위한 최소 기능 제품이다.

|질문|분리를 검토할 이유|
|---|---|
|변경 빈도와 배포 주기가 다른가?|다른 업무와 함께 배포하는 부담을 줄일 수 있음|
|확장 요구가 다른가?|부하가 큰 업무만 자원을 늘릴 수 있음|
|장애를 격리할 필요가 있는가?|업무별 영향 범위를 제한할 수 있음|
|외부 시스템 의존성이 다른가?|별도의 장애·호환성 관리를 할 수 있음|
|적합한 기술이 다른가?|업무 특성에 맞는 기술을 선택할 수 있음|

전체 업무에서 출발하는 **하향식**, 기존 기능과 데이터 관계를 분석하는 **상향식**, 독립 필요성이 큰 일부 영역부터 추출하는 방식이 있다.

분할 전에 기능만 보지 말고 다음 세 관계도 함께 확인한다.

|분석 관계|확인할 내용|무시하면 생길 수 있는 문제|
|---|---|---|
|서비스와 데이터|어느 업무가 데이터를 생성·수정하는가?|데이터 책임이 여러 서비스에 흩어짐|
|서비스 간 종속성|어떤 호출이 반드시 성공해야 하는가?|한 서비스 장애가 여러 업무로 전파|
|데이터 간 종속성|어떤 데이터들이 함께 일치해야 하는가?|분리 후 상태가 모순되는 상황 발생|

독립 확장을 원한다는 이유만으로 모든 데이터를 잘라내면 안 된다. 기능의 독립성과 데이터의 연결 관계를 함께 분석해야 실제로 운영 가능한 경계를 정할 수 있다.

단순히 Controller, Service, Repository를 각각 네트워크 서비스로 분리하는 것은 업무 경계를 나누는 것과 다르다. 요청마다 여러 계층을 원격 호출하게 되어 통신 비용만 커질 수 있다.

### 2.4 데이터 소유권과 Polyglot Persistence

서비스 경계에는 코드뿐 아니라 **어떤 서비스가 데이터를 책임지는가**도 포함된다.

- 회원 서비스는 회원 정보를 관리한다.
- 주문 서비스는 주문 정보를 관리한다.
- 다른 서비스의 정보가 필요하면 API나 이벤트 같은 계약으로 전달받는다.

서로의 테이블을 직접 수정하면 테이블 구조와 변경 시점에 강하게 묶일 수 있다. 데이터 접근 경계를 지키는 것이 서비스 독립성에 중요하다.

주문 서비스가 상품 DB를 직접 읽는다면 상품 테이블의 열 이름이 바뀔 때 주문 서비스도 영향을 받는다. 상품 서비스의 API 계약을 사용하면 내부 테이블 변경을 상품 서비스 안에서 흡수할 수 있다. 물론 API의 응답 계약 자체를 바꾸면 소비자도 영향을 받으므로 계약 관리가 필요하다.

서비스별 데이터 소유권은 서비스마다 물리 DB 서버를 반드시 한 대씩 둔다는 뜻은 아니다. 같은 DB 서버를 사용하더라도 스키마와 접근 권한 등의 경계를 설계할 수 있다. 다만 공유 자원의 장애 영향도는 따로 고려해야 한다.

**Polyglot Persistence**는 업무 특성에 맞춰 여러 저장 기술을 사용하는 방식이다.

|업무 특성|저장 기술 선택의 예|
|---|---|
|주문 관계와 트랜잭션|관계형 DB|
|검색과 검색 조건 처리|검색에 적합한 저장 기술|
|빠른 임시 조회|키-값 기반 캐시|

서로 다른 기술을 많이 쓰는 것 자체가 목표는 아니다. 장점과 함께 운영, 백업, 장애 대응 비용을 판단해야 한다.

### 2.5 동기·비동기 통신과 정합성

|비교 기준|동기 요청·응답|비동기 메시지·이벤트|
|---|---|---|
|진행 방식|요청 후 응답을 기다림|전달 후 상대가 별도로 처리|
|예시|주문 서비스가 상품 가격 조회|주문 완료 이벤트로 알림 요청|
|장점|즉시 결과와 처리 흐름을 이해하기 쉬움|처리 시점과 직접 의존을 분리하기 쉬움|
|주요 부담|지연, 시간 초과, 상대 서비스 장애|지연, 중복, 순서, 실패 후 재처리|

이벤트는 “주문이 완료되었다”처럼 발생한 사실을 나타낸다. Publish는 발행, Subscribe는 구독이며, 큐와 메시지 시스템은 전달과 대기를 돕는다.

설명용 이벤트 흐름은 다음과 같다.

```text
주문 서비스의 주문 처리
    ↓ 업무 결과를 이벤트로 전달한다
메시지 시스템
    ↓ 관심 있는 소비자에게 전달한다
알림 서비스의 이벤트 수신
    ↓ 알림을 별도로 처리한다
처리 결과 기록 또는 실패 후 재처리
```

DB 저장과 이벤트 발행 사이에도 실패할 수 있다. 위 흐름만으로 메시지 유실이나 중복이 방지되는 것은 아니다.

분산 환경에서는 주문 저장은 성공하고 결제 요청은 실패할 수 있다. 한 서비스 안의 트랜잭션 성공이 업무 전체의 성공을 보장하지 않는다.

|보충 개념|의미|업무 예시|
|---|---|---|
|정합성|관련 데이터가 업무 규칙에 맞고 모순이 없음|결제 상태와 주문 상태가 일치해야 함|
|최종적 일관성|일시적 차이를 후속 처리로 일치시킴|전달 지연 후 알림 상태가 갱신됨|
|멱등성|동일 작업을 반복해도 의도한 효과가 중복되지 않음|같은 주문 이벤트를 두 번 받아도 중복 결제하지 않음|

이 개념들은 서비스 분리의 부담을 이해하기 위한 보충이다. 구체적인 분산 트랜잭션 구현까지 수행했다는 의미는 아니다.

#### 왜 하나의 트랜잭션처럼 생각하면 안 될까?

트랜잭션은 관련 데이터 작업을 하나의 성공·실패 단위로 처리하는 개념이다. 한 DB 안의 작업은 트랜잭션으로 묶기 쉬운 경우가 있지만, 다른 서비스가 이미 수행한 작업이 내 서비스의 실패로 자동 취소되는 것은 아니다.

```text
주문 서비스가 주문을 저장
    ↓ 주문 DB에서는 성공
결제 서비스에 결제 요청
    ↓ 통신 실패 또는 결제 실패
주문은 존재하지만 결제 완료는 확인되지 않음
    ↓ 업무 규칙에 따라 후속 처리 설계
상태 확인·재처리·취소 등의 대응이 필요
```

특히 응답만 유실되었다면 결제 서비스에서는 이미 성공했을 수도 있다. 실패 응답이나 시간 초과만 보고 같은 결제를 무조건 다시 요청하면 중복 결제가 생길 수 있다. 따라서 **성공 판정, 상태 확인, 재시도, 중복 방지**를 함께 생각해야 한다.

서비스마다 다음 질문을 남겨 두면 분리의 실제 부담을 확인할 수 있다.

- 어느 단계까지 완료되어야 업무 전체를 성공으로 볼 것인가?
- 늦게 도착한 데이터와 중복 이벤트를 어떻게 다룰 것인가?
- 실패 후 재처리해도 동일 업무가 두 번 수행되지 않는가?
- 일시적 불일치를 허용한다면 언제, 어떤 처리로 일치시킬 것인가?

### 2.6 조직의 책임과 API 계약

**Ownership**은 담당 팀이 기획·개발·테스트·배포·운영에 책임과 의사결정 권한을 갖는 것이다. Two Pizza Team은 작은 자율 팀을 설명하는 비유이며, 고정 인원 규칙은 아니다.

팀 간 협력은 요청 주소, 데이터 형식, 상태 코드, 오류 규칙을 담은 **API 계약**을 기준으로 진행한다. Consumer Driven Contract는 API 사용자의 기대를 계약으로 만들고 제공자가 그 기대를 충족하는지 검증하는 방식이다.

예를 들어 주문 팀이 상품 조회 응답의 `id`, `name`, `price`를 사용한다면, 상품 팀이 `price`를 삭제하거나 의미를 바꾸는 변경은 계약에 영향을 준다. 계약 검증은 각 서비스의 테스트가 따로 통과해도 실제 연결이 깨질 수 있다는 문제를 확인하는 데 도움을 준다.

#### 자료의 MSA 특징을 하나의 설계로 연결하기

|특징|실제로 고민할 내용|
|---|---|
|Challenges|네트워크 실패, 데이터 불일치, 운영 복잡성을 감당할 수 있는가?|
|Small Well Chosen Deployable Units|업무 의미가 있고 독립 배포 가치가 있는 단위를 골랐는가?|
|Bounded Context|용어·데이터 모델·업무 규칙의 경계가 일관되는가?|
|RESTful|사용하는 쪽이 이해할 수 있는 요청·응답 계약이 있는가?|
|Configuration Management|실행 환경별 설정을 일관되게 관리하는가?|
|Cloud Enabled|실행 위치와 인스턴스 수의 변화에 대응하는가?|
|Dynamic Scaling|서비스별로 자원을 늘리고 줄일 수 있는가?|
|CI/CD|서비스마다 변경을 검증하고 배포할 수 있는가?|
|Visibility|상태와 요청 흐름을 보고 문제 원인을 찾을 수 있는가?|

이 특징들은 별도의 암기 목록이라기보다 **경계 설계부터 운영까지 확인할 질문**으로 연결된다.

> 서비스의 경계는 업무 책임, 데이터 소유권, 통신 계약, 담당 팀의 책임을 함께 나누는 경계다.

## 3. 나뉜 서비스를 운영하기 위한 클라우드 네이티브 원칙

업무를 나누면 배포 대상과 통신 경로가 늘어난다. 이를 사람이 매번 수작업으로 운영하기 어렵기 때문에 확장, 자동화, 복구, 관찰을 고려한 운영 방식이 필요하다.

### 3.1 안정성: 견고함에서 회복과 개선으로

자료는 IT 시스템이 하드웨어 중심의 취약한 구조에서 분산 구조의 견고함을 거쳐, 회복력과 지속적 개선을 강조하는 방향으로 발전했다고 설명한다.

|개념|의미|
|---|---|
|Fragile|충격과 변화에 쉽게 망가짐|
|Robust|일정한 충격을 견디고 상태를 유지함|
|Resilient|장애 뒤 정상 상태로 회복함|
|Antifragile|충격과 불확실성을 통해 더 나아짐|

Auto Scaling, Microservices, Chaos Engineering, Continuous Deployment는 이 방향을 지원하는 실천이다. 특히 Chaos Engineering은 통제된 장애 실험으로 취약점을 확인하는 접근이다.

이 기술들을 도입한 사실만으로 안티프래질이 되는 것은 아니다. 장애를 관찰하고 학습한 결과를 설계와 운영에 반영해야 한다.

|실천|기대하는 변화|쉬운 예시|
|---|---|---|
|Auto Scaling|부하 변화에 맞춰 자원 조절|행사 중 상품 조회 인스턴스를 자동 추가|
|Microservices|업무별 변경·확장·장애 영향 관리|상품 업무와 주문 업무의 배포 주기 분리|
|Chaos Engineering|장애 가정을 실제로 검증|서버 하나가 중단될 때 영향 범위 확인|
|Continuous Deployment|작은 변경을 자주 검증·반영|큰 변경을 오래 모으기보다 검증한 작은 변경 반영|

“고장 나지 않게 만든다”는 목표와 “고장 나도 회복하고 배운다”는 목표는 다르다. 회복력은 정상 상태로 돌아오는 능력이며, 안티프래질은 그 경험을 통해 더 나아지는 성질이다.

### 3.2 클라우드 네이티브와 확장 방식

**클라우드 네이티브**는 실행 자원이 늘거나 줄고 일부가 고장 날 수 있는 환경을 고려해 애플리케이션을 설계·운영하는 접근이다.

|핵심 성질|필요한 이유|
|---|---|
|확장성|요청 증가에 맞춰 처리 자원을 늘림|
|탄력성과 변화 대응|업무와 실행 환경 변화에 빠르게 대응|
|장애 격리|한 서비스의 문제로 전체 업무가 중단되는 영향을 줄임|

|확장 방식|조정 대상|비유|
|---|---|---|
|Scale Up, 수직 확장|한 서버의 CPU·메모리 성능|한 직원의 처리 능력 향상|
|Scale Out, 수평 확장|같은 역할의 실행 인스턴스 수|같은 일을 할 직원 추가|
|Auto Scaling|지표와 정책에 따른 자원 자동 조절|업무량에 따른 자동 인력 배치|

인스턴스는 프로그램이 실제 실행되는 개별 단위다. 확장할 수 있는 구조와 자동 확장 기능은 구분해야 한다.

**Stateless**는 특정 서버의 로컬 메모리에 남은 이전 요청 상태에 의존하지 않도록 설계하는 것이다. 로그인 정보를 한 서버 메모리에만 두면 다른 서버가 다음 요청을 받았을 때 문제가 될 수 있다.

영구 데이터는 DB 같은 저장소에 보관하고, 필요한 상태는 공유 저장소나 적절한 인증 방식으로 관리할 수 있다. 무상태는 데이터가 없거나 인증이 필요 없다는 뜻이 아니다.

#### 수평 확장과 무상태가 연결되는 이유

서버 A에서 로그인한 사용자의 다음 요청이 서버 B로 전달될 수 있다. 로그인 상태가 A의 메모리에만 있으면 B는 그 상태를 바로 알 수 없다. 이처럼 특정 인스턴스에 묶인 상태는 자유로운 분산과 교체를 어렵게 만든다.

인스턴스의 로컬 상태 의존을 줄이면 요청을 다른 인스턴스로 보내거나 기존 인스턴스를 교체하기 쉬워진다. 다만 DB와 캐시 같은 공유 저장소의 용량과 장애도 함께 고려해야 한다. 앱 인스턴스를 늘린다고 모든 병목이 사라지는 것은 아니다.

#### 가용성과 장애 격리

**가용성**은 필요할 때 서비스를 이용할 수 있는 정도다. 장애 격리는 한 부분의 문제가 전체로 번지는 것을 줄여 가용성을 유지하려는 설계다.

예를 들어 상품 상세 화면이 추천 서비스의 성공을 반드시 기다린다면, 추천 장애가 상세 조회 장애로 이어질 수 있다. 추천 실패 시 기본 정보는 보여 주도록 업무 흐름을 설계하면 영향 범위를 줄일 수 있다. 서비스가 별도 프로세스에 있다는 사실과 사용자 업무가 독립적으로 유지된다는 사실은 구분해야 한다.

### 3.3 CI/CD와 배포 전략

**CI(Continuous Integration)**는 변경을 자주 통합하고 빌드·테스트로 검증하는 과정이다. 빌드는 소스코드를 실행·배포할 형태로 준비하고, 테스트는 기대한 동작을 확인한다.

```text
코드 변경과 저장소 반영
    ↓ 변경 통합
빌드
    ↓ 실행·배포 가능한 형태로 준비
자동 테스트
    ↓ 통과한 변경만 다음 단계로 진행
배포 가능한 버전 준비
    ↓ 운영 반영 방식에 따라 구분
승인·결정 후 반영: Continuous Delivery
또는 검증 통과 후 자동 반영: Continuous Deployment
```

|구분|초점|운영 반영|
|---|---|---|
|CI|변경 통합과 자동 검증|운영 배포 자체가 핵심은 아님|
|Continuous Delivery|언제든 배포 가능한 상태 유지|최종 반영은 별도 승인·결정 가능|
|Continuous Deployment|검증에서 운영 반영까지 자동화|통과한 변경을 자동 반영|

파이프라인은 위 작업들을 순서와 조건에 따라 연결한 흐름이다. Jenkins 등은 이를 구현하는 도구이며, CI/CD라는 개념 자체와는 구분한다.

|배포 전략|동작|장점과 고려점|
|---|---|---|
|카나리|일부 트래픽에 새 버전을 먼저 제공하고 점진 확대|영향 범위를 제한하며 반응 확인, 두 버전의 공존 고려|
|블루그린|기존·신규 환경을 준비하고 트래픽 전환|전환·이전 버전 복귀가 쉬움, 두 환경 준비 비용 고려|

트래픽을 이전 버전으로 돌릴 수 있어도 DB 변경이 자동으로 복구되지는 않는다. 새 버전과 이전 버전이 같은 데이터 구조를 다룰 수 있는지 확인해야 한다.

**카나리의 판단 기준**은 새 버전으로 보내는 사용자 비율을 단계적으로 늘리는 것이다. 예를 들어 5%에서 오류율과 응답 시간을 관찰한 뒤 비율을 높인다. 이상이 생기면 확대를 멈추거나 이전 버전으로 요청을 돌릴 수 있다.

**블루그린의 판단 기준**은 두 환경을 준비하고 사용자의 진입 경로를 전환하는 것이다. 현재 Blue가 서비스 중일 때 Green에 새 버전을 올려 검증하고, 준비되면 Green으로 트래픽을 바꾼다. 이전 환경을 유지하면 되돌리기 쉽지만 추가 자원이 필요하다.

CI/CD는 이 배포를 반복 가능한 과정으로 만드는 기반이다. 자동화 범위가 빌드와 테스트까지인지, 배포 준비까지인지, 운영 반영까지인지 구분해야 실제 파이프라인을 정확하게 설명할 수 있다.

### 3.4 DevOps, 이미지, 컨테이너

**DevOps**는 개발과 운영이 함께 품질을 책임지고, 개발부터 배포·관찰·개선까지 연결하는 문화와 실천 방식이다. 특정 제품이 아니며 CI/CD는 이를 돕는 방법 중 하나다.

**컨테이너**는 애플리케이션을 격리된 환경에서 실행하는 단위다. 필요한 실행 요소를 이미지로 묶어 환경 차이를 줄일 수 있다.

|개념|역할|
|---|---|
|이미지|실행 파일·의존성·기본 설정 등이 담긴 패키지|
|컨테이너|이미지를 기반으로 실제 실행되는 단위|
|Docker|이미지와 컨테이너를 만들고 실행하는 대표 도구|
|가상 머신|일반적으로 별도의 게스트 운영체제를 실행하는 가상 환경|

컨테이너는 일반적으로 호스트 커널을 공유한다. 컨테이너를 사용한다고 MSA가 되는 것은 아니며, 모놀리식도 컨테이너에서 실행할 수 있다.

같은 이미지로 여러 컨테이너를 실행하면 동일한 애플리케이션 버전을 여러 인스턴스로 띄울 수 있다. 실행 환경별 주소와 비밀 정보까지 이미지에 고정하기보다 외부 설정으로 주입하면 같은 패키지를 여러 환경에서 활용하기 쉽다. 이것이 다음 12-Factor의 설정 분리 원칙과 연결된다.

**DevOps·CI/CD·컨테이너·MSA의 관계**도 구분한다. DevOps는 협업과 운영 문화, CI/CD는 변경 검증·배포 과정, 컨테이너는 패키징과 실행 기술, MSA는 업무 구조다. 어느 하나를 사용했다고 나머지가 자동으로 완성되지는 않는다.

### 3.5 12-Factor: 배포와 실행의 일관성

12-Factor는 환경 차이를 줄이고 배포·확장하기 쉬운 애플리케이션을 만들기 위한 원칙이다. 다음은 원래 12개 항목을 복습용으로 정리한 것이다.

|원칙|설계에서 기억할 내용|이해를 돕는 예시|
|---|---|---|
|Codebase|하나의 버전 관리 코드 기반, 여러 배포 환경|같은 앱의 코드를 기준으로 개발·운영 버전 관리|
|Dependencies|의존성을 명시하고 격리|필요한 라이브러리를 빌드 설정에 선언|
|Config|환경별 설정을 코드와 분리|DB 주소와 비밀 정보를 소스코드 밖에서 제공|
|Backing Services|외부 자원을 연결 대상으로 취급|DB 접속 정보를 바꿔 다른 환경의 DB에 연결|
|Build, Release, Run|빌드·배포 버전 준비·실행을 구분|코드 빌드 후 환경 설정을 결합해 실행|
|Processes|상태 없는 프로세스로 실행|재시작해도 영구 데이터는 외부 DB에 유지|
|Port Binding|포트를 통해 서비스를 제공|앱이 정해진 포트에서 HTTP 요청 수신|
|Concurrency|프로세스 종류와 수로 확장|요청 처리 인스턴스를 여러 개 실행|
|Disposability|빠른 시작과 정상적인 종료 처리|종료 시 진행 중 요청을 정리하고 인스턴스 교체|
|Dev/Prod Parity|환경 사이 차이를 최소화|개발과 운영의 저장 기술·버전 차이를 관리|
|Logs|로그를 이벤트 흐름으로 다룸|앱이 출력한 로그를 외부 수집 시스템에서 관리|
|Admin Processes|관리 작업을 일관된 환경에서 실행|데이터 수정 작업도 동일한 코드·설정 기준으로 수행|

자료의 **12 Factors + 3**은 기존 항목을 재구성한 확장 목록이다. 단순히 원래 목록의 끝에 세 항목을 붙인 것으로 외우지 않는다. API First, Telemetry, Authentication and Authorization을 포함해 서비스 계약과 운영·보안을 강조한다.

- **API First**: 구현 전에 API 계약을 먼저 설계한다.
- **Telemetry**: 시스템의 상태를 파악할 데이터를 수집한다.
- **Authentication**: 사용자가 누구인지 확인한다.
- **Authorization**: 해당 작업이 허용되는지 확인한다.

#### 자료의 15개 항목을 원래 목록과 혼동하지 않기

|순서|자료의 확장 항목|기억할 책임|
|---|---|---|
|1|One codebase, one application|코드 기반과 앱의 관계|
|2|API first|소비자와 먼저 합의할 계약|
|3|Dependency management|의존성 명시와 관리|
|4|Design, build, release, and run|설계부터 실행까지 단계 구분|
|5|Configuration, credentials, and code|설정·자격 정보·코드의 분리|
|6|Logs|외부에서 관리할 실행 기록|
|7|Disposability|빠른 시작과 종료|
|8|Backing services|DB 등 외부 자원|
|9|Environment parity|환경 간 일관성|
|10|Administrative processes|일관된 관리 작업|
|11|Port binding|서비스 제공 포트|
|12|Stateless processes|로컬 상태 의존 최소화|
|13|Concurrency|처리 단위의 병렬 실행과 확장|
|14|Telemetry|상태를 판단할 데이터 수집|
|15|Authentication and authorization|인증과 권한 판단|

목록 자체보다 “다른 환경에 배포하거나 서버를 교체해도 일관되게 동작하는가?”라는 질문을 기억하면 원칙들이 연결된다.

### 3.6 관찰 가능성과 Service Mesh

서비스가 나뉘면 “어디서 느려졌는가?”를 하나의 로그만으로 답하기 어렵다. **Observability, 관찰 가능성**은 수집한 정보로 내부 상태와 원인을 이해할 수 있는 능력이다.

|데이터|확인할 수 있는 것|예시|
|---|---|---|
|Logs|어떤 사건이 발생했는가?|주문 조회 실패 기록|
|Metrics|상태가 수치상 어떻게 변했는가?|요청 수, 오류율, 응답 시간|
|Traces|요청이 어떤 경로와 구간을 거쳤는가?|Gateway부터 주문·상품 호출까지 소요 시간|

모니터링은 정해진 상태와 지표를 감시하는 데 초점이 있고, 관찰 가능성은 이를 포함한 데이터로 내부 동작과 문제를 이해하는 능력이다.

예를 들어 오류율 지표로 “주문 요청의 실패가 늘었다”는 사실을 확인하고, 추적으로 “상품 호출 구간이 느리다”는 위치를 찾고, 해당 구간의 로그로 오류 내용을 확인할 수 있다. 세 데이터는 같은 것을 반복 기록하는 용도가 아니라 **현상·경로·구체적 사건을 함께 설명하는 역할**이다.

**Service Mesh**는 서비스 간 통신에 필요한 기능을 공통 인프라에서 관리하는 방식이다. 프록시, 통신 보안, 라우팅, 부하 분산, 통신 관찰 등을 제품과 구성에 따라 제공한다.

|구분|주로 다루는 통신|
|---|---|
|API Gateway|외부에서 내부 서비스로 들어오는 요청|
|Service Mesh|내부 서비스 사이의 요청과 통신 정책|

메시를 도입해도 업무 오류와 데이터 정합성이 자동으로 해결되지는 않는다. DB, 캐시, 메시지 시스템 같은 Backing Services, 실행 플랫폼, 자동화와 보안 기반도 각각 필요에 맞게 구성한다.

자료의 CNCF Landscape는 클라우드 네이티브 기술 생태계를 분야별로 살펴보는 지도다. 제품 이름보다 어떤 운영 책임을 맡는지 이해하는 데 활용한다.

|운영 기반|필요한 이유|
|---|---|
|Identity / Security|인증, 인가, 통신 보안을 공통 정책으로 관리|
|Runtime / Platform|업무 앱과 컨테이너가 실행될 환경 제공|
|Backing Services|업무 데이터를 저장하고 캐시·메시지를 제공|
|Automation|검증·배포·반복 작업을 일관되게 실행|
|Telemetry / Observability|상태를 보고 장애 위치와 원인을 파악|

서비스 메시는 이 전체 기반 중 **서비스 간 통신 책임**을 주로 다룬다. Gateway나 메시가 주문·결제의 업무 규칙까지 대신 구현하는 것은 아니다.

> 나뉜 서비스를 안정적으로 운영하려면 독립 배포 구조에 자동 검증, 확장, 장애 대응, 관찰 기반을 함께 갖춰야 한다.

## 4. 서비스의 협력 규칙을 REST API로 표현하기

여러 서비스와 팀이 협력하려면 서로의 내부 코드를 몰라도 요청하고 결과를 해석할 수 있어야 한다. 이를 위해 API 계약이 필요하며, 자료는 REST 방식의 자원 표현과 HTTP 활용을 소개한다.

### 4.1 자원, URI, HTTP 메서드

API는 프로그램 사이의 기능 사용 규칙이다. REST API에서는 관리 대상을 **자원(Resource)**으로 표현하고, URI로 구분하며 HTTP 메서드로 작업을 나타낸다.

|메서드|설명용 URI|의미|
|---|---|---|
|GET|`/users`|회원 목록 조회|
|GET|`/users/10`|특정 회원 조회|
|POST|`/users`|회원 생성|
|PUT|`/users/10`|해당 자원의 전체 교체 의미|
|PATCH|`/users/10`|일부 수정|
|DELETE|`/users/10`|회원 삭제|

`/getUser?id=10`처럼 주소에 행위를 넣기보다, `/users/10`이라는 자원과 GET이라는 작업을 분리하면 일관되게 이해하기 쉽다. 복수형·명사 사용은 권장 관례이며, 특수한 업무 동작은 API 계약에서 일관되게 정의한다.

URI는 자원을 식별하는 주소 표현이다. 클라이언트는 요청하는 프로그램이나 화면이고, 서버는 그 요청을 처리해 응답하는 쪽이다. HTTP 요청에는 메서드·주소·헤더와 필요한 본문이, 응답에는 상태 코드·헤더와 필요한 본문이 담긴다.

**GET `/users/10`을 해석하는 순서**는 “회원 자원 중 10번을 대상으로, 조회 작업을 요청한다”이다. 주소를 먼저 보고 대상을, 메서드를 보고 작업을, 상태 코드를 보고 결과를 해석한다.

PATCH는 학습 노트의 보충 항목이다. PUT과 PATCH를 단순히 “수정 메서드” 하나로 외우지 말고, 전체 교체와 부분 변경이라는 의미를 구분한다.

예를 들어 이름과 연락처를 가진 자원에서 연락처만 바꾸려는 요청은 부분 변경 계약으로 표현할 수 있다. PUT으로 전체 교체를 설계했다면 누락한 필드를 어떻게 다루는지도 계약에 명확하게 정해야 한다. URI와 메서드만 보고 서버의 모든 세부 동작을 추측하면 안 된다.

### 4.2 요청과 응답의 예시

아래는 **회원 조회 계약을 설명하는 예시**다. 실제 서버에 요청하거나 확인한 응답이 아니다.

```http
GET /users/10 HTTP/1.1
Host: api.example.com
Accept: application/json
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 10,
  "name": "회원 A"
}
```

요청은 회원 10번이라는 자원 조회를 표현한다. 응답의 200은 성공을, JSON 본문은 반환 데이터를 나타낸다. 존재하지 않는 회원을 조회하면 계약에 따라 404와 일관된 오류 응답을 제공할 수 있다.

### 4.3 상태 코드와 오류 계약

|상태 코드|의미|구분할 점|
|---|---|---|
|200 OK|요청 성공|결과를 본문으로 제공할 수 있음|
|201 Created|자원 생성 성공|생성 결과를 조회 성공과 구분|
|204 No Content|성공, 응답 본문 없음|본문이 비어도 실패는 아님|
|400 Bad Request|잘못된 요청|입력과 요청 형식 확인|
|401 Unauthorized|유효한 인증이 없거나 인증 실패|인증 필요 여부 확인|
|403 Forbidden|요청한 작업이 허용되지 않음|권한·정책 확인|
|404 Not Found|자원을 찾을 수 없음|자원 존재 여부 확인|
|500 Internal Server Error|서버 내부 처리 오류|서버 측 실패 확인|

204, 403, 500은 개념을 연결하기 위한 보충이다. 오류를 모두 200으로 반환하거나 제각각 다른 구조로 표현하면 사용하는 쪽이 결과를 해석하기 어렵다.

민감 정보는 URI에 담지 않는다. 주소가 기록이나 로그에 남을 수 있기 때문이다. 인증 방식과 오류 처리 규칙도 소비자 관점에서 명확히 정해야 한다.

인증과 인가를 출입 절차로 비유하면 인증은 “누구인지 확인”, 인가는 “이 방에 들어가도 되는지 판단”이다. 보통 401은 유효한 인증이 필요한 상황을, 403은 요청이 허용되지 않는 상황을 나타낸다.

빈 목록과 없는 개별 자원도 구분한다. 회원 목록 조회 결과가 0명이면 성공 응답과 빈 배열 `[]`을 반환할 수 있다. 회원 10번 자체가 존재하지 않는 상황은 404로 표현할 수 있다. 정확한 규칙은 API 계약에 맞추지만, “데이터가 비었다”는 사실만으로 모두 같은 오류로 처리하지 않는다.

### 4.4 REST 성숙도 모델과 HATEOAS

|단계|핵심|예시와 구분 기준|
|---|---|---|
|Level 0|HTTP를 작업 호출 통로로 사용|자원 구분과 HTTP 의미를 충분히 활용하지 않음|
|Level 1|자원별 URI 구분|`/accounts`, `/accounts/10`으로 대상 구분|
|Level 2|HTTP 메서드·상태 코드 활용|같은 자원에 GET·PUT·DELETE를 의미에 맞게 사용|
|Level 3|HATEOAS 활용|응답에 다음 가능한 동작의 링크 제공|

**HATEOAS**는 클라이언트가 응답의 링크를 통해 다음 동작을 발견하게 하는 개념이다. 아래는 취소 가능한 주문에 링크를 포함한 설명용 응답이다.

```json
{
  "id": 100,
  "status": "CREATED",
  "links": [
    {
      "rel": "self",
      "href": "/orders/100"
    },
    {
      "rel": "cancel",
      "href": "/orders/100/cancellation"
    }
  ]
}
```

링크의 형식과 취소 요청 메서드는 실제 계약에서 정한다. 단순히 `links`라는 필드를 추가하는 것만으로 완전한 HATEOAS 설계가 되는 것은 아니다.

Level 2가 “어떤 자원에 어떤 HTTP 작업을 수행하는가?”를 분명히 한다면, Level 3는 “이 상태에서 다음에 무엇을 할 수 있는가?”까지 응답으로 안내하는 방향이다. 주문이 취소 불가능한 상태라면 취소 링크를 제공하지 않는 식으로 상태와 가능한 행동을 연결할 수 있다.

#### API 계약에 최소한 담아야 할 것

|계약 항목|주문 조회에서 확인할 내용|
|---|---|
|자원과 작업|GET `/orders/{orderId}`|
|요청 데이터|주문 ID의 형식과 인증 조건|
|성공 응답|주문 ID·상태 등 각 필드의 의미와 타입|
|실패 응답|없는 주문, 인증 실패 등의 상태 코드와 오류 형식|
|소비자 관점|화면이나 다른 서비스가 결과를 어떻게 구분하는가?|

REST 성숙도는 API 표현을 이해하는 틀이다. 높은 단계라는 이유만으로 시스템 전체의 성능·보안·운영 품질이 자동 보장되지는 않는다.

> REST에서는 URI가 자원, 메서드가 작업, 상태 코드가 결과를 표현한다. REST를 사용한다는 사실만으로 MSA가 되는 것은 아니다.

## 5. Spring Cloud 구성요소를 하나의 요청 흐름으로 연결하기

업무 경계와 API를 설계해도 주소 변화, 설정 차이, 서비스 간 호출, 장애 처리 문제는 남는다. Spring Cloud는 이런 분산 시스템의 반복적인 문제를 지원한다.

### 5.1 Spring Boot와 Spring Cloud의 관계

|구분|주 역할|예시|
|---|---|---|
|Spring Boot|개별 Spring 앱의 설정·개발·실행 지원|회원 API 애플리케이션 개발|
|Spring Cloud|분산 시스템 기능을 지원하는 프로젝트 모음|설정 관리, 서비스 검색, Gateway, 장애 대응|

각 매장을 만드는 기반이 Boot라면 여러 매장 사이의 공통 운영과 연결을 돕는 도구들이 Cloud다. Cloud 전체가 하나의 서버인 것은 아니다. Config·Eureka처럼 별도 서버가 될 수 있는 역할과, OpenFeign처럼 각 서비스에 적용하는 라이브러리 역할을 구분해야 한다.

Spring Boot와 Spring Cloud는 호환되는 버전 조합을 선택한다.

- **Release Train**: 관련 Cloud 프로젝트의 호환 버전 묶음
- **BOM**: 라이브러리 버전을 일관되게 관리하는 목록
- **Starter**: 기능 도입에 필요한 의존성을 묶은 패키지

자료의 버전 표를 그대로 최신 조합으로 사용하지 말고, 실제 도입 시 공식 호환표를 확인한다.

### 5.2 문제별로 도구의 역할 구분하기

|해결하려는 문제|구성요소|역할|
|---|---|---|
|설정이 여러 서비스에 흩어짐|Spring Cloud Config|환경별 설정 중앙 관리·제공|
|서비스 주소가 바뀌고 인스턴스가 증감함|Eureka / Service Discovery|서비스 위치 등록·검색|
|외부에서 여러 서비스에 접근해야 함|Spring Cloud Gateway|공통 입구에서 요청 라우팅|
|같은 서비스가 여러 개 실행됨|Spring Cloud LoadBalancer|요청 대상 인스턴스 선택|
|HTTP 호출 코드가 반복됨|Spring Cloud OpenFeign|선언적인 HTTP 클라이언트 구성|
|실패 호출이 누적되고 장애가 전파됨|Spring Cloud CircuitBreaker|실패 조건에 따른 호출 제한|
|여러 서비스를 거친 요청 원인을 찾기 어려움|분산 추적 / Zipkin|요청 경로·구간 시간 수집과 확인|
|여러 앱에 설정 변경 같은 이벤트 전달이 필요함|Spring Cloud Bus|메시지 기반 이벤트 전파|

Config의 설정 변경이 모든 앱에 곧바로 적용되는 것은 아니다. 갱신 방식과 적용 가능한 항목을 설계해야 한다. Gateway의 공통 필터 역시 구성해야 동작하며, 설치만으로 모든 인증·인가가 완성되지는 않는다.

#### Config: 설정과 코드를 분리하는 책임

설정은 프로그램의 실행 환경과 동작을 정하는 값이다. 같은 주문 코드라도 개발·운영 환경의 DB 주소나 외부 API 주소가 다를 수 있다. 환경마다 코드를 수정하기보다 설정을 따로 관리하면 같은 애플리케이션을 여러 환경에서 사용하기 쉽다.

Config Server는 설정을 제공하고 Config Client는 이를 사용하는 앱이다. 중앙 관리의 장점과 별개로 **언제 읽고 언제 다시 반영하는가**를 구분해야 한다. 저장소에서 값을 바꾼 사실과 실행 중인 앱이 새 값을 적용한 사실은 다르다.

#### Eureka: 이름과 실행 위치를 연결하는 책임

서비스 이름은 업무 대상을, 실행 위치는 실제 접속할 주소와 포트를 나타낸다. 포트는 한 컴퓨터 안에서 통신할 프로그램을 구분하는 번호다.

|서비스 이름|사용 가능한 인스턴스의 예|
|---|---|
|`order-service`|주문 A: `host-a:8080`, 주문 B: `host-b:8080`|
|`product-service`|상품 A: `host-c:8080`|

실행 위치는 인스턴스 추가나 교체로 바뀔 수 있다. 호출자가 주소를 코드에 고정하는 대신 등록 정보를 이용하면 이런 변화에 대응하기 쉽다. 실제 위치를 직접 고정하지 않고 이름으로 접근하는 성질을 **위치 투명성(Location Transparency)**이라고 한다.

Eureka는 서비스가 스스로 실행 정보를 등록하고 상태 신호를 갱신하는 구조를 지원한다. 이것이 업무 요청을 대신 처리한다는 뜻은 아니다.

#### Gateway와 LoadBalancer: 목적지 판단의 두 단계

|판단|예시|담당 책임|
|---|---|---|
|어느 업무로 보낼까?|`/orders/**`는 주문 서비스로|Gateway의 라우팅|
|어느 실행 대상으로 보낼까?|주문 A와 주문 B 중 선택|LoadBalancer의 인스턴스 선택|

공통 입구를 사용하면 외부 클라이언트가 내부 서비스 주소를 각각 관리하는 부담을 줄일 수 있다. 인증·요청 제한 등의 공통 필터를 둘 수 있지만, 내부 업무의 권한과 데이터 접근 규칙도 함께 설계해야 한다.

#### Bus: 여러 앱에 이벤트를 전파하는 책임

Config와 Bus를 연결하는 구성에서는 설정 변경을 알리는 이벤트를 여러 앱에 전달할 수 있다. 다만 이벤트 전달, 앱의 갱신 처리, 실제 변경 가능한 설정은 서로 다른 확인 대상이다. 이벤트가 전달되었다는 사실만으로 모든 설정이 즉시 바뀌었다고 단정하지 않는다.

### 5.3 시작 시점과 사용자 요청 시점을 분리하기

Config와 Eureka를 사용자 요청이 지나가는 중계 서버로 외우면 흐름이 잘못된다. 다음은 Config Server와 Eureka를 사용하는 **설명용 구성**이다.

**애플리케이션 시작과 운영 준비**

```text
서비스 애플리케이션 시작
    ↓ 구성에 따라 Config Server에서 설정을 읽는다
실행에 필요한 설정 준비
    ↓ 서비스 이름과 실행 위치를 등록한다
Eureka에 인스턴스 정보 등록
    ↓ 상태 신호와 등록 정보를 갱신한다
다른 호출자가 서비스 위치를 찾을 수 있는 상태
```

**사용자의 주문 조회 요청**

```text
GET /orders/100 요청
    ↓ 외부 진입점
Gateway
    ↓ 경로와 구성된 필터·인증 정책 적용
주문 서비스로 라우팅 결정
    ↓ 검색 정보로 사용 가능한 인스턴스를 확인
LoadBalancer가 주문 인스턴스 선택
    ↓ 실제 업무 요청 전달
선택된 주문 서비스
    ↓ 주문 데이터 조회와 필요한 처리
응답을 Gateway를 통해 사용자에게 반환
```

서비스 검색 정보는 캐시될 수 있으므로 매 요청마다 Eureka를 직접 조회한다고 단정하지 않는다. **업무 요청은 실제 주문 서비스로 전달되며, 항상 Eureka 서버를 통과하지 않는다.**

라우팅은 “어느 서비스로 보낼 것인가?”, 부하 분산은 “그 서비스의 어느 인스턴스로 보낼 것인가?”라는 서로 다른 판단이다.

### 5.4 OpenFeign: 인터페이스와 실제 HTTP 호출의 연결

OpenFeign은 Java 인터페이스의 선언으로 HTTP 클라이언트를 구성한다. 아래 코드는 **학습 내용을 구현 형태와 연결하기 위한 예시**이며, 오늘 작성·실행한 코드가 아니다.

```java
import java.math.BigDecimal;
import org.springframework.cloud.openfeign.FeignClient;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;

@FeignClient(name = "product-service")
public interface ProductClient {

    @GetMapping("/products/{productId}")
    ProductResponse getProduct(@PathVariable("productId") Long productId);

    record ProductResponse(Long id, String name, BigDecimal price) {}
}
```

|코드 요소|역할|
|---|---|
|`@FeignClient(name = "product-service")`|호출할 클라이언트와 서비스 이름 지정|
|`@GetMapping`|요청 메서드와 경로 선언|
|`@PathVariable`|인자를 URI의 경로 값으로 전달|
|`ProductResponse`|성공 응답을 변환할 Java 반환 타입|

예를 들어 `getProduct(10L)`을 호출하면 GET `/products/10` 요청을 보내고 응답을 `ProductResponse`로 변환하는 클라이언트가 동작한다. 이는 성공 응답을 전제로 한 설명이며, 통신 실패나 오류 응답 처리는 별도로 필요하다.

이 예시의 전제는 OpenFeign 의존성, `@EnableFeignClients`를 통한 클라이언트 활성화, DTO와 맞는 서버 응답이다. 서비스 이름으로 인스턴스를 선택하려면 LoadBalancer와 서비스 검색 또는 별도 서버 목록 구성도 필요하다. 이 코드 하나만으로 실행 구성이 완성되지는 않는다.

DTO는 요청·응답 데이터를 옮기기 위한 객체다. 예시의 `record`는 응답의 ID·이름·가격을 담는 Java 데이터 구조이며, 이를 이해하기 위해 별도의 도메인 객체 설계까지 확장할 필요는 없다.

```text
주문 서비스에서 ProductClient.getProduct(10L) 호출
    ↓ OpenFeign이 메서드 선언을 HTTP 요청으로 해석
GET /products/10 구성
    ↓ 설정된 주소 또는 검색·분산 구성으로 대상 결정
상품 서비스에 요청
    ↓ 성공 응답 수신
응답 데이터를 ProductResponse로 변환
    ↓ 주문 로직으로 반환
필요한 상품 정보 사용
```

OpenFeign은 HTTP 클라이언트 구성 방식이고, GraphQL은 필요한 데이터를 질의하는 API 기술이다. “다른 서비스의 데이터를 받는다”는 공통점만으로 같은 개념으로 보면 안 된다.

> Java 메서드처럼 보이더라도 실제 작업은 네트워크 HTTP 호출이다. 호출 코드의 반복을 줄이는 것과 통신 실패를 없애는 것은 다르다.

### 5.5 장애 대응: Timeout, Retry, Circuit Breaker, Fallback

상품 서비스가 느려지면 주문 서비스가 응답을 기다리고, 그 대기가 Gateway와 사용자까지 영향을 줄 수 있다. MSA의 장애 격리는 구조만으로 보장되지 않는다.

|방법|역할|주의점|
|---|---|---|
|Timeout|정해진 시간이 지나면 기다림을 종료|처리 중인 원격 작업까지 취소된다고 보장하지 않음|
|Retry|실패한 작업을 다시 시도|중복 효과와 부하 증가를 고려|
|Circuit Breaker|실패 조건에 따라 호출을 잠시 제한|원인을 고치거나 데이터를 복구하는 기능은 아님|
|Fallback|실패 시 업무에 맞는 대체 동작 제공|실패를 잘못된 성공으로 처리하면 안 됨|

서킷 브레이커의 대표 상태는 다음과 같다.

|상태|호출 동작|확인하는 것|
|---|---|---|
|Closed|정상 호출 허용|실패·지연 등의 지표|
|Open|보호 대상 호출 차단|설정된 대기·전환 조건|
|Half-Open|제한된 시험 호출 허용|정상화 여부|

회복이 확인되면 Closed로 돌아가고, 실패 조건이 충족되면 다시 Open으로 전환될 수 있다. 구체적인 기준은 구현체와 설정에 따라 달라진다.

추천 기능 실패 시 기본 목록을 제공하는 것은 대체 동작이 될 수 있다. 반면 결제 실패를 결제 성공으로 응답하는 것은 업무 의미를 훼손한다.

#### 세 상태를 차단기 비유로 읽기

Closed는 회로가 연결된 상태라 호출이 흐른다. 실패가 설정된 기준을 충족하면 Open으로 바뀌어 추가 호출을 막는다. 일정 조건 뒤 Half-Open에서 일부 요청만 시험하고 정상화 여부를 확인한다.

“Open이면 호출을 열어 준다”라고 외우면 반대로 이해하게 된다. 전기 회로가 열려 연결이 끊긴 상태이므로, 보호 대상 호출은 차단되는 상태다.

Timeout으로 오래 기다리지 않게 하고 Circuit Breaker로 반복 장애의 호출 누적을 줄일 수 있다. Retry를 추가할 때는 호출 대상이 회복 가능한 상황인지와 작업의 멱등성을 확인해야 한다. 각 기능은 다른 문제를 다루며 항상 모두 적용하는 것이 정답은 아니다.

### 5.6 분산 추적과 생태계의 다른 구성요소

한 요청이 여러 서비스를 거칠 때 **Trace ID**는 전체 흐름을 묶는 식별자이고, **Span**은 그 안의 개별 작업 구간이다. Zipkin은 추적 정보를 저장하고 확인하는 시스템이다.

예를 들어 주문 조회가 느리다면 전체 요청 시간만 보고는 DB 조회가 느린지 상품 서비스 호출이 느린지 알기 어렵다. 추적 정보가 각 구간을 연결하면 병목을 구분할 수 있다. 구간 시간에는 포함 관계와 대기 시간이 있을 수 있으므로 숫자를 무조건 더하는 것보다 경로와 구간 관계를 읽는 것이 중요하다.

#### 전체 사례: 주문 요청 한 번으로 역할 연결하기

다음 표는 시작 준비, 실제 업무 요청, 실패, 관찰을 한 시나리오에 연결한 것이다. 모든 시스템에 이 도구들이 필수로 들어간다는 뜻은 아니다.

|시점·상황|수행할 일|관련 구성요소|
|---|---|---|
|서비스 시작|환경에 맞는 실행 설정 준비|Config|
|인스턴스 실행·변경|서비스 이름과 위치 등록·갱신|Eureka|
|사용자의 주문 조회|외부 요청을 주문 업무로 전달|Gateway|
|주문 인스턴스 여러 개|실제로 요청받을 인스턴스 선택|LoadBalancer|
|주문 처리 중 상품 정보 필요|상품 서비스 HTTP 요청|OpenFeign|
|상품 호출이 지연·실패|기다림과 반복 호출 영향 제한|Timeout, CircuitBreaker 등|
|원인 분석|요청 경로와 구간, 오류 확인|Tracing, Metrics, Logs|
|설정 변경 전파|구성에 맞춰 갱신 이벤트 전달|Bus|

요청 중 다른 서비스가 필요하지 않으면 OpenFeign 호출도 생기지 않는다. 추적은 마지막에 한 번만 실행하는 별도 업무 단계라기보다 요청 처리 구간을 관찰하도록 연계되는 기능이다.

Config, Discovery, Gateway, LoadBalancer, HTTP 클라이언트, 장애 대응, 추적은 모든 요청이 차례로 통과하는 서버 목록이 아니다. 각자의 사용 시점과 책임이 다르다.

자료의 다른 프로젝트는 다음 역할을 중심으로 묶어 볼 수 있다.

|관련 영역|자료의 프로젝트 예시|학습 포인트|
|---|---|---|
|검색·설정 연계|Consul, Zookeeper|서비스와 환경 정보를 관리하는 다른 선택지|
|메시지·이벤트|Bus, Stream|메시지 기반 협력과 이벤트 전파|
|계약·작업|Contract, Task, Function|계약 검증, 짧은 작업, 함수 기반 처리|
|공통·플랫폼|Commons, Starters, Kubernetes|공통 기반과 실행 플랫폼 연계|
|데이터 흐름|Data Flow|데이터 처리 파이프라인 관리|

생태계 목록에 등장하는 모든 프로젝트가 필수 의존성은 아니다. Cloudfoundry, CLI, Security, Sleuth 등도 자료의 작성 시점 맥락과 지원 상태를 구분해 읽는다.

### 5.7 자료의 과거 기술명을 읽는 방법

|자료에서 만나는 이름|담당 개념|연결해서 볼 도구·흐름|
|---|---|---|
|Ribbon|클라이언트 측 부하 분산|Spring Cloud LoadBalancer|
|Hystrix|서킷 브레이커와 장애 대응|Spring Cloud CircuitBreaker와 Resilience4j|
|Netflix Gateway / Zuul 계열|API Gateway|Spring Cloud Gateway|
|Sleuth|분산 추적|Spring Boot 3 이후 Micrometer Tracing|

이 표는 동일한 코드를 그대로 교체할 수 있다는 뜻이 아니라 **해결하는 문제의 대응 관계**다. CircuitBreaker는 구현체를 사용할 공통 API를 제공하고, Resilience4j는 그 구현 선택지 중 하나다. Sleuth는 공식 문서상 Spring Boot 3 이상과 호환되지 않으며 Micrometer Tracing으로 이어진다.

### 5.8 Spring Cloud와 Kubernetes, 개발 도구

|구분|주된 관점|대표 책임|
|---|---|---|
|Spring Cloud|분산 애플리케이션 개발|호출, 설정 연계, Gateway, 장애 대응|
|Kubernetes|컨테이너 실행과 운영|배치, 실행 유지, 복구, 확장|

서비스 검색과 설정, 통신 영역에서는 기능이 일부 겹칠 수 있다. Kubernetes의 검색 기능을 활용하면 Eureka를 별도로 두지 않는 구성도 가능하다. 둘은 반드시 함께 사용해야 하는 관계도, 한쪽이 다른 쪽을 항상 대체하는 관계도 아니다.

예를 들어 Spring Boot로 주문 앱을 만들고 Spring Cloud 기능으로 호출·장애 대응을 구성한 뒤, 컨테이너 이미지로 패키징해 Kubernetes에서 여러 인스턴스로 실행할 수 있다. 각 기술이 같은 프로그램의 **개발, 연결, 포장, 운영**이라는 다른 책임을 맡는 것이다.

Kubernetes의 컨테이너 재시작은 실행 복구를 돕지만 결제 데이터의 모순을 자동으로 고치지는 않는다. 운영 플랫폼의 복구와 애플리케이션의 업무 복구를 구분해야 한다.

자료는 IntelliJ IDEA Ultimate, Git, VS Code, Postman을 개발 도구로 안내한다. 각각 개발·실행, 변경 이력, 편집, API 요청 확인을 담당한다. 다음은 JDK와 빌드 도구까지 포함한 **설치 여부 확인용 명령**이며, 실행 결과를 기록한 것은 아니다.

```bash
java -version
javac -version
git --version
mvn -v
gradle -v
```

Maven과 Gradle을 모두 전역 설치할 필요는 없다. 프로젝트의 빌드 도구와 Wrapper 제공 여부를 먼저 확인한다.

|도구|역할|구분할 점|
|---|---|---|
|IntelliJ IDEA / VS Code|코드·설정 작성과 개발 작업|편집기가 업무 앱을 대신하는 것은 아님|
|Git|변경 이력과 협업 관리|실행·빌드 도구와 다른 책임|
|Postman|API 요청과 응답 확인|서버 API가 준비되어야 실제 결과 확인 가능|
|JDK|Java 개발·실행 도구|앱 실행과 컴파일의 기반|
|Maven / Gradle|의존성 관리·빌드 작업|프로젝트가 선택한 도구를 사용|

Wrapper가 제공되면 해당 프로젝트에서 정한 빌드 도구 버전을 활용할 수 있다. 설치 확인과 실제 프로젝트 실행 성공은 다른 결과이므로 따로 확인한다.

> 설정은 Config, 위치는 Discovery, 입구는 Gateway, 인스턴스 선택은 LoadBalancer, HTTP 호출은 OpenFeign, 장애 제한은 CircuitBreaker, 경로 확인은 Tracing으로 구분한다.

# 🧠 오늘 이해한 핵심

- **서비스 독립성은 코드 분할보다 넓은 개념이다.** 업무 경계와 함께 데이터 소유권, API 계약, 배포 주기, 담당 팀의 책임이 정해져야 독립적인 변경과 운영이 가능하다.
- **MSA의 장점은 운영 설계와 함께 성립한다.** 선택적 확장과 장애 격리를 얻으려면 무상태 처리, 자동 검증, 통신 실패 대응, 관찰 기반을 함께 고려해야 한다.
- **Spring Cloud의 도구는 사용 시점과 책임으로 연결해야 한다.** 시작 시 설정·등록을 준비하는 흐름과 사용자 요청을 라우팅·호출·관찰하는 흐름을 구분하면 전체 구조를 설명하기 쉽다.

### 오늘 배운 내용의 전체 관계

### 30초로 설명하기

> 오늘은 큰 서비스를 업무별로 나누어 독립적으로 변경·배포·확장하는 마이크로서비스 아키텍처를 학습했다. 서비스를 나누면 네트워크 실패와 데이터 정합성 관리가 어려워지므로, 업무 경계와 실패 처리도 함께 설계해야 한다. 이를 지속적으로 운영하기 위해 CI/CD, 컨테이너, 확장과 관찰 기반이 필요하다. REST API로 협력 규칙을 정하고 Spring Cloud의 설정·검색·라우팅·호출·장애 대응 기능을 연결한다.

|질문|핵심 답변|

|무상태이면 데이터를 저장하면 안 되는가?|특정 인스턴스의 로컬 상태에 의존하지 않는다는 뜻이다. 영구 데이터는 DB 같은 저장소에 보관한다.|
|Delivery와 Deployment의 차이는 무엇인가?|Delivery는 언제든 배포 가능한 상태, Deployment는 검증 통과 후 운영 반영까지 자동화하는 것이다.|

|REST의 URI·메서드·상태 코드는 무엇인가?|URI는 자원, 메서드는 작업, 상태 코드는 결과다. API 계약은 각 데이터와 오류의 의미까지 정한다.|
|HATEOAS는 무엇을 추가하는가?|응답 데이터에 다음 가능한 동작을 발견할 링크를 제공한다. 자원 상태와 행동을 연결하는 방향이다.|

### Spring Cloud의 역할

|질문|핵심 답변|
|---|---|
|Boot와 Cloud는 어떤 관계인가?|Boot는 개별 앱 개발·실행의 기반이고, Cloud는 분산 시스템의 반복 문제를 지원하는 프로젝트 모음이다.|
|Config와 Eureka를 모든 요청이 통과하는가?|그렇지 않다. 설정 로딩과 위치 등록·검색은 요청을 중계하는 업무 흐름과 다르다.|
|Eureka·Gateway·LoadBalancer는 어떻게 다른가?|Eureka는 위치 정보, Gateway는 요청 경로, LoadBalancer는 대상 인스턴스를 담당한다.|
|OpenFeign이 통신 실패도 없애 주는가?|HTTP 클라이언트 작성의 반복을 줄인다. 실제 네트워크 호출은 남으므로 시간 초과와 오류 처리가 필요하다.|
|Circuit Breaker의 Open은 왜 차단 상태인가?|전기 회로가 열려 연결이 끊긴 상태에 비유한다. 추가 호출을 제한하고 시험 호출로 회복 여부를 확인한다.|
|Gateway와 Service Mesh는 어디에 초점을 두는가?|Gateway는 주로 외부 진입, 메시는 주로 내부 서비스 간 통신을 다룬다. 업무 정합성을 대신 해결하지는 않는다.|
|Kubernetes가 모든 업무 장애를 복구하는가?|컨테이너 실행 복구를 도울 수 있지만 주문·결제 데이터 문제는 앱의 업무 규칙으로 처리해야 한다.|

# 🔍 복습할 부분

- **구조 판단 기준**: 프론트·백 분리, 모듈러 모놀리스, MSA를 업무 경계와 독립 배포 여부로 비교하고, 저장소·DB 개수만으로 판단할 수 없는 이유를 설명하기.
- **서비스 분리와 데이터**: 회원·상품·주문 예시에서 데이터 소유자를 정하고, 동기·비동기 각각의 실패·지연·중복 처리 질문을 확인하기.
- **배포와 API 의미**: Delivery와 Deployment는 운영 반영 자동화 여부로, 카나리와 블루그린은 트래픽 전환 방식으로 구분하기. PUT·PATCH 및 401·403의 차이도 확인하기.
- **요청 흐름 재구성**: 설정 로딩·Eureka 등록과 사용자 요청을 분리해서 설명하고, Gateway·LoadBalancer·OpenFeign·CircuitBreaker가 각각 어느 판단과 처리를 담당하는지 연결하기.
