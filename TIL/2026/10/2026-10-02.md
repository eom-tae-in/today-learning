# 📚 Today I Learned

## Service Discovery — 서비스 이름으로 실행 위치를 찾는 방법

사용자 서비스가 실행되는 주소와 개수는 달라질 수 있다. 오늘의 학습은 **실행 중인 서비스를 등록하고, 같은 기능을 제공하는 여러 실행본을 구분하는 방법**을 중심으로 정리한다.

서비스가 어디에 있는지 찾는 일에서 시작해, Eureka 서버와 클라이언트를 구성하고, 여러 인스턴스를 실행한 뒤 랜덤 포트와 고유 ID의 관계까지 연결한다. 마지막에는 **등록 상태, 실제 API 응답, 요청 분산이 각각 무엇을 증명하는지** 구분한다.

> 기본 프로젝트의 코드는 학습 내용을 재현할 수 있도록 정리한 예제다. **추가 확인 예제**는 원리를 확인하기 위한 보충 코드이며, 실행 결과의 포트·PID·ID는 설명용 값이다.

## 📚 학습 내용

### 1. Service Discovery가 필요한 이유부터 이해하기

#### 1-1. 마이크로서비스에서는 다른 서비스의 위치를 알아야 한다

마이크로서비스는 큰 프로그램의 기능을 여러 서비스로 나누고, 각 서비스가 독립적으로 실행되며 통신하는 구조다.

쇼핑몰을 예로 들면 사용자 서비스는 회원 정보를, 상품 서비스는 상품 정보를, 주문 서비스는 주문 처리를 담당할 수 있다. 주문 서비스가 회원 정보를 필요로 한다면 사용자 서비스에 네트워크 요청을 보내야 한다.

이때 가장 먼저 필요한 정보는 **“사용자 서비스가 어디에서 실행되고 있는가?”**이다.

주소를 고정해 두면 처음에는 간단하다. 하지만 재배포로 실행 위치가 달라지거나, 요청이 많아 실행본을 추가하면 호출자가 관리해야 할 주소도 달라진다.

|상황|주소를 직접 고정했을 때의 부담|
|---|---|
|다른 서버에서 다시 실행|호출할 호스트나 IP를 변경해야 한다.|
|여러 실행본으로 확장|새 실행본의 주소와 포트를 관리해야 한다.|
|실행본 종료 또는 장애|더 이상 사용할 수 없는 대상을 구분해야 한다.|
|배포 중 실행본 교체|이전 주소와 새 주소의 변화를 반영해야 한다.|

따라서 **필요한 기능의 이름**과 **그 기능이 현재 실행되는 위치**를 분리해 관리하는 방법이 필요하다.

#### 1-2. 서비스, 인스턴스, 프로젝트, 프로세스

처음에는 “서비스 하나를 네 번 실행한다”는 표현이 헷갈릴 수 있다. 무엇을 기준으로 하나와 여러 개를 세는지 구분하면 이해하기 쉽다.

|개념|의미|이번 학습의 예|
|---|---|---|
|프로젝트|소스 코드·설정·빌드 파일을 담은 작업 단위|`user-service` 프로젝트|
|서비스|같은 기능을 제공하는 논리적인 단위|사용자 정보를 제공하는 기능|
|인스턴스|서비스를 실제로 실행한 개별 실행본|60000번 포트의 실행본 하나|
|프로세스|운영체제에서 실행 중인 프로그램|`java`로 실행한 프로그램|
|PID|프로세스를 구분하는 운영체제의 번호|각 Java 프로세스의 번호|

카페로 생각하면 서비스는 **같은 메뉴를 제공하는 브랜드**, 인스턴스는 **실제로 손님을 받는 각 지점**에 가깝다.

하나의 `user-service` 프로젝트를 네 번 실행하면, 사용자 기능이라는 서비스는 한 종류이고 인스턴스는 네 개다. 이번 실습에서는 각 실행본이 별도의 Java 프로세스이며, 메모리와 실행 상태도 각각 가진다.

프로젝트를 네 벌 복사할 필요는 없다. **같은 코드나 같은 JAR을 서로 다른 실행 설정으로 실행**하면 된다.

#### 1-3. 접속 주소는 호스트·포트·경로로 나누어 읽는다

아래는 학습용 API에 접속하는 주소의 예다.

```text
http://127.0.0.1:60000/demo/instance
```

|부분|역할|쉬운 설명|
|---|---|---|
|`http`|통신 방식|어떤 방식으로 요청을 보내는가?|
|`127.0.0.1`|루프백 IP 주소|요청하는 쪽 자신의 컴퓨터|
|`60000`|포트|그 컴퓨터의 어느 서버 프로그램인가?|
|`/demo/instance`|요청 경로|서버 안의 어떤 기능을 호출하는가?|

`localhost`는 자기 컴퓨터를 가리키는 호스트 이름이다. 일반적인 로컬 실습에서는 `127.0.0.1`과 같은 목적에 사용한다. 다만 환경에 따라 IPv6 주소로 연결될 수 있다.

**포트는 같은 컴퓨터에서 실행 중인 네트워크 프로그램을 구분하는 번호**다. 컴퓨터가 건물이라면 포트는 그 안의 출입구 번호라고 생각할 수 있다.

|실행 위치|포트 사용 예|해석|
|---|---|---|
|같은 PC|`localhost:8080`, `localhost:8081`|실행본마다 포트를 다르게 사용한다.|
|서로 다른 서버|`my-server1:8080`, `my-server2:8080`|호스트가 다르므로 같은 포트 번호를 사용할 수 있다.|

이번 실습처럼 같은 주소·프로토콜의 포트를 사용하는 웹 서버를 중복 실행하면 충돌한다. 또한 다른 컴퓨터나 컨테이너의 `localhost`는 개발 PC가 아니라 **그 요청을 보내는 환경 자신**을 뜻한다.

#### 1-4. Service Registry와 Service Discovery

**Service Registry**는 서비스 이름, 인스턴스 ID, 호스트, 포트, 상태 등을 보관하는 등록 목록이다. **Service Discovery**는 이 정보를 이용해 필요한 서비스의 실제 실행 위치를 찾는 체계다.

비유하면 Registry는 **영업 중인 지점과 연락처를 적은 안내부**, Discovery는 **안내부에서 필요한 지점을 찾아 연락하는 과정**이다.

Eureka는 이 등록과 탐색을 지원하는 기술이다. Eureka Server가 목록을 관리하고, Eureka Client가 등록과 조회에 참여한다.

#### 1-5. Eureka·Load Balancer·Gateway가 맡는 일

|구성 요소|맡는 역할|답하는 질문|
|---|---|---|
|Eureka Server|서비스 등록 목록을 관리한다.|어떤 인스턴스가 어디에 있는가?|
|Eureka Client|자신을 등록하고 서비스 목록을 가져온다.|나를 어떻게 등록하고 다른 서비스를 어떻게 찾는가?|
|Load Balancer|여러 인스턴스 중 요청 대상을 선택한다.|이번 요청은 어느 실행본으로 보낼 것인가?|
|API Gateway|외부 요청을 적절한 내부 서비스로 라우팅한다.|이 요청은 어느 서비스가 처리해야 하는가?|

여기서 **Eureka Client는 프론트엔드나 웹 브라우저를 뜻하지 않는다.** `user-service`는 HTTP 요청을 받는 서버이면서, Eureka Server와 통신하는 클라이언트이기도 하다.

API Gateway는 다음 학습과 연결되는 진입점의 개념이다. Gateway 프로젝트 구성은 이번 범위에 포함하지 않는다.

#### 1-6. 서비스 등록부터 업무 요청까지

```text
Eureka Server 실행
    ↓ 등록을 받아 줄 공간이 준비된다
user-service 실행
    ↓ 이름·ID·주소·포트·상태를 등록한다
Eureka의 서비스 목록에 실행본이 기록된다
    ↓ 호출자가 목록을 가져와 사용한다
Load Balancer가 요청 대상 인스턴스를 선택한다
    ↓ 선택한 실제 호스트와 포트로 접속한다
user-service가 업무 요청을 처리하고 응답한다
```

등록 정보는 **업무 데이터를 올려놓는 것**과 다르다. Eureka에는 서비스의 실행 정보가 등록된다. 사용자 조회 요청 자체는 선택된 사용자 서비스가 처리한다.

등록과 목록 조회를 위한 통신, 실제 업무 요청을 위한 통신은 구분해야 한다. **Eureka Server 자체가 사용자 조회 요청을 대신 중계하는 프록시는 아니다.**

#### 1-7. Heartbeat와 캐시 때문에 반영 시점이 달라질 수 있다

등록한 실행본은 주기적으로 **“아직 실행 중이다”**라는 신호를 보낸다. 이를 heartbeat라고 한다. 일반적인 Eureka Client의 기본 heartbeat 주기는 30초다.

호출자는 등록 목록을 로컬에 보관하고 갱신할 수 있다. 이 캐시 덕분에 일반적인 Eureka Client 기반 호출은 매 업무 요청마다 Eureka 서버에 목록을 물어보지 않는다.

정상 종료 시에는 등록 해제를 시도한다. 강제 종료나 통신 단절에서는 서버가 상태를 판단하는 데 시간이 걸릴 수 있고, 캐시와 자기 보호 모드의 영향으로 표시가 남을 수도 있다.

따라서 대시보드의 정보와 실제 프로세스 상태가 항상 같은 순간에 바뀐다고 가정하지 않는다. **목록의 표시, 실행 로그, 실제 접속 결과를 함께 비교한다.**

> Service Discovery는 필요한 서비스를 찾는 과정이고, Load Balancing은 찾은 여러 실행본 중 요청 대상을 고르는 과정이다. 서비스 등록 정보와 업무 요청의 흐름을 구분하는 것이 출발점이다.

### 2. Eureka 서버와 사용자 서비스를 구성하기

서비스를 등록하고 찾는 원리를 알았다면, 이제 **목록을 관리할 서버**와 **그 목록에 들어갈 사용자 서비스**를 각각 준비한다.

#### 2-1. 두 프로젝트의 역할과 학습 환경

|프로젝트|역할|기본 실행 포트|핵심 의존성|
|---|---|---|---|
|`service-discovery`|Eureka Server|`8761`|Eureka Server Starter|
|`user-service`|사용자 기능의 서버이자 Eureka Client|`60000`|Eureka Client Starter, Spring Web|

|항목|이번 학습의 기준|
|---|---|
|Java / JDK|`21`|
|Spring Boot|`3.5.0`|
|Spring Cloud|`2025.0.0`|
|빌드 도구|Maven|
|패키징|JAR|

Spring Boot는 Spring 애플리케이션의 설정과 실행을 쉽게 만드는 기반이다. Spring Cloud는 서비스 탐색과 라우팅 등 분산 시스템에 필요한 기능을 제공하는 도구 모음이다. 그중 Spring Cloud Netflix Eureka를 사용한다.

Boot와 Cloud는 버전 번호 체계가 다르다. 숫자를 같게 맞추는 것이 아니라 **서로 호환되는 조합**을 사용해야 한다. 이 노트는 위 학습 환경을 기준으로 작성한다.

#### 2-2. JDK를 설치하는 것과 프로젝트에서 사용하는 것은 다르다

JDK는 Java 개발과 컴파일에 필요한 도구를 포함한다. JVM은 컴파일된 Java 프로그램을 실행하는 환경이다.

프로젝트가 Java 21을 사용하도록 설정되어 있는데 Project SDK가 17이면 버전 불일치가 발생할 수 있다. JDK 21을 설치한 뒤 프로젝트와 실행 설정이 그 JDK를 사용하는지도 확인해야 한다.

```bash
java -version
javac -version
mvn -v
```

|명령|확인할 내용|
|---|---|
|`java -version`|터미널에서 실행하는 Java 버전|
|`javac -version`|사용하는 Java 컴파일러 버전|
|`mvn -v`|Maven 버전과 Maven이 사용하는 Java 버전|

IntelliJ의 Project SDK, 실행 설정의 JRE, Maven 실행 JDK가 서로 다를 수 있다. 터미널에서 확인한 Java와 IDE에서 선택한 Java도 별도로 비교한다.

#### 2-3. Maven·Starter·BOM을 한 번에 연결하기

Maven은 Java 프로젝트의 의존성과 빌드를 관리한다. `pom.xml`에는 프로젝트 정보, 버전, 사용할 라이브러리와 빌드 플러그인을 적는다.

|용어|의미|이 구성에서의 역할|
|---|---|---|
|Dependency|프로그램이 사용하는 외부 라이브러리|Eureka 기능과 Spring Web을 추가한다.|
|Starter|특정 기능에 필요한 라이브러리 묶음|필요한 기능을 쉽게 구성한다.|
|BOM|함께 사용할 라이브러리 버전 조합의 목록|Spring Cloud 의존성의 버전을 관리한다.|
|Maven Plugin|빌드 과정에서 작업을 수행하는 도구|Spring Boot 실행과 JAR 패키징을 지원한다.|

`dependencies`는 **실제로 사용할 라이브러리**를 추가하는 곳이다. `dependencyManagement`는 **그 라이브러리를 사용할 때 적용할 버전**을 관리하는 곳이다.

BOM을 가져오는 것만으로 Eureka 기능이 추가되지는 않는다. 해당 Starter도 `dependencies`에 넣어야 한다.

#### 2-4. Eureka Server 프로젝트 만들기

IntelliJ의 새 Spring Boot 프로젝트에서 다음 정보를 기준으로 생성한다.

|항목|값|
|---|---|
|Name / Artifact|`service-discovery`|
|Group|`com.example`|
|Package|`com.example.servicediscovery`|
|Language|Java|
|Build Tool|Maven|
|Java / JDK|21|
|Packaging|Jar|
|핵심 의존성|Eureka Server|

**파일: `service-discovery/pom.xml`**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project>
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.5.0</version>
        <relativePath/>
    </parent>

    <groupId>com.example</groupId>
    <artifactId>service-discovery</artifactId>
    <version>1.0</version>
    <name>service-discovery</name>

    <properties>
        <java.version>21</java.version>
        <spring-cloud.version>2025.0.0</spring-cloud.version>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-starter-netflix-eureka-server</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>org.springframework.cloud</groupId>
                <artifactId>spring-cloud-dependencies</artifactId>
                <version>${spring-cloud.version}</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
        </dependencies>
    </dependencyManagement>

    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
```

이 예제의 Spring Boot 버전은 `parent`의 `version`, Cloud 버전은 `spring-cloud.version`과 BOM에서 결정된다. `spring-boot-maven-plugin`은 실행과 실행 가능한 JAR 패키징을 지원한다.

`spring-boot-starter-test`는 테스트 코드에서 사용하는 라이브러리이며, Eureka 서버 기능을 담당하는 의존성은 아니다.

**파일: `service-discovery/src/main/java/com/example/servicediscovery/ServiceDiscoveryApplication.java`**

```java
package com.example.servicediscovery;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.cloud.netflix.eureka.server.EnableEurekaServer;

@SpringBootApplication
@EnableEurekaServer
public class ServiceDiscoveryApplication {

    public static void main(String[] args) {
        SpringApplication.run(ServiceDiscoveryApplication.class, args);
    }
}
```

|애너테이션|역할|
|---|---|
|`@SpringBootApplication`|Spring Boot의 기본 설정과 실행 진입점을 표시한다.|
|`@EnableEurekaServer`|Eureka Server 기능을 활성화한다.|

의존성으로 필요한 라이브러리를 추가하고, 메인 클래스에서 서버 기능을 활성화하는 구성이 연결된다.

**파일: `service-discovery/src/main/resources/application.yml`**

```yaml
server:
  port: 8761

spring:
  application:
    name: service-discovery

eureka:
  client:
    register-with-eureka: false
    fetch-registry: false
```

이 서버는 **다른 Eureka 서버와 연결하지 않는 단독 서버**로 구성한다.

|설정|의미|
|---|---|
|`server.port: 8761`|Eureka 서버 자신의 웹 서버 포트|
|`spring.application.name`|애플리케이션 이름|
|`register-with-eureka: false`|서버 자신의 클라이언트 등록 동작을 끈다.|
|`fetch-registry: false`|서버 자신의 클라이언트 목록 조회 동작을 끈다.|

`register-with-eureka: false`는 **다른 서비스의 등록을 받지 않겠다는 뜻이 아니다.** Eureka Server 기능은 유지하면서, 자신이 클라이언트로 등록하려는 동작을 끄는 설정이다.

마찬가지로 `fetch-registry: false`는 서버의 등록 목록을 삭제하거나 조회 API를 끄는 설정이 아니다. 다른 Eureka의 목록을 가져오는 클라이언트 동작을 끈다.

Eureka 서버를 여러 개 연결하는 구성에서는 이 설정이 달라질 수 있다. 단독 실습의 설정을 모든 운영 구성의 절대 규칙으로 외우지 않는다.

#### 2-5. User Service 프로젝트 만들기

사용자 서비스는 HTTP 요청을 처리하면서 Eureka에 자신의 실행 정보를 등록한다.

|항목|값|
|---|---|
|Name / Artifact|`user-service`|
|Group|`com.example`|
|Package|`com.example.userservice`|
|Java / JDK|21|
|핵심 의존성|Eureka Discovery Client, Spring Web|

학습 자료에 선택된 DevTools는 개발 중 재시작 등을 돕고, Lombok은 반복되는 Java 코드를 줄인다. 아래 예제는 두 도구 없이도 핵심을 확인할 수 있도록 구성한다.

**파일: `user-service/pom.xml`**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project>
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.5.0</version>
        <relativePath/>
    </parent>

    <groupId>com.example</groupId>
    <artifactId>user-service</artifactId>
    <version>1.0</version>
    <name>user-service</name>

    <properties>
        <java.version>21</java.version>
        <spring-cloud.version>2025.0.0</spring-cloud.version>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-starter-netflix-eureka-client</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>org.springframework.cloud</groupId>
                <artifactId>spring-cloud-dependencies</artifactId>
                <version>${spring-cloud.version}</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
        </dependencies>
    </dependencyManagement>

    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
```

**파일: `user-service/src/main/java/com/example/userservice/UserServiceApplication.java`**

```java
package com.example.userservice;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.cloud.client.discovery.EnableDiscoveryClient;

@SpringBootApplication
@EnableDiscoveryClient
public class UserServiceApplication {

    public static void main(String[] args) {
        SpringApplication.run(UserServiceApplication.class, args);
    }
}
```

`@EnableDiscoveryClient`는 서비스 탐색 클라이언트 사용 의도를 나타낸다. **이번 버전 계열에서는 적절한 Client Starter와 설정으로 자동 등록되므로 필수 애너테이션은 아니다.** 학습 코드의 형태를 유지하기 위해 포함한다.

등록이 안 되는 경우 이 애너테이션의 유무만 검사하지 않는다. 의존성, 접속 주소, 활성 설정과 실행 로그를 확인해야 한다.

**파일: `user-service/src/main/resources/application.yml`**

```yaml
server:
  port: 60000

spring:
  application:
    name: user-service

eureka:
  client:
    service-url:
      defaultZone: http://127.0.0.1:8761/eureka/
    fetch-registry: true
    register-with-eureka: true
```

|설정|의미|
|---|---|
|`server.port: 60000`|사용자 서비스가 HTTP 요청을 받을 포트|
|`spring.application.name: user-service`|같은 기능의 실행본을 묶는 서비스 이름|
|`defaultZone`|등록과 조회를 위해 접속할 Eureka Server 주소|
|`fetch-registry: true`|다른 서비스의 등록 목록을 가져온다.|
|`register-with-eureka: true`|자신의 실행 정보를 Eureka에 등록한다.|

두 `true` 설정은 기본값이지만 동작을 분명히 보기 위해 명시한다. **자기 등록과 다른 서비스 목록 조회는 별개의 동작**이다.

`server.port`는 사용자 서비스 자신의 포트이고, `defaultZone`에 적는 `8761`은 접속할 Eureka 서버의 포트다. 서로 다른 애플리케이션의 포트를 지정하고 있다.

#### 2-6. YAML을 읽고 properties와 대응시키기

설정 파일의 기본 위치는 `src/main/resources`다. `application.properties`는 점으로 계층을 표현하고, `application.yml` 또는 `application.yaml`은 들여쓰기로 계층을 표현한다.

다음 properties 설정은 위 사용자 서비스 YAML과 대응한다.

```yaml
server.port=60000
spring.application.name=user-service
eureka.client.service-url.defaultZone=http://127.0.0.1:8761/eureka/
eureka.client.fetch-registry=true
eureka.client.register-with-eureka=true
```

형식을 바꾸려면 파일 확장자뿐 아니라 **파일 내용의 문법도 함께 바꿔야 한다.**

- YAML의 들여쓰기는 탭 대신 공백으로 맞춘다. 예제는 계층마다 2칸을 사용한다.
- 콜론 뒤에 공백을 둔다. 예: `port: 60000`.
- `server`, `spring`, `eureka`는 각각 최상위 항목이다.
- 같은 최상위 키를 여러 번 작성하지 말고 기존 블록에 합친다.
- `defaultZone`은 Map의 키이므로 대소문자를 유지한다. `default-zone`으로 바꾸지 않는다.
- 같은 위치의 properties와 YAML에 값이 중복되면 properties가 우선할 수 있다. 학습 단계에서는 한 형식으로 통일해 적용 값을 확인한다.

#### 2-7. 서버를 먼저 실행하고 사용자 서비스를 등록한다

```text
service-discovery 실행
    ↓ 8761번 포트의 대시보드를 확인한다
user-service 실행
    ↓ 60000번 포트의 웹 서버 시작을 확인한다
Eureka Client의 등록 로그를 확인한다
    ↓ 등록 목록 반영 후 새로고침한다
USER-SERVICE 그룹의 UP (1)을 확인한다
```

각 프로젝트의 `pom.xml`이 있는 폴더에서 다음 명령을 실행한다. 두 프로그램을 유지하려면 터미널도 따로 사용한다.

```bash
mvn spring-boot:run
```

대시보드는 `localhost:8761`의 기본 경로에서 확인한다. 사용자 서비스의 `defaultZone`은 같은 Eureka 서버의 `/eureka/` 경로를 사용한다.

|표시 또는 로그 예|읽는 방법|
|---|---|
|`No instances available`|등록된 인스턴스가 없다. 서버만 실행했다면 정상이다.|
|`Tomcat started on port 60000`|사용자 서비스의 실제 웹 서버 시작 포트|
|`registering service`|Eureka 등록을 진행하는 로그|
|`registration status: 204`|등록 요청 성공. 별도 응답 본문은 없다는 뜻이다.|
|`USER-SERVICE / UP (1)`|사용자 서비스 그룹의 UP 인스턴스 한 개|

서비스 이름이 대시보드에서 대문자로 표시되어도 별개의 서비스가 된 것은 아니다. 서버의 자기 등록을 껐으므로 `service-discovery` 자체가 목록에 보이지 않아도 이 구성에서는 정상이다.

> Eureka Server에는 목록 관리 기능을, user-service에는 등록할 실행 정보를 설정한다. 설정의 `false`와 `true`를 외우기 전에 **어느 애플리케이션의 어떤 클라이언트 동작을 지정하는지** 먼저 구분한다.

### 3. 같은 서비스를 여러 번 실행하고 포트를 바꾸기

서비스 하나가 등록되었다면, 이제 같은 기능의 실행본을 더 늘릴 수 있다. 이때 달라지는 것은 프로젝트의 기능이 아니라 **각 프로세스의 실행 환경과 접속 포트**다.

#### 3-1. Scale Up과 Scale Out

|확장 방식|늘리는 것|예|
|---|---|---|
|Scale Up · 수직 확장|한 서버의 CPU·메모리 등 성능|같은 서버의 메모리를 늘린다.|
|Scale Out · 수평 확장|같은 기능을 제공하는 실행본이나 서버 수|`user-service`를 여러 개 실행한다.|

이번 다중 실행은 수평 확장의 기본 형태를 확인하는 실습이다. 다만 한 PC에서 실행본 수를 늘린 것만으로 처리량 증가가 보장되지는 않는다. PC 자원, 데이터베이스, 실제 요청 분산 방식도 영향을 준다.

#### 3-2. Maven 실행과 JAR 실행의 차이

**빌드**는 소스 코드를 컴파일하고 필요한 파일을 모아 결과물을 만드는 과정이다. 컴파일은 Java 소스 코드를 실행 환경이 사용할 수 있는 클래스 파일로 변환하는 단계다.

**JAR**은 Java 클래스와 리소스를 담는 패키지 파일이다. 이번 구성에서는 Spring Boot 플러그인을 사용해 실행 가능한 JAR을 만든다.

|방식|준비물|사용하는 명령|하는 일|
|---|---|---|---|
|프로젝트에서 바로 실행|프로젝트·의존성·빌드 환경|`mvn spring-boot:run`|프로젝트를 이용해 서버를 실행한다.|
|JAR 만들기|프로젝트·빌드 환경|`mvn clean package`|실행 결과물을 만든다.|
|만든 JAR 실행|실행 가능한 JAR·맞는 Java 환경|`java -jar 파일.jar`|패키지 파일로 서버를 실행한다.|

`package`가 끝났다고 서버가 계속 실행되는 것은 아니다. **파일을 만드는 작업과 그 파일을 실행하는 작업을 구분한다.**

Maven 명령은 기본적으로 해당 프로젝트의 `pom.xml`이 있는 폴더에서 실행한다. `java -jar`는 현재 폴더를 기준으로 실행할 JAR 경로를 찾아간다.

#### 3-3. Maven 설치와 Wrapper

프로젝트에 `mvnw`와 `mvnw.cmd`가 있으면 Maven Wrapper를 사용할 수 있다. 프로젝트가 지정한 Maven을 받아 실행하므로 전역 Maven이 없어도 사용할 수 있다. 최초 실행에는 다운로드를 위한 네트워크 연결이 필요할 수 있다.

macOS · Linux · Git Bash:

```bash
./mvnw -v
./mvnw spring-boot:run
```

Windows PowerShell:

```powershell
.\mvnw.cmd -v
.\mvnw.cmd spring-boot:run
```

전역 Maven을 사용하는 경우에는 `mvn -v`로 준비 여부를 확인한다. 아래 `mvn` 명령은 환경에 따라 `./mvnw` 또는 `.\mvnw.cmd`로 바꿔 사용한다. Wrapper 파일이 없는 프로젝트에서는 Wrapper 명령을 사용할 수 없다.

#### 3-4. 다중 실행 전에 JAR을 먼저 준비한다

사용자 서비스의 실행본을 잠시 종료한 뒤 `user-service` 폴더에서 빌드한다. Eureka 서버는 유지한다.

```bash
mvn clean package
```

|작업|의미|
|---|---|
|`clean`|이전 빌드 결과를 정리한다. 일반적으로 `target`을 삭제한다.|
|`package`|컴파일·테스트 등의 필요한 단계를 거쳐 JAR 결과물을 만든다.|

`package`가 앞선 컴파일 단계를 포함하므로 기본 실습에서는 `clean compile package`보다 `clean package`로 충분하다.

이 노트의 `pom.xml`은 `artifactId`가 `user-service`, 프로젝트 `version`이 `1.0`이다. 따라서 기본 결과물은 다음 경로다.

```bash
target/user-service-1.0.jar
```

프로젝트 버전이 `0.0.1-SNAPSHOT`이면 기본 파일 이름은 `user-service-0.0.1-SNAPSHOT.jar`다. `finalName` 등을 따로 설정했다면 이름이 달라질 수 있으므로 실제 파일을 확인한다.

macOS · Linux · Git Bash:

```bash
ls target/*.jar
```

Windows PowerShell:

```powershell
Get-ChildItem .\target\*.jar
```

#### 3-5. 첫 번째 실행본: 기본 포트 60000

빌드 후 기본 사용자 서비스를 다시 실행한다. YAML의 포트는 `60000`으로 유지한다.

```bash
mvn spring-boot:run
```

실행 로그에서 실제 포트가 `60000`인지 확인한다. 이 프로세스를 유지하면서 다른 실행본을 추가한다.

#### 3-6. 두 번째 실행본: IntelliJ에서 60001

1. 실행 설정 목록에서 **Edit Configurations**를 연다.
2. 기존 `UserServiceApplication` 설정을 복제한다.
3. 이름을 `UserServiceApplication-60001`처럼 구분한다.
4. 필요하면 **Modify options**에서 **VM options**를 표시한다.
5. VM options에 아래 값을 넣는다.
6. 저장한 뒤 복제한 설정으로 추가 실행한다.

```bash
-Dserver.port=60001
```

UI의 버튼 이름과 위치는 IntelliJ 버전에 따라 다를 수 있다. 기존 프로세스가 중지된다면 다중 실행 허용 옵션도 확인한다.

YAML의 공통 기본값을 바꾸지 않고 **이번 실행에만 다른 값을 전달**하므로 첫 번째 실행본은 60000, 두 번째 실행본은 60001로 동작할 수 있다.

#### 3-7. 세 번째 실행본: Maven에서 60002

새 터미널의 `user-service` 폴더에서 실행한다.

```bash
mvn spring-boot:run "-Dspring-boot.run.jvmArguments=-Dserver.port=60002"
```

이 명령은 두 층으로 읽는다.

|인자|전달받는 대상|역할|
|---|---|---|
|`-Dspring-boot.run.jvmArguments=...`|Maven의 Spring Boot 플러그인|실행할 Java 프로그램에 줄 JVM 옵션을 지정한다.|
|`-Dserver.port=60002`|애플리케이션 JVM|Spring Boot가 읽을 포트 설정을 전달한다.|

즉 **“Maven이 실행할 Java 프로그램의 포트를 60002로 지정해 달라”**는 의미다.

애플리케이션 인자로 전달하는 방법도 있다.

```bash
mvn spring-boot:run "-Dspring-boot.run.arguments=--server.port=60002"
```

두 방식 중 하나를 선택하면 된다. `mvn spring-boot:run -Dserver.port=60002`만으로는 별도 프로세스로 실행되는 애플리케이션에 값이 전달된다고 보장할 수 없다.

#### 3-8. 네 번째 실행본: JAR을 60003으로 실행

앞에서 만든 JAR을 새 터미널에서 실행한다.

```bash
java -Dserver.port=60003 -jar ./target/user-service-1.0.jar
```

Spring Boot 명령행 인자를 사용하는 방식도 가능하다.

```bash
java -jar ./target/user-service-1.0.jar --server.port=60003
```

|부분|의미|
|---|---|
|`java`|Java 프로그램을 실행한다.|
|`-Dserver.port=60003`|JVM의 시스템 속성을 지정한다.|
|`-jar`|JAR 파일을 실행하는 방식을 지정한다.|
|`./target/user-service-1.0.jar`|실제 실행할 파일 경로다.|
|`--server.port=60003`|프로그램에 전달되어 Spring Boot가 읽는 인자다.|

JVM의 `-D` 옵션은 `-jar` 앞에 두는 표준적인 형태로 정리한다. JAR 뒤의 `--` 설정과 역할을 구분하기 쉽다.

다음과 같이 **JAR 파일 뒤에 `-Dserver.port`를 두면** 일반적인 Spring Boot 포트 설정 방식으로 적용되지 않는다.

```bash
# 포트 설정 방법으로 사용하지 않는 예
java -jar ./target/user-service-1.0.jar -Dserver.port=60003
```

이 위치의 `-D`는 JVM 옵션이 아니라 `main`에 전달되는 애플리케이션 인자가 되기 때문이다.

#### 3-9. 네 개의 실행본을 어떻게 읽는가?

|실행본|실행 방식|실제 포트|
|---|---|---|
|1|기본 프로젝트 실행|`60000`|
|2|IntelliJ의 복제한 실행 설정|`60001`|
|3|Maven에 JVM 옵션 전달|`60002`|
|4|만든 JAR 실행|`60003`|

네 실행본의 등록이 반영되면 하나의 `USER-SERVICE` 그룹 아래 **`UP (4)`** 형태를 확인할 수 있다. 이는 네 종류의 서비스가 아니라 **같은 서비스의 UP 인스턴스 네 개**라는 의미다.

기본 ID가 호스트·서비스 이름·포트를 조합하면, 실행별 포트가 다르므로 ID도 구분된다.

같은 JAR을 포트별로 새로 만들 필요는 없다. 실행 옵션만 다르게 줄 때는 기존 JAR을 사용하고, 소스나 JAR 내부 설정이 바뀌었을 때 다시 빌드한다.

#### 3-10. JVM 옵션과 프로그램 인자는 넣는 위치도 다르다

|구분|값의 형태|IntelliJ 입력 위치|
|---|---|---|
|JVM 시스템 속성|`-Dserver.port=60001`|VM options|
|Spring Boot 명령행 인자|`--server.port=60001`|Program arguments|

Spring Boot는 여러 곳에서 설정을 읽는다. 이번 실습에 필요한 일반적인 우선순위를 **낮은 쪽부터** 추리면 다음과 같다.

```text
application.yml 등의 설정 파일
    ↓ 실행 환경에서 덮어쓸 수 있다
OS 환경 변수: SERVER_PORT
    ↓
JVM 시스템 속성: -Dserver.port
    ↓
Spring Boot 명령행 인자: --server.port
```

예를 들어 YAML이 `60000`이고 VM options가 `60001`이면 실행 옵션의 `60001`이 적용된다. 같은 실행에서 `--server.port=60002`까지 전달하면 기본 설정에서는 명령행 인자 `60002`가 우선한다.

프로필과 테스트 설정 등까지 포함한 전체 우선순위는 더 세분화된다. 여기서는 **공통 기본값과 실행별 덮어쓰기**를 이해하는 것이 핵심이다.

포트를 바꿨는데 기대한 값으로 실행되지 않으면 다음 위치를 확인한다.

- IntelliJ의 VM options와 Program arguments
- 터미널 명령의 `-D`와 `--` 옵션
- `SERVER_PORT` 환경 변수
- 활성 프로필의 설정 파일과 남아 있는 properties
- 실행한 JAR에 포함된 이전 설정

최종 적용 값을 판단할 때는 **실행 로그의 실제 웹 서버 포트**를 확인한다.

#### 3-11. 테스트를 건너뛰는 옵션의 차이

```bash
# 테스트 실행을 건너뛰고 패키징
mvn clean package -DskipTests

# 테스트 컴파일과 실행을 모두 건너뛰고 패키징
mvn clean package "-Dmaven.test.skip=true"
```

|옵션|테스트 컴파일|테스트 실행|기억할 점|
|---|---|---|---|
|`-DskipTests`|수행|생략|테스트 코드의 컴파일 오류는 남을 수 있다.|
|`-Dmaven.test.skip=true`|생략|생략|테스트 컴파일 단계까지 생략한다.|

이는 표준 Maven Compiler·Surefire·Failsafe 구성 기준이다. 별도 테스트 플러그인이 있는 프로젝트는 그 플러그인의 설정도 확인한다.

테스트 생략은 빌드 과정의 선택이며 실제 API 응답 검사를 대신하지 않는다.

#### 3-12. PowerShell과 Git Bash의 파일 경로

Windows PowerShell:

```powershell
java -Dserver.port=60003 -jar .\target\user-service-1.0.jar
```

macOS · Linux · Git Bash:

```bash
java -Dserver.port=60003 -jar ./target/user-service-1.0.jar
```

Git Bash에서는 백슬래시가 다음 문자를 이스케이프할 수 있다. PowerShell 형식의 경로를 그대로 넣으면 슬래시가 사라져 다른 파일 이름으로 전달될 수 있다.

예를 들어 `.\user-service-0.0.1-SNAPSHOT.jar`가 `.user-service-0.0.1-SNAPSHOT.jar`로 전달되면 실제 파일을 찾지 못한다. Windows에서도 Git Bash를 사용한다면 `./` 경로를 사용하는 편이 명확하다.

포트 설정 이름도 정확히 적는다. `server:port`는 Spring Boot가 기대하는 `server.port`와 다른 이름이다.

> 같은 서비스를 늘리는 기본 방법은 같은 코드를 여러 프로세스로 실행하는 것이다. **기본 설정, 실행별 옵션, 실제 포트**를 나누어 보면 실행 방식이 달라도 같은 원리로 이해할 수 있다.

### 4. 랜덤 포트와 인스턴스 ID를 함께 이해하기

고정 포트 방식은 실행본마다 포트를 직접 정해야 한다. 이 부담을 줄이려면 사용 가능한 포트를 자동 할당받을 수 있다. 하지만 **접속할 포트가 달라지는 것과 등록 식별자가 달라지는 것은 별개의 문제**다.

#### 4-1. `server.port: 0`의 의미

```yaml
server:
  port: 0
```

이 설정은 0번 포트로 서비스하라는 뜻이 아니다. 웹 서버를 시작할 때 운영체제가 사용 가능한 포트를 할당하도록 요청한다.

|항목|첫 번째 실행본 예|두 번째 실행본 예|
|---|---|---|
|YAML의 설정값|`0`|`0`|
|실제 할당 포트|`53308`|`53317`|

실제 포트는 실행할 때 달라질 수 있다. 브라우저로 확인할 때도 `localhost:0`이 아니라 **로그에서 확인한 실제 포트**를 사용해야 한다.

```text
Tomcat started on port 53308
Updating port to 53308
```

첫 줄은 실제 웹 서버의 시작 포트를 보여 준다. 두 번째 줄은 등록 정보에 실제 포트가 반영되는 상황을 보여 준다. 문구와 출력 순서는 버전·환경에 따라 달라질 수 있다.

설정값 `server.port`를 그대로 읽으면 `0`이 나올 수 있다. 코드에서 실제 포트를 확인하려면 **서버가 시작된 이후 웹 서버의 정보를 읽어야 한다.**

#### 4-2. 인스턴스 ID와 접속 정보는 역할이 다르다

|값|답하는 질문|예|
|---|---|---|
|서비스 이름|어떤 기능의 그룹인가?|`user-service`|
|인스턴스 ID|그 그룹의 어느 실행본인가?|`user-service:4ab8c...`|
|호스트·실제 포트|어디로 접속해야 하는가?|`127.0.0.1:53308`|

인스턴스 ID는 실행본을 구분하는 문자열이다. HTTP 주소 자체가 아니며, ID 안에 포트 번호가 반드시 들어갈 필요도 없다. 실제 연결 정보는 등록 메타데이터에 따로 들어간다.

메타데이터는 호스트·포트·상태 URL처럼 인스턴스에 관한 부가 정보다. 서비스의 업무 데이터와는 다르다.

#### 4-3. 실제 포트가 다른데 왜 하나의 인스턴스로 보이는가?

Spring Cloud Eureka의 기본 인스턴스 ID는 대체로 다음 값을 조합한다.

```properties
${spring.cloud.client.hostname}:${spring.application.name}:${spring.application.instance_id:${server.port}}
```

읽는 방법은 **호스트 + 서비스 이름 + 실행별 ID 또는 설정 포트**다. 별도 실행별 ID가 없으면 `server.port` 값을 구분값으로 사용할 수 있다.

이번 랜덤 포트 실습에서는 같은 호스트, 같은 서비스 이름, 같은 설정값 `0`으로 ID가 구성될 수 있다.

|항목|실행본 A|실행본 B|
|---|---|---|
|서비스 이름|`user-service`|`user-service`|
|설정 포트|`0`|`0`|
|실제 포트 예|`53308`|`53317`|
|겹치는 ID 예|`호스트:user-service:0`|`호스트:user-service:0`|

실제 접속 포트는 달라도 같은 서비스 그룹 안에서 등록 ID가 같으면, 두 실행본을 별도 인스턴스로 구분하지 못할 수 있다.

```text
두 실행본의 server.port 설정값이 모두 0
    ↓ 기본 ID가 같은 값으로 구성될 수 있다
같은 서비스 그룹에 같은 인스턴스 ID로 등록
    ↓ 별도 실행본으로 구분되지 않는다
여러 프로세스인데 대시보드에는 UP (1)로 보일 수 있다
```

**같은 서비스 이름 때문에 그룹이 하나인 것은 정상이다.** 해결할 것은 실행본 수에 비해 인스턴스가 적게 구분되는 ID 문제다.

서비스 이름을 실행마다 바꾸면 서로 다른 서비스 그룹이 된다. 목표는 이름을 다르게 만드는 것이 아니라 **같은 이름 아래 고유한 ID로 여러 실행본을 등록하는 것**이다.

#### 4-4. 랜덤 포트 실습용 전체 설정

사용자 서비스의 기존 YAML을 다음 설정으로 교체한다. Eureka 서버의 YAML은 유지한다.

**파일: `user-service/src/main/resources/application.yml`**

```yaml
server:
  port: 0

spring:
  application:
    name: user-service

eureka:
  instance:
    instance-id: "${spring.application.name}:${spring.application.instance_id:${random.value}}"
  client:
    service-url:
      defaultZone: http://127.0.0.1:8761/eureka/
    fetch-registry: true
    register-with-eureka: true
```

`eureka.instance.instance-id`는 Eureka에 등록할 실행본의 식별자다. `instanceId`와 같은 설정을 YAML의 하이픈 표기로 작성한 형태다.

핵심 표현을 나누어 읽는다.

```text
${spring.application.name}
    → 설정된 서비스 이름을 사용한다.

${spring.application.instance_id:${random.value}}
    → 실행별 instance_id가 있으면 그 값을 사용한다.
    → 없으면 random.value를 사용한다.
```

`${...}`는 다른 설정값을 채워 넣는 **placeholder**다. `${설정이름:기본값}`에서 콜론은 설정이 없을 때 사용할 기본값을 뜻한다. 두 표현 사이의 바깥 콜론은 문자열을 구분하는 문자다.

설명용 ID 결과:

```text
USER-SERVICE 그룹

인스턴스 A: user-service:4ab8c...
인스턴스 B: user-service:9f1d2...
```

같은 이름으로 묶이면서 실행본마다 등록 ID가 구분된다. ID에 포트가 표시되지 않아도 실제 포트는 메타데이터에 반영된다.

더 짧게 작성하는 대안은 다음과 같다.

```yaml
eureka:
  instance:
    instance-id: "${spring.application.name}:${random.uuid}"
```

`random.uuid`는 UUID 형식의 랜덤 식별값을 제공한다. 일반적인 JVM 기반 로컬 실습에서 실행별 등록 ID를 구분하는 대안이며, 비밀번호나 인증 토큰을 의미하지 않는다. 위 조각을 사용한다면 기존 `eureka.instance`에 합쳐 넣고 ID 설정을 중복해서 남기지 않는다.

#### 4-5. 재현할 때 확인할 순서

1. 고정 포트의 사용자 서비스 실행본들을 종료한다.
2. 사용자 서비스 YAML을 랜덤 포트 설정으로 바꾼다.
3. VM options·Program arguments·환경 변수에 남은 포트 지정 값을 제거한다.
4. 서로 다른 터미널에서 사용자 서비스를 두 번 실행한다.
5. 각 실행 로그에서 실제 포트를 기록한다.
6. 대시보드에서 새로 등록된 ID가 서로 다른지 비교한다.

```bash
mvn spring-boot:run
```

|확인 대상|기대하는 형태|
|---|---|
|서비스 그룹|`USER-SERVICE` 하나|
|실제 포트|실행별로 할당된 다른 포트|
|인스턴스 ID|실행별로 구분되는 ID|
|등록 상태|새 실행본 두 개가 반영된 `UP (2)`|

이전 실행본의 등록 정보가 남아 있으면 개수가 잠시 다르게 보일 수 있다. 현재 프로세스의 ID·포트와 목록을 비교한다.

JAR 방식이라면 YAML을 바꾼 뒤 다시 빌드한다. 이전 JAR을 실행하면 그 안의 고정 포트 설정이 사용될 수 있다.

```bash
mvn clean package
java -jar ./target/user-service-1.0.jar
```

다른 터미널에서 같은 JAR을 다시 실행한다. `-Dserver.port=60001` 같은 기존 옵션을 붙이면 YAML의 랜덤 포트 설정보다 그 옵션이 우선할 수 있다.

> `port: 0`은 빈 포트 할당을 요청하고, `instance-id`는 실행본을 구분한다. **포트 충돌과 등록 ID 충돌을 따로 해결해야** 같은 이름의 여러 인스턴스를 올바르게 확인할 수 있다.

### 5. 서비스 등록·API 응답·요청 분산을 따로 확인하기

인스턴스가 목록에 보이는 것까지 확인했다면, 이제 **그 표시가 무엇을 보장하는지** 이해해야 한다. 등록 성공과 업무 API의 정상 동작, 실제 요청 분산은 서로 다른 확인 단계다.

#### 5-1. 대시보드를 읽는 기준

|표시|의미|혼동하지 않을 점|
|---|---|---|
|`USER-SERVICE`|서비스 그룹 이름|실행본마다 별도 그룹을 만들 필요는 없다.|
|`UP (1)`|그룹 안에 UP 상태의 인스턴스 한 개|프로젝트 수를 표시하는 것이 아니다.|
|`UP (4)`|그룹 안에 UP 상태의 인스턴스 네 개|업무 서비스가 네 종류라는 뜻은 아니다.|
|`호스트:user-service:60000`|인스턴스를 구분하는 ID 예|HTTP 주소 자체는 아니다.|
|`user-service:랜덤값`|고유 ID를 지정한 예|포트가 표시되지 않아도 연결 정보는 따로 있다.|

대시보드의 다른 칸도 다음 기준으로 읽는다.

|영역|용도|
|---|---|
|AMIs|AWS 이미지 관련 표시다. 로컬의 `n/a`만으로 오류라고 판단하지 않는다.|
|Availability Zones|가용 영역 관련 표시다. 이 칸이 있다고 여러 클라우드 영역에 배포했다는 뜻은 아니다.|
|DS Replicas|Eureka 서버의 복제·피어 관련 영역이다. 업무 서비스 목록과 구분한다.|

이번 학습에서는 **Instances currently registered with Eureka** 영역의 서비스 이름, ID, 상태와 실제 접속 포트를 중심으로 확인한다.

#### 5-2. `UP`과 실제 기능 정상 여부

기본 설정에서 `UP`은 Eureka의 등록 상태다. 별도 헬스 체크 연동 없이 데이터베이스 오류나 특정 API의 실패까지 모두 검사해 상태를 바꾸는 것은 아니다.

|확인 단계|확인할 것|알 수 있는 범위|
|---|---|---|
|등록 확인|Eureka의 인스턴스 목록|실행 정보가 등록되었는가?|
|HTTP 확인|실제 포트의 API 응답|해당 서버가 요청을 처리하는가?|
|업무 확인|필요한 기능의 응답 내용|사용자 조회 등 업무 로직이 올바른가?|
|분산 확인|이름 기반 호출의 대상 변화|여러 인스턴스가 선택되는가?|

예를 들어 `UP (2)`가 보여도 브라우저에서 `localhost:60000`으로 직접 요청하면 그 실행본으로 간다. 등록만으로 브라우저 요청의 목적지가 자동 변경되는 것은 아니다.

#### 5-3. 인스턴스 링크의 `/actuator/info`가 404인 이유

학습 자료에서는 등록된 인스턴스 링크로 `/actuator/info`에 접속했을 때 404 화면을 볼 수 있다.

**HTTP 404**는 요청한 경로의 처리 대상이나 리소스를 찾지 못했다는 의미다. Spring Boot의 기본 오류 화면인 **Whitelabel Error Page**는 별도 오류 화면이 없을 때 표시될 수 있다.

Eureka는 상태 페이지 URL 같은 메타데이터를 표시할 수 있지만, 그 경로의 API를 사용자 서비스에 자동 구현하지는 않는다.

|상태|의미|
|---|---|
|Eureka 등록 성공|서비스 실행 정보가 목록에 들어갔다.|
|`/actuator/info` 성공|그 경로의 Actuator 기능을 실제로 제공한다.|
|`/actuator/info`의 404|기능이 없거나 노출·경로 설정이 맞지 않을 수 있다.|

따라서 등록 상태와 URL 응답은 따로 확인한다. 해당 주소의 오류 응답이 있다는 것은 HTTP 서버에 접속했다는 단서지만, 필요한 기능 전체가 정상이라는 뜻은 아니다.

#### 5-4. Actuator로 상태 정보를 확인하기 — 추가 확인 예제

Actuator는 Spring Boot 애플리케이션의 상태와 운영 정보를 제공하는 기능 모음이다. `health`는 상태 확인에, `info`는 설정된 애플리케이션 정보 확인에 사용한다.

사용자 서비스 `pom.xml`의 기존 `dependencies` 안에 추가한다.

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

기존 사용자 서비스 YAML에 다음 **최상위 설정**을 추가한다.

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info
  info:
    env:
      enabled: true

info:
  app:
    name: user-service
    description: Service Discovery learning example
```

`management.endpoints.web.exposure.include`는 웹에서 접근할 엔드포인트를 지정한다. `management.info.env.enabled`는 `info` 속성에 작성한 정보를 제공하도록 설정한다.

모든 관리 엔드포인트가 기본으로 웹에 노출되는 것은 아니다. `info`가 사용 가능해도 제공할 데이터가 없으면 정상 응답이 빈 JSON 객체로 보일 수 있다.

기본 예제의 실제 포트가 60000이라면 다음 요청 경로를 확인한다.

```text
localhost:60000/actuator/health
localhost:60000/actuator/info
```

랜덤 포트라면 60000을 실제 할당 포트로 바꾼다.

Eureka에 표시할 상태 페이지 경로를 명시적으로 맞추려면 아래 항목을 **기존 `eureka.instance`에 합친다.**

```yaml
eureka:
  instance:
    status-page-url-path: /actuator/info
    health-check-url-path: /actuator/health
```

위 설정은 표시 경로를 맞추는 조각이다. 기존 `instance-id` 등을 유지하고 `eureka` 키를 중복해서 만들지 않는다.

이 경로 지정만으로 Actuator가 추가되거나 health 결과의 Eureka 상태 전파가 활성화되는 것은 아니다. **Actuator 응답과 Eureka 등록 상태의 연동도 별도의 구성 문제**다.

#### 5-5. 실제 응답한 실행본을 구분하기 — 추가 확인 예제

등록 목록의 표시를 넘어 어느 프로세스가 요청을 처리했는지 확인하려면, 실제 포트와 PID를 반환하는 작은 API를 만들 수 있다.

**파일: `user-service/src/main/java/com/example/userservice/InstanceController.java`**

```java
package com.example.userservice;

import java.util.Map;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.web.context.WebServerApplicationContext;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class InstanceController {

    private final WebServerApplicationContext context;
    private final String serviceName;

    public InstanceController(
            WebServerApplicationContext context,
            @Value("${spring.application.name}") String serviceName) {
        this.context = context;
        this.serviceName = serviceName;
    }

    @GetMapping("/demo/instance")
    public Map<String, Object> instance() {
        return Map.of(
                "service", serviceName,
                "port", context.getWebServer().getPort(),
                "pid", ProcessHandle.current().pid()
        );
    }
}
```

이 API는 실행본의 이름·실제 포트·PID를 반환한다.

|코드|역할|
|---|---|
|`@RestController`|메서드 결과를 HTTP 응답 본문으로 반환한다.|
|`@GetMapping("/demo/instance")`|해당 경로의 GET 요청을 처리한다.|
|생성자의 `@Value`|설정된 서비스 이름을 받는다.|
|`getWebServer().getPort()`|실행 중인 웹 서버의 실제 포트를 읽는다.|
|`ProcessHandle.current().pid()`|현재 Java 프로세스의 PID를 읽는다.|
|`Map<String, Object>`|이름이 있는 여러 타입의 값을 응답에 담는다.|

생성자에서는 웹 서버 컨텍스트 객체를 받아 저장하고, **API 요청이 들어온 시점에 실제 포트를 읽는다.** `server.port: 0`의 설정값을 반환하는 코드와 다르다.

일반 Bean 생성 시점에는 웹 서버가 아직 시작되지 않았을 수 있다. `${local.server.port}`를 일반 애플리케이션의 초기 생성 단계에 바로 주입하기보다, 시작 이후의 서버 정보와 읽는 시점을 구분한다.

아래는 설명용 응답이다. 항목의 출력 순서는 달라질 수 있다.

```json
{
  "service": "user-service",
  "port": 60000,
  "pid": 12345
}
```

각 실제 포트의 `/demo/instance`를 호출해 `port`와 `pid`를 비교한다. 이는 **각 인스턴스의 HTTP 응답 확인**이며, 아직 이름 기반 분산 호출을 확인한 것은 아니다.

#### 5-6. 이름으로 호출할 때 LoadBalancer가 대상을 선택한다

Spring Cloud LoadBalancer는 호출하는 애플리케이션 쪽에서 대상 인스턴스를 선택하는 **클라이언트 측 부하 분산**을 지원한다.

기본 구현은 라운드 로빈인 `RoundRobinLoadBalancer`다. 여러 대상을 돌아가며 선택하는 방식이지만, 목록 순서·캐시·호출자의 선택 위치 등에 따라 실제 응답 순서는 달라질 수 있다. 포트가 작은 순서로 반드시 선택된다고 이해하지 않는다.

이 구성의 `user-service`는 일반 DNS 주소가 아니라 **논리적인 서비스 이름**이다. 일반 브라우저가 Eureka를 조회해 자동 해석하는 이름은 아니다.

```text
호출자가 user-service라는 이름으로 요청한다
    ↓ Discovery Client의 인스턴스 목록을 사용한다
LoadBalancer가 실행본 하나를 선택한다
    ↓ 실제 호스트와 포트로 요청을 보낸다
선택된 실행본의 응답이 호출자에게 돌아온다
```

#### 5-7. 이름 기반 HTTP 클라이언트 만들기 — 추가 확인 예제

기존 사용자 서비스 `pom.xml`의 `dependencies` 안에 LoadBalancer Starter를 추가한다. Eureka Client와 Spring Web은 유지한다.

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-loadbalancer</artifactId>
</dependency>
```

**파일: `user-service/src/main/java/com/example/userservice/LoadBalancerConfig.java`**

```java
package com.example.userservice;

import org.springframework.cloud.client.loadbalancer.LoadBalanced;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.client.RestClient;

@Configuration
public class LoadBalancerConfig {

    @Bean
    @LoadBalanced
    public RestClient.Builder loadBalancedRestClientBuilder() {
        return RestClient.builder();
    }
}
```

`RestClient`는 다른 HTTP 서버로 요청을 보내는 Spring의 도구다. 위 코드에서 Builder를 만들고, 이름 기반 대상 선택을 적용한다.

|애너테이션|의미|
|---|---|
|`@Configuration`|Spring이 사용할 객체의 구성 방법을 정의한다.|
|`@Bean`|반환한 객체를 Spring이 관리하게 한다.|
|`@LoadBalanced`|이 Builder를 사용하는 호출에 서비스 이름 기반 대상 선택을 연결한다.|

여기서 **Bean은 Spring이 생성과 사용을 관리하는 객체**다. 일반 RestClient에 서비스 이름만 적는 것으로는 부족하며, Discovery Client·LoadBalancer·HTTP 클라이언트 구성이 함께 연결되어야 한다.

#### 5-8. 분산 호출을 확인하는 API — 추가 확인 예제

**파일: `user-service/src/main/java/com/example/userservice/LoadBalancingDemoController.java`**

```java
package com.example.userservice;

import org.springframework.cloud.client.loadbalancer.LoadBalanced;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.client.RestClient;

@RestController
public class LoadBalancingDemoController {

    private final RestClient restClient;

    public LoadBalancingDemoController(@LoadBalanced RestClient.Builder builder) {
        this.restClient = builder.build();
    }

    @GetMapping("/demo/load-balanced")
    public String loadBalancedCall() {
        return restClient.get()
                .uri("http://user-service/demo/instance")
                .retrieve()
                .body(String.class);
    }
}
```

이 예제는 별도 호출자 프로젝트를 추가하지 않고 사용자 서비스 안에 호출자 역할도 넣는다. 실제 서비스에서는 이 로직을 주문 서비스나 Gateway 쪽에 배치할 수 있다.

동작을 두 요청으로 나누어 읽는다.

|요청|목적지|역할|
|---|---|---|
|브라우저의 첫 요청|지정한 포트의 `/demo/load-balanced`|확인 API를 호출한다.|
|해당 서버가 보내는 내부 요청|이름 기반 `/demo/instance`|LoadBalancer가 고른 실행본의 정보를 가져온다.|

`/demo/load-balanced`가 다시 자신을 반복 호출하는 구조는 아니다. `/demo/instance`는 포트와 PID를 반환하고 끝난다. 선택 대상이 자기 인스턴스가 되는 경우도 가능하다.

#### 5-9. 분산 호출에서 확인할 결과

1. 확인용 코드와 의존성을 반영한 실행본을 두 개 이상 실행한다.
2. 대시보드에서 서비스 이름은 같고 ID는 다른지 확인한다.
3. 각 실제 포트의 `/demo/instance`가 응답하는지 확인한다.
4. 호출자가 등록 목록을 가져올 시간을 준다.
5. **하나의 고정된 포트**에서 `/demo/load-balanced`를 반복 호출한다.

```text
호출 주소 예: localhost:60000/demo/load-balanced

첫 번째 응답 예: port 60000 / pid 12345
다른 요청의 응답 예: port 60001 / pid 12346
```

브라우저는 계속 60000번 실행본으로 요청한다. 그 실행본이 내부에서 보내는 두 번째 요청의 대상이 달라지는 것이다.

랜덤 포트라면 호출 주소의 60000을 **호출자에게 실제로 할당된 포트**로 바꾼다.

항상 같은 응답이 보이거나 실패한다면 호출자의 목록에 인스턴스가 두 개 이상 있는지, ID가 겹치지 않는지, 등록된 호스트·포트로 실제 접속 가능한지 확인한다. 수정한 코드와 의존성이 실행본 또는 JAR에 반영되었는지도 확인한다.

#### 5-10. 전체 재현 순서와 확인 기준

|단계|적용할 구성|확인할 결과|
|---|---|---|
|1. 등록 서버 실행|Eureka Server · 8761|대시보드 접근|
|2. 기본 서비스 등록|user-service · 60000|서비스 그룹과 `UP (1)`|
|3. 다중 실행|실행별 60000~60003|한 그룹 안의 다른 ID와 `UP (4)`|
|4. 랜덤 포트 적용|`port: 0` + 고유 ID|실제 포트와 등록 ID의 구분|
|5. HTTP 확인 예제|`/demo/instance`|각 실행본의 포트·PID 응답|
|6. 분산 확인 예제|`@LoadBalanced` 호출|같은 호출 주소에서 대상 변화 확인|

확인 결과를 기록할 때는 서비스 이름, 실행 방식, 설정 포트, 실제 포트, ID와 응답을 함께 남긴다. **설정과 결과의 대응 관계**가 있어야 문제의 원인을 설명하기 쉽다.

> 등록은 실행 정보가 목록에 들어갔다는 뜻이다. API 응답은 해당 기능이 요청을 처리했다는 뜻이고, 분산 확인은 여러 실행본이 선택되었다는 뜻이다. **각 확인이 증명하는 범위를 나누어 판단한다.**

## 🐛 오류 메시지로 복습하기

오류를 찾을 때는 마지막의 `BUILD FAILURE`만 읽기보다 **그 위의 구체적인 메시지와 실패한 단계**를 확인한다. 아래는 학습 내용에 나온 오류를 구분하는 기준이며, 모든 항목을 직접 겪었다는 기록은 아니다.

```text
Java·프로젝트 환경 준비
    ↓
명령어 해석과 빌드
    ↓
JAR 파일 접근과 Java 실행
    ↓
웹 서버의 포트 확보
    ↓
Eureka 등록
    ↓
실제 API 처리와 이름 기반 호출
```

실패한 단계에 맞춰 원인을 찾으면 불필요한 설정 변경을 줄일 수 있다. 예를 들어 Java가 JAR 파일을 찾지 못한 상태에서 Eureka 주소를 고쳐도 파일 접근 문제는 해결되지 않는다.

### 빌드·실행 준비 단계

|증상|먼저 볼 원인|확인·해결 기준|
|---|---|---|
|Java 21을 SDK 17이 지원하지 않는다는 오류|프로젝트 수준과 SDK 불일치|Project SDK·실행 JRE·Maven JDK를 21로 맞춘다.|
|`mvn`을 찾지 못함|Maven 또는 실행 경로 미설정|Wrapper가 있으면 사용하고, 전역 Maven은 `mvn -v`로 확인한다.|
|POM이 없는 폴더라는 오류|명령의 실행 위치|해당 서비스의 `pom.xml`이 있는 폴더로 이동한다.|
|`Unknown lifecycle phase`|플러그인·goal·옵션 구분 오류|`spring-boot:run`의 콜론과 옵션 앞 공백을 확인한다.|
|`Unable to access jarfile`|파일 이름·경로·빌드 결과|실제 JAR의 존재와 셸에 맞는 경로를 확인한다.|
|`no main manifest attribute`|실행 가능한 패키징 누락 또는 다른 JAR|Boot 플러그인·빌드 성공·선택한 JAR을 확인한다.|
|`UnsupportedClassVersionError`|빌드보다 낮은 Java로 실행|빌드와 실행 환경의 Java 버전을 비교한다.|

#### 명령은 플러그인과 옵션을 분리해서 읽는다

```bash
# 형식이 잘못된 예
mvn spring-boot-runDspring-boot.run.jvmArguments='-Dserver.port=60002'

# 올바른 형식
mvn spring-boot:run "-Dspring-boot.run.jvmArguments=-Dserver.port=60002"
```

첫 명령은 `spring-boot`와 `run` 사이의 콜론, 옵션 앞의 공백이 없다. Maven이 전체를 알 수 없는 작업 이름으로 읽는다.

#### JAR은 실제 파일 이름과 현재 위치를 확인한다

```text
빌드가 성공했는가?
    ↓
target에 실제 JAR이 있는가?
    ↓
명령에 적은 파일 이름과 버전이 같은가?
    ↓
현재 위치에서 그 경로를 찾을 수 있는가?
    ↓
사용 중인 셸에 맞는 경로 표기인가?
```

프로젝트 버전이 `0.0.1-SNAPSHOT`이고 파일이 `target`에 있다면 다음과 같이 실행한다.

```bash
java -Dserver.port=60004 -jar ./target/user-service-0.0.1-SNAPSHOT.jar
```

JAR을 현재 폴더로 옮겼다면 `target/`을 제외한 경로를 사용한다. 공백이 있는 파일 경로는 큰따옴표로 묶는다.

`.jar.original`은 재패키징 전 원본일 수 있다. 실행 대상으로는 실제 Spring Boot 실행 가능한 JAR을 선택한다.

Java 21 수준으로 컴파일한 프로그램을 Java 17로 실행하면 클래스 버전 문제가 생길 수 있다. **파일을 못 찾는 오류와, 파일을 찾은 뒤 실행 환경이 맞지 않는 오류를 구분한다.**

### 서버 시작·등록·API 호출 단계

|증상|먼저 볼 원인|확인·해결 기준|
|---|---|---|
|`Port 60000 was already in use`|같은 포트의 기존 서버|다른 포트로 추가 실행하거나 기존 실행본을 종료한다.|
|웹 서버는 시작했지만 목록이 비어 있음|Eureka 주소·의존성·등록 설정|서버 접근, Client Starter, `defaultZone`, 등록 옵션과 로그를 확인한다.|
|랜덤 포트의 여러 프로세스가 `UP (1)`|인스턴스 ID 중복|실제 포트와 등록 ID를 각각 비교하고 고유 ID를 적용한다.|
|YAML은 `0`인데 고정 포트로 실행|우선순위가 높은 기존 설정|VM options·Program arguments·환경 변수·이전 JAR을 확인한다.|
|`/actuator/info`의 404|API 미제공·미노출·경로 불일치|의존성, 노출 설정, 실제 관리 경로를 확인한다.|
|`user-service` 이름 해석 실패|일반 클라이언트로 논리 이름 사용|이름 기반 호출에 Discovery·LoadBalancer 구성을 적용한다.|
|등록된 호스트로 접근 불가|호출 환경에서 주소 해석·접속 불가|등록된 호스트·실제 포트가 호출자에게 접근 가능한지 확인한다.|

#### Eureka 등록이 안 될 때의 확인 순서

1. Eureka 대시보드 자체에 접근할 수 있는가?
2. 사용자 서비스에 Eureka Client Starter가 있는가?
3. `defaultZone`의 주소·포트·`/eureka/` 경로가 맞는가?
4. YAML 계층과 `defaultZone` 대소문자가 맞는가?
5. `register-with-eureka`가 활성화되어 있는가?
6. `spring.application.name`이 설정되어 있는가?
7. 등록 로그에 연결 거부 등의 오류가 있는가?
8. 다른 설정이나 이전 JAR이 값을 덮어쓰고 있지 않은가?
9. 목록이 반영될 시간을 두고 확인했는가?

등록 ID가 겹치는 문제는 애너테이션을 추가하는 것만으로 해결되지 않는다. 어떤 값으로 ID가 만들어졌는지 확인해야 한다.

#### 포트를 사용하는 실행본 확인

macOS · Linux에서 도구가 준비되어 있다면:

```bash
lsof -nP -iTCP:60000 -sTCP:LISTEN
```

Windows PowerShell:

```powershell
Get-NetTCPConnection -LocalPort 60000 -State Listen
```

기존 실행 창을 찾을 수 있다면 그 창의 `Ctrl+C` 또는 IDE의 Stop으로 정상 종료한다. 추가 실행이 목적이면 기존 프로세스를 유지하고 새 포트를 선택한다.

등록된 호스트 이름을 호출 환경에서 해석하지 못한다면, 로컬 실습에서 다음 항목을 기존 `eureka.instance`에 합쳐 주소 등록 방식을 조정할 수 있다.

```yaml
eureka:
  instance:
    prefer-ip-address: true
```

이는 IP 주소를 우선 등록하도록 하는 설정이다. 포트 충돌이나 ID 중복을 해결하는 설정은 아니다. 실제 서버·컨테이너에서는 호출자가 접근할 수 있는 주소인지 확인해야 한다.

> 오류 메시지를 **준비·파일 접근·서버 시작·등록·API 호출 중 어느 단계의 실패인지** 먼저 분류한다. 설정을 바꾸기 전에 실패한 단계와 관련된 값을 확인한다.

## 🧠 오늘 이해한 핵심

### 1. 기능의 이름, 실행본의 ID, 접속 위치는 서로 다른 정보를 표현한다

서비스 이름은 필요한 기능을 묶는다. 인스턴스 ID는 그 기능을 실행하는 개별 대상을 구분한다. 호스트와 실제 포트는 선택된 대상에 접속할 위치를 나타낸다.

이 세 정보를 분리하면 같은 서비스 이름을 유지하면서 실행본을 늘리고, 실행 포트가 바뀌어도 실행 정보를 등록해 사용할 수 있다.

### 2. 같은 코드도 실행별 설정에 따라 다른 인스턴스가 된다

프로젝트와 JAR은 실행할 내용을 담고, 옵션과 환경 변수는 이번 실행의 값을 정한다. 실제 웹 서버는 그 최종 설정을 바탕으로 시작된다.

따라서 실행본마다 프로젝트를 복사하기보다 **공통 설정과 실행별 설정을 구분**하고, 설정 포트와 실제 포트를 대조하는 방식으로 이해할 수 있다.

### 3. 확인한 결과마다 판단할 수 있는 범위가 있다

등록 목록은 서비스 탐색의 정보를 보여 주고, 실제 API 응답은 해당 요청의 처리를 보여 준다. 분산 호출의 대상 변화는 인스턴스 선택을 보여 준다.

기본 `UP` 표시 하나로 기능 전체를 판단하기보다, **목록·실제 연결·응답 내용·대상 선택을 단계별로 확인하는 기준**을 정리했다.

-  **서비스 이름과 ID의 관계**: 같은 이름의 실행본 두 개가 하나의 그룹으로 보이는 것과, 같은 ID 때문에 하나의 인스턴스로 보이는 것을 구분한다.

-  **확인의 단계**: `UP`, 404, 직접 포트 호출, 이름 기반 호출이 각각 어떤 상태를 알려 주는지 설명한다.
