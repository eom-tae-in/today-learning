오늘은 Docker 이미지를 저장·공유하는 방법과 AWS CLI 사용 준비를 정리하고, Ubuntu 가상머신을 여러 대 만들어 Kubernetes 클러스터를 구축하는 흐름을 학습했다. 내부 원리를 깊게 확장하기보다 어떤 방법을 언제 쓰는지, 어디에서 어떤 순서로 실행해야 하는지를 중심으로 기록한다.

Kubernetes는 마스터 초기화, 네트워크 구성, 워커 연결, 구축 상태 확인까지 다룬다. 이후의 애플리케이션 Pod·Deployment·Service 생성과 스케일 조정은 오늘 정리 범위에 포함하지 않는다.

> 이미지는 레지스트리에서 공유하고, 노드는 서로 다른 주소와 이름으로 준비하며, 클러스터는 공통 준비 → 마스터 초기화 → 네트워크 구성 → 워커 연결 순서로 만든다.

## 🎯 오늘의 학습 목표

- Docker Hub·직접 운영하는 레지스트리·Amazon ECR의 차이와 이미지 업로드 순서를 구분할 수 있다.
- AWS CLI 설치와 자격 증명 설정을 나누고, 현재 사용 계정을 확인할 수 있다.

### 1. 이미지를 저장하고 공유하는 세 가지 방식

[이미지 저장 자료](https://lgcns-docker-container-edu.oopy.io/docker12)는 Docker Hub, 직접 실행한 Private Registry, AWS ECR을 소개한다. **레지스트리**는 이미지를 보관하는 서버이고, 그 안에서 이미지 이름별로 구분한 저장 단위를 리포지토리라고 한다.

아래 명령은 수업 내용을 다시 따라가기 위한 예시이며, 실제 계정명·파일·권한·실행 환경을 준비해야 한다. 강의 자료의 화면이나 예제를 사용자의 실제 성공 결과로 간주하지 않는다.

#### 1.1 저장 방식은 운영 주체와 접근 주소가 다르다

| 방식 | 누가 운영하는가? | 사용할 때의 기준 |
| --- | --- | --- |
| Docker Hub | Docker의 서비스 | 계정의 리포지토리로 쉽게 공유 |
| 직접 운영하는 Registry | 내 서버·조직 | 저장소 서버와 데이터·인증을 직접 관리 |
| Amazon ECR | AWS의 관리형 서비스 | AWS 계정·리전·IAM 권한과 연계 |

사설이라는 말이 특정 제품만 뜻하는 것은 아니다. Docker Hub와 ECR에도 접근을 제한한 리포지토리를 둘 수 있다. 오늘 비교하는 것은 주로 저장소를 직접 운영할지 관리형 서비스를 사용할지의 차이다.

공통 순서는 이미지 준비 → 저장소 주소에 맞는 태그 연결 → 필요 시 로그인 → `push`다. 가져올 때는 같은 주소로 `pull`한다. 태그만 붙여서는 업로드되지 않는다.

#### 1.2 Docker Hub는 계정 이름을 앞에 붙여 업로드한다

로컬에 `nginxweb:v1.0` 이미지가 있고 Docker Hub 계정의 업로드 권한이 있다는 전제다. `yourdockerid`는 실제 자신의 계정명으로 바꾼다.

```bash
sudo docker login --username yourdockerid
sudo docker tag nginxweb:v1.0 yourdockerid/nginxweb:v1.0
sudo docker push yourdockerid/nginxweb:v1.0
sudo docker pull yourdockerid/nginxweb:v1.0
```

이미지 이름은 `계정명/리포지토리:태그`로 읽는다. `tag`는 같은 이미지에 다른 이름표를 붙이는 작업이며 이미지 파일 전체를 새로 빌드하는 작업은 아니다.

#### 1.3 로컬 Registry는 컨테이너로 실행하고 주소에 포트를 붙인다

다음은 강의의 `registry:2`를 같은 호스트에서만 사용하는 형태로 정리한 예제다. 데이터 위치를 명확하게 하려고 이름 있는 볼륨을 추가했다.

```bash
sudo docker volume create registry-data
sudo docker run -d --name registry --restart always \
  -p 127.0.0.1:5000:5000 \
  -v registry-data:/var/lib/registry registry:2
sudo docker pull ubuntu:focal
sudo docker tag ubuntu:focal localhost:5000/ubuntu:v1.0
sudo docker push localhost:5000/ubuntu:v1.0
sudo docker pull localhost:5000/ubuntu:v1.0
```

`localhost:5000/ubuntu:v1.0`은 **레지스트리 주소 + 리포지토리 + 태그**다. 호스트의 특정 폴더를 직접 지정한 문자열이 아니다. 레지스트리가 실제 데이터를 `/var/lib/registry`에 기록하고, 여기서는 `registry-data` 볼륨이 그 데이터를 보관한다.

다른 VM에서 `localhost`는 그 VM 자신이다. 공동 저장소로 쓰려면 서버 주소·수신 인터페이스·TLS·접근 인증을 따로 준비해야 하며, 위의 로컬 예제만으로 외부용 저장소가 완성되는 것은 아니다.

> 저장소가 바뀌어도 태그와 push·pull의 관계는 같다. 저장소 주소와 운영 주체, 로그인 방식, 데이터 보관 책임을 구분하면 된다.

### 2. AWS CLI를 준비하고 ECR에 이미지 올리기

[AWS CLI 설치 자료](https://lgcns-docker-container-edu.oopy.io/docker16)는 Ubuntu에서 AWS 명령을 사용할 준비를 설명한다. **AWS CLI**는 터미널에서 AWS 서비스에 명령을 보내는 도구이며, 설치와 로그인 권한 준비는 별도 단계다.

ECR의 자세한 정책 설계보다 설치 → 계정 확인 → 저장소 인증 → 업로드 순서를 기억한다.

#### 2.1 CPU 아키텍처에 맞는 AWS CLI 설치 파일을 고른다

Ubuntu에서 다음과 같이 현재 아키텍처와 압축 해제 도구를 확인한다.

```bash
uname -m
sudo apt-get update
sudo apt-get install -y curl unzip
```

출력이 `x86_64`라면 강의처럼 아래 설치 파일을 사용한다. ARM64 환경이면 URL의 `linux-x86_64.zip`을 `linux-aarch64.zip`으로 바꿔야 한다.

```bash
curl -fL https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip -o awscliv2.zip
unzip awscliv2.zip
sudo ./aws/install
aws --version
```

위는 새 설치 기준이다. 기존 설치를 갱신할 때는 공식 안내의 업데이트 옵션과 설치 경로를 확인한다. `aws --version`은 도구 설치 확인이며 AWS 계정 접근 성공까지 확인하는 명령은 아니다. [AWS CLI 공식 설치 안내](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html)

#### 2.2 사용할 자격 증명을 설정하고 실제 계정을 확인한다

수업의 키 입력 방식은 다음과 같다. 키를 사용할 권한이 있는 IAM 사용자 자격 증명을 준비하고, 같은 Linux 사용자 계정에서 진행한다.

```bash
aws configure
aws configure list
aws sts get-caller-identity
```

| 입력 항목 | 의미 | 수업 설정 기준 |
| --- | --- | --- |
| Access Key ID | 사용할 자격 증명의 식별자 | 자신의 승인된 키 입력 |
| Secret Access Key | 요청 인증에 사용하는 비밀값 | 문서·소스에 기록하지 않음 |
| Default region name | 기본 작업 리전 | `ap-northeast-2` |
| Default output format | 결과 출력 형식 | `json` |

`configure list`는 설정의 출처를 확인하고, `get-caller-identity`는 실제 API 요청에 사용된 계정·주체를 확인한다. 이것이 ECR의 모든 작업 권한까지 보장하는 것은 아니다.

> [!WARNING]
> 원문의 `rootkey.csv` 안내를 따라 루트 계정의 액세스 키를 새로 만들지 않는다. EC2에서는 IAM 역할, 조직 계정에서는 IAM Identity Center 같은 임시 자격 증명을 우선 사용한다. `aws configure`에 넣은 정보는 실행한 Linux 사용자에게 적용되므로 `ubuntu`와 `root` 계정을 섞지 않는다.

역할이나 SSO로 인증한 환경에서는 장기 키를 중복 입력할 필요가 없다. 실제 자격 증명은 노트에 남기지 않고 사용 방식과 리전만 기록한다. [AWS CLI 자격 증명과 설정](https://docs.aws.amazon.com/cli/latest/userguide/cli-chap-configure.html)

#### 2.3 ECR 로그인과 이미지 push를 순서대로 진행한다

AWS 콘솔에서 서울 리전에 `nginxweb`이라는 Private ECR 리포지토리를 만들었다고 가정한 보완 예제다. 로컬 이미지 `nginxweb:v1.0`과 ECR 업로드 권한도 필요하다.

```bash
til_region=ap-northeast-2
til_account=$(aws sts get-caller-identity --query Account --output text)
til_registry="$til_account.dkr.ecr.$til_region.amazonaws.com"
aws ecr get-login-password --region "$til_region" \
  | sudo docker login --username AWS --password-stdin "$til_registry"
sudo docker tag nginxweb:v1.0 "$til_registry/nginxweb:v1.0"
sudo docker push "$til_registry/nginxweb:v1.0"
```

`aws`가 ECR 인증 토큰을 받고, `docker login`이 그 토큰으로 레지스트리에 인증한다. 로그인 사용자명 `AWS`는 이 인증 방식에서 사용하는 고정값이다. 콘솔의 해당 리포지토리에서 태그와 이미지가 올라왔는지 확인하며, 인증이 만료되면 다시 로그인한다. [ECR 이미지 업로드 절차](https://docs.aws.amazon.com/AmazonECR/latest/userguide/docker-push-ecr-image.html)

> AWS CLI 설치, AWS 계정 인증, ECR 저장소 인증, 이미지 업로드는 서로 다른 단계다. 오류가 나면 어느 단계까지 확인됐는지부터 구분한다.

### 3. Ubuntu 가상머신의 네트워크와 복제 환경 준비하기

[VMware 설치·네트워크 자료](https://lgcns-kubernetes-core-edu.oopy.io/k8s01)와 [Ubuntu 설치·복제 자료](https://lgcns-kubernetes-core-edu.oopy.io/k8s03)는 클러스터를 올리기 전의 서버 준비 과정이다. **VM**은 한 컴퓨터 안에서 별도 운영체제를 실행하는 가상 컴퓨터다.

메뉴 이름은 수업의 VMware Workstation 기준이다. 다른 VMware 제품에서는 같은 역할의 설정을 찾고, ISO와 게스트 OS의 CPU 아키텍처도 실행 환경에 맞춘다.

#### 3.1 NAT 네트워크와 고정 IP의 기준을 먼저 맞춘다

Ubuntu 24.04 ISO를 준비해 VM을 만든 뒤, Virtual Network Editor의 `VMnet8`을 수업 네트워크에 맞춘다.

| 설정 | 수업 기준 | 의미 |
| --- | --- | --- |
| 연결 방식 | VMnet8 / NAT | VM이 호스트를 거쳐 외부로 통신 |
| Subnet | `10.0.2.0/24` | 노드들이 사용할 네트워크 대역 |
| Gateway | `10.0.2.2` | 외부 네트워크로 나가는 경로 |
| DHCP 범위 | `10.0.2.128`~`10.0.2.254` | 자동 할당할 주소 범위 |
| 정적 주소 예시 | `10.0.2.10`~`10.0.2.13` | 실습 노드별 고정 주소 |

Ubuntu의 IPv4 설정에는 주소, 넷마스크 `255.255.255.0`, 게이트웨이 `10.0.2.2`, 수업 DNS `10.0.2.2`를 넣는다. 이미 사용 중인 LAN·VPN 대역과 겹치면 환경에 맞게 변경해야 한다.

`VMnet1`은 보통 Host-only여서 호스트·VM 간 통신용이고, 외부 인터넷 연결이 기본 목적은 아니다. “아무 네트워크 통신도 안 된다”는 뜻은 아니다. 설정 뒤 `ip -br addr`, `ip route`, `curl -I https://ubuntu.com`으로 주소·경로·외부 접속을 나눠 확인한다.

#### 3.2 기본 도구와 SSH 접속을 준비한다

기본 VM에서 다음 패키지를 설치한다. SSH는 원격 터미널 접속, Xftp·SFTP는 파일 전송에 사용하는 방식이다.

```bash
sudo apt-get update
sudo apt-get install -y openssh-server curl vim tree
sudo systemctl enable --now ssh
hostnamectl
ip -br addr
```

터미널에서는 `ssh ubuntu@10.0.2.10`으로 접속할 수 있다. Xshell에서는 프로토콜 SSH, 호스트 IP, 포트 22, 실제 Ubuntu 계정을 지정한다. VM 이름·Ubuntu 호스트 이름·로그인 계정 이름은 서로 다른 값이다.

강의에 등장하는 계정·암호는 예시이므로 자신의 설치값을 사용한다. VM 자원은 호스트 여유를 고려해 배정하며, 자료의 메모리 `4MB` 표기는 `4GB`와 혼동하지 않는다.

#### 3.3 VM 복제 방법은 파일 복사와 Full Clone으로 나뉜다

먼저 원본 VM의 전원을 정상 종료하고 복제한다. 복제는 OS 설치 시간을 줄이는 방법이지 노드의 신원과 주소까지 똑같이 사용하라는 뜻은 아니다.

| 방법 | 진행 방식 | 확인할 점 |
| --- | --- | --- |
| VM 파일 복사 | VM 폴더를 복사한 뒤 새 VM으로 열기 | VMware의 복사 여부 질문에서 복사본으로 처리하고 MAC 중복 확인 |
| Full Clone | Manage → Clone → Full Clone | 원본 디스크에 계속 의존하는 Linked Clone과 구분 |

수업 예시는 다음과 같이 주소를 나눈다. 기본 구성은 마스터 1대와 워커 2대이며, 워커 3대 구성이라면 마지막 행도 준비한다. Kubernetes가 언제나 최소 3대의 VM을 요구한다는 뜻은 아니다.

| 역할 | 호스트 이름 | 고정 IP |
| --- | --- | --- |
| 마스터 | `k8s-master` | `10.0.2.10` |
| 워커 1 | `k8s-worker1` | `10.0.2.11` |
| 워커 2 | `k8s-worker2` | `10.0.2.12` |
| 워커 3, 구성한 경우 | `k8s-worker3` | `10.0.2.13` |

#### 3.4 복제한 VM마다 이름과 주소를 바꾼 뒤 상호 통신을 확인한다

각 VM에서 자신의 고정 IP를 설정한다. 호스트 이름은 다음처럼 바꾸며, 예제의 이름은 해당 VM의 역할에 맞게 바꾼다.

```bash
sudo hostnamectl set-hostname k8s-worker1
sudoedit /etc/hosts
```

각 노드의 `/etc/hosts`에 실제 구성한 노드의 주소와 이름을 반영한다. 기존 localhost·IPv6 항목은 유지하고, 복제 전 이름이 남은 `127.0.1.1` 항목도 해당 노드 이름에 맞게 확인한다.

```text
10.0.2.10 k8s-master
10.0.2.11 k8s-worker1
10.0.2.12 k8s-worker2
10.0.2.13 k8s-worker3
```

네 번째 VM이 없으면 마지막 행은 제외한다. `hostnamectl`, `ip -br addr`, `ping -c 3 k8s-worker1`, 각 노드로의 SSH 접속을 확인한다. 필요한 재부팅 뒤에도 주소가 유지되는지 확인하며, 이름 변경을 위해 Docker 컨테이너와 이미지를 전부 삭제할 필요는 없다.

> VM을 복제한 뒤에는 IP·호스트 이름·MAC 중복을 먼저 확인한다. 여러 서버가 서로를 이름으로 찾고 SSH로 접속할 수 있어야 클러스터 구축으로 넘어갈 수 있다.

### 4. Docker 설치를 확인하고 이미지 버전 바꾸기

[Docker 설치·이미지 실습 자료](https://lgcns-kubernetes-core-edu.oopy.io/k8s04)는 각 VM의 Docker 동작을 확인하고, 마스터에서 웹 이미지를 만들어 공유하는 과정을 다룬다. 같은 수작업을 여러 서버에서 반복하기 어려워지는 지점이 Kubernetes의 필요성과 연결된다.

#### 4.1 제공받은 설치 파일을 실행하고 Docker 동작을 확인한다

강의의 `install-docker.sh` 파일을 각 VM의 `/home/ubuntu`에 전송한 경우의 절차다. 파일 내용은 자료에 제공되지 않았으므로 임의의 설치 스크립트를 만들어 같은 파일인 것처럼 취급하지 않는다.

```bash
cd /home/ubuntu
less install-docker.sh
bash -n install-docker.sh
chmod +x install-docker.sh
sudo ./install-docker.sh
sudo systemctl status docker --no-pager
sudo docker version
```

스크립트 내용과 설치 대상을 확인한 뒤 실행한다. `docker version`에서 Client뿐 아니라 Server 응답까지 확인해야 데몬 연결을 확인할 수 있다. 복제 전에 이미 설치했다면 각 복제 VM에서 설치 상태를 먼저 확인한다.

#### 4.2 기본 Nginx 실행으로 포트와 응답을 확인한다

각 VM의 80번 포트가 비어 있는 상태에서 진행하는 수업 예제다.

```bash
sudo docker run -d --name mynginx -p 80:80 nginx
sudo docker ps
curl http://127.0.0.1/
sudo docker stop mynginx
sudo docker rm mynginx
```

여기서 `127.0.0.1`은 명령을 실행하는 VM 자신이다. 노트북 브라우저에서 확인할 때는 접근 가능한 VM의 IP를 사용한다. 확인 후 해당 예제 컨테이너를 정리하면 다음 실습에서 같은 이름·포트가 충돌하는 것을 피할 수 있다.

#### 4.3 페이지 수정은 다시 빌드하고 새 버전으로 실행한다

마스터에 강의의 `dockerfile-folder`가 있고 Dockerfile·`index.html`이 준비되어 있다는 전제다. `yourdockerid`는 실제 Docker Hub 계정명으로 바꾼다.

```bash
cd /home/ubuntu/dockerfile-folder
sudo docker build -t nginxweb:v1.0 .
sudo docker tag nginxweb:v1.0 yourdockerid/nginxweb:v1.0
sudo docker push yourdockerid/nginxweb:v1.0
sudo docker run -d --name mynginx -p 80:80 yourdockerid/nginxweb:v1.0
```

이후 `index.html`을 수정·저장하고 다음 순서로 버전을 바꾼다. 레지스트리 로그인은 1장의 계정과 같은 Docker 실행 방식으로 먼저 준비한다.

```bash
sudo docker build -t nginxweb:v2.0 .
sudo docker tag nginxweb:v2.0 yourdockerid/nginxweb:v2.0
sudo docker push yourdockerid/nginxweb:v2.0
sudo docker stop mynginx
sudo docker rm mynginx
sudo docker run -d --name mynginx -p 80:80 yourdockerid/nginxweb:v2.0
curl http://127.0.0.1/
```

이미지를 다시 빌드해도 기존 컨테이너가 자동 교체되지는 않는다. 이전 버전으로 돌아가려면 같은 방식으로 컨테이너를 교체하되 실행 이미지의 태그를 `v1.0`으로 선택한다. 이 단순 실습 방식에는 중지 시간이 생길 수 있다.

> 페이지 변경, 이미지 빌드, 저장소 업로드, 컨테이너 교체는 별도 작업이다. 여러 노드의 상태를 직접 맞추는 부담을 줄이기 위해 다음 단계에서 Kubernetes를 사용한다.

### 5. 역할을 나누어 Kubernetes 클러스터 구축하기

[구성도 자료](https://lgcns-kubernetes-core-edu.oopy.io/k8s02)는 전체 교육의 확장 구조를 보여 주고, [클러스터 구축 자료](https://lgcns-kubernetes-core-edu.oopy.io/k8s05)는 실제 설치 순서를 설명한다. 오늘은 한 대의 마스터와 준비한 워커를 연결하는 기본 구축을 기준으로 삼는다.

구성도에 있는 Argo CD·Ingress·여러 마스터·DB 이중화까지 오늘 구축한 것으로 기록하지 않는다. 아래는 수업 절차의 요약이며, 설치 스크립트·Kubernetes·런타임·CNI의 버전 조합은 다시 설치할 시점에 확인해야 한다.

#### 5.1 도구의 역할과 실행할 노드를 먼저 구분한다

**클러스터**는 여러 노드를 하나의 관리 환경으로 묶은 것이다. 마스터라고 부른 노드는 클러스터를 관리하는 컨트롤 플레인이고, 워커는 주로 애플리케이션을 실행한다.

| 구성 요소 | 역할 | 사용할 위치 |
| --- | --- | --- |
| `kubeadm` | 클러스터 초기화와 노드 참가 | 마스터 init, 워커 join |
| `kubelet` | 노드에서 컨테이너 실행 상태 관리 | 모든 노드 |
| `kubectl` | 클러스터 API에 명령 전달 | 관리자 설정이 있는 계정 |
| containerd | 실제 컨테이너 실행을 담당하는 런타임 | 모든 노드 |
| CNI 네트워크 구성 | 노드 간 Pod 통신 환경 제공 | 클러스터에 배포 |

Docker Engine 설치와 Kubernetes 런타임 준비는 같은 작업이 아니다. 여기서는 Kubernetes가 CRI라는 인터페이스를 통해 containerd를 사용하는 구성을 기준으로 한다. Docker 데몬의 설정만 바꿨다고 containerd의 설정까지 맞춰지는 것은 아니다.

#### 5.2 모든 노드에서 swap과 네트워크 설정을 준비한다

먼저 IP·호스트 이름·시간·노드 간 통신을 확인한다. 수업처럼 swap을 사용하지 않는 구성에서는 다음을 실행하고 `/etc/fstab`의 swap 항목도 비활성화해 재부팅 후 다시 켜지지 않게 한다.

```bash
swapon --show
sudo swapoff -a
sudoedit /etc/fstab
```

브리지 트래픽 처리와 IPv4 전달도 준비한다. 다음은 새 실습 VM에 설정을 추가하는 보완 예제이며, 기존 파일이 있으면 내용을 확인해 반영한다.

```bash
printf 'br_netfilter\n' | sudo tee /etc/modules-load.d/k8s.conf
sudo modprobe br_netfilter
sudo tee /etc/sysctl.d/k8s.conf <<'EOF'
net.bridge.bridge-nf-call-ip6tables = 1
net.bridge.bridge-nf-call-iptables = 1
net.ipv4.ip_forward = 1
EOF
sudo sysctl --system
```

원문의 `ufw disable`은 수업 실습망에서의 단순화다. 다른 환경에서는 방화벽을 통째로 끄는 대신 Kubernetes와 선택한 CNI에 필요한 통신을 허용한다. UFW 중지는 SELinux를 해제하는 명령도 아니다. [kubeadm 설치 전제조건](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/install-kubeadm/)

#### 5.3 모든 노드에서 containerd의 CRI와 cgroup 설정을 맞춘다

**cgroup**은 프로세스 자원을 관리하는 기능이다. Ubuntu의 systemd 환경에서는 kubelet과 containerd의 cgroup 관리 방식도 systemd로 맞추는 것이 기본 기준이다.

```bash
containerd --version
sudo systemctl status containerd --no-pager
sudoedit /etc/containerd/config.toml
```

설정 파일이 없다면 `containerd config default`로 해당 버전의 기본 설정을 확인해 작성한다. 기존 설정을 삭제하는 원문 명령을 그대로 실행하기보다 먼저 백업하고, CRI가 `disabled_plugins`로 꺼져 있지 않은지와 `SystemdCgroup = true`를 확인한다.

| containerd 버전 | 기본 설정에서 찾아볼 runc 옵션 경로 |
| --- | --- |
| 1.x | `plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options` |
| 2.x | `plugins."io.containerd.cri.v1.runtime".containerd.runtimes.runc.options` |

설정 위치는 버전별 기본 파일을 기준으로 확인하고 해당 옵션을 수정한 뒤 서비스를 재시작한다.

```bash
sudo systemctl enable --now containerd
sudo systemctl restart containerd
sudo systemctl status containerd --no-pager
```

원문의 `/etc/docker/daemon.json`에 적는 `native.cgroupdriver=systemd`는 Docker 쪽 설정이다. containerd를 CRI 런타임으로 사용하는 경우 그 설정을 대신할 수 없다. [런타임·CRI·systemd cgroup 설정](https://kubernetes.io/docs/setup/production-environment/container-runtimes/)

#### 5.4 모든 노드에 같은 계열의 Kubernetes 도구를 설치한다

수업의 저장소 주소는 `v1.32` 계열이다. 다음은 그 설치 경로를 복원한 예시이며, 새 환경에 적용할 때는 지원 중인 Kubernetes와 런타임·CNI의 호환 조합을 먼저 정한다. 저장소의 버전과 실제 설치 버전을 혼용하지 않는다.

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl gpg
sudo install -d -m 755 /etc/apt/keyrings
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.32/deb/Release.key \
  | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.32/deb/ /' \
  | sudo tee /etc/apt/sources.list.d/kubernetes.list
sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl
kubeadm version
```

위는 새 실습 노드 기준이다. `hold`는 패키지가 의도치 않게 자동 갱신되는 것을 막는 설정이다. 원문의 `kubernetes-cni` 같은 기본 플러그인 패키지 설치만으로 클러스터 전체의 Pod 네트워크 배포가 끝나는 것은 아니다.

#### 5.5 마스터에서 init을 실행하고 관리자 접속 설정을 만든다

마스터 `10.0.2.10`에서만 실행한다. 적용할 CNI를 먼저 정하고, 그 CNI가 Pod 대역 지정을 요구하면 `--pod-network-cidr`도 초기화 옵션에 맞춰 추가한다.

```bash
sudo kubeadm init --apiserver-advertise-address=10.0.2.10 \
  --kubernetes-version="$(kubeadm version -o short)" \
  --cri-socket=unix:///var/run/containerd/containerd.sock
```

출력에서 관리자 설정 안내와 `kubeadm join ...` 명령을 확보한다. 강의 화면의 토큰을 복사하는 것이 아니라 방금 만든 자신의 클러스터가 출력한 명령을 사용한다.

이어서 `kubectl`을 사용할 일반 사용자, 예를 들어 `ubuntu`의 셸에서 다음을 실행한다. `sudo -i`로 들어간 root 셸에 계속 머물러 있다면 먼저 나와서 진행한다.

```bash
mkdir -p "$HOME/.kube"
sudo cp /etc/kubernetes/admin.conf "$HOME/.kube/config"
sudo chown "$(id -u):$(id -g)" "$HOME/.kube/config"
kubectl get nodes
```

`admin.conf`는 클러스터 관리자 권한을 가진 접속 설정이다. 워커에 무조건 배포하거나 공개 저장소에 올리는 일반 설정 파일로 취급하지 않는다.

#### 5.6 마스터에서 CNI 네트워크를 배포한다

CNI 구성은 서로 다른 노드의 Pod가 통신할 수 있게 하는 단계다. `init` 직후에는 네트워크가 아직 준비되지 않아 노드가 `NotReady`이거나 CoreDNS가 대기할 수 있다.

강의는 Weave Net `v2.8.1` 매니페스트를 적용한다. 그러나 [Weave 저장소](https://github.com/weaveworks/weave)는 보관 상태이므로, 이 URL을 현재의 모든 Kubernetes 버전에 그대로 적용할 수 있다고 보지 않는다. 수업 환경을 재현할 때도 강의에서 검증한 배포 파일과 이미지의 가용성을 확인한다.

새로 구축할 때는 선택한 Kubernetes 버전에 지원되는 CNI의 공식 설치 안내를 기준으로 배포 파일과 Pod 대역을 맞춘다. 다음 명령의 경로는 실제 확보한 CNI 매니페스트 경로로 바꿔야 하며, 이 문서가 해당 파일을 제공하는 것은 아니다.

```bash
kubectl apply -f /path/to/validated-cni.yaml
kubectl get pods -n kube-system
```

CNI는 하나를 선택해 구성한다. 여러 제품의 설치 명령을 섞어 적용하지 않으며, 여기까지는 네트워크 플러그인을 설치하는 작업이지 오늘 범위 밖의 앱 배포 실습이 아니다. [kubeadm 클러스터와 Pod 네트워크 설치](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/)

#### 5.7 각 워커에서 마스터가 출력한 join 명령을 실행한다

워커 1·2와 추가로 구성한 워커 3에서 각각 실행한다. 다음은 명령의 형태를 보여 주는 예시이며, `TOKEN`과 `HASH`는 자신의 실제 출력값으로 바꿔야 한다.

```bash
sudo kubeadm join 10.0.2.10:6443 \
  --token TOKEN \
  --discovery-token-ca-cert-hash sha256:HASH \
  --cri-socket=unix:///var/run/containerd/containerd.sock
```

재접속할 때 토큰이 만료됐거나 명령을 잃어버렸다면 마스터에서 `sudo kubeadm token create --print-join-command`로 새 참가 명령을 확인한다. 인증서 해시 확인을 건너뛰는 옵션으로 문제를 덮기보다, 올바른 마스터 주소·토큰·해시·시간·통신 상태부터 확인한다.

#### 5.8 마스터에서 노드와 시스템 구성요소를 확인하면 오늘 구축은 끝난다

관리자 설정이 있는 마스터의 사용자 셸에서 조회한다.

```bash
kubectl get nodes -o wide
kubectl get pods -n kube-system -o wide
```

| 확인 대상 | 구축 완료 판단 기준 |
| --- | --- |
| 노드 목록 | 준비한 마스터·워커가 모두 나타남 |
| 노드 상태 | 각 노드가 `Ready` |
| 노드 주소 | 계획한 IP와 호스트 이름이 일치 |
| 네트워크·DNS | CNI 구성요소와 CoreDNS가 정상 동작 |
| 컨트롤 플레인 | API 서버·스케줄러·컨트롤러·etcd 등 필수 구성요소가 정상 동작 |

`NotReady`면 CNI·런타임·kubelet 상태를 나눠 확인한다. 기본 조회 명령은 `kubectl describe node 노드명`, `sudo systemctl status kubelet --no-pager`, `sudo journalctl -u kubelet -n 50 --no-pager`다. 오류를 확인하기 전에 `kubeadm reset`부터 반복하지 않는다.

이 상태 확인이 오늘 정리의 마지막 단계다. Metrics Server, 편의용 별명, 애플리케이션 생성·확장 실습은 기본 클러스터 구축과 구분한다.

> 공통 준비는 모든 노드에서, init·관리자 설정·CNI 배포는 마스터에서, join은 워커에서 진행한다. 명령 실행 자체보다 계획한 노드가 Ready이고 시스템 네트워크·DNS가 정상인지로 구축 완료를 판단한다.

## 🧠 오늘 이해한 핵심

1. **이미지 공유 방식은 저장소 주소와 인증 방식으로 구분한다.** Docker Hub·로컬 Registry·ECR 모두 태그와 push·pull을 사용하지만, 저장소를 운영하고 권한을 준비하는 주체가 다르다.
2. **VM 복제와 클러스터 노드 준비는 같은 작업이 아니다.** 복제 뒤에도 각 VM의 IP·이름·통신 상태를 맞춰야 별개의 노드로 연결할 수 있다.
3. **클러스터 구축 명령은 실행할 노드와 계정을 함께 기억해야 한다.** 마스터의 init, 워커의 join, 관리자의 kubectl 설정을 나누고 런타임·CNI를 준비해야 정상 상태까지 이어진다.
