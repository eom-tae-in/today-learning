# 📚 Today I Learned: API Gateway와 서비스 연결

📅 **작성일:** 2026-10-06  
☕ **학습 언어:** Java  
**핵심 기술:** Spring Cloud Gateway · WebFlux · Filter · Eureka · Spring Cloud LoadBalancer

외부 요청이 Gateway를 거쳐 내부 서비스에 도착하고, 응답이 다시 돌아오는 과정을 정리한다. 고정 주소로 연결하는 기본 라우팅부터 필터, 서비스 검색, 여러 인스턴스에 대한 부하 분산까지 하나의 흐름으로 연결한다.

### 1. API Gateway의 역할과 기술 선택

여러 서비스를 연결하려면 먼저 ‘어떤 기능을 호출하는가’와 ‘그 기능이 어디서 실행되는가’를 구분해야 한다. 이 구분을 바탕으로 Gateway, 서비스 검색, 부하 분산의 필요성을 이해한다.

#### 1.1 먼저 구분할 용어

|용어|의미|오늘의 예제|
|---|---|---|
|클라이언트|다른 프로그램에 요청을 보내는 쪽|브라우저, 내부 서비스를 호출하는 Gateway|
|서버|요청을 받아 처리하는 프로그램 또는 컴퓨터|Gateway, First Service, Second Service|
|API|프로그램의 기능을 호출하기 위한 입력·처리·응답의 약속|`GET /first-service/welcome`|
|서비스|특정 기능을 담당하는 논리적 애플리케이션 단위|First Service|
|인스턴스|서비스를 실제로 실행한 개별 프로그램|First Service를 8081과 8083에서 실행한 두 프로그램|
|포트|같은 컴퓨터에서 접속할 서버 프로그램을 구분하는 번호|Gateway의 8000, Eureka의 8761|

‘First Service와 Second Service’는 서로 다른 두 서비스다. ‘First Service 8081과 First Service 8083’은 같은 서비스의 두 인스턴스다. 부하 분산은 보통 **같은 기능을 제공하는 인스턴스들** 사이에서 요청을 나눈다.

클라이언트와 서버는 호출 관계에 따라 달라진다. Gateway는 브라우저의 요청을 받을 때 서버이고, 내부 서비스로 HTTP 요청을 보낼 때 클라이언트다.

**URL을 나누어 읽기**

```text
http://localhost:8000/first-service/welcome?name=taein
```

|URL의 부분|의미|
|---|---|
|`http`|통신 방식|
|`localhost`|요청을 보내는 프로그램이 실행되는 자기 환경|
|`8000`|접속할 프로그램의 포트|
|`/first-service/welcome`|호출할 API 경로|
|`name=taein`|쿼리 문자열로 전달한 추가 조건|

여러 컴퓨터나 컨테이너로 나누면 각 환경의 `localhost`는 서로 다르다. Gateway 컨테이너에서 `localhost:8081`로 요청하면 그 컨테이너 안의 8081에 접속한다.

**HTTP 요청과 응답의 구성**

|구분|주요 구성 요소|예|
|---|---|---|
|요청|메서드, 경로, 헤더, 필요한 경우 본문|`GET /first-service/welcome`|
|응답|상태 코드, 헤더, 필요한 경우 본문|`200 OK`, 환영 메시지|

|HTTP 메서드|주된 사용 목적|
|---|---|
|`GET`|조회|
|`POST`|생성 또는 처리 요청|
|`PUT`|대상 전체 수정|
|`PATCH`|대상 일부 수정|
|`DELETE`|삭제|
|`OPTIONS`|지원 방식 확인, CORS 사전 요청 등|

#### 1.2 마이크로서비스에서 Gateway가 필요한 이유

마이크로서비스는 회원, 주문, 상품 같은 업무를 별도 애플리케이션으로 나누어 실행하는 방식이다. 서비스를 각각 수정하거나 늘릴 수 있지만, 호출 주소와 공통 처리도 관리해야 한다.

브라우저가 각 서비스의 내부 주소를 직접 알아야 한다면 다음 문제가 생긴다.

- 서비스의 주소나 포트가 바뀔 때 호출하는 쪽의 설정도 영향을 받는다.
- 인증, 로그, 요청 제한을 서비스마다 반복해서 구성하기 쉽다.
- 서비스가 늘수록 클라이언트가 알아야 할 주소와 호출 규칙이 많아진다.

API Gateway는 외부 요청을 받는 **공통 입구**다. 회사의 안내 데스크처럼 요청 목적을 확인하고 담당 서비스로 연결한다.

```text
클라이언트: Gateway의 8000으로 요청
    ↓ 공개 API 경로로 서비스 선택
Gateway: First Service의 주소로 전달
    ↓ 업무 처리
First Service: 응답 생성
    ↓ 응답 전달과 공통 후처리
Gateway: 클라이언트에 응답
```

Gateway는 라우팅과 공통 처리를 담당하고, 회원 가입·주문 생성 같은 업무 규칙은 해당 서비스가 담당한다. Gateway에 업무 로직까지 모두 모으면 서비스 분리의 이점이 줄어든다.

‘공통 입구’는 클라이언트가 사용하는 논리적 접점을 뜻한다. 운영 환경에서는 Gateway 자체도 여러 인스턴스로 구성할 수 있다.

#### 1.3 Gateway에서 구성할 수 있는 기능

|기능|해결하는 문제|기억할 조건|
|---|---|---|
|인증·인가|누가 요청했는지, 해당 작업을 허용할지 판단|인증은 신원 확인, 인가는 권한 확인이다.|
|서비스 검색 연동|서비스 이름을 실제 인스턴스 주소와 연결|Eureka 같은 검색 기능과 연동한다.|
|응답 캐싱|재사용할 응답을 저장하여 반복 호출을 줄임|사용자별 결과가 섞이지 않도록 캐시 기준을 정한다.|
|타임아웃·회로 차단기·재시도|지연이나 장애가 다른 요청으로 번지는 것을 제어|주문·결제처럼 중복 처리될 수 있는 요청은 재시도 조건을 신중히 정한다.|
|요청 속도 제한|일정 시간에 들어오는 요청 수를 제한|사용자·IP 등 제한 기준과 허용량을 설정한다.|
|부하 분산|같은 서비스의 여러 인스턴스 중 하나를 선택|인스턴스 목록과 선택 정책이 필요하다.|
|로깅·추적·상관관계|요청의 이동과 결과를 여러 로그에서 연결|상관관계 ID로 같은 요청에 속한 로그를 찾을 수 있다.|
|요청·응답 변환|헤더, 경로, 쿼리 등을 내부 규칙에 맞게 조정|변환 전후의 값을 구분한다.|
|IP 허용 목록|정해진 네트워크나 IP의 접근만 허용|접근 정책을 실제로 구성해야 한다.|

회로 차단기(Circuit Breaker)는 실패가 반복되는 대상 호출을 잠시 제한하는 장치다. QoS는 서비스 품질을 관리하기 위한 처리 정책을 가리킨다.

Gateway를 실행하는 것만으로 이 기능들이 모두 켜지지는 않는다. 오늘의 주요 구현 범위는 **라우팅, 헤더 처리, 로그 필터, 서비스 검색과 부하 분산 연동**이다.

#### 1.4 Gateway·Eureka·LoadBalancer의 역할

|구성 요소|핵심 질문|책임|
|---|---|---|
|Gateway|이 요청을 어느 서비스로 전달할까?|요청 수신, 라우트 선택, 필터 처리, 전달|
|Eureka|그 서비스는 현재 어디서 실행 중인가?|서비스 이름과 인스턴스 주소의 등록·조회|
|LoadBalancer|그 서비스의 여러 인스턴스 중 어디로 보낼까?|사용할 인스턴스 선택|
|내부 서비스|요청한 업무를 어떻게 처리할까?|실제 API와 업무 처리|

Eureka에 주소가 등록되어 있다는 것과 해당 주소를 선택하여 HTTP 요청을 보내는 것은 서로 다른 단계다. 서비스 검색은 후보를 알려 주고, 부하 분산은 후보 중 하나를 고른다.

#### 1.5 Ribbon·Zuul과 현재 예제의 연결

|기술|주요 역할|오늘의 학습에서 구분할 점|
|---|---|---|
|Netflix Ribbon|호출하는 쪽에서 인스턴스를 선택하는 부하 분산|기존 Spring Cloud Netflix 통합 방식의 이해에 사용한다.|
|Netflix Zuul|외부 요청을 내부 서비스로 전달하는 Gateway|기존 `@EnableZuulProxy`와 Zuul 필터 구조를 이해한다.|
|Spring Cloud Gateway|라우팅과 필터를 구성하는 Gateway|뒤의 주요 예제에 사용한다.|
|Spring Cloud LoadBalancer|서비스 인스턴스 선택|뒤의 `lb://` 라우팅에 사용한다.|
|Netflix Eureka|서비스 등록과 검색|Gateway 예제에서도 사용한다.|

기존 Ribbon·Zuul의 Spring Cloud Netflix 통합은 유지보수 모드로 전환된 기술이다. 이 사실을 Eureka까지 동일한 상태라고 확대해서 이해하지 않는다.

**기존 Zuul 방식의 특징**

이전 환경에서는 `spring-cloud-starter-netflix-zuul`과 `@EnableZuulProxy`를 사용했다. Zuul 설정은 `zuul.routes` 아래에 `path`와 `url`을 연결하는 방식이었다.

|Zuul 필터 메서드|역할|
|---|---|
|`filterType()`|`pre`, `route`, `post`, `error` 같은 실행 단계|
|`filterOrder()`|같은 단계 안에서의 실행 순서|
|`shouldFilter()`|필터 실행 여부|
|`run()`|실제 처리 내용|

기존 Zuul의 라우트 접두사 제거 동작과 Spring Cloud Gateway의 기본 경로 처리는 다르다. `/first-service/welcome`이 내부에서도 같은 경로로 전달되는지는 사용하는 Gateway와 경로 필터를 기준으로 확인해야 한다.

**HTTP 호출 도구도 별도로 구분하기**

|도구|호출 방식|서비스 이름 호출의 조건|
|---|---|---|
|`RestTemplate`|코드에서 HTTP 요청을 직접 구성|단순히 `new`로 생성하면 검색·부하 분산이 자동 적용되지 않는다.|
|Feign Client|인터페이스에 HTTP 호출 규칙을 선언|의존성, 활성화, 서비스 검색·부하 분산 연동이 필요하다.|

다음은 호출 방식만 비교하는 **부분 예제**다.

```java
RestTemplate restTemplate = new RestTemplate();
String result = restTemplate.getForObject(
        "http://localhost:8081/first-service/welcome",
        String.class
);
```

```java
@FeignClient(name = "my-first-service")
public interface FirstClient {
    @GetMapping("/first-service/welcome")
    String welcome();
}
```

HTTP 호출 도구는 요청을 보내고, Discovery는 주소를 찾고, LoadBalancer는 인스턴스를 고른다. 이 세 책임을 구분하면 서비스 이름으로 호출할 때 필요한 설정도 찾기 쉬워진다.

#### 1.6 Spring Cloud Gateway의 WebMVC와 WebFlux

|비교 기준|Gateway Server WebMVC|Gateway Server WebFlux|
|---|---|---|
|기반 기술|Spring MVC, Servlet, WebMvc.fn|Spring WebFlux, Project Reactor|
|대표 서버 런타임|Tomcat·Jetty 같은 Servlet 서버|Reactor Netty|
|처리 모델|MVC·블로킹 방식과 연결|비동기·논블로킹 I/O 기반|
|Starter|`spring-cloud-starter-gateway-server-webmvc`|`spring-cloud-starter-gateway-server-webflux`|
|예제 라우트 설정 경로|`spring.cloud.gateway.server.webmvc.routes`|`spring.cloud.gateway.server.webflux.routes`|
|뒤의 필터 코드|별도의 MVC 필터 API 사용|`AbstractGatewayFilterFactory`, `GatewayFilterChain`, `Mono<Void>` 사용|

Servlet은 Java 서버에서 HTTP 요청·응답을 처리하는 규약이고, Tomcat은 이 규약을 실행하는 서버다. Reactor는 비동기 처리 흐름을 조합하는 라이브러리이며, Reactor Netty는 네트워크 통신을 담당한다.

**블로킹**은 결과를 기다리는 동안 실행 흐름이 대기하는 방식이다. **논블로킹 I/O**는 네트워크 결과를 기다리느라 처리 스레드를 계속 붙잡아 두지 않는 방식이다. 비동기 처리에서도 앞 작업의 완료를 조건으로 다음 작업을 연결할 수 있다.

오늘의 구성은 **WebFlux Gateway + Spring MVC 내부 서비스**다. 서로 HTTP로 통신하므로 모든 서비스를 같은 웹 기술로 만들 필요는 없다.

- 한 Gateway에서는 선택한 방식에 맞는 starter와 설정을 사용한다.
- WebFlux Gateway에 `spring-boot-starter-web`을 추가하면 MVC 런타임 선택이나 호환성 문제가 생길 수 있다.
- WebFlux 필터의 코드를 WebMVC 필터에 그대로 옮길 수는 없다.
- WebFlux의 이벤트 루프에서 블로킹 작업을 수행하면 다른 요청의 처리도 지연될 수 있다.

#### 1.7 버전과 설정 경로를 함께 읽기

아래 코드는 **학습용 예제**이며, 응답과 로그는 해당 구성을 실행할 때 확인할 결과다.

|항목|이 문서의 예제 기준|

|Spring Boot|3.5.x|
|Spring Cloud|2025.0.x|

|주요 Gateway 방식|Gateway Server WebFlux|

> Gateway의 전달 기능, Eureka의 주소 검색, LoadBalancer의 인스턴스 선택을 먼저 구분한다. 구현할 때는 웹 처리 방식과 버전에 맞는 의존성·설정·필터 API를 함께 선택한다.

### 2. Route·Predicate·Filter로 요청 연결

Gateway의 역할을 알았다면 실제 요청을 연결할 규칙이 필요하다. 먼저 고정 주소로 내부 서비스에 연결하고, 경로와 헤더가 어떻게 전달되는지 살펴본다.

#### 2.1 프로그램 구성과 의존성

|프로그램|프로젝트 이름 예|`spring.application.name`|초기 포트|역할|
|---|---|---|---|---|
|Gateway|`apigateway-service`|`apigateway-service`|8000|외부 요청 수신과 전달|
|First Service|`first-service`|`my-first-service`|8081|`/first-service/**` API 처리|
|Second Service|`second-service`|`my-second-service`|8082|`/second-service/**` API 처리|
|Eureka Server|`discovery-service`|`discovery-service`|8761|서비스 등록과 조회|

프로젝트 폴더 이름, 서비스 이름, 라우트의 `id`는 각각 별도 항목이다. 문자열을 비슷하게 정하더라도 역할이 같아지지는 않는다.

Maven의 `pom.xml`에는 사용할 **의존성**, 즉 외부 라이브러리를 선언한다. `groupId`는 조직·프로젝트 식별자, `artifactId`는 라이브러리 이름, `version`은 사용할 버전이다. Starter는 특정 기능의 라이브러리와 자동 설정을 묶은 출발 패키지다.

**Spring Cloud BOM: 라이브러리 버전 묶음 관리**

다음은 기존 `pom.xml`의 해당 위치에 넣을 부분 설정이다. 이미 같은 항목이 있다면 그 안에 병합한다.

```xml
<properties>
    <java.version>21</java.version>
    <spring-cloud.version>2025.0.0</spring-cloud.version>
</properties>
```

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-dependencies</artifactId>
            <version>${spring-cloud.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

BOM은 호환되는 라이브러리 버전을 함께 관리하는 목록이다. BOM을 가져오는 것만으로 모든 라이브러리가 추가되지는 않으며, 사용할 의존성은 따로 선언한다. `2025.0.0`은 예제를 구체화한 값이다.

**WebFlux Gateway의 의존성**

```xml
<dependencies>
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-gateway-server-webflux</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-netflix-eureka-client</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-loadbalancer</artifactId>
    </dependency>
    <dependency>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <optional>true</optional>
    </dependency>
</dependencies>
```

Eureka Client와 LoadBalancer는 뒤에서 서비스 이름 라우팅에 사용한다. 개발 편의 기능인 DevTools는 라우팅의 필수 요소가 아니다.

**First·Second Service의 의존성**

```xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-netflix-eureka-client</artifactId>
    </dependency>
    <dependency>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <optional>true</optional>
    </dependency>
</dependencies>
```

Gateway에는 WebFlux Gateway starter를, 내부 서비스에는 Spring Web starter를 넣는다는 구분이 중요하다. 예제의 `@Slf4j`, `@Data`를 사용하려면 Lombok 의존성과 어노테이션 처리도 준비되어야 한다.

**Gateway 실행 클래스: `ApigatewayServiceApplication.java`**

```java
package com.example.apigateway;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class ApigatewayServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(ApigatewayServiceApplication.class, args);
    }
}
```

Gateway의 설정 클래스와 필터는 `com.example.apigateway`의 하위 패키지에 둔다. `@SpringBootApplication`의 기본 컴포넌트 검색 범위에 포함되도록 하기 위해서다.

#### 2.2 properties와 YAML 설정 읽기

같은 설정을 평면적인 키로 쓰면 `application.properties`, 들여쓰기로 계층을 표현하면 `application.yml`이다.

```properties
server.port=8000
spring.application.name=apigateway-service
```

```yaml
server:
  port: 8000
spring:
  application:
    name: apigateway-service
```

|YAML 표현|읽는 방법|
|---|---|
|`key: value`|하나의 설정 값|
|들여쓰기|상위·하위 항목의 관계|
|`- id: first-route`|목록의 한 항목|
|`routes` 아래의 여러 `-`|여러 라우트|
|`filters` 아래의 여러 `-`|한 라우트에 적용할 여러 필터|

`spring.cloud.gateway.server.webflux.routes[0].id`처럼 properties에 `[0]`이 있으면 라우트 목록의 첫 번째 요소를 뜻한다. YAML에서는 해당 목록이 첫 번째 `- id:`로 보인다.

YAML 들여쓰기에는 공백을 사용한다. 동일한 파일에 `spring:` 같은 키를 여러 번 만들면 중복 키나 덮어쓰기 문제가 생길 수 있다.

#### 2.3 내부 서비스가 받을 API부터 만들기

처음에는 First Service를 8081, Second Service를 8082에서 실행한다. First의 초기 `application.yml`은 다음과 같다.

```yaml
server:
  port: 8081
spring:
  application:
    name: my-first-service
```

Second에서는 포트를 `8082`, 애플리케이션 이름을 `my-second-service`로 바꾼다. Eureka 연결은 뒤에서 추가한다.

**학습용 예제: `FirstServiceController.java`**

```java
package com.example.firstservice.controller;

import jakarta.servlet.http.HttpServletRequest;
import lombok.extern.slf4j.Slf4j;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestHeader;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@Slf4j
@RestController
@RequestMapping("/first-service")
public class FirstServiceController {

    @GetMapping("/welcome")
    public String welcome() {
        return "Welcome to the First service.";
    }

    @GetMapping("/message")
    public String message(@RequestHeader("f-request") String header) {
        log.info("First Service received f-request={}", header);
        return "Hello World in First Service.";
    }

    @GetMapping("/check")
    public String check(HttpServletRequest request) {
        int localPort = request.getLocalPort();
        log.info("First Service local port={}", localPort);
        return "Hi, there. This is a message from First Service on PORT "
                + localPort + ".";
    }
}
```

**학습용 예제: `SecondServiceController.java`**

```java
package com.example.secondservice.controller;

import jakarta.servlet.http.HttpServletRequest;
import lombok.extern.slf4j.Slf4j;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestHeader;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@Slf4j
@RestController
@RequestMapping("/second-service")
public class SecondServiceController {

    @GetMapping("/welcome")
    public String welcome() {
        return "Welcome to the Second service.";
    }

    @GetMapping("/message")
    public String message(@RequestHeader("s-request") String header) {
        log.info("Second Service received s-request={}", header);
        return "Hello World in Second Service.";
    }

    @GetMapping("/check")
    public String check(HttpServletRequest request) {
        int localPort = request.getLocalPort();
        log.info("Second Service local port={}", localPort);
        return "Hi, there. This is a message from Second Service on PORT "
                + localPort + ".";
    }
}
```

|코드 요소|역할|확인할 점|
|---|---|---|
|`@RestController`|반환값을 HTTP 응답 본문으로 제공|문자열 반환도 응답 본문이 된다.|
|클래스의 `@RequestMapping`|API 공통 경로 지정|`/first-service` 또는 `/second-service`|
|메서드의 `@GetMapping`|GET 요청의 세부 경로 지정|공통 경로와 합쳐 최종 경로가 된다.|
|`@RequestHeader`|요청 헤더를 메서드 인자로 받음|기본적으로 필수 헤더다.|
|`@Slf4j`|Lombok이 `log` 필드를 생성|로그로 내부 서비스에 도착한 값을 확인한다.|
|`request.getLocalPort()`|요청을 받은 서버의 실제 로컬 포트 조회|여러 인스턴스 중 누가 처리했는지 확인한다.|

`/welcome`은 기본 연결, `/message`는 요청 헤더, `/check`는 처리 인스턴스 확인에 사용한다. Boot 3 예제의 Servlet 타입은 `jakarta.servlet` 패키지다.

#### 2.4 Route·Predicate·Filter의 책임

|구성 요소|의미|예|
|---|---|---|
|Route|하나의 전달 규칙 전체|`id`, `uri`, `predicates`, `filters`의 묶음|
|Predicate|이 요청이 라우트에 해당하는지 검사하는 조건|`Path=/first-service/**`|
|Filter|선택된 라우트에서 요청·응답을 처리하는 작업|헤더 추가, 경로 변환, 로그|

라우트에는 ‘이름’과 ‘전달 대상’이 따로 있다. `id: first-route`는 라우트의 식별자이고, `uri`가 실제 전달할 주소 또는 서비스 이름을 정한다.

**고정 주소로 연결하는 WebFlux Gateway의 초기 `application.yml`**

```yaml
server:
  port: 8000
spring:
  application:
    name: apigateway-service
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: first-route
              uri: http://localhost:8081
              predicates:
                - Path=/first-service/**
            - id: second-route
              uri: http://localhost:8082
              predicates:
                - Path=/second-service/**
```

```text
GET /first-service/welcome 수신
    ↓ Path 조건 검사
first-route 선택
    ↓ uri의 호스트·포트로 전달
http://localhost:8081/first-service/welcome 호출
    ↓ Controller 매핑 확인
FirstServiceController.welcome() 실행
```

`**`는 해당 경로 아래의 하위 경로를 매칭하는 패턴이다. `Path`는 요청을 고르는 조건이며, 그 자체가 경로를 변경하지는 않는다.

**WebMVC를 선택했다면** Gateway starter를 WebMVC용으로 바꾸고, 같은 라우트 목록을 `server.webmvc` 아래에 둔다. 구조를 비교하는 부분 예제는 다음과 같다.

```yaml
spring:
  cloud:
    gateway:
      server:
        webmvc:
          routes:
            - id: first-route
              uri: http://localhost:8081
              predicates:
                - Path=/first-service/**
```

뒤의 사용자 정의 필터 코드는 WebFlux용이다. 위 WebMVC 설정과 결합하여 사용하지 않는다.

**여러 Predicate의 관계**

```yaml
- id: first-get-route
  uri: http://localhost:8081
  predicates:
    - Path=/first-service/**
    - Method=GET
```

이 라우트 목록의 부분 예제는 경로 조건과 메서드 조건을 **모두** 만족해야 한다. 서로 다른 Predicate는 AND로 결합된다. 하나의 `Path` Predicate에 여러 경로 패턴을 넣으면 그 패턴 중 하나에 매칭되는 조건으로 사용할 수 있다.

#### 2.5 경로를 유지할지, 접두사를 제거할지

|구성|Gateway가 받은 경로|내부 서비스에 전달한 경로|내부 Controller의 매핑|
|---|---|---|---|
|경로 변환 필터 없음|`/first-service/welcome`|`/first-service/welcome`|`/first-service` + `/welcome`|
|`StripPrefix=1` 적용|`/first-service/welcome`|`/welcome`|`/welcome`|

`StripPrefix=1`은 경로 앞의 한 구간을 제거한다. 다음은 라우트 목록에 넣을 **부분 설정**이다.

```yaml
- id: first-strip-route
  uri: http://localhost:8081
  predicates:
    - Path=/first-service/**
  filters:
    - StripPrefix=1
```

이 설정을 적용하면서 Controller에 `@RequestMapping("/first-service")`를 그대로 두면 전달된 `/welcome`과 매핑이 맞지 않아 404가 발생할 수 있다. 이 문서의 기본·최종 예제는 접두사를 유지하므로 `StripPrefix`를 사용하지 않는다.

> 경로 조건과 경로 변환을 따로 읽는다. `Path`는 라우트를 고르고, `StripPrefix` 같은 필터가 실제 전달 경로를 바꾼다.

#### 2.6 Java 코드로 라우트와 헤더 필터 등록하기

YAML 대신 Java의 `RouteLocatorBuilder`로도 같은 구조를 정의할 수 있다. 다음은 **학습용 대체 설정**인 `FilterConfig.java`다.

```java
package com.example.apigateway.config;

import org.springframework.cloud.gateway.route.RouteLocator;
import org.springframework.cloud.gateway.route.builder.RouteLocatorBuilder;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class FilterConfig {

    @Bean
    public RouteLocator gatewayRoutes(RouteLocatorBuilder builder) {
        return builder.routes()
                .route("first-route", r -> r
                        .path("/first-service/**")
                        .filters(f -> f
                                .addRequestHeader("f-request", "first-header-by-java")
                                .addResponseHeader("f-response", "first-response-by-java"))
                        .uri("http://localhost:8081"))
                .route("second-route", r -> r
                        .path("/second-service/**")
                        .filters(f -> f
                                .addRequestHeader("s-request", "second-header-by-java")
                                .addResponseHeader("s-response", "second-response-by-java"))
                        .uri("http://localhost:8082"))
                .build();
    }
}
```

|Java 표현|의미|YAML 대응|
|---|---|---|
|`.route("first-route", ...)`|하나의 라우트 정의|`id: first-route`|
|`.path(...)`|경로 선택 조건|`predicates`의 `Path`|
|`.filters(...)`|필터 등록|`filters`|
|`.addRequestHeader(...)`|내부로 보낼 요청에 헤더 추가|`AddRequestHeader`|
|`.addResponseHeader(...)`|클라이언트에 보낼 응답에 헤더 추가|`AddResponseHeader`|
|`.uri(...)`|전달 대상 지정|`uri`|
|`.build()`|라우트 목록 생성|설정에서 라우트 목록을 읽는 결과에 해당|

`r -> ...`는 라우트 조건을 구성하는 람다이고, `f -> ...`는 필터들을 구성하는 람다다. `@Bean`은 생성한 `RouteLocator`를 Spring이 관리하도록 등록한다.

같은 경로의 Java 라우트와 YAML 라우트를 함께 등록하면 규칙이 중복되거나 의도한 필터가 선택되지 않을 수 있다. 아래와 뒤의 최종 YAML을 사용한다면 이 Java 대체 설정은 함께 활성화하지 않는다.

#### 2.7 YAML로 요청·응답 헤더 추가하기

헤더는 HTTP 메시지에 붙는 이름과 값의 부가 정보다. 예를 들어 요청 헤더는 인증 정보나 내부 전달 값을, 응답 헤더는 콘텐츠 형식이나 처리 정보를 담는다.

다음은 `spring.cloud.gateway.server.webflux.routes`에 넣을 라우트 목록의 교체 예제다.

```yaml
- id: first-route
  uri: http://localhost:8081
  predicates:
    - Path=/first-service/**
  filters:
    - AddRequestHeader=f-request,first-header-by-yaml
    - AddResponseHeader=f-response,first-response-by-yaml
- id: second-route
  uri: http://localhost:8082
  predicates:
    - Path=/second-service/**
  filters:
    - AddRequestHeader=s-request,second-header-by-yaml
    - AddResponseHeader=s-response,second-response-by-yaml
```

|필터|적용 구간|값의 사용 위치|
|---|---|---|
|`AddRequestHeader=f-request,...`|Gateway → First Service|First의 `@RequestHeader("f-request")`|
|`AddResponseHeader=f-response,...`|Gateway → 클라이언트 응답|브라우저 응답 헤더, `curl -i`|
|`AddRequestHeader=s-request,...`|Gateway → Second Service|Second의 `@RequestHeader("s-request")`|
|`AddResponseHeader=s-response,...`|Gateway → 클라이언트 응답|브라우저 응답 헤더, `curl -i`|

`AddRequestHeader=이름,값`처럼 축약형을 쓰면 쉼표 앞은 헤더 이름, 뒤는 추가할 값이다. 헤더 이름은 대소문자를 구분하지 않지만, `f-request`와 `first-request`는 서로 다른 이름이다.

#### 2.8 헤더를 어느 구간에서 확인해야 하는가

```text
브라우저가 /first-service/message 요청
    ↓ Gateway의 요청 헤더 필터
내부 요청에 f-request 추가
    ↓ First Service에 HTTP 요청 전달
Controller가 f-request를 읽고 로그 기록
    ↓ 업무 응답 반환
Gateway가 f-response를 응답에 추가
    ↓
클라이언트가 본문과 응답 헤더 수신
```

|확인하려는 값|확인 위치|이유|
|---|---|---|
|브라우저가 처음 보낸 요청 헤더|브라우저 Network의 Request Headers|브라우저 → Gateway 구간이다.|
|Gateway가 추가한 `f-request`|First Service 로그 또는 Controller|Gateway → 내부 서비스 구간에서 추가된다.|
|Gateway가 추가한 `f-response`|브라우저 Response Headers, `curl -i`|클라이언트가 받는 응답에 포함된다.|
|처리한 인스턴스의 포트|`/check` 응답|내부 서버의 실제 로컬 포트를 본문에 넣었다.|

Gateway가 내부 요청에 추가한 헤더는 브라우저가 원래 보낸 요청 헤더 목록에 소급해서 나타나지 않는다. 서로 다른 HTTP 통신 구간이기 때문이다.

```bash
curl -i http://localhost:8000/first-service/message
curl -i http://localhost:8000/second-service/message
```

First 응답에서 확인할 값의 예는 다음과 같다. 실제 HTTP 헤더의 표시 순서와 대소문자는 달라질 수 있다.

```text
응답 상태: 200 OK
응답 헤더: f-response: first-response-by-yaml
응답 본문: Hello World in First Service.

First Service 로그:
First Service received f-request=first-header-by-yaml
```

**내부 서비스를 직접 호출하는 경우**에는 Gateway의 필터를 거치지 않는다.

```bash
curl -i http://localhost:8081/first-service/message
curl -i -H "f-request: manual-test" http://localhost:8081/first-service/message
```

첫 번째 호출은 필수 `f-request` 헤더가 없어 400이 발생할 수 있다. 두 번째는 헤더를 직접 제공한다. 이 차이는 `/message`의 헤더 요구 조건과 관련되며, 헤더를 요구하지 않는 `/welcome`이나 `/check`와 구분해야 한다.

브라우저에서 다른 출처의 응답 헤더를 JavaScript로 읽으려면 CORS의 응답 헤더 노출 설정이 필요할 수 있다. Network 탭에서 보인다는 것과 JavaScript에서 읽을 수 있다는 것은 별도 조건이다.

> 라우트의 조건, 전달 주소, 전달 경로, 헤더 적용 구간을 함께 추적한다. 요청 헤더는 내부 서비스에서, 응답 헤더는 클라이언트에서 확인하면 필터의 역할이 선명해진다.

### 3. WebFlux 필터의 객체와 실행 흐름

헤더 추가처럼 정해진 처리는 기본 필터로 구성할 수 있다. 요청 ID를 기록하거나 설정 값에 따라 로그를 켜고 끄려면 사용자 정의 필터가 필요하다. 이때 먼저 요청·응답 객체와 비동기 처리 흐름을 이해해야 한다.

#### 3.1 필터 코드에 등장하는 객체

|타입|역할|주요 사용 예|
|---|---|---|
|`ServerWebExchange`|한 요청의 요청·응답·속성 등을 묶는 처리 문맥|`exchange.getRequest()`, `exchange.getResponse()`|
|`ServerHttpRequest`|Gateway가 받은 HTTP 요청의 표현|요청 ID, URI, 헤더 조회|
|`ServerHttpResponse`|클라이언트에 보낼 HTTP 응답의 표현|상태 코드, 응답 헤더 설정|
|`GatewayFilterChain`|남아 있는 필터와 라우팅 처리를 연결|`chain.filter(exchange)`|
|`GatewayFilter`|요청별로 실행할 필터 함수|`(exchange, chain) -> ...`|
|`Mono<Void>`|처리의 완료 또는 오류를 전달하는 비동기 결과|다음 처리와 후속 작업 연결|

`ServerWebExchange`는 요청별 작업 묶음처럼 생각할 수 있다. 동일한 요청의 필터들이 이 문맥을 받아 다음 단계로 전달한다. Gateway의 reactive 요청 타입과 내부 MVC 서비스의 `HttpServletRequest`는 서로 다른 API다.

#### 3.2 요청·응답 객체는 언제 만들어지는가

필터에서 `getRequest()`를 먼저 호출한 뒤 `getResponse()`를 호출한다고 해서 그 줄에서 각각의 HTTP 객체가 새로 만들어지는 것은 아니다.

WebFlux Gateway가 요청을 받는 과정은 다음과 같이 이해할 수 있다.

```text
Reactor Netty가 HTTP 요청을 수신
    ↓ Spring의 HTTP 어댑터가 연결
요청을 표현하는 ServerHttpRequest 래퍼 준비
    ↓ 같은 초기화 과정에서 순차적으로 준비
응답을 표현하는 ServerHttpResponse 래퍼 준비
    ↓ WebFlux의 요청 처리 문맥 구성
ServerWebExchange 준비
    ↓ 웹 처리와 라우트 선택
GlobalFilter와 라우트 필터의 체인 실행
```

이 예제의 Reactor Netty 연동에서는 Spring의 `ReactorHttpHandlerAdapter`가 요청·응답 래퍼를 준비하여 WebFlux 처리로 넘긴다. 두 객체는 같은 초기화 과정 안에서 순차적으로 준비되며, 정확히 같은 순간에 생성된다는 의미는 아니다.

**Gateway의 첫 필터가 실행될 때는 요청 객체와 응답 객체가 이미 준비되어 있다.** 따라서 다음 두 메서드는 현재 문맥에서 객체를 꺼내는 동작이다.

```java
ServerHttpRequest request = exchange.getRequest();
ServerHttpResponse response = exchange.getResponse();
```

|구분|의미|
|---|---|
|요청 객체가 준비됨|요청 정보를 읽고 처리할 수 있는 객체가 있다.|
|요청 본문이 모두 읽힘|본문 스트림을 실제로 소비한 상태다. 객체 준비와 별개다.|
|응답 객체가 준비됨|상태·헤더·본문을 설정할 대상이 있다.|
|응답이 완성됨|필요한 처리와 응답 데이터 작성이 이루어진 상태다.|
|응답이 커밋됨|상태·헤더가 전송 단계에 들어가 자유롭게 바꾸기 어려워진 상태다.|

응답 객체가 있다는 것은 업무 결과가 이미 정해졌다는 뜻이 아니다. 아직 명시적으로 상태를 설정하지 않았다면 `response.getStatusCode()`가 `null`일 수도 있다.

**Gateway와 내부 서비스는 Java 객체를 공유하지 않는다.** Gateway가 내부 서비스에 새 HTTP 요청을 보내면 내부 서비스도 자신의 요청·응답 객체를 만든다. 경로·헤더·본문 같은 HTTP 정보가 전달되는 것이다.

**CORS Preflight와도 구분한다.** 브라우저의 `OPTIONS` 사전 요청은 별도의 HTTP 요청이며, 자신의 요청 처리 문맥을 가진다. 사전 요청이 응답 객체를 먼저 만들어 주어야 본 요청을 처리할 수 있는 구조는 아니다.

#### 3.3 요청을 바꾸면 변경한 문맥을 다음 단계로 전달하기

WebFlux 요청 정보를 변경할 때는 빌더로 변경한 요청을 만들고, 그것을 담은 exchange를 체인에 전달한다. 다음은 필터 내부에 넣는 **부분 예제**다.

```java
ServerHttpRequest changedRequest = exchange.getRequest()
        .mutate()
        .header("x-example", "gateway-value")
        .build();

ServerWebExchange changedExchange = exchange.mutate()
        .request(changedRequest)
        .build();

return chain.filter(changedExchange);
```

변경한 객체를 만들어 놓고 원래 `exchange`를 전달하면 의도한 요청 변경이 다음 단계에 반영되지 않을 수 있다. 단순한 헤더 추가에는 앞에서 본 `AddRequestHeader`를 사용할 수 있다.

#### 3.4 Pre·Post와 `Mono<Void>` 읽기

Pre는 다음 단계로 넘기기 전의 처리이고, Post는 연결한 다음 처리의 완료 후 이어지는 처리다. WebFlux에서는 두 부분을 별개의 동기 호출처럼 실행하기보다 비동기 흐름으로 조합한다.

```java
// GatewayFilter 람다의 본문에 들어가는 부분 예제
log.info("PRE");

return chain.filter(exchange)
        .then(Mono.fromRunnable(() -> {
            log.info("POST");
        }));
```

|표현|의미|
|---|---|
|`chain.filter(exchange)`|남은 필터와 라우팅 처리를 이어갈 `Mono<Void>`를 얻는다.|
|`.then(...)`|앞 흐름이 정상 완료되면 다음 비동기 작업으로 이어진다.|
|`Mono.fromRunnable(...)`|해당 단계가 실행될 때 Runnable의 작업을 수행한다.|
|`return`|조합한 전체 흐름을 프레임워크에 돌려준다.|

`Mono<T>`는 최대 하나의 값을 전달하고 완료하거나, 오류를 전달하는 Reactor 타입이다. `Mono<Void>`는 값을 전달하는 대신 **완료·오류 신호**로 처리 결과를 연결한다.

`Mono<Void>`를 반환한다고 HTTP 응답 본문이 비어 있어야 하는 것은 아니다. 응답 본문은 HTTP 응답 처리 과정에서 작성되며, 필터의 반환값은 그 처리의 완료를 나타낸다.

```text
필터의 Pre 처리
    ↓ 다음 단계의 흐름 반환
남은 필터와 라우팅 처리
    ↓ 내부 서비스 응답 처리
앞 흐름이 정상 완료
    ↓ then에 연결한 작업 실행
필터의 Post 처리
    ↓
전체 흐름 완료
```

`chain.filter(exchange)`는 Controller만 직접 호출하는 메서드가 아니다. 다음 필터와 실제 전달·응답 처리까지 남아 있는 체인을 진행시킨다.

필터 안에서 `.block()`으로 기다리면 처리 스레드를 막을 수 있다. `.subscribe()`를 따로 호출하면 프레임워크가 관리하는 흐름과 분리될 수 있다. **조합한 Mono를 반환하여 프레임워크가 실행을 관리하게 한다.**

#### 3.5 Post 실행 조건과 응답 수정 시점

|상황|`.then(Mono.fromRunnable(...))`의 후속 작업|
|---|---|
|앞 흐름의 정상 완료|실행한다.|
|앞 흐름에서 오류 신호 발생|일반적으로 실행하지 않는다.|
|완료 전에 구독이 취소됨|정상 완료 후속 작업이 생략될 수 있다.|
|HTTP 500 응답을 정상적으로 전달함|reactive 흐름이 정상 완료라면 실행할 수 있다.|

**HTTP 오류 상태와 비동기 오류 신호는 같은 개념이 아니다.** 내부 서비스의 500 응답을 정상적으로 전달하는 경우와, 네트워크 연결 실패로 처리 흐름이 오류 종료되는 경우를 구분한다.

오류 관찰에는 `doOnError`, 종료 종류 관찰에는 `doFinally` 등을 사용할 수 있다. 다만 `doFinally` 실행 시점의 상태가 언제나 최종 클라이언트 응답 상태를 보장하는 것은 아니다.

**체인을 계속 진행하지 않는 경우**도 있다. 아래는 접근을 거부하고 응답을 끝내는 부분 예제다.

```java
exchange.getResponse().setStatusCode(HttpStatus.FORBIDDEN);
return exchange.getResponse().setComplete();
```

이 경우 해당 분기에서는 `chain.filter(exchange)`를 호출하지 않으므로 남은 필터나 내부 서비스까지 진행하지 않는다.

**응답 헤더 변경은 커밋 전에 이루어져야 한다.** 단순히 Post 위치에 코드를 적었다고 안전한 수정 시점이 보장되지는 않는다. 체인 순서에 따라 Post가 응답 쓰기 이후에 실행될 수 있다.

```java
// 응답이 커밋되기 전에 미리 등록하는 부분 예제
exchange.getResponse().beforeCommit(() -> {
    exchange.getResponse().getHeaders()
            .set("x-example-response", "gateway-value");
    return Mono.empty();
});

return chain.filter(exchange);
```

`beforeCommit`은 ‘커밋 직전에 할 일’을 미리 등록하는 방식이다. 기본적인 응답 헤더 추가는 `AddResponseHeader`로 구성할 수도 있다.

#### 3.6 필터 Factory와 요청별 Filter 구분

Factory는 설정을 받아 필터를 만들어 주는 객체다. Filter는 그렇게 만들어진 요청 처리 함수다.

```text
Spring이 @Component Factory를 등록
    ↓ 라우트 설정을 읽음
YAML의 name으로 Factory를 찾음
    ↓ args를 Config에 바인딩
apply(Config)로 GatewayFilter 생성
    ↓ 라우트의 필터 체인 구성
요청마다 필터 람다 실행
```

`apply(Config)`가 필터를 만드는 단계와, `(exchange, chain) -> ...`가 요청마다 실행되는 단계는 다르다. 라우트를 다시 구성하면 Factory의 `apply`가 다시 호출될 수 있으므로 ‘프로그램 전체에서 한 번만 실행된다’고 단정하지 않는다.

|클래스·설정 요소|책임|
|---|---|
|`AbstractGatewayFilterFactory<Config>`|설정을 받아 Gateway 필터를 만드는 기반 클래스|
|`super(Config.class)`|사용할 설정 타입을 부모 Factory에 전달|
|`apply(Config config)`|설정을 적용한 `GatewayFilter` 생성|
|`(exchange, chain) -> ...`|각 요청의 실제 Pre·Post 처리|
|`@Component`|Spring이 Factory를 찾아 관리하도록 등록|
|YAML의 `name`|어떤 Factory를 사용할지 선택|
|YAML의 `args`|선택한 Factory의 Config 값 지정|

표준 이름 규칙은 `GatewayFilterFactory` 접미사를 제외한 이름을 YAML에서 사용하는 것이다.

|Java 클래스 이름|YAML의 `name`|
|---|---|
|`CustomFilterGatewayFilterFactory`|`CustomFilter`|
|`GlobalLogGatewayFilterFactory`|`GlobalLog`|
|`LoggingFilterGatewayFilterFactory`|`LoggingFilter`|

#### 3.7 CustomFilter: 특정 라우트의 Pre·Post 로그

다음 학습용 `CustomFilterGatewayFilterFactory.java`는 요청 ID와 응답 상태를 기록한다.

```java
package com.example.apigateway.filter;

import lombok.extern.slf4j.Slf4j;
import org.springframework.cloud.gateway.filter.GatewayFilter;
import org.springframework.cloud.gateway.filter.OrderedGatewayFilter;
import org.springframework.cloud.gateway.filter.factory.AbstractGatewayFilterFactory;
import org.springframework.http.server.reactive.ServerHttpRequest;
import org.springframework.http.server.reactive.ServerHttpResponse;
import org.springframework.stereotype.Component;
import reactor.core.publisher.Mono;

@Slf4j
@Component
public class CustomFilterGatewayFilterFactory
        extends AbstractGatewayFilterFactory<CustomFilterGatewayFilterFactory.Config> {

    public CustomFilterGatewayFilterFactory() {
        super(Config.class);
    }

    @Override
    public GatewayFilter apply(Config config) {
        GatewayFilter filter = (exchange, chain) -> {
            ServerHttpRequest request = exchange.getRequest();
            ServerHttpResponse response = exchange.getResponse();

            log.info("Custom PRE: request id={}", request.getId());

            return chain.filter(exchange)
                    .then(Mono.fromRunnable(() -> {
                        log.info("Custom POST: response status={}", response.getStatusCode());
                    }));
        };

        return new OrderedGatewayFilter(filter, 10);
    }

    public static class Config {
    }
}
```

현재 이 필터는 외부 설정 값을 받지 않아 Config가 비어 있다. 요청·응답 객체는 Pre 시점에 모두 꺼낼 수 있고, Post에서 같은 요청의 응답 정보를 읽는다. `OrderedGatewayFilter`의 `10`은 이 필터의 우선순위다.

해당 라우트의 `filters`에 다음 항목을 추가해야 실제로 연결된다.

```yaml
filters:
  - AddRequestHeader=f-request,first-header-by-yaml
  - AddResponseHeader=f-response,first-response-by-yaml
  - name: CustomFilter
```

Factory에 `@Component`를 붙이는 것만으로 모든 라우트에서 실행되지는 않는다. 등록된 Factory를 라우트 설정이 선택해야 한다.

#### 3.8 GlobalLog: 설정을 받아 여러 라우트에 공통 적용

공통 로그도 Factory로 만들고 `default-filters`에 등록할 수 있다. 다음은 학습용 `GlobalLogGatewayFilterFactory.java`다.

```java
package com.example.apigateway.filter;

import lombok.Data;
import lombok.extern.slf4j.Slf4j;
import org.springframework.cloud.gateway.filter.GatewayFilter;
import org.springframework.cloud.gateway.filter.OrderedGatewayFilter;
import org.springframework.cloud.gateway.filter.factory.AbstractGatewayFilterFactory;
import org.springframework.stereotype.Component;
import reactor.core.publisher.Mono;

@Slf4j
@Component
public class GlobalLogGatewayFilterFactory
        extends AbstractGatewayFilterFactory<GlobalLogGatewayFilterFactory.Config> {

    public GlobalLogGatewayFilterFactory() {
        super(Config.class);
    }

    @Override
    public GatewayFilter apply(Config config) {
        GatewayFilter filter = (exchange, chain) -> {
            log.info("GlobalLog baseMessage={}", config.getBaseMessage());

            if (config.isPreLogger()) {
                log.info("GlobalLog PRE: request id={}", exchange.getRequest().getId());
            }

            return chain.filter(exchange)
                    .then(Mono.fromRunnable(() -> {
                        if (config.isPostLogger()) {
                            log.info("GlobalLog POST: response status={}",
                                    exchange.getResponse().getStatusCode());
                        }
                    }));
        };

        return new OrderedGatewayFilter(filter, 0);
    }

    @Data
    public static class Config {
        private String baseMessage;
        private boolean preLogger;
        private boolean postLogger;
    }
}
```

`@Data`는 getter·setter 등을 생성한다. YAML의 `args`가 Config에 바인딩되고, 생성된 메서드로 값을 읽는다. boolean 필드의 getter는 `isPreLogger()`, `isPostLogger()` 형태다.

다음 부분 설정을 **`spring.cloud.gateway.server.webflux` 아래**, `routes`와 같은 깊이에 둔다.

```yaml
default-filters:
  - name: GlobalLog
    args:
      baseMessage: Common gateway log
      preLogger: true
      postLogger: true
```

|Config 값|처리 방식|
|---|---|
|`baseMessage`|매 요청에 출력할 기본 메시지|
|`preLogger`|요청 ID를 출력하는 Pre 로그 활성화 여부|
|`postLogger`|정상 완료 후 응답 상태 로그 활성화 여부|

`preLogger`와 `postLogger`는 해당 분기 로그를 제어한다. 위 코드의 `baseMessage` 로그까지 끄는 설정은 아니다. 값을 지정하지 않은 boolean은 기본적으로 `false`다.

#### 3.9 `default-filters`와 실제 `GlobalFilter` 비교

공통 적용 방법에는 설정으로 모든 라우트에 추가하는 방식과 실제 `GlobalFilter` 인터페이스를 구현하는 방식이 있다.

|비교 기준|Factory + `default-filters`|실제 `GlobalFilter` 구현|
|---|---|---|
|Java 기반|`AbstractGatewayFilterFactory<Config>`|`GlobalFilter` 인터페이스|
|등록 방법|Factory 빈 + YAML의 `name`|구현체를 Spring 빈으로 등록|
|설정 값|`args`를 Config에 바인딩|구현에 맞게 별도 설정|
|적용|기본 필터가 각 라우트에 추가됨|라우트가 선택되면 글로벌 필터 체인에 참여|
|순서|생성한 필터의 `Ordered` 값|구현체의 `Ordered` 값|
|클래스 이름|이름을 YAML에서 참조|클래스 이름 자체가 역할을 결정하지 않음|

다음 `TraceGlobalFilter.java`는 인터페이스를 비교하기 위한 **별도 학습용 예제**다. 뒤의 최종 조합은 앞뒤의 세 Factory를 사용한다.

```java
package com.example.apigateway.filter;

import lombok.extern.slf4j.Slf4j;
import org.springframework.cloud.gateway.filter.GatewayFilterChain;
import org.springframework.cloud.gateway.filter.GlobalFilter;
import org.springframework.core.Ordered;
import org.springframework.stereotype.Component;
import org.springframework.web.server.ServerWebExchange;
import reactor.core.publisher.Mono;

@Slf4j
@Component
public class TraceGlobalFilter implements GlobalFilter, Ordered {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        log.info("Trace PRE: request id={}", exchange.getRequest().getId());

        return chain.filter(exchange)
                .then(Mono.fromRunnable(() -> {
                    log.info("Trace POST: status={}", exchange.getResponse().getStatusCode());
                }));
    }

    @Override
    public int getOrder() {
        return -10;
    }
}
```

이 구현체는 YAML에서 `name: TraceGlobalFilter`로 Factory를 선택할 필요가 없다. `GlobalFilter` 빈이므로 Gateway가 필터 체인에 포함한다.

자료에 `GlobalFilter`라는 클래스 이름이 있어도 상속·구현한 타입을 확인해야 한다. 클래스가 `AbstractGatewayFilterFactory`를 상속하고 `default-filters`로 연결되어 있다면 Factory 방식이다.

여기서 ‘글로벌’은 Gateway에서 **라우트가 선택된 처리 흐름**의 범위다. 매칭되는 라우트가 없거나 더 앞 단계에서 CORS 처리가 끝난 요청까지 무조건 실행된다는 뜻은 아니다. WebFlux의 `WebFilter`와 Gateway의 `GlobalFilter`도 서로 다른 단계의 API다.

#### 3.10 LoggingFilter: 특정 라우트의 상세 로그

Second 라우트에만 상세 URI 로그를 추가하는 학습용 `LoggingFilterGatewayFilterFactory.java`다.

```java
package com.example.apigateway.filter;

import lombok.Data;
import lombok.extern.slf4j.Slf4j;
import org.springframework.cloud.gateway.filter.GatewayFilter;
import org.springframework.cloud.gateway.filter.OrderedGatewayFilter;
import org.springframework.cloud.gateway.filter.factory.AbstractGatewayFilterFactory;
import org.springframework.stereotype.Component;
import reactor.core.publisher.Mono;

@Slf4j
@Component
public class LoggingFilterGatewayFilterFactory
        extends AbstractGatewayFilterFactory<LoggingFilterGatewayFilterFactory.Config> {

    private static final int FILTER_ORDER = 20;

    public LoggingFilterGatewayFilterFactory() {
        super(Config.class);
    }

    @Override
    public GatewayFilter apply(Config config) {
        GatewayFilter filter = (exchange, chain) -> {
            log.info("Logging baseMessage={}", config.getBaseMessage());

            if (config.isPreLogger()) {
                log.info("Logging PRE: request uri={}", exchange.getRequest().getURI());
            }

            return chain.filter(exchange)
                    .then(Mono.fromRunnable(() -> {
                        if (config.isPostLogger()) {
                            log.info("Logging POST: response status={}",
                                    exchange.getResponse().getStatusCode());
                        }
                    }));
        };

        return new OrderedGatewayFilter(filter, FILTER_ORDER);
    }

    @Data
    public static class Config {
        private String baseMessage;
        private boolean preLogger;
        private boolean postLogger;
    }
}
```

Second 라우트의 `filters`에 다음 항목을 추가한다.

```yaml
- name: LoggingFilter
  args:
    baseMessage: Detailed second service log
    preLogger: true
    postLogger: true
```

`GlobalLog`와 Config 구조는 같지만 적용 범위와 로그 내용이 다르다. 공통 필터는 모든 라우트의 기본 기록을, 특정 라우트 필터는 필요한 상세 기록을 맡는다.

#### 3.11 필터 순서: 먼저 들어간 필터가 나중에 나온다

필터 체인은 겹겹이 감싼 구조다. 작은 `order`가 Pre에서 먼저 실행되고, 연결한 Post는 안쪽 작업부터 역순으로 풀린다.

|사용자 정의 필터|설정한 order|적용 범위|
|---|---|---|
|GlobalLog|0|`default-filters`로 두 라우트에 적용|
|CustomFilter|10|First·Second 라우트에 적용|
|LoggingFilter|20|Second 라우트에 적용|

Second 요청의 정상 완료를 가정하면, **이 세 사용자 정의 필터 사이**의 상대 순서는 다음과 같다.

```text
GlobalLog PRE        order 0
    ↓
Custom PRE           order 10
    ↓
Logging PRE          order 20
    ↓
내부 서비스 호출과 응답 처리
    ↓
Logging POST
    ↓
Custom POST
    ↓
GlobalLog POST
```

실제 체인에는 라우팅과 응답 쓰기를 위한 Gateway 내부 필터도 함께 들어간다. 위 흐름은 전체 내부 필터 목록이 아니라 예제 로그 필터의 상대 순서다. 오류, 취소, 중간 응답 종료가 있으면 정상 완료 시의 흐름과 달라질 수 있다.

**`HIGHEST_PRECEDENCE`를 사용하면**

```java
// LoggingFilter의 우선순위를 바꾸는 부분 예제
private static final int FILTER_ORDER = Ordered.HIGHEST_PRECEDENCE;
```

상수를 사용할 때는 `org.springframework.core.Ordered`를 import한다. `Ordered.HIGHEST_PRECEDENCE`는 `Integer.MIN_VALUE`다. 앞의 `20` 대신 이 값을 사용하면 세 로그 필터 중 Logging의 Pre가 가장 먼저, Post가 가장 나중에 실행된다. 같은 우선순위를 가진 다른 필터와의 세부 순서를 이 상수 하나로 보장할 수는 없다.

|순서 설정|무엇의 순서를 정하는가|
|---|---|
|라우트의 order|여러 후보 라우트 중 어떤 라우트를 먼저 검사할지|
|필터의 order|선택된 요청 처리 체인에서 필터가 어떻게 둘러싸일지|
|YAML의 필터 목록 위치|기본 구성 순서에 영향을 주지만 명시적 필터 order와 함께 판단해야 함|

> 필터는 이미 준비된 요청·응답 문맥을 받아 처리한다. `Mono<Void>`로 다음 처리와 완료 후 작업을 연결하고, 작은 order부터 들어가 큰 order부터 Post를 마친다.

### 4. Eureka와 LoadBalancer로 인스턴스 선택

지금까지는 Gateway에 `http://localhost:8081`처럼 전달 주소를 직접 적었다. 서비스 주소가 바뀌거나 같은 서비스를 여러 개 실행하면 고정 주소만으로는 관리가 어렵다. 서비스 검색과 인스턴스 선택을 연결하여 이 문제를 해결한다.

#### 4.1 고정 주소에서 서비스 이름으로 전환하기

|호출 대상 표현|Gateway가 알고 있는 것|주소 변화에 대한 처리|
|---|---|---|
|`http://localhost:8081`|특정 인스턴스의 호스트와 포트|주소가 바뀌면 라우트 설정도 영향을 받는다.|
|`lb://MY-FIRST-SERVICE`|호출할 논리적 서비스 이름|검색한 인스턴스 중 하나를 선택한다.|

Discovery는 현재 실행 중인 서비스의 위치를 찾는 기능이다. Eureka Server는 이름과 주소를 등록하는 명부 역할을 하고, Eureka Client는 자신의 위치를 등록하거나 명부를 조회한다.

Eureka Server가 업무 요청을 First Service로 대신 전달하는 것은 아니다. 업무 요청은 Gateway에서 선택된 인스턴스로 전달된다.

#### 4.2 Eureka Server 구성

Eureka Server 프로젝트에는 다음 starter를 추가한다. Spring Boot·Cloud 버전 관리는 앞의 기준을 따른다.

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-netflix-eureka-server</artifactId>
</dependency>
```

**학습용 예제: `DiscoveryServiceApplication.java`**

```java
package com.example.discovery;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.cloud.netflix.eureka.server.EnableEurekaServer;

@EnableEurekaServer
@SpringBootApplication
public class DiscoveryServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(DiscoveryServiceApplication.class, args);
    }
}
```

`@EnableEurekaServer`는 이 프로그램에 서비스 등록·조회 서버 역할을 활성화한다.

**단독 Eureka Server의 `application.yml`**

```yaml
server:
  port: 8761
spring:
  application:
    name: discovery-service
eureka:
  instance:
    hostname: localhost
  client:
    register-with-eureka: false
    fetch-registry: false
```

단독 서버 예제이므로 자신을 다른 Eureka에 등록하거나 다른 명부를 가져오는 Client 동작을 끈다. 이 두 값이 `false`여도 **Eureka Server의 등록·조회 기능은 동작한다.**

#### 4.3 Gateway와 내부 서비스를 Eureka Client로 연결

Gateway와 First·Second Service에는 Eureka Client starter와 다음 공통 설정을 사용한다.

```yaml
eureka:
  client:
    register-with-eureka: true
    fetch-registry: true
    service-url:
      defaultZone: http://localhost:8761/eureka/
```

|설정|의미|구분할 점|
|---|---|---|
|`register-with-eureka`|자신의 인스턴스를 Eureka에 등록|다른 서비스를 찾는 기능과 별개다.|
|`fetch-registry`|등록된 서비스 목록을 가져옴|Gateway가 이름으로 대상을 찾을 때 필요하다.|
|`service-url.defaultZone`|접속할 Eureka Server 주소|map 키인 `defaultZone` 표기를 유지한다.|
|`spring.application.name`|인스턴스가 속할 서비스 이름의 기준|같은 서비스의 인스턴스들은 같은 이름을 사용한다.|

등록과 조회는 독립된 설정이다. Gateway가 대상 서비스를 조회하려면 명부를 가져와야 하지만, 자기 자신을 반드시 등록해야만 다른 서비스를 검색할 수 있는 것은 아니다. 오늘의 예제에서는 설정을 통일하여 두 동작을 모두 켠다.

Eureka Client는 서비스 목록을 로컬에 캐시하고 주기적으로 갱신한다. **업무 요청마다 Eureka Server에 전체 목록을 새로 물어보는 구조로 이해하지 않는다.** 등록·조회와 갱신에는 시간이 걸릴 수 있다.

#### 4.4 서비스 이름·라우트 ID·인스턴스 ID

|이름|예|식별하는 대상|
|---|---|---|
|프로젝트 이름|`first-service`|개발 프로젝트나 폴더|
|애플리케이션 이름|`my-first-service`|서비스의 논리적 이름|
|Eureka에서 표시하는 이름|`MY-FIRST-SERVICE`|등록된 서비스 묶음|
|라우트 ID|`first-route`|Gateway의 전달 규칙|
|인스턴스 ID|`my-first-service:어떤-랜덤-값`|그 서비스의 개별 실행본|

같은 First Service를 두 번 실행하면 서비스 이름은 하나, 인스턴스 ID는 두 개가 된다. 애플리케이션 이름까지 각각 다르게 만들면 같은 서비스의 인스턴스 묶음으로 검색하기 어렵다.

Eureka 화면에서 확인할 것은 서비스 이름, 등록된 인스턴스 개수, 호스트·포트, 상태다. `UP`으로 표시된다는 것만으로 모든 업무 API의 정상 응답까지 검증된 것은 아니다.

#### 4.5 `lb://`와 LoadBalancer의 동작

라우트의 전달 대상을 다음처럼 바꾼다.

```yaml
- id: first-route
  uri: lb://MY-FIRST-SERVICE
  predicates:
    - Path=/first-service/**
- id: second-route
  uri: lb://MY-SECOND-SERVICE
  predicates:
    - Path=/second-service/**
```

위 코드는 라우트 목록의 부분 설정이다. 헤더와 사용자 정의 필터는 뒤의 최종 설정에서 함께 넣는다.

`lb://`는 Gateway에 LoadBalancer를 사용하라고 알려 주는 URI 방식이다. 브라우저가 직접 접속하는 주소도 아니고, 서비스 이름을 일반 DNS 주소로 바꾼 표현도 아니다.

```text
Gateway가 first-route 선택
    ↓ uri가 lb://MY-FIRST-SERVICE
Discovery에서 해당 서비스의 인스턴스 목록 확보
    ↓ 캐시된 등록 정보 등을 사용
LoadBalancer가 인스턴스 하나 선택
    ↓ 실제 호스트·포트 결정
선택한 인스턴스의 HTTP 주소로 요청 전달
```

명시적으로 `lb://` 라우트를 작성하는 경우 서비스 검색을 통한 자동 라우트 생성 기능을 별도로 켤 필요는 없다. 검색 기능과 자동 라우트 생성 기능은 구분한다.

**Round Robin의 의미**

Spring Cloud LoadBalancer의 기본 선택 구현은 Round Robin이다. 사용 가능한 인스턴스 목록을 순환하며 선택하는 방식으로 이해한다.

|서비스|인스턴스 A|인스턴스 B|선택 대상|
|---|---|---|---|
|First Service|8081|8083|First 요청은 First의 인스턴스 중 하나|
|Second Service|8082|8084|Second 요청은 Second의 인스턴스 중 하나|

하나의 요청을 모든 인스턴스에 동시에 보내는 방식은 아니다. 첫 호출이 언제나 A로 시작하거나 실제 관찰 결과가 반드시 `A → B → A → B`가 된다고 보장하지도 않는다. 동시 요청, 목록 갱신, 인스턴스 상태와 선택 정책에 따라 관찰 결과가 달라질 수 있다.

**Client-side Load Balancing에서 Client는 누구인가?**

이 예제에서는 Gateway가 내부 서비스를 호출하는 클라이언트다. 인스턴스 선택 기능이 Gateway의 호출 처리 안에 있으므로 클라이언트 측 부하 분산이라고 부른다. 브라우저가 서비스 인스턴스를 직접 고른다는 뜻은 아니다.

#### 4.6 랜덤 포트와 인스턴스 ID

같은 주소·포트에서 두 서버를 실행하면 충돌할 수 있다. 포트를 직접 다르게 지정할 수도 있고, 다음처럼 운영체제가 사용 가능한 포트를 고르게 할 수도 있다.

```yaml
server:
  port: 0
spring:
  application:
    name: my-first-service
eureka:
  instance:
    hostname: localhost
    instance-id: "${spring.application.name}:${random.value}"
```

`server.port: 0`은 실제로 0번 포트에서 서비스를 제공하겠다는 뜻이 아니다. 실행할 때 사용 가능한 포트가 배정된다.

|항목|의미|예|
|---|---|---|
|설정한 포트|실행 전 지정한 값|`server.port=0`|
|실제 포트|서버가 실행하며 바인딩한 번호|51057 등 실행 시 배정된 값|
|서비스 이름|같은 기능을 제공하는 인스턴스의 묶음|`my-first-service`|
|인스턴스 ID|실행본을 구분하는 이름|이름과 랜덤 값의 조합|

`${spring.application.name}`은 애플리케이션 이름을 가져오고, `${random.value}`는 Spring의 랜덤 값을 사용한다. 실제 포트와 다른 기준으로 인스턴스 ID를 만들기 때문에 랜덤 포트로 여러 번 실행할 때도 실행본을 구분하기 쉽다.

이 예제의 `hostname: localhost`는 같은 컴퓨터에서 실행하는 구성을 위한 것이다. 여러 컴퓨터나 컨테이너에서 실행한다면 Gateway가 접속할 수 있는 주소를 등록해야 한다.

#### 4.7 모든 기능을 연결하는 최종 설정

다음 설정은 **WebFlux 라우팅 + 헤더 필터 + 세 사용자 정의 Factory + Eureka + LoadBalancer**를 함께 사용하는 조합이다. 앞의 고정 주소 설정을 이 설정으로 교체한다.

|준비 대상|사용할 구성|
|---|---|
|Gateway 라우트|아래 YAML 라우트 정의|
|Gateway 사용자 정의 필터|`CustomFilterGatewayFilterFactory`, `GlobalLogGatewayFilterFactory`, `LoggingFilterGatewayFilterFactory`|
|비교용 코드|Java 라우트 `FilterConfig`와 `TraceGlobalFilter`는 별도 예제로 분리|
|내부 서비스 API|앞의 First·Second Controller|
|내부 서비스 포트|최종 예제에서는 `0`, 필요하면 실행 옵션으로 고정 포트 지정|
|검색 서버|앞의 Eureka Server 구성|

**① Gateway의 `application.yml`**

```yaml
server:
  port: 8000

spring:
  application:
    name: apigateway-service
  cloud:
    gateway:
      server:
        webflux:
          default-filters:
            - name: GlobalLog
              args:
                baseMessage: Common gateway log
                preLogger: true
                postLogger: true

          routes:
            - id: first-route
              uri: lb://MY-FIRST-SERVICE
              predicates:
                - Path=/first-service/**
              filters:
                - AddRequestHeader=f-request,first-header-by-yaml
                - AddResponseHeader=f-response,first-response-by-yaml
                - name: CustomFilter

            - id: second-route
              uri: lb://MY-SECOND-SERVICE
              predicates:
                - Path=/second-service/**
              filters:
                - AddRequestHeader=s-request,second-header-by-yaml
                - AddResponseHeader=s-response,second-response-by-yaml
                - name: CustomFilter
                - name: LoggingFilter
                  args:
                    baseMessage: Detailed second service log
                    preLogger: true
                    postLogger: true

eureka:
  instance:
    hostname: localhost
  client:
    register-with-eureka: true
    fetch-registry: true
    service-url:
      defaultZone: http://localhost:8761/eureka/
```

`default-filters`와 `routes`는 같은 계층에 있다. 공통 로그는 두 라우트에, 상세 Logging은 Second 라우트에 적용한다. `uri`가 서비스 이름으로 바뀌어도 공개 경로와 Controller의 경로는 유지된다.

**② First Service의 `application.yml`**

```yaml
server:
  port: 0

spring:
  application:
    name: my-first-service

eureka:
  instance:
    hostname: localhost
    instance-id: "${spring.application.name}:${random.value}"
  client:
    register-with-eureka: true
    fetch-registry: true
    service-url:
      defaultZone: http://localhost:8761/eureka/
```

**③ Second Service의 `application.yml`**

```yaml
server:
  port: 0

spring:
  application:
    name: my-second-service

eureka:
  instance:
    hostname: localhost
    instance-id: "${spring.application.name}:${random.value}"
  client:
    register-with-eureka: true
    fetch-registry: true
    service-url:
      defaultZone: http://localhost:8761/eureka/
```

같은 서비스의 인스턴스를 두 개 실행할 때는 해당 프로젝트를 두 번 실행한다. `spring.application.name`은 유지하고, 포트와 인스턴스 ID로 실행본을 구분한다.

#### 4.8 한 요청을 끝까지 추적하기

최종 구성에서 `GET /second-service/message`를 요청한다고 가정한다.

```text
클라이언트가 localhost:8000으로 요청
    ↓ WebFlux 요청 문맥 준비
Path 조건으로 second-route 선택
    ↓ 선택한 라우트의 필터 체인 실행
GlobalLog·CustomFilter·LoggingFilter의 Pre 처리
    ↓ 내부 요청 준비
s-request 헤더가 포함된 전달 요청 구성
    ↓ lb://MY-SECOND-SERVICE 해석
Second Service 인스턴스 목록에서 하나 선택
    ↓ 선택한 주소로 HTTP 요청
/second-service/message의 Controller 실행
    ↓ s-request를 읽고 응답 생성
응답 처리와 s-response 헤더 추가
    ↓ 정상 완료 시 안쪽부터 후속 작업 실행
LoggingFilter·CustomFilter·GlobalLog의 Post 처리
    ↓
클라이언트에 응답 전달
```

이 흐름은 핵심 역할을 묶어 표현한 것이다. 모든 내부 필터의 정확한 위치나 응답 바이트가 전송되는 시점을 나열한 것은 아니다. Pre·Post 순서는 세 사용자 정의 필터의 상대 순서를 보여 준다.

정상 응답의 상태가 200으로 설정되고 Pre·Post 로그가 모두 켜진 경우, 사용자 정의 로그에서 확인할 순서의 예는 다음과 같다.

```text
GlobalLog baseMessage=Common gateway log
GlobalLog PRE: request id=...
Custom PRE: request id=...
Logging baseMessage=Detailed second service log
Logging PRE: request uri=http://localhost:8000/second-service/message

[Second Service 로그]
Second Service received s-request=second-header-by-yaml

[Gateway 후속 로그]
Logging POST: response status=200 OK
Custom POST: response status=200 OK
GlobalLog POST: response status=200 OK
```

Gateway 로그와 내부 서비스 로그는 서로 다른 프로세스에서 출력된다. 한 요청의 전체 흐름을 확인할 때는 두 위치를 함께 보며, 여러 요청이 섞이면 요청 ID 등의 식별 기준도 함께 사용한다.

> 같은 서비스 이름 아래 여러 인스턴스를 등록한다. Eureka가 알려 주는 주소 목록과 LoadBalancer의 선택을 연결하면 Gateway의 공개 주소를 유지하면서 내부 실행본을 바꿀 수 있다.

### 5. 실행 방법과 오류 확인 기준

설정과 코드의 의미를 알았다면, 실행한 프로그램이 그 구성대로 연결되는지 확인해야 한다. 이 절에서는 학습용 구성의 실행 절차와 확인 기준을 정리한다. 오류 항목은 해당 증상이 나타났을 때 사용할 점검 기준이다.

#### 5.1 실행과 확인의 순서

```text
Eureka Server를 8761에서 실행
    ↓ 등록할 서버가 준비됨
First·Second Service 실행
    ↓ 이름·주소·포트 등록
Eureka에서 각 서비스의 인스턴스 확인
    ↓ 호출하는 쪽 준비
Gateway를 8000에서 실행
    ↓ 명부 조회·갱신 확인
Gateway 주소로 API 요청
    ↓
응답·헤더·서비스 로그·실제 포트 확인
```

이 순서는 등록과 연결을 관찰하기 쉬운 학습용 절차다. 서버가 실행되었다는 로그만 보지 말고, 내부 서비스 직접 호출과 Gateway 경유 호출을 나누어 확인한다.

|확인 단계|볼 대상|판단할 내용|
|---|---|---|
|프로그램 실행|시작 로그, 실제 포트|해당 프로세스가 정상적으로 실행됐는가?|
|내부 서비스 직접 호출|`/welcome`, `/check`|Controller 경로와 서비스 자체가 동작하는가?|
|서비스 등록|Eureka의 이름·인스턴스 목록|예상한 서비스 이름과 주소로 등록됐는가?|
|Gateway 경유 호출|Gateway의 공개 API 경로|라우트 조건과 전달 대상이 맞는가?|
|필터 처리|응답 헤더, 내부 서비스 로그|필요한 헤더와 로그가 해당 구간에 적용됐는가?|
|부하 분산|여러 번 호출한 `/check` 결과|같은 서비스의 여러 포트가 처리에 참여하는가?|

#### 5.2 같은 서비스를 여러 인스턴스로 실행하기

**IntelliJ 실행 옵션의 위치**

|옵션을 넣는 위치|예|해석|
|---|---|---|
|VM options|`-Dserver.port=8083`|JVM 시스템 속성|
|Program arguments|`--server.port=8083`|Spring Boot 애플리케이션 인자|

First 프로젝트의 실행 설정을 두 개 만들어 각각 8081과 8083을 지정하면 된다. Second는 8082와 8084로 지정할 수 있다. 이미 실행 중인 프로세스가 종료되지 않도록 별도 실행 설정이나 다중 인스턴스 실행 옵션도 확인한다.

**Maven으로 실행하기**

다음 두 명령은 **First 프로젝트의 루트에서 각각 별도 터미널**로 실행하는 예다.

```bash
mvn spring-boot:run "-Dspring-boot.run.jvmArguments=-Dserver.port=8081"
mvn spring-boot:run "-Dspring-boot.run.jvmArguments=-Dserver.port=8083"
```

다음은 **Second 프로젝트의 루트에서 각각 별도 터미널**로 실행한다.

```bash
mvn spring-boot:run "-Dspring-boot.run.jvmArguments=-Dserver.port=8082"
mvn spring-boot:run "-Dspring-boot.run.jvmArguments=-Dserver.port=8084"
```

`spring-boot:run`은 Maven의 Spring Boot 플러그인 goal이다. `spring-boot.run.jvmArguments`는 실행할 애플리케이션 JVM에 넘기는 옵션이고, 그 안의 `-Dserver.port=...`가 포트를 지정한다. 인자 전체를 따옴표로 감싸면 셸이 나누어 해석하는 문제를 줄일 수 있다.

최종 YAML의 `server.port: 0`을 그대로 사용하려면 포트 덮어쓰기 옵션 없이 같은 프로젝트를 여러 터미널에서 실행할 수 있다.

```bash
mvn spring-boot:run
```

프로젝트에 Maven Wrapper가 준비되어 있다면 환경에 맞게 `./mvnw` 또는 `mvnw.cmd`를 사용할 수도 있다.

**JAR로 빌드하여 실행하기**

각 프로젝트 루트에서 빌드한다.

```bash
mvn clean package
```

|Maven 단계|의미|
|---|---|
|`clean`|이전 빌드 산출물 정리|
|`compile`|소스 컴파일|
|`test`|테스트 실행|
|`package`|앞선 빌드 단계를 거쳐 JAR 등 산출물 생성|

`package`를 수행하면 컴파일 단계도 포함된다. 필요에 따라 `mvn clean package -DskipTests`로 테스트 실행을 건너뛸 수 있지만, 일반적으로 테스트 소스 컴파일까지 생략하는 옵션은 아니다.

아래 JAR 파일 이름은 **예시**다. 실제 `target`에 생성된 파일 이름으로 바꾼다. 각 실행은 별도 터미널에서 진행한다.

```bash
java -Dserver.port=8081 -jar ./target/first-service-0.0.1-SNAPSHOT.jar
java -Dserver.port=8083 -jar ./target/first-service-0.0.1-SNAPSHOT.jar
```

애플리케이션 인자를 사용하는 대체 방식도 가능하다.

```bash
java -jar ./target/first-service-0.0.1-SNAPSHOT.jar --server.port=8083
```

|실행 형식|옵션 위치|
|---|---|
|JVM 시스템 속성|`java` 다음, `-jar` 앞에 `-Dserver.port=...`|
|Spring Boot 인자|JAR 파일 이름 뒤에 `--server.port=...`|

소스나 설정을 수정한 뒤 기존 JAR를 실행하면 이전 빌드 내용이 사용된다. JAR 방식으로 변경을 확인할 때는 산출물을 다시 빌드해야 한다.

#### 5.3 설정한 포트와 실제 포트 조회하기

랜덤 포트에서는 설정 값 `0`과 실제 서버 포트를 구분하는 것이 중요하다. 랜덤 포트는 **서버를 시작할 때** 정해지며, 같은 인스턴스가 요청마다 새 포트를 배정받는 것은 아니다.

|조회 방법|얻는 값|적절한 시점·주의점|
|---|---|---|
|`server.port`|실행 설정에서 지정한 포트|랜덤 포트 설정이면 `0`일 수 있다.|
|`local.server.port`|서버 시작 후 알려지는 실제 포트|서버 초기화가 완료된 뒤 조회한다.|
|`request.getLocalPort()`|이 요청을 받은 서버의 실제 로컬 포트|`/check`에서 처리 인스턴스를 확인하는 데 적합하다.|
|`request.getServerPort()`|요청에서 표현되는 서버 포트|프록시·전달 헤더 처리에 따라 클라이언트가 보는 포트를 나타낼 수 있다.|
|Eureka 등록 정보|해당 인스턴스에 접속할 주소·포트|실제 실행 주소와 검색 정보가 일치하는지 확인한다.|

앞의 Controller는 요청 처리 시점에 `request.getLocalPort()`를 사용한다. Gateway 뒤에서 어떤 내부 인스턴스가 처리했는지 확인하려는 목적에 맞는 방법이다.

**`@Value`의 문자열과 placeholder 구분**

다음은 주입 문법을 설명하는 부분 코드다.

```java
@Value("local.server.port")
private String port;
```

이 코드는 설정 값을 조회하는 표현이 아니다. 문자열 `local.server.port` 자체를 주입한다. 응답에 이 필드를 출력하면 포트 번호 대신 해당 문자열이 나올 수 있다.

```java
@Value("${local.server.port}")
private String port;
```

`${...}`는 설정 placeholder를 조회하는 문법이다. 하지만 문법을 고쳤다는 것과 값이 그 시점에 준비되었다는 것은 별개다. 일반 빈의 필드 주입 시점에는 서버가 아직 시작되지 않아 `local.server.port`를 해석하지 못할 수 있다.

```text
설정 파일과 실행 옵션 읽기
    ↓ Spring 빈 생성·의존성 주입
일반 @Value 필드 주입이 이루어질 수 있음
    ↓ 웹 서버 시작
실제 포트 결정
    ↓ 서버 초기화 완료
local.server.port 값 제공
    ↓ 요청 처리
getLocalPort() 또는 준비된 Environment 값 조회
```

|표현|해석|적용 기준|
|---|---|---|
|`@Value("local.server.port")`|문자열 자체를 주입|포트 조회에 사용하지 않는다.|
|`@Value("${server.port}")`|설정한 포트를 주입|`0`과 실제 포트의 차이를 고려한다.|
|`@Value("${local.server.port}")`|실제 포트 속성을 조회|서버 초기화 전 주입이면 값이 아직 없을 수 있다.|
|`environment.getProperty("local.server.port")`|호출 시점에 Environment에서 조회|주입된 `Environment`로 서버 시작 후 조회한다.|
|`request.getLocalPort()`|현재 요청의 로컬 포트 조회|이 문서의 MVC `/check`에서 사용한다.|

> 실제 포트를 출력하려면 올바른 키뿐 아니라 조회 시점도 맞아야 한다. 요청을 처리한 인스턴스를 확인할 때는 요청 시점의 `getLocalPort()`가 명확하다.

#### 5.4 최종 구성에서 확인할 API와 결과

아래 경로는 모두 **Gateway의 `http://localhost:8000` 뒤에 붙여 호출**한다.

|경로|확인할 응답·처리|검증하는 역할|
|---|---|---|
|`/first-service/welcome`|`Welcome to the First service.`|First 라우트와 Controller 연결|
|`/second-service/welcome`|`Welcome to the Second service.`|Second 라우트와 Controller 연결|
|`/first-service/message`|First 메시지, `f-response`, 내부 `f-request` 로그|First의 요청·응답 헤더 처리|
|`/second-service/message`|Second 메시지, `s-response`, 내부 `s-request` 로그|Second의 헤더와 상세 로그 처리|
|`/first-service/check`|처리한 First 인스턴스의 포트|First 서비스 검색·인스턴스 선택|
|`/second-service/check`|처리한 Second 인스턴스의 포트|Second 서비스 검색·인스턴스 선택|

```bash
curl -i http://localhost:8000/first-service/welcome
curl -i http://localhost:8000/second-service/welcome
curl -i http://localhost:8000/first-service/message
curl -i http://localhost:8000/second-service/message
curl -i http://localhost:8000/first-service/check
curl -i http://localhost:8000/second-service/check
```

Windows PowerShell에서 `curl`이 다른 명령의 별칭으로 동작하면 실제 curl 실행 파일을 지정한다.

```powershell
curl.exe -i http://localhost:8000/first-service/message
curl.exe -i http://localhost:8000/first-service/check
```

**부하 분산을 확인하는 절차**

1. 같은 서비스의 인스턴스를 두 개 실행한다.
2. Eureka에서 같은 서비스 이름 아래 두 인스턴스가 등록되었는지 확인한다.
3. Gateway가 갱신된 목록을 가져올 수 있도록 등록·조회 상태를 확인한다.
4. 같은 `/check` API를 여러 번 호출한다.
5. 응답에 나온 포트를 실행 로그와 Eureka 등록 정보에 대조한다.

First를 고정 포트 8081과 8083으로 실행했다면 다음과 같은 **서로 다른 처리 포트**가 관찰 대상이다.

```text
Hi, there. This is a message from First Service on PORT 8081.
Hi, there. This is a message from First Service on PORT 8083.
```

랜덤 포트라면 실행 시 배정된 다른 번호가 나타난다. 결과가 한 포트로만 나온다면 먼저 인스턴스 등록 수, 이름, Gateway의 목록 갱신, 실행한 API와 선택 정책을 확인한다.

#### 5.5 증상별 오류 확인 기준

오류는 ‘클라이언트 → Gateway → 인스턴스 선택 → 내부 서비스’ 중 어느 단계에서 발생했는지 좁혀야 한다. 상태 코드 하나만으로 원인을 단정하기보다, 직접 호출과 Gateway 경유 호출의 차이를 함께 본다.

|증상|우선 확인할 원인 후보|확인·수정 기준|
|---|---|---|
|`404 Not Found`|라우트 불일치, 설정 경로 불일치, 내부 Controller 경로 불일치|요청 경로·Predicate·설정 prefix·전달 경로·Controller 매핑을 순서대로 대조한다.|
|`StripPrefix` 적용 후 404|전달된 경로와 Controller의 공통 경로가 다름|접두사를 유지하거나, 제거한 경로에 맞게 Controller를 구성한다.|
|`/message` 직접 호출 시 400|필수 `f-request` 또는 `s-request`가 없음|`@RequestHeader` 이름을 확인하고 헤더를 제공한다.|
|`lb://` 호출 시 503|선택 가능한 인스턴스가 없을 수 있음|Eureka 이름·등록 상태·Client 조회·LoadBalancer 의존성을 확인한다.|
|`Connection refused`|대상 주소·포트 오류, 프로세스 종료, 오래된 등록 정보|같은 주소를 직접 호출하고 실제 실행 포트와 등록 정보를 대조한다.|
|`Port already in use`|다른 프로세스가 같은 주소·포트를 사용|실행본마다 다른 포트를 쓰거나 `server.port: 0`으로 구성한다.|
|Factory를 찾을 수 없음|YAML 이름, 클래스 이름 규칙, 컴포넌트 검색 범위 불일치|`...GatewayFilterFactory` 접미사·YAML name·`@Component`·패키지 위치를 확인한다.|
|WebFlux Gateway가 MVC 환경으로 실행|Gateway starter 혼합, `spring-boot-starter-web` 추가|Gateway의 의존성을 선택한 웹 방식에 맞춘다.|
|설정 변경이 반영되지 않음|들여쓰기, 중복 키, 활성 프로필, 실행 옵션, 잘못된 버전 경로|실제로 읽는 설정 파일과 덮어쓰기 값을 확인한다.|
|Eureka에 인스턴스가 하나만 보임|실제 실행본 하나, 동일한 인스턴스 ID, 이름 분리|프로세스 수·서비스 이름·서로 다른 instance-id를 확인한다.|
|Post 로그가 없음|설정 값 false, 오류·취소, 중간 응답 종료|`postLogger`와 정상 완료 여부, `chain.filter` 호출 경로를 확인한다.|
|로그 순서가 예상과 다름|명시적 order, 글로벌·라우트 필터의 합성, 내부 필터 개입|전체 체인의 order와 Pre·Post 역순 관계를 확인한다.|
|`Unknown lifecycle phase`|Maven goal 오타, 인자 사이 공백 누락, 잘못된 셸 해석|`spring-boot:run`의 콜론과 인자 구분을 확인한다.|
|`Unable to access jarfile`|현재 디렉터리, 파일 이름·경로, 빌드 산출물 문제|실제 생성한 JAR와 `./target/...` 경로를 확인한다.|
|`log`, getter·setter를 찾을 수 없음|Lombok 의존성·어노테이션 처리 문제|`@Slf4j`, `@Data`, 빌드 도구의 Lombok 처리를 확인한다.|
|포트 대신 `local.server.port` 출력|`@Value`에 placeholder 문법이 없음|문자열 주입과 `${...}` 조회 문법을 구분한다.|
|`local.server.port` 해석 실패|실제 포트 제공 전의 일반 빈 주입|서버 시작 후 조회하거나 요청의 `getLocalPort()`를 사용한다.|

**상태 코드 해석의 범위**

- 인스턴스를 찾지 못한 Gateway의 기본 응답은 일반적으로 503이지만, 설정에 따라 다른 상태를 사용할 수 있다. 모든 503이 같은 원인인 것은 아니다.
- 404는 Gateway의 라우트 선택 단계에서도, 내부 서비스의 Controller 매핑 단계에서도 발생할 수 있다.
- Eureka의 `UP` 상태와 현재 네트워크 연결 가능 여부는 함께 확인해야 한다.
- 브라우저에 내부 요청 헤더가 보이지 않는 것은 확인 구간의 차이일 수 있다. 내부 서비스 로그를 먼저 확인한다.

**명령어에서 특히 확인할 점**

|확인 항목|올바른 형태|
|---|---|
|플러그인 goal|`spring-boot:run`|
|옵션 분리|goal 뒤에 공백을 두고 `-D...` 전달|
|컴파일 단계 철자|`compile`|
|JVM 옵션 위치|`java -D... -jar ...`|
|애플리케이션 옵션 위치|`java -jar ... --server.port=...`|
|JAR 경로|실제 파일 이름에 맞춘 `./target/파일명.jar`|

Bash 계열에서 Windows의 역슬래시 경로를 그대로 쓰면 역슬래시가 이스케이프 문자로 해석될 수 있다. 현재 셸에 맞는 경로를 사용하고, 산출물이 있는 위치에서 실행한다.

> 동작 확인은 단계별로 한다. 서비스 자체, 등록 정보, Gateway 라우트, 헤더, 필터 완료, 처리 포트를 차례로 대조하면 문제의 위치를 좁힐 수 있다.

## 🧠 오늘 이해한 핵심

1. **논리적 서비스 선택과 실제 인스턴스 선택은 두 단계다.** Route의 Predicate가 담당 서비스를 정하고, `lb://`와 서비스 검색·LoadBalancer가 실제 호출 주소를 정한다. 이 분리를 통해 공개 API 경로를 유지하면서 내부 실행본을 늘리거나 바꿀 수 있다.
2. **HTTP 정보의 전달과 Java 객체의 생성은 구분해야 한다.** Gateway의 요청·응답 문맥은 필터 실행 전에 준비되지만, 내부 서비스는 별도의 HTTP 요청을 받아 자신의 객체를 사용한다. 따라서 내부 요청 헤더와 외부 응답 헤더의 확인 위치도 달라진다.
3. **코드의 형태와 실행 시점을 함께 읽어야 한다.** `apply(Config)`는 필터를 만들고 요청별 람다는 실제 처리를 수행한다. `Mono<Void>`의 정상 완료 조건, 필터 order, 서버 시작 후 실제 포트 제공 시점을 구분해야 로그·후처리·포트 조회를 정확히 해석할 수 있다.

## 🔍 복습할 부분

- `/second-service/message` 한 요청을 기준으로 Predicate, 서비스 이름, 인스턴스 선택, `s-request`, Controller, `s-response`의 역할과 확인 위치를 다시 설명한다.
- 세 로그 필터의 order가 `0·10·20`일 때와 Logging이 `HIGHEST_PRECEDENCE`일 때의 Pre·Post 순서를 각각 적고, `default-filters`와 실제 `GlobalFilter`의 등록 방법을 비교한다.
- 요청·응답 객체 준비, 응답 완성, 응답 커밋을 구분하고, `Mono<Void>`의 정상 완료·오류·취소에 따라 `.then(...)`의 Post가 어떻게 달라지는지 확인한다.
- `server.port: 0`, `${local.server.port}`, `@Value` 주입 시점, `getLocalPort()`의 차이를 정리하고, 두 인스턴스의 `/check` 응답을 Eureka 등록 포트와 대조하는 절차를 복습한다.
