어제는 VM과 Kubernetes 클러스터를 연결하고 노드의 `Ready` 상태까지 확인했다. 오늘은 그 위에서 애플리케이션을 실행하고, 실행 개수와 버전을 관리하며, 사용자가 접속할 경로를 만드는 과정을 연결한다. 학습 자료는 [05번의 구축 이후 내용](https://lgcns-kubernetes-core-edu.oopy.io/k8s05), [06번 Kubernetes 소개와 아키텍처](https://lgcns-kubernetes-core-edu.oopy.io/k8s06), [07번 kubectl 명령어 실습](https://lgcns-kubernetes-core-edu.oopy.io/k8s07)이다.

아래 명령과 YAML은 강의 내용을 다시 따라 하기 위한 예제다. 강의 예제의 이름과 구조를 사용하되, 자원이 섞이지 않도록 `til-lab` 네임스페이스를 추가했다. 사용자 환경의 실제 실행 결과를 뜻하지 않으며, 강의에 포함된 EKS 출력도 오늘 EKS를 구축했다는 의미로 해석하지 않는다.

> Kubernetes에서는 실행할 애플리케이션의 원하는 상태를 선언하고, 그 상태를 유지할 관리 객체와 접속 경로를 함께 만든다.

### 1. 컨테이너를 원하는 상태로 유지하는 구조

컨테이너가 적을 때는 서버에 직접 접속해 실행할 수 있지만, 서버와 애플리케이션이 늘어나면 배치·장애 대응·업데이트를 사람이 계속 맞추기 어렵다. Kubernetes는 여러 서버를 묶고 컨테이너화된 애플리케이션의 배포·확장·관리를 조정하는 **컨테이너 오케스트레이션** 시스템이다.

#### 1.1 실행 명령보다 원하는 상태를 먼저 생각한다

식당에 “주방을 세 개 운영해 달라”고 주문하는 상황을 떠올리면 쉽다. 담당자는 현재 주방 수를 확인하고 부족하면 준비한다. Kubernetes에서도 `replicas: 3`처럼 원하는 상태를 적고, 컨트롤러가 현재 상태와의 차이를 계속 줄인다. 이런 반복적인 조정을 **reconciliation**이라고 한다.

| 기능 | 해결하는 문제 | 함께 필요한 조건 |
| --- | --- | --- |
| 스케줄링 | 어느 노드에서 실행할지 결정 | 자원 요청량·노드 상태·배치 조건 |
| 자동 복구 | 실행 중단 후 필요한 상태 복원 | 관리 컨트롤러·실행 가능한 자원 |
| 배포와 롤백 | 애플리케이션 버전 교체 | 올바른 이미지·템플릿·보관된 이력 |
| 수평 확장 | 처리할 실행 단위 수 조절 | 수동 scale 또는 별도의 자동 확장 설정 |

자동 복구가 고장 난 프로그램의 코드를 수정하거나 삭제된 데이터를 복원해 주는 것은 아니다. 잘못된 이미지나 설정을 반복해서 실행할 수도 있으므로, 무엇을 원하는 상태로 선언했는지와 실행 실패 원인을 함께 봐야 한다. [컨트롤러의 상태 조정 원리](https://kubernetes.io/docs/concepts/architecture/controller/)

#### 1.2 관리하는 구성요소와 실행하는 구성요소를 나눈다

**노드**는 클러스터에 참여하는 서버이고, 컨트롤 플레인은 클러스터를 관리하는 구성요소의 집합이다. 강의에서 마스터라고 부른 노드가 컨트롤 플레인을 실행하며, 워커 노드는 주로 애플리케이션을 실행한다.

| 구성요소 | 역할 | 쉽게 구분하는 기준 |
| --- | --- | --- |
| kube-apiserver | API 요청 처리·인증·인가·검증의 진입점 | 요청과 상태 조회의 창구 |
| etcd | 클러스터의 API 객체와 상태 저장 | 관리 정보의 저장소 |
| kube-scheduler | 아직 배치되지 않은 Pod의 노드 선택 | 어디서 실행할지 결정 |
| kube-controller-manager | 여러 컨트롤러의 상태 조정 반복 실행 | 원하는 상태와 현재 상태 비교 |
| kubelet | 자신에게 할당된 Pod의 실행 상태 관리 | 각 노드의 실행 담당 에이전트 |
| 컨테이너 런타임 | 이미지 준비와 실제 컨테이너 실행 | 이 환경에서는 containerd |
| kube-proxy | Service 통신을 위한 노드의 전달 규칙 관리 | 앱 실행과는 다른 네트워크 역할 |
| CoreDNS | Service 이름 등의 DNS 조회 제공 | 이름으로 서비스를 찾도록 지원 |

kubelet은 워커에만 있는 프로그램이 아니다. kubeadm으로 구성한 컨트롤 플레인 노드에서도 실행된다. 클라우드 연동을 담당하는 `cloud-controller-manager`는 구성에 따라 사용하며, 로컬 VM 클러스터에 반드시 존재하는 것은 아니다. [공식 구성요소 설명](https://kubernetes.io/docs/concepts/overview/components/)

#### 1.3 Pod 생성은 API에 기록된 상태를 각 담당자가 관찰하는 과정이다

**Pod**는 Kubernetes가 배치하고 실행하는 가장 작은 단위다. 하나 이상의 컨테이너를 포함하며, 같은 Pod의 컨테이너는 네트워크 공간을 공유한다. 단순한 웹 서버 예제에서는 Pod 하나에 컨테이너 하나를 넣는다.

다음은 단독 Pod 생성의 논리적 흐름이다. 각 단계가 한 번의 동기 함수 호출로 연결된다는 뜻은 아니다.

```text
kubectl이 Pod 생성을 API 서버에 요청
    ↓ 권한과 객체를 검증하고 상태를 저장
아직 실행 노드가 정해지지 않은 Pod 등록
    ↓ 스케줄러가 관찰하고 적절한 노드를 선택
Pod의 실행 노드가 API에 반영
    ↓ 해당 노드의 kubelet이 할당 내용을 확인
CRI를 통해 런타임에 컨테이너 실행 요청
    ↓ 필요한 이미지와 Pod 네트워크를 준비
노드에서 컨테이너 실행
    ↓ kubelet이 실행 상태를 보고
API를 통해 현재 Pod 상태 조회
```

강의의 “API 서버가 스케줄러와 kubelet을 호출한다”는 설명은 역할 순서를 이해하기 위한 단순화다. 실제로는 스케줄러와 kubelet 등이 API를 통해 관련 상태의 변화를 관찰하고 자신의 작업 결과를 반영한다. etcd에 각 구성요소가 직접 접속해 명령을 전달하는 구조로 이해하지 않는다.

Docker로 빌드한 이미지는 containerd 같은 호환 런타임에서도 실행할 수 있다. Kubernetes가 반드시 Docker Engine에 직접 실행 명령을 보낸다는 뜻은 아니다. 또한 **CNI**는 컨테이너 네트워크를 구성하는 인터페이스이며, 모든 CNI 플러그인이 VXLAN 방식인 것도 아니다.

#### 1.4 어제 만든 클러스터에서 오늘 작업할 준비를 확인한다

이후 `kubectl` 명령은 kubeconfig가 준비된 관리자 사용자 셸에서 실행한다. 예제 경로는 어제와 같은 Ubuntu 환경이며, 앱 자원은 학습용 `til-lab`에 모은다.

```bash
kubectl config current-context
kubectl get nodes -o wide
kubectl get pods -n kube-system
kubectl create namespace til-lab
mkdir -p /home/ubuntu/k8s
cd /home/ubuntu/k8s
```

`til-lab`이 이미 있으면 생성 명령 대신 `kubectl get namespace til-lab`으로 확인한다. `Ready`가 아닌 노드나 비정상 시스템 Pod가 있다면 어제의 런타임·CNI·kubelet 점검부터 이어간다. 앱이 실행되지 않는다는 이유만으로 클러스터 초기화 명령을 반복하지 않는다.

> API 서버는 요청과 상태의 창구, 스케줄러는 배치 담당, kubelet과 런타임은 노드의 실행 담당이다. 컨트롤러는 이 구조 위에서 원하는 상태를 계속 맞춘다.

### 2. kubectl과 YAML로 첫 Pod 실행하기

구성요소의 역할을 알았다면 이제 원하는 상태를 전달해야 한다. `kubectl`은 Kubernetes API에 요청하는 명령줄 도구이고, YAML 매니페스트는 만들거나 관리할 객체의 모습을 적는 문서다.

#### 2.1 명령을 동작·종류·이름·범위로 읽는다

기본 형태는 `kubectl 동작 리소스종류 이름 옵션`이다. 다음 명령에서 `get`은 조회, `pod`는 종류, `netflixweb-pod`는 이름, `-n til-lab`은 네임스페이스 범위다.

```bash
kubectl get pod netflixweb-pod -n til-lab -o wide
kubectl --help
kubectl logs --help
kubectl api-resources
```

첫 명령은 뒤에서 Pod를 만든 후 조회할 때 사용한다. `api-resources`는 서버가 제공하는 리소스 종류·약어·API 버전·네임스페이스 적용 여부를 보여 준다. kubeconfig 파일의 내용을 출력하는 명령은 아니다.

| 동작·옵션 | 의미 | 구분할 점 |
| --- | --- | --- |
| `run` | 단독 Pod 생성 | Deployment를 만들지 않음 |
| `create -f` | 파일의 객체 신규 생성 | 같은 이름이 있으면 일반적으로 실패 |
| `apply -f` | 파일의 선언을 생성·갱신 | 모든 필드를 자유롭게 바꿀 수 있는 것은 아님 |
| `get` | 목록·현재 객체 조회 | `-o wide`, `-o yaml`, `-o json`으로 표현 변경 |
| `describe` | 상세 상태·조건·관련 이벤트 확인 | 애플리케이션 출력 로그와 다름 |
| `logs` | 컨테이너의 표준 출력·표준 오류 조회 | `-f`로 추가 로그 계속 확인 |
| `edit` | API의 현재 객체를 편집해 반영 | 로컬 YAML은 자동으로 바뀌지 않음 |
| `delete -f` | 파일에 적힌 객체 삭제 | 로컬 YAML 파일 자체는 남음 |

`po`, `deploy`, `rs`, `svc`, `ns`, `no`는 각각 Pod·Deployment·ReplicaSet·Service·Namespace·Node의 약어다. `kubectl get all -A`의 `-A`는 모든 네임스페이스라는 뜻이지만, `all`이 Secret·ConfigMap·PV 등을 포함한 모든 리소스 종류를 뜻하지는 않는다.

#### 2.2 Bash 자동완성과 vi는 서로 다른 편의 기능이다

강의의 `alias k=kubectl`과 completion 설정은 셸 입력을 편하게 하는 기능이다. Bash를 사용하는 경우 `~/.bashrc`에 다음 세 줄을 한 번 추가한 뒤 적용한다. Zsh에서는 Bash 설정을 그대로 읽지 않고 Zsh용 completion 설정을 사용한다.

```bash
alias k=kubectl
source <(kubectl completion bash)
complete -F __start_kubectl k
```

```bash
source ~/.bashrc
k get nodes
```

YAML 들여쓰기는 편집기의 영역이다. Vim을 사용한다면 `:set expandtab tabstop=2 shiftwidth=2 autoindent`로 공백 두 칸 기준 편집을 준비할 수 있다. 실제 YAML에는 탭 대신 공백을 사용한다.

| vi·Vim 조작 | 의미 |
| --- | --- |
| `i` / `a` / `o` | 앞에서 입력 / 뒤에서 입력 / 아래 새 줄 입력 |
| `Esc` | 입력을 끝내고 일반 모드로 전환 |
| `h j k l` / `w b` | 좌하상우 이동 / 다음·이전 단어 이동 |
| `0` / `$` / `gg` / `G` | 줄 시작 / 줄 끝 / 파일 시작 / 파일 끝 |
| `yy` / `dd` / `p` | 줄 복사 / 줄 삭제 / 붙여넣기 |
| `/문자열` / `n` | 검색 / 다음 검색 결과 |
| `:w` / `:wq` / `:q!` | 저장 / 저장 후 종료 / 변경을 버리고 종료 |

일반 모드에서 `:`를 눌러 명령줄 모드로 들어간다. `kubectl edit`의 편집기에서 저장하고 종료하면 API 변경이 제출되므로, 파일을 열어 보기만 한 경우와 구분한다.

#### 2.3 출력 옵션과 dry-run의 효과를 구분한다

**명령형 방식**은 `run`, `create deployment`, `scale`처럼 지금 할 일을 명령한다. **선언형 방식**은 YAML에 원하는 상태를 저장하고 `apply`로 반영한다. YAML을 먼저 생성해 수정하면 실행 내용을 파일로 남기기 쉽다.

```bash
kubectl run webserver --image=nginx:1.14 --port=80 \
  --dry-run=client -o yaml > webserver.yaml
vi webserver.yaml
kubectl apply --dry-run=server -n til-lab -f webserver.yaml
kubectl apply -n til-lab -f webserver.yaml
```

`nginx:1.14`는 강의의 구버전 태그를 재현한 예다. 새 서비스를 운영할 때의 권장 버전이라는 뜻은 아니며, 강의용 이미지도 다시 사용할 시점에 태그 가용성을 확인한다.

| 형태 | 객체 생성 여부 | 확인되는 범위 |
| --- | --- | --- |
| `run ... -o yaml` | 생성됨 | 생성 요청 후 YAML로 출력 |
| `run ... --dry-run=client -o yaml` | 생성 안 됨 | 클라이언트에서 요청 객체 생성 |
| `apply --dry-run=server -f 파일` | 저장 안 됨 | API 서버의 검증·승인 과정 확인 |
| `apply -f 파일` | 생성 또는 갱신 | 서버에 선언 반영 |

`-o yaml`만 붙였다고 미리보기가 되는 것은 아니다. `>`는 셸이 출력을 파일에 저장하는 기능이며, 같은 파일에 다시 쓰면 덮어쓴다. 두 dry-run 모두 이미지 다운로드·컨테이너 실행·실제 접속 성공까지 검증하지는 않는다. [kubectl 공식 명령 참조](https://kubernetes.io/docs/reference/generated/kubectl/kubectl-commands)

#### 2.4 강의 Pod 예제에서 이름·이미지·자원을 함께 읽는다

다음은 강의의 `netflixweb.yaml` 본문이다. `metadata.name`은 Pod 이름, 컨테이너의 `name`은 Pod 내부에서 컨테이너를 구분하는 이름, `image`는 실행할 이미지 주소다.

```yaml title="netflixweb.yaml"
apiVersion: v1
kind: Pod
metadata:
  name: netflixweb-pod
  labels:
    app: nginx-app
spec:
  containers:
  - name: nginx-app
    image: powermvp/netflix:v2.0
    ports:
    - containerPort: 80
    resources:
      limits:
        cpu: 200m
        memory: 256Mi
      requests:
        cpu: 100m
        memory: 128Mi
```

YAML의 `apiVersion`은 객체를 다룰 API 버전, `kind`는 종류, `metadata`는 이름과 레이블 등 식별 정보, `spec`은 원하는 설정이다. `containerPort: 80`은 컨테이너의 포트 정보를 선언하며, 이것만으로 외부 접속 포트가 열리지는 않는다.

| 설정 | 이 예제의 값 | 해석 |
| --- | --- | --- |
| CPU request | `100m` | 배치 판단에 사용하는 CPU 0.1코어 요청량 |
| CPU limit | `200m` | CPU 0.2코어 한도이며 초과 사용 시 throttling 가능 |
| 메모리 request | `128Mi` | 배치 판단에 사용하는 메모리 요청량 |
| 메모리 limit | `256Mi` | 메모리 한도 초과 시 OOM 종료 가능 |

request는 현재 사용량도, 반드시 그만큼 계속 소비한다는 뜻도 아니다. limit 이하라면 request를 넘겨 사용할 수 있지만, 노드 사정과 자원 종류의 제약을 받는다. 메모리 한도를 넘긴다고 CPU처럼 속도만 줄어드는 것으로 이해하지 않는다. [컨테이너 자원 관리](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)

```bash
kubectl apply -n til-lab -f netflixweb.yaml
kubectl get pods -n til-lab -o wide
kubectl describe pod netflixweb-pod -n til-lab
kubectl logs netflixweb-pod -n til-lab -c nginx-app
kubectl exec -n til-lab -it netflixweb-pod -- /bin/sh
```

`exec`은 실행 중인 컨테이너 안에서 명령을 수행한다. `--` 뒤가 컨테이너에서 실행할 명령이며, 모든 이미지에 Bash가 있는 것은 아니므로 셸의 존재도 확인한다. 셸에 들어갔다면 `exit`로 빠져나온다.

#### 2.5 목록·이벤트·로그에서 서로 다른 정보를 찾는다

| 보고 싶은 것 | 명령 | 읽을 항목 |
| --- | --- | --- |
| 실행 상태와 배치 | `kubectl get pods -n til-lab -o wide` | `STATUS`, `READY`, 재시작 수, IP, 노드 |
| 실패 이유와 이벤트 | `kubectl describe pod netflixweb-pod -n til-lab` | Conditions·컨테이너 상태·Events |
| 프로그램이 남긴 출력 | `kubectl logs netflixweb-pod -n til-lab -c nginx-app` | 표준 출력·표준 오류 |
| 재시작 직전 출력 | `kubectl logs netflixweb-pod -n til-lab -c nginx-app --previous` | 남아 있는 이전 컨테이너 로그 |
| 네임스페이스 이벤트 | `kubectl get events -n til-lab --sort-by=.metadata.creationTimestamp` | 최근 생성·실패·스케줄링 이벤트 |

`Running`은 Pod의 실행 단계이고 `READY`는 준비된 컨테이너 수다. 둘을 같은 의미로 읽지 않는다. 이후 실제 서비스의 준비 상태를 세밀하게 판단하려면 애플리케이션에 맞는 readiness probe가 필요하다.

`watch kubectl get pods -n til-lab -o wide`는 보통 2초 간격으로 명령을 다시 실행해 화면을 갱신한다. `kubectl get pods -n til-lab -o wide --watch`는 초기 목록 뒤에 객체 변경을 이어서 보여 주며, 둘 다 `Ctrl+C`로 끝낸다.

> kubectl의 출력 형식은 실행 여부를 바꾸지 않는다. 생성 여부는 동작과 dry-run으로, 원인 확인은 상태·이벤트·로그의 차이로 판단한다.

### 3. Deployment로 복제와 배포 관리하기

단독 Pod를 만들 수 있어도 “같은 앱을 세 개 유지하고, 하나가 사라지면 다시 준비한다”는 운영 요구는 남는다. 이를 위해 Pod를 직접 반복 생성하기보다 Deployment에 실행 템플릿과 복제본 수를 맡긴다.

#### 3.1 Deployment·ReplicaSet·Pod는 관리 관계다

Deployment는 배포할 Pod 템플릿과 업데이트를 관리하고, 그 아래의 **ReplicaSet**이 필요한 Pod 수를 맞춘다. 관계는 `Deployment → ReplicaSet → Pod → 컨테이너`로 읽는다. 이 화살표는 네트워크 요청 경로가 아니라 관리 관계다.

| 상황 | 단독 Pod | Deployment가 관리하는 Pod |
| --- | --- | --- |
| 컨테이너 프로세스 종료 | restartPolicy에 따라 같은 Pod 안에서 재시작 가능 | 같은 Pod 안에서 재시작 가능 |
| Pod 객체 삭제 | 관리자가 없으면 새 Pod 생성 안 됨 | ReplicaSet이 필요한 수를 맞추도록 새 Pod 생성 |
| 실행 노드 장애 | 다른 노드에 대체 Pod를 만들어 줄 관리자가 없음 | 장애 감지·배치 조건 충족 후 대체 Pod 생성 가능 |
| 앱 버전 변경 | Pod의 변경 제한을 직접 고려 | 템플릿 변경을 통해 새 Pod로 교체 |

“단독 Pod는 복구가 안 된다”는 말은 **Pod 삭제 후 새 Pod를 보충할 컨트롤러가 없다**는 뜻이다. Pod 내부 컨테이너의 재시작까지 모두 불가능하다는 뜻은 아니다. 새 Pod의 이름·UID·IP와 로컬 데이터가 이전 Pod와 그대로 유지되는 것도 아니다.

#### 3.2 강의 Deployment를 만들고 관리 관계를 확인한다

먼저 앞 장의 단독 예제를 정리한다. `netflixweb-pod`와 뒤의 Deployment가 같은 `app: nginx-app` 레이블을 쓰므로, 함께 남겨 두면 Service의 선택 대상에 서로 다른 앱이 섞일 수 있다.

```bash
kubectl delete -n til-lab -f netflixweb.yaml
```

다음은 강의의 `nginx-deploy.yaml`이다. 강조한 selector와 Pod 템플릿의 레이블이 일치해야 하며, 실제 컨테이너 설정은 `spec.template.spec` 아래에 둔다.

```yaml title="nginx-deploy.yaml" {8-9,12-13}
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-app-deploy
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx-app
  template:
    metadata:
      labels:
        app: nginx-app
    spec:
      containers:
      - name: nginx-app
        image: powermvp/marvel-collection:v1.0
        ports:
        - containerPort: 80
        resources:
          limits:
            cpu: 200m
            memory: 256Mi
          requests:
            cpu: 100m
            memory: 128Mi
```

```bash
kubectl apply -n til-lab -f nginx-deploy.yaml
kubectl get deploy,rs,pods -n til-lab
kubectl rollout status deployment/nginx-app-deploy -n til-lab --timeout=120s
kubectl get pods -n til-lab -l app=nginx-app --show-labels -o wide
```

Pod 이름은 Deployment 이름과 같지 않다. 생성된 이름을 목록에서 확인해 개별 Pod 명령에 사용한다. `replicas: 3`이라고 해서 Pod 세 개가 반드시 서로 다른 노드에 하나씩 배치되는 것도 아니다.

#### 3.3 개수 조절과 삭제 후 보충은 원인이 다르다

별도 터미널에서 변경을 관찰하면서 복제본 수를 조절한다.

```bash
kubectl get pods -n til-lab -l app=nginx-app -o wide --watch
```

```bash
kubectl scale deployment nginx-app-deploy -n til-lab --replicas=5
kubectl get deployment nginx-app-deploy -n til-lab
kubectl scale deployment nginx-app-deploy -n til-lab --replicas=2
```

| 변경 | 원하는 수 | 관찰할 변화 |
| --- | --- | --- |
| 처음 생성 | 3 | 템플릿을 기반으로 Pod 생성 |
| scale out | 5 | 부족한 복제본 추가 |
| scale in | 2 | 초과 복제본 종료 |
| 관리되는 Pod 하나 삭제 | 2 그대로 | 부족해진 수를 새 Pod로 보충 |

삭제 실습은 `kubectl get pods -n til-lab -l app=nginx-app`에서 실제 이름을 확인한 후 `kubectl delete pod 실제Pod이름 -n til-lab`으로 진행한다. 종료·생성은 비동기적이므로 잠시 개수가 달라 보일 수 있으며, 항상 한 개씩 순서대로 종료된다고 단정하지 않는다.

수동 `scale`은 HPA 같은 자동 확장 설정과 다르다. 또한 로컬 파일에 여전히 `replicas: 3`이 남아 있으면 이후 `apply`에서 수동 조정이 다시 바뀔 수 있으므로, 최종 목표 개수와 파일을 맞춘다.

#### 3.4 YAML 생성 문제는 컨테이너 이름까지 확인한다

07번의 연습 조건은 Deployment `nginx-web`, 이미지 `nginx:1.14`, 컨테이너 이름 `web`, 복제본 3개다. 명령으로 틀을 만들면 컨테이너 이름이 자동 생성되므로 그 부분까지 직접 확인해야 한다.

```bash
kubectl create deployment nginx-web --image=nginx:1.14 --replicas=3 \
  --dry-run=client -o yaml > nginx-web.yaml
vi nginx-web.yaml
```

다음은 네 조건을 만족하도록 정리한 설명용 완성 예제다. 생성되는 관리 필드는 생략하고 필요한 선언만 남겼다.

```yaml title="nginx-web.yaml" {15-16}
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx-web
  template:
    metadata:
      labels:
        app: nginx-web
    spec:
      containers:
      - name: web
        image: nginx:1.14
        ports:
        - containerPort: 80
```

강조한 컨테이너 목록의 `name: web`이 문제 조건이다. `replicas`를 `5`로 바꾸고 저장한 다음 아래와 같이 검증·적용하면 다섯 개를 원하는 상태로 전달한다.

```bash
kubectl apply --dry-run=server -n til-lab -f nginx-web.yaml
kubectl apply -n til-lab -f nginx-web.yaml
kubectl get deployment nginx-web -n til-lab
```

Deployment의 컨테이너 이름처럼 Pod 템플릿에 속한 변경은 보통 템플릿 수정 후 적용해 교체할 수 있다. 기존 Deployment를 항상 삭제할 필요는 없다. 반면 `apps/v1` Deployment의 `spec.selector`는 생성 후 변경할 수 없으므로 같은 방법으로 바꿀 수 있는 필드가 아니다.

#### 3.5 버전 변경·재시작·일시정지·롤백을 구분한다

**rollout**은 변경된 Pod 템플릿을 실행 중인 Pod에 반영하는 배포 과정이다. 이미지·컨테이너 설정 등 템플릿 변경과 단순 복제본 수 변경은 다르며, scale만으로 새 배포 revision이 생기지는 않는다.

| 명령 | 목적 | 주의할 의미 |
| --- | --- | --- |
| `kubectl rollout status deploy/nginx-web -n til-lab` | 배포 진행·완료 확인 | 완료가 앱의 모든 기능 정상까지 보장하지는 않음 |
| `kubectl rollout history deploy/nginx-web -n til-lab` | 보관된 배포 revision 확인 | 모든 설정 변경을 기록하는 감사 로그와 다름 |
| `kubectl rollout history deploy/nginx-web -n til-lab --revision=1` | 특정 revision 템플릿 확인 | 실제 존재하는 revision 선택 |
| `kubectl rollout pause deploy/nginx-web -n til-lab` | 템플릿 변경의 rollout 일시정지 | 실행 중인 앱을 종료하는 명령 아님 |
| `kubectl rollout resume deploy/nginx-web -n til-lab` | 멈췄던 rollout 재개 | pause와 짝으로 사용 |
| `kubectl rollout restart deploy/nginx-web -n til-lab` | Pod를 교체하는 재시작 유도 | 노드 재부팅이나 자동 이미지 버전 갱신이 아님 |
| `kubectl rollout undo deploy/nginx-web -n til-lab` | 이전 revision 템플릿으로 되돌림 | 이전 이력이 있어야 하며 데이터까지 복원하지 않음 |
| `kubectl rollout undo deploy/nginx-web -n til-lab --to-revision=1` | 지정한 revision으로 되돌림 | history를 먼저 확인 |

이미지를 바꾸려면 YAML의 `spec.template.spec.containers` 안 `image`를 실제 사용할 버전으로 수정하고 `apply`한다. RollingUpdate 전략에서는 새 Pod를 준비하면서 이전 Pod를 줄이지만, 여유 자원·준비 상태·업데이트 전략에 따라 실제 가용성이 달라진다. 배포 실패를 감지했다고 Kubernetes가 항상 자동 롤백하는 것도 아니다. pause 상태에서 롤백하려면 먼저 resume해야 한다.

현재 객체를 `kubectl edit deployment nginx-web -n til-lab`으로 수정했다면 로컬 YAML도 맞춰 둔다. `kubectl get deployment nginx-web -n til-lab -o yaml`은 상태·관리 필드가 포함된 현재 객체 조회이므로, 그대로 깨끗한 새 배포 파일이라고 생각하지 않는다. [Deployment의 업데이트·revision·변경 제한](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)

> Pod를 지우는 것은 실행 인스턴스를 없애는 일이고, Deployment의 목표를 바꾸는 것은 계속 유지할 상태를 바꾸는 일이다. 복제본 수 조절과 버전 배포도 서로 다른 변경이다.

### 4. Service로 애플리케이션 접속 경로 만들기

Deployment가 Pod를 교체하면 접속할 Pod IP도 달라질 수 있다. **Service**는 Pod 하나의 주소를 직접 외우는 대신 일정한 이름과 접속 지점을 제공한다. 어떤 Pod에 연결할지는 이름의 유사성이 아니라 레이블과 selector로 결정한다.

#### 4.1 레이블은 대상을 고르고 포트는 접속 지점을 연결한다

강의 Service의 selector는 `app: nginx-app`이다. 같은 네임스페이스에서 이 레이블을 가진 Pod가 대상이 되므로, 앞에서 만든 `nginx-app-deploy`의 Pod와 연결되고 `app: nginx-web`인 연습용 Pod는 제외된다.

| 항목 | 예제 값 | 의미 |
| --- | --- | --- |
| Pod 레이블 | `app: nginx-app` | Pod에 붙은 분류 정보 |
| Service selector | `app: nginx-app` | 연결할 Pod를 고르는 조건 |
| `port` | `80` | 클러스터에서 Service로 접속할 포트 |
| `targetPort` | `80` | 대상 Pod의 애플리케이션 포트 |
| `nodePort` | `30080` | NodePort 방식에서 노드 주소로 접속할 포트 |

EndpointSlice는 Service가 연결할 엔드포인트 주소와 준비 상태 등을 담는다. Service 이름과 Deployment 이름이 같아야 하는 것은 아니며, Service를 만들었다고 애플리케이션 프로세스가 자동으로 해당 포트에서 수신하는 것도 아니다.

#### 4.2 ClusterIP를 만들고 port-forward로 확인한다

다음은 강의의 내부용 Service다. 기본 타입도 ClusterIP이며, 여기서는 의미를 분명히 하기 위해 명시한다.

```yaml title="nginx-clusterIp.yaml"
apiVersion: v1
kind: Service
metadata:
  name: nginx-app-clusterip
spec:
  selector:
    app: nginx-app
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80
  type: ClusterIP
```

```bash
kubectl apply -n til-lab -f nginx-clusterIp.yaml
kubectl get svc -n til-lab
kubectl port-forward -n til-lab svc/nginx-app-clusterip 8080:80
```

port-forward를 실행한 셸은 그대로 두고, **같은 머신의 다른 터미널**에서 확인한다.

```bash
curl http://127.0.0.1:8080
```

`8080:80`은 kubectl을 실행한 머신의 로컬 8080을 Service가 선택한 Pod의 해당 포트로 연결한다는 뜻이다. VM에서 실행했다면 노트북 브라우저의 `localhost`는 그 VM이 아니다. port-forward는 임시 터널이므로 외부 공개용 Service로 바뀐 것도 아니며, Service의 실제 ClusterIP 전달 경로 전체를 검증하는 테스트도 아니다.

#### 4.3 NodePort와 LoadBalancer는 접속을 제공하는 방식이 다르다

다음은 강의의 NodePort 예제다. ClusterIP 예제와 동시에 존재할 수 있지만, 강의처럼 전환해서 확인하려면 앞의 port-forward를 `Ctrl+C`로 끝내고 `kubectl delete -n til-lab -f nginx-clusterIp.yaml`로 이전 Service를 정리한다.

```yaml title="nginx-nodePort.yaml"
apiVersion: v1
kind: Service
metadata:
  name: nginx-app-nodeport
spec:
  selector:
    app: nginx-app
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80
    nodePort: 30080
  type: NodePort
```

```bash
kubectl apply -n til-lab -f nginx-nodePort.yaml
kubectl get svc nginx-app-nodeport -n til-lab
kubectl get nodes -o wide
curl http://10.0.2.11:30080
```

`10.0.2.11`은 어제 정리한 워커 주소 예시다. 실제 노드 IP로 바꾸고, 그 IP에 도달할 수 있는 머신에서 요청한다. VM NAT·호스트 라우팅·방화벽 설정에 따라 외부 PC에서 바로 접속되지 않을 수 있다.

| Service 타입 | 기본 접속 지점 | 필요한 환경 |
| --- | --- | --- |
| ClusterIP | 클러스터 내부의 Service IP·DNS 이름 | 내부 통신 환경 |
| NodePort | 접근 가능한 노드 IP와 nodePort | 노드까지의 경로·포트 허용 |
| LoadBalancer | 외부 로드밸런서의 주소 | 클라우드 연동 또는 별도 LB 구현 |

NodePort의 기본 할당 범위는 `30000–32767`이다. `nodePort`를 생략하면 할당되지만 이 예제는 `30080`을 지정했으므로 매번 임의 포트를 고르는 예가 아니다. `127.0.0.1:30080` 접속 여부는 구현·설정에 따라 달라지므로 노드 IP를 기준으로 이해한다.

기존 Deployment로 Service를 만드는 명령형 방법도 있다. 다음은 앞의 YAML 방식과 구분한 별도 예제이며, 같은 실습에서 불필요하게 모두 만들 필요는 없다.

```bash
kubectl expose deployment nginx-web -n til-lab \
  --name=nginx-web-svc --port=80 --target-port=80 --type=LoadBalancer
kubectl get svc nginx-web-svc -n til-lab
```

로컬 kubeadm 클러스터에서 외부 LB 구현이 없다면 주소가 `Pending`에 머물 수 있다. 타입을 적는 것만으로 외부 장비가 준비되지는 않는다. [Service 타입과 NodePort](https://kubernetes.io/docs/concepts/services-networking/service/)

#### 4.4 접속 실패는 대상 선택과 포트부터 나누어 확인한다

```bash
kubectl get pods -n til-lab -l app=nginx-app --show-labels -o wide
kubectl describe service nginx-app-nodeport -n til-lab
kubectl get endpointslices -n til-lab \
  -l kubernetes.io/service-name=nginx-app-nodeport -o yaml
```

먼저 같은 네임스페이스의 selector가 실제 Pod 레이블과 맞는지, Pod가 준비됐는지 확인한다. 다음으로 애플리케이션 수신 포트와 `targetPort`를 비교하고, NodePort라면 노드 IP까지의 경로와 포트 허용을 확인한다.

> Service의 연결 대상은 레이블로, 도착 포트는 targetPort로 정한다. 외부에서 접속할 수 있는지는 Service 타입과 실제 네트워크 환경을 함께 봐야 한다.

### 5. 상태 확인과 비공개 이미지 인증 준비하기

Pod가 만들어졌다는 사실만으로 운영 상태를 판단하기는 어렵다. CPU·메모리의 현재 사용량을 보려면 Metrics API가 필요하고, 비공개 저장소의 이미지를 실행하려면 노드가 이미지를 가져올 인증 정보가 필요하다.

#### 5.1 Metrics Server는 설정한 자원과 실제 사용량을 구분하게 해 준다

`requests`와 `limits`는 선언한 설정이고, `kubectl top`은 Metrics API가 제공하는 최근 CPU·메모리 사용량을 보여 준다. Metrics Server는 kubelet에서 사용량을 모아 이 API로 제공하며, 장기 시계열을 보관하는 Prometheus 같은 모니터링 저장소와 역할이 다르다.

강의의 `releases/latest` URL은 실행 시점에 다른 버전을 가리킬 수 있다. 어제 설치 예시인 Kubernetes `1.32`에서는 공식 호환표의 Metrics Server `0.8.x` 계열을 선택할 수 있다. 다음은 [v0.8.0 릴리스](https://github.com/kubernetes-sigs/metrics-server/releases/tag/v0.8.0)를 고정한 재현 예제이며, 다른 클러스터 버전에서는 [공식 호환표와 전제조건](https://github.com/kubernetes-sigs/metrics-server)을 먼저 확인한다.

```bash
kubectl version
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.8.0/components.yaml
kubectl rollout status deployment/metrics-server -n kube-system --timeout=120s
kubectl get apiservice v1beta1.metrics.k8s.io
kubectl top nodes
kubectl top pods -n til-lab
```

처음 설치한 직후에는 수집 전이라 값이 없을 수 있다. 계속 실패하면 `kubectl logs -n kube-system deployment/metrics-server`와 `kubectl describe apiservice v1beta1.metrics.k8s.io`로 인증서·통신·API 연결 문제를 나누어 본다. `top`이 안 된다는 사실만으로 애플리케이션 Pod가 고장 났다고 판단하지 않는다.

> [!WARNING]
> 강의의 `--kubelet-insecure-tls`는 Metrics Server가 kubelet 인증서를 검증하지 않도록 하는 실습용 우회 옵션이다. 인증서 오류를 확인한 격리된 학습 환경에서만 선택하고, 운영 환경은 올바른 kubelet 인증서와 신뢰 관계를 준비한다.

아래는 그 실습 조건에서만 적용하는 원문 패치다. 정상 설치에 항상 필요한 단계가 아니며, 같은 인자를 반복 추가하지 않는다.

```bash
kubectl patch deployment metrics-server -n kube-system \
  --type='json' \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl rollout status deployment/metrics-server -n kube-system --timeout=120s
kubectl top pods -n kube-system
```

#### 5.2 Docker 로그인과 Kubernetes의 이미지 pull 인증은 별도다

관리 PC에서 `docker login`을 했더라도 Kubernetes 워커의 런타임이 그 로그인 정보를 자동으로 사용하는 것은 아니다. 강의는 ECR 로그인 비밀번호를 Kubernetes Secret으로 저장하고, Pod의 `imagePullSecrets`에 연결하는 방식을 사용한다.

아래는 강의의 계정 번호 대신 자신의 AWS 계정을 조회하도록 바꾼 설명용 예제다. AWS CLI 인증과 ECR pull 권한, 앞서 올린 `ecr-nginx:v2.0` 이미지가 준비되어 있어야 한다. 다른 계정의 저장소를 사용할 때는 해당 저장소 주소와 교차 계정 권한을 별도로 확인한다.

```bash
AWS_REGION=ap-northeast-2
ECR_ACCOUNT_ID="$(aws sts get-caller-identity --query Account --output text)"
ECR_REGISTRY="${ECR_ACCOUNT_ID}.dkr.ecr.${AWS_REGION}.amazonaws.com"
kubectl create secret docker-registry ecr-secret \
  --docker-server="$ECR_REGISTRY" \
  --docker-username=AWS \
  --docker-password="$(aws ecr get-login-password --region "$AWS_REGION")" \
  --namespace=til-lab --dry-run=client -o yaml \
  | kubectl apply -f -
kubectl get secret ecr-secret -n til-lab
```

파이프 앞은 Secret 객체를 출력하고, 뒤의 `apply -f -`는 표준 입력에서 읽어 반영한다. 같은 방식으로 새 비밀번호를 반영할 수 있지만 Secret의 갱신이 자동 예약되는 것은 아니다. 비밀번호와 Secret 내용을 로그·스크린샷·공개 저장소에 남기지 않는다.

ECR 인증 토큰은 **12시간 유효**하므로, 한 번 생성한 Secret을 계속 재사용할 수 있다고 가정하지 않는다. 토큰 만료가 이미 실행 중인 컨테이너를 즉시 종료시키는 것은 아니지만, 이후 이미지가 필요한 새 Pod나 새 노드에서 pull에 실패할 수 있다. [ECR 비공개 레지스트리 인증](https://docs.aws.amazon.com/AmazonECR/latest/userguide/registry_auth.html)

#### 5.3 imagePullSecrets는 Pod 설정에 연결한다

다음은 강의 ECR Pod를 `til-lab`에 맞춰 정리한 설명용 예제다. `YOUR_ACCOUNT_ID`는 자신의 계정 번호로 바꾼다. YAML 안에 `$ECR_REGISTRY`를 적는다고 kubectl이 셸 변수로 자동 치환하지는 않는다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-ecr
  namespace: til-lab
spec:
  imagePullSecrets:
  - name: ecr-secret
  containers:
  - name: nginx
    image: YOUR_ACCOUNT_ID.dkr.ecr.ap-northeast-2.amazonaws.com/ecr-nginx:v2.0
    ports:
    - containerPort: 80
```

이를 학습용 YAML 파일로 저장해 계정·리포지토리·태그를 수정한 뒤 `kubectl apply -f 실제파일명.yaml`로 반영하고 `kubectl describe pod nginx-ecr -n til-lab`에서 확인한다. Secret은 해당 Pod와 같은 네임스페이스에 있어야 한다. [비공개 이미지와 imagePullSecrets](https://kubernetes.io/docs/tasks/configure-pod-container/pull-image-private-registry/)

Deployment에서도 같은 원리지만 경로가 다르다. 다음은 전체 Deployment가 아닌 **Pod 템플릿 부분 발췌**이며, `spec.template.spec`의 `imagePullSecrets`와 `containers`를 나란히 둔다.

```yaml
spec:
  template:
    spec:
      imagePullSecrets:
      - name: ecr-secret
      containers:
      - name: nginx
        image: YOUR_ACCOUNT_ID.dkr.ecr.ap-northeast-2.amazonaws.com/ecr-nginx:v2.0
```

#### 5.4 실패 상태는 다음에 볼 정보를 가리키는 단서다

다음은 실제 발생 기록이 아니라, 강의 실습을 다시 진행할 때 사용할 확인 기준이다.

| 상태·증상 | 먼저 확인할 정보 | 판단 기준 |
| --- | --- | --- |
| `Pending` | Pod의 Events·노드 자원·배치 조건 | 노드 미배치인지 다른 준비 대기인지 구분 |
| `ErrImagePull` / `ImagePullBackOff` | 이미지 주소·태그·Secret·레지스트리 통신 | 인증 문제와 이미지 부재를 구분 |
| `CrashLoopBackOff` | 현재·이전 컨테이너 로그와 종료 이유 | 시작 후 반복 종료하는 원인 확인 |
| `OOMKilled` | 컨테이너 종료 이유·메모리 설정·사용 패턴 | 메모리 부족이나 한도 문제 확인 |
| Service 연결 실패 | selector·준비 상태·EndpointSlice·포트 | 대상 선택부터 외부 경로까지 단계별 확인 |
| `top` 조회 실패 | Metrics Server 로그·APIService 상태 | 앱 실행 문제와 Metrics API 문제 구분 |

`ImagePullBackOff`와 `CrashLoopBackOff`는 목록에서 보이는 상태 설명이며 Pod phase와 같은 분류는 아니다. 상태 이름만으로 원인을 확정하지 않고 이벤트나 종료 이유로 좁혀 간다.

> 실행 설정, 실제 사용량, 컨테이너 출력, 이미지 인증은 서로 다른 정보다. 실패한 단계에 맞는 정보를 조회해야 원인을 좁힐 수 있다.

### 6. Namespace와 레이블 및 노드 관리 구분하기

같은 조회·수정 명령도 어느 네임스페이스와 노드에 적용하는지에 따라 결과가 달라진다. 07번의 많은 명령은 개별 문장을 외우기보다 “어떤 대상을 골라 무엇을 바꾸는가”로 묶으면 다시 사용할 때 실수가 줄어든다.

#### 6.1 Namespace는 이름의 범위이고 레이블은 선택 조건이다

Namespace는 같은 클러스터의 자원을 논리적으로 나눈다. `dev`, `stg`, `prod`처럼 환경 이름을 사용할 수 있지만, 네임스페이스를 나누기만 했다고 네트워크와 권한이 자동으로 완전히 격리되는 것은 아니다.

```bash
kubectl get namespaces
kubectl get pods -n til-lab
kubectl get pods -A
kubectl get pods -n til-lab --show-labels
kubectl get pods -n til-lab -L app,env
kubectl get pods -n til-lab -l app=nginx-app
kubectl get pods -n til-lab -l '!env'
```

`-L app,env`는 해당 레이블을 출력 열에 추가하고, `-l app=nginx-app`은 대상을 필터링한다. `-l '!env'`는 `env` 레이블이 없는 대상을 고른다. `get pods -n green`의 `green`은 Pod 이름이 아니라 네임스페이스 이름이다.

노드에도 레이블을 붙이고 조회할 수 있다. 다음은 디스크 특성을 표시하는 설명용 예제이며, `disk=ssd`를 붙인다고 실제 디스크가 SSD로 바뀌는 것은 아니다. Pod의 `nodeSelector`는 이런 노드 레이블을 배치 조건으로 사용한다.

```bash
kubectl label node k8s-worker1 disk=ssd
kubectl get nodes -L disk
kubectl get nodes -l disk=ssd
```

다음은 앞에서 만든 단독 Pod `webserver`에 분류 정보를 추가·수정·제거하는 예다. Deployment의 selector로 쓰는 `app` 레이블을 임의로 바꾸는 것과 구분한다.

```bash
kubectl label pod webserver -n til-lab env=debug
kubectl label pod webserver -n til-lab env=practice --overwrite
kubectl get pod webserver -n til-lab -L env
kubectl label pod webserver -n til-lab env-
```

`kubectl get pods | wc -l`에는 헤더가 포함되고 빈 목록 안내도 고려해야 한다. 종류별 실제 항목 수가 필요하다면 `kubectl get pods -n til-lab -o name | wc -l`처럼 이름만 출력해 센다. Node는 네임스페이스에 속하지 않는 클러스터 범위 자원이다.

#### 6.2 NoSchedule을 조회하는 명령은 상태를 바꾸지 않는다

06번의 다음 명령은 노드 상세 정보에서 `NoSchedule` 문자열을 찾는 조회다.

```bash
kubectl describe node k8s-master | grep -i noschedule
kubectl describe node k8s-worker1
```

이 명령이 스케줄러를 멈추거나 워커의 스케줄링을 끄는 것은 아니다. 검색 결과가 없다고 “워커에는 스케줄링 기능이 없다”고 판단하지도 않는다. 스케줄러는 컨트롤 플레인에서 실행되고 워커는 배치 대상이 된다.

**taint**는 특정 Pod를 노드에 배치하지 않도록 제한하는 노드의 조건이고, toleration은 Pod가 그 조건을 허용하도록 하는 설정이다. kubeadm 컨트롤 플레인에는 일반 앱 배치를 제한하는 taint가 기본적으로 붙을 수 있다. `NoSchedule`은 이를 허용하지 않는 새 Pod의 배치를 막지만 이미 실행 중인 Pod를 그 이유만으로 쫓아내지는 않는다. toleration이 있다고 특정 노드 배치가 보장되는 것도 아니다. [taint와 toleration](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/)

#### 6.3 cordon·drain·uncordon은 노드 정비의 서로 다른 단계다

| 명령 | 변경하는 것 | 기존 Pod에 대한 의미 |
| --- | --- | --- |
| `kubectl cordon k8s-worker1` | 일반적인 새 Pod 배치 중지 | 기존 Pod를 내보내지 않음 |
| `kubectl drain k8s-worker1 --ignore-daemonsets` | 노드 배치를 막고 퇴거 가능한 Pod를 비움 | 관리 컨트롤러가 다른 노드에 대체 Pod 생성 가능 |
| `kubectl uncordon k8s-worker1` | 다시 새 Pod 배치 허용 | 다른 노드의 Pod를 자동으로 원위치 이동시키지는 않음 |
| `kubectl delete node k8s-worker1` | API의 Node 객체 삭제 | VM 종료·kubelet 제거·데이터 정리와 다른 작업 |

drain은 실행 중인 컨테이너를 그대로 다른 서버로 옮기는 기능이 아니다. Pod를 퇴거하고 그 관리자가 대체 Pod를 만들도록 하는 과정이다. 다른 노드의 자원, 스토리지 제약, 가용성 정책에 따라 비우기나 대체 실행이 막힐 수 있다.

다음은 실제 노드 정비가 필요할 때 사용하는 순서 예제다. Node 작업은 `til-lab`을 넘어 그 노드의 다른 네임스페이스 Pod에도 영향을 준다. 먼저 대상 Pod와 여유 자원을 확인한다.

```bash
kubectl get pods -A -o wide --field-selector spec.nodeName=k8s-worker1
kubectl cordon k8s-worker1
kubectl drain k8s-worker1 --ignore-daemonsets --dry-run=server
```

위 dry-run은 실제 drain을 수행하지 않으며, 전체 정비 과정의 성공까지 보장하지 않는다. 확인을 마친 경우에만 `kubectl drain k8s-worker1 --ignore-daemonsets`로 진행한다. 정비 후에는 `kubectl uncordon k8s-worker1`과 `kubectl get nodes`로 복귀를 확인한다. [노드를 안전하게 비우는 절차](https://kubernetes.io/docs/tasks/administer-cluster/safely-drain-node/)

> [!WARNING]
> `--ignore-daemonsets`는 DaemonSet Pod를 건너뛰는 옵션이다. `--force`는 관리자가 없는 Pod도 비울 수 있게 하지만 대체 Pod를 만들어 주지 않으며, `--delete-emptydir-data`는 emptyDir 데이터 손실을 수반한다. drain이 막혔을 때 원인 확인 없이 두 옵션을 붙이지 않는다.

강의의 `kubeadm token create`는 워커 참가용 토큰 생성이고 `kubeadm reset`은 노드의 kubeadm 설정 초기화다. 앱을 재시작하는 명령과 구분한다. 다시 참가할 때는 마스터에서 `sudo kubeadm token create --print-join-command`로 자신의 참가 명령을 얻고, 워커에서 그 명령을 사용한다.

#### 6.4 긴 명령 목록은 자원 종류를 확인하는 사전으로 읽는다

07번에는 오늘의 기본 앱 실습 외에도 여러 자원의 조회·관리 명령이 모여 있다. 다음은 명령을 읽기 위한 역할 구분이며, 해당 자원들의 전체 구축 절차를 수행했다는 뜻은 아니다.

| 자원 | 역할 | 기본 조회 |
| --- | --- | --- |
| ReplicaSet | 같은 템플릿의 Pod 개수 유지 | `kubectl get rs -n til-lab` |
| ReplicationController | 이전 방식의 Pod 복제 관리 | `kubectl get rc -n til-lab` |
| DaemonSet | 대상 노드마다 필요한 Pod 실행 | `kubectl get ds -n kube-system` |
| Job | 완료되는 작업 실행 | `kubectl get jobs -n til-lab` |
| ConfigMap | 애플리케이션의 일반 설정 전달 | `kubectl get cm -n til-lab` |
| Secret | 인증 정보 등의 객체 관리 | `kubectl get secrets -n til-lab` |
| PV·PVC | 저장 공간과 그 사용 요청 | `kubectl get pv` / `kubectl get pvc -n til-lab` |
| Ingress | HTTP 등의 진입 규칙 정의 | `kubectl get ingress -n til-lab` |

Deployment가 관리하는 ReplicaSet을 직접 수정·삭제하기보다 최상위 Deployment의 목표를 관리한다. PVC 삭제는 저장소의 회수 정책과 데이터 보관에 영향을 줄 수 있으므로, Pod 삭제와 같은 의미로 취급하지 않는다.

특정 필드만 필요하면 JSON 문자열을 `grep`으로 찾는 대신 필드를 지정할 수 있다. 다음은 단독 Pod의 IP와 Deployment가 사용하는 이미지의 조회 예다.

```bash
kubectl get pod webserver -n til-lab -o jsonpath='{.status.podIP}{"\n"}'
kubectl get deploy nginx-web -n til-lab \
  -o jsonpath='{.spec.template.spec.containers[*].image}{"\n"}'
```

#### 6.5 정리는 소유한 자원과 유지할 설정을 확인한 뒤 한다

Deployment를 지우면 기본적으로 그 아래 ReplicaSet과 Pod도 삭제된다. Service와 별도로 만든 Secret은 독립 객체이므로 별도로 정리해야 한다. `kubectl delete --all all`은 현재 네임스페이스의 여러 종류를 한꺼번에 지우는 명령이며, 모든 종류를 완전히 지우는 명령도 아니다.

오늘 예제만 모아 둔 `til-lab` 전체가 더 이상 필요 없다면 다음처럼 범위를 먼저 확인하고 네임스페이스를 정리할 수 있다. 그 안의 다른 학습 자원을 계속 사용할 계획이라면 필요한 객체만 이름이나 파일로 지정해 지운다.

```bash
kubectl get deploy,rs,pods,svc,secrets -n til-lab
kubectl delete namespace til-lab
```

Namespace 삭제는 그 안의 자원까지 삭제하므로 기본·시스템 네임스페이스에 같은 작업을 적용하지 않는다. `kube-system`의 Metrics Server와 셸의 alias 설정은 `til-lab` 삭제에 포함되지 않으며, 이 문서의 명령 예제를 정리하는 것과 로컬 YAML 파일을 삭제하는 것도 별개다.

> 명령은 동작만 외우지 않고 종류·이름·네임스페이스·노드 범위를 함께 읽는다. 조회, 실행 상태 변경, 자원 삭제, 클러스터 초기화는 영향 범위가 서로 다르다.

## 🧠 오늘 이해한 핵심

1. **Kubernetes의 자동 관리는 원하는 상태와 현재 상태의 차이를 줄이는 과정이다.** API 서버·스케줄러·kubelet의 역할을 구분하면 생성 요청이 실제 실행으로 이어지는 과정을 설명할 수 있다.
2. **단독 Pod 실행과 Deployment 운영은 복구 책임이 다르다.** 컨테이너 재시작과 삭제된 Pod의 대체 생성을 나누고, 복제본 수와 Pod 템플릿을 관리해야 한다.
3. **Service 접속은 대상 선택과 네트워크 경로가 함께 맞아야 한다.** 레이블·selector·targetPort를 먼저 확인하고, Service 타입에 맞는 실제 접속 환경을 준비한다.
4. **정확한 운영 명령은 관찰할 정보와 변경 범위에서 출발한다.** 상태·이벤트·로그·사용량·인증을 나누어 확인하고, 네임스페이스와 노드에 미치는 영향을 구분한다.
