오늘은 마이크로서비스의 상태를 수치로 관찰하는 모니터링을 학습했다. Hystrix Dashboard와 Turbine으로 여러 서비스의 장애 통계를 모으는 구조에서 출발해, Micrometer로 메트릭을 계측하고 Spring Boot Actuator로 노출한 뒤 Prometheus에 저장하고 Grafana에서 시각화하는 흐름을 연결했다.

강의의 설정과 화면을 중심으로 정리하되, 이를 이해하는 데 필요한 메트릭 유형, 시계열과 라벨, 요청 처리량·오류율·지연 시간을 구하는 PromQL을 함께 살펴본다. 강의에 나온 코드·화면과 설명을 위해 추가한 예제는 구분하며, 구버전의 계측 방식과 현재 문서의 사용 조건도 함께 짚는다.

> 모니터링은 그래프를 만드는 작업에서 끝나지 않는다. 무엇을 측정했고, 어느 인스턴스에서 수집했으며, 그 숫자가 어떤 상태를 뜻하는지 연결해야 한다.

### 1. 마이크로서비스 모니터링과 Hystrix·Turbine의 역할

분산 추적은 한 요청이 어떤 서비스를 거쳤는지 보여 준다. 하지만 운영 중에는 특정 요청의 경로뿐 아니라, 서비스 전체의 오류가 늘었는지, 요청이 느려졌는지, JVM 자원이 부족한지도 알아야 한다.

이런 질문에 답하려면 개별 사건을 모아 수치로 관찰하는 메트릭이 필요하다. 강의는 먼저 Hystrix의 통계를 한 화면에 모으는 구조를 소개하고, 이후 일반적인 애플리케이션 모니터링으로 범위를 넓힌다.

#### 1.1 메트릭·로그·분산 추적은 서로 다른 질문에 답한다

**메트릭**은 요청 수·처리 시간·메모리 사용량처럼 집계 가능한 측정값이다. 시간에 따라 수치를 쌓으면 평소와 다른 변화가 생겼는지 비교할 수 있다.

| 관찰 자료 | 답하려는 질문 | 예시 |
| --- | --- | --- |
| 메트릭 | 서비스 전체에서 어떤 변화가 생겼는가? | 최근 요청 처리량, 5xx 비율, JVM 메모리 |
| 로그 | 특정 시점에 무슨 사건이 발생했는가? | 예외 메시지, 실패한 작업의 문맥 |
| 분산 추적 | 한 요청이 어디를 거쳤고 어디서 지연됐는가? | Trace ID로 연결한 서비스별 Span |

오류율 상승을 메트릭에서 발견하면 해당 시간대의 Trace와 로그로 원인을 좁힐 수 있다. 메트릭은 개별 요청의 모든 내용을 보존하는 자료가 아니므로, 오류율 그래프만 보고 특정 사용자의 실패 원인을 확정할 수는 없다.

#### 1.2 살아 있는 것과 정상적인 서비스를 제공하는 것은 다르다

프로세스가 실행 중이고 상태 확인 요청에 응답하더라도, 실제 업무 요청이 느리거나 일부 기능만 실패할 수 있다. 따라서 생존 여부와 사용자에게 제공하는 품질을 함께 봐야 한다.

| 관찰 기준 | 확인할 내용 | 연결되는 지표 |
| --- | --- | --- |
| 트래픽 | 얼마나 많은 요청을 처리하는가? | 초당 요청 수 |
| 오류 | 요청 중 얼마가 실패하는가? | 상태 코드별 요청 수와 오류 비율 |
| 지연 | 응답까지 얼마나 걸리는가? | 평균·p95 응답 시간 |
| 자원과 포화 | 처리 여력이 남아 있는가? | CPU, 메모리, 스레드, 연결 풀 |

오류율과 지연 시간은 요청량과 함께 해석한다. 요청이 거의 없어서 오류가 관찰되지 않은 상태와, 많은 요청을 정상 처리한 상태는 같은 의미가 아니다.

#### 1.3 Turbine은 여러 Hystrix 스트림을 모으고 Dashboard는 보여 준다

Hystrix는 원격 호출을 감싸는 과정에서 성공·실패·타임아웃·호출 차단과 같은 통계를 만든다. **Hystrix Dashboard**는 이 스트림을 시각화하고, **Turbine**은 여러 인스턴스의 스트림을 하나로 집계한다.

강의의 회원 확인·상품 주문·배송 처리 서비스는 Eureka Client로 표현된다. Turbine은 Eureka에서 대상 인스턴스를 찾아 스트림에 연결하고, Dashboard는 Turbine이 제공하는 통합 스트림을 읽는다. [Spring Cloud Netflix의 Turbine 설명](https://cloud.spring.io/spring-cloud-netflix/multi/multi__hystrix_timeouts_and_ribbon_clients.html)

```text
각 서비스의 Hystrix가 호출 통계를 스트림으로 제공한다
    ↓ Turbine이 Eureka에서 대상 인스턴스를 찾아 연결한다
Turbine이 여러 Hystrix 스트림을 집계한다
    ↓ Dashboard가 통합 스트림을 구독한다
Hystrix Dashboard가 회로와 스레드 풀의 상태를 표시한다
```

| 구성 요소 | 책임 | 구분할 점 |
| --- | --- | --- |
| Hystrix | 호출 보호와 호출 통계 생성 | 실제로 호출을 차단하는 쪽이다. |
| Eureka | 서비스 인스턴스 등록과 발견 | 통계를 저장하거나 그래프를 그리지 않는다. |
| Turbine | 여러 Hystrix 스트림 집계 | 임의의 JVM 메트릭을 모두 수집하는 도구는 아니다. |
| Hystrix Dashboard | 스트림 시각화 | Dashboard 자체가 회로 차단기는 아니다. |

강의 화면에서는 Dashboard의 `/hystrix` 페이지에 `http://localhost:9999/turbine.stream`을 입력한다. 이후 화면은 회로의 상태·오류·요청량·지연과 스레드 풀 관련 통계를 보여 준다. 이 주소와 포트는 강의 구성의 값이다.

#### 1.4 수집 대상 이름은 Eureka에 등록한 이름과 맞아야 한다

강의는 `turbine.appConfig`로 집계할 서비스를 지정하고, `clusterNameExpression`으로 스트림을 묶는 클러스터 이름을 설정한다. 아래는 이 관계를 설명하기 위해 서비스 이름을 일치시킨 설명용 설정이다.

```yaml
turbine:
  appConfig: msa-service-order,msa-service-member,msa-service-delivery
  clusterNameExpression: 'new String("default")'
```

`appConfig`는 Turbine이 Eureka에서 찾을 서비스 ID 목록이다. `clusterNameExpression`은 여기서 모든 인스턴스를 `default`라는 집계 그룹으로 묶도록 하는 표현식이다.

강의 4쪽의 `appConfig` 예시 문자열과 오른쪽 서비스 이름에는 차이가 있다. 따라서 문자열 자체를 복사하기보다 실제 Eureka 등록 이름과 일치시키는 것이 중요하다.

#### 1.5 장애 방어와 모니터링을 각각 대체한다

강의의 전환 표는 Hystrix를 Resilience4j로, Hystrix Dashboard·Turbine을 Micrometer와 모니터링 시스템으로 대체하는 방향을 보여 준다. 두 전환은 책임이 다르다.

| 기존 구성 | 대응하는 구성 | 담당하는 문제 |
| --- | --- | --- |
| Hystrix | Resilience4j 등 | 실패하는 호출을 차단하고 장애 전파를 제한한다. |
| Hystrix Dashboard·Turbine | Micrometer와 Prometheus·Grafana 등 | 측정값을 수집·조회·시각화한다. |

Micrometer를 추가했다고 회로 차단기가 생기지는 않는다. 반대로 Resilience4j가 호출을 보호한다고 JVM·HTTP·업무 지표의 전체 대시보드까지 자동으로 완성되는 것도 아니다.

> [!NOTE]
> Hystrix·Turbine 관련 Spring Cloud Netflix 모듈은 유지보수 모드로 전환된 구성이므로, 강의의 구조를 이해하는 자료로 구분한다. Spring Boot 3 이후 프로젝트에 강의의 구형 스타터를 그대로 추가하는 방식은 피한다. [Spring Cloud Netflix 유지보수 모드 안내](https://cloud.spring.io/spring-cloud-netflix/multi/multi__modules_in_maintenance_mode.html)

> 장애를 막는 장치와 장애를 관찰하는 장치는 역할이 다르다. 모니터링은 회로 차단기뿐 아니라 요청·JVM·자원 상태까지 함께 관찰하는 방향으로 확장된다.

### 2. Micrometer와 Actuator로 측정값 노출하기

서비스 상태를 관찰하려면 먼저 애플리케이션 안에서 수치를 기록하고, 외부 시스템이 읽을 수 있도록 제공해야 한다. Micrometer는 계측을 담당하고, Actuator는 관리·모니터링용 접근 창구를 제공한다.

이 둘을 연결하면 HTTP 요청과 JVM의 기본 지표를 활용하면서, 필요한 업무 구간에는 별도의 계측을 추가할 수 있다.

#### 2.1 Micrometer는 계측 API이고 Registry는 백엔드와의 연결점이다

**Micrometer**는 특정 모니터링 제품에 종속되지 않는 계측 API를 제공한다. 애플리케이션은 `MeterRegistry`를 통해 측정값을 등록하고, Prometheus용 Registry는 이를 Prometheus가 읽을 수 있는 형식으로 표현한다.

| 요소 | 역할 | 예시 |
| --- | --- | --- |
| Meter | 하나의 측정 도구 | `Counter`, `Gauge`, `Timer` |
| MeterRegistry | 측정 도구를 등록하고 관리 | 이름과 태그로 Meter 조회·생성 |
| Prometheus Registry | Prometheus 형식으로 변환 | 점으로 구분한 이름을 밑줄 형태 등으로 변환 |
| Actuator | 관리용 HTTP 엔드포인트 제공 | `/actuator/metrics`, `/actuator/prometheus` |

Spring Boot Actuator는 Micrometer의 자동 설정과 여러 기본 계측을 제공한다. 다만 실제로 생성되는 지표는 사용 중인 웹 서버·라이브러리·버전에 따라 달라진다. [Spring Boot의 메트릭 지원](https://docs.spring.io/spring-boot/3.5/reference/actuator/metrics.html)

#### 2.2 의존성 추가와 HTTP 노출은 별도 설정이다

강의 10쪽은 `pom.xml`에 `micrometer-registry-prometheus`를 추가한다. Actuator가 이미 있는 프로젝트에 Prometheus용 Registry를 더하는 장면이다.

아래는 두 의존성의 관계를 함께 보여 주는 설명용 `pom.xml` 발췌다. Spring Boot의 의존성 관리를 적용한 프로젝트를 전제로 버전을 생략했다.

```xml title="pom.xml"
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

의존성을 추가하는 것과 엔드포인트를 HTTP로 노출하는 것은 별개다. 강의의 `application.yml`에는 기존 관리 기능에 `prometheus`, `metrics`가 추가되어 있다.

```yaml title="application.yml"
management:
  endpoints:
    web:
      exposure:
        include: refresh,health,beans,busrefresh,info,prometheus,metrics
```

위 목록에 이름을 적는다고 해당 기능이 모두 생성되는 것은 아니다. 예를 들어 `refresh`·`busrefresh`는 관련 Spring Cloud 구성도 필요하다.

다음은 메트릭 확인에 필요한 범위로 줄이고 서비스 구분 태그를 추가한 설명용 설정이다. 강의 설정 전체를 그대로 재현한 코드는 아니다.

```yaml title="application.yml"
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  metrics:
    tags:
      application: ${spring.application.name}
```

`application` 태그는 서비스 이름으로 조회 대상을 구분할 때 유용하다. 노출 설정은 접근 허용과도 별개이므로, Spring Security가 있다면 수집 주체에 대한 인증·인가 설정까지 맞아야 한다. [Actuator 엔드포인트의 노출과 보안](https://docs.spring.io/spring-boot/3.5/reference/actuator/endpoints.html)

#### 2.3 점검용 JSON과 수집용 텍스트를 구분한다

| 엔드포인트 | 응답과 용도 | 이름 예시 |
| --- | --- | --- |
| `/actuator/metrics` | 등록된 Meter 이름을 JSON 목록으로 확인 | `http.server.requests` |
| `/actuator/metrics/{name}` | 특정 Meter의 측정값과 사용 가능한 태그 확인 | `http.server.requests`의 `COUNT` 등 |
| `/actuator/prometheus` | Prometheus가 수집하는 형식으로 전체 지표 노출 | `http_server_requests_seconds_count` |

Micrometer의 논리적 이름과 Prometheus에 노출되는 이름은 다를 수 있다. Prometheus 쿼리는 실제 수집 응답에 나온 이름을 기준으로 작성해야 한다.

아래는 서비스의 로컬 포트가 `8081`이라고 가정한 설명용 확인 명령이다. 실제 실행 결과를 기록한 명령은 아니다.

```bash
curl -i http://localhost:8081/actuator/metrics
curl -i 'http://localhost:8081/actuator/metrics/http.server.requests?tag=method:GET'
curl -i http://localhost:8081/actuator/prometheus
```

`/actuator/metrics`의 JSON을 Prometheus 수집 대상으로 넣으면 안 된다. Spring Boot의 Prometheus 엔드포인트는 별도로 노출해야 한다. [Spring Boot의 Prometheus 연동](https://docs.spring.io/spring-boot/3.5/reference/actuator/metrics.html#actuator.metrics.export.prometheus)

#### 2.4 일반 Timer는 완료된 작업의 횟수와 시간을 기록한다

**Timer**는 작업 시간을 기록하면서 완료된 측정 횟수도 함께 센다. 따라서 요청 시간을 Timer로 측정했다면 같은 구간의 호출 수를 세기 위해 Counter를 반드시 하나 더 만들 필요는 없다.

일반 Timer를 Prometheus에 노출하면 보통 다음 시계열을 읽게 된다. 정확한 출력은 Registry와 설정에 따라 확인한다. [Micrometer의 Timer 설명](https://docs.micrometer.io/micrometer/reference/concepts/timers.html)

| 시계열 | 의미 | 해석 기준 |
| --- | --- | --- |
| `_seconds_count` | 완료되어 기록된 작업 수 | 누적값의 변화율로 처리량 계산 |
| `_seconds_sum` | 기록된 처리 시간의 누적 합 | 요청 수와 같은 범위로 나누어 평균 계산 |
| `_seconds_max` | 시간 윈도우에서 관찰한 최대 처리 시간 | 프로세스 시작 이후 영구 최대값은 아니다. |
| `_seconds_bucket` | 경계값 이하에 속한 누적 관측 수 | 히스토그램 설정이 있어야 제공된다. |

예를 들어 이름이 `users.welcome`인 일반 Timer는 `users_welcome_seconds_count` 등의 이름으로 표현될 수 있다. 이것은 다음 소주제에 나오는 강의의 `longTask = true` 출력과 구분해야 한다.

#### 2.5 강의의 longTask 설정은 진행 중인 작업을 측정한다

강의 11쪽에서 두 메서드에 추가한 애너테이션은 다음과 같다. 아래는 강의 코드의 계측 애너테이션만 발췌한 것이다.

```java
@Timed(value="users.status", longTask = true)
```

```java
@Timed(value="users.welcome", longTask = true)
```

`longTask = true`는 **LongTaskTimer**를 사용한다는 뜻이다. 단순히 일반 Timer를 더 정밀하게 측정하는 옵션이 아니라, 진행 중인 작업의 수와 지금까지 지속된 시간을 관찰하는 방식이다. [Micrometer의 LongTaskTimer 설명](https://docs.micrometer.io/micrometer/reference/concepts/long-task-timers.html)

| 비교 기준 | 일반 Timer | LongTaskTimer |
| --- | --- | --- |
| 관찰 대상 | 완료되어 기록된 작업 | 아직 실행 중인 작업 |
| 대표 질문 | 최근 요청을 얼마나 빨리 처리했는가? | 지금 몇 개의 작업이 얼마나 오래 실행 중인가? |
| 작업 완료 후 | 완료 횟수와 누적 시간에 반영 | 해당 작업은 활성 통계에서 빠진다. |
| 적합한 상황 | HTTP 요청, 짧은 메서드 실행 | 오래 걸리는 배치·동기화 작업의 진행 상태 |

강의 12쪽에는 `users_welcome_seconds_active_count`, `users_welcome_seconds_duration_sum`이 보이고, 값은 `0.0`으로 표시되어 있다. 이 값은 수집 시점에 진행 중인 작업이 없다는 의미로 읽어야 하며, 이전에 한 번도 호출하지 않았다고 단정할 수 없다.

짧은 HTTP 요청은 두 수집 시점 사이에 시작하고 끝날 수 있다. 이런 경우 일반 Timer에는 완료 기록이 남지만, LongTaskTimer는 수집 순간에 실행 중인 작업이 없어서 계속 0으로 보일 수 있다.

> [!WARNING]
> LongTaskTimer의 활성 작업 수·활성 작업 시간은 완료 요청의 누적 카운터가 아니다. 강의의 `_active_count`나 `_duration_sum`에 일반 Timer의 요청 처리량·평균 지연 시간 공식을 그대로 적용하지 않는다. 출력 이름도 Micrometer·Prometheus 클라이언트 버전에 따라 달라질 수 있으므로 의미와 실제 응답을 함께 확인한다. [Registry별 출력 차이](https://docs.micrometer.io/micrometer/reference/implementations/prometheus.html)

#### 2.6 애너테이션을 붙이는 것과 실제로 계측되는 것은 다르다

`@Timed`가 동작하려면 이를 해석하는 웹 계측 기능이나 AOP 구성이 필요하다. Spring Boot 2 시절의 웹 계측 지원을 현재의 임의의 서비스 메서드에 그대로 일반화하면 안 된다.

아래는 Spring Boot 3.5 계열의 일반적인 Spring Bean 메서드에 `@Timed`를 적용하는 설명용 구성이다. AOP 스타터가 없다면 먼저 추가하며, 기존 의존성에 같은 항목이 있는지 확인한다.

```xml title="pom.xml"
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-aop</artifactId>
</dependency>
```

다음 설명용 설정은 `TimedAspect`를 Bean으로 등록한다. 여기서 사용하는 애너테이션은 `io.micrometer.core.annotation.Timed`다.

```java title="MetricsConfig.java"
import io.micrometer.core.aop.TimedAspect;
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class MetricsConfig {
    @Bean
    public TimedAspect timedAspect(MeterRegistry registry) {
        return new TimedAspect(registry);
    }
}
```

이 구성에서는 계측할 메서드 호출이 Spring AOP 프록시를 통과해야 한다. 같은 객체 내부에서 자기 메서드를 직접 호출하면 프록시를 거치지 않아 계측되지 않을 수 있다. [Micrometer의 TimedAspect 구성](https://docs.micrometer.io/micrometer/reference/concepts/timers.html#_the_timed_annotation)

다음은 위 설정과 연결하는 설명용 서비스다. `longTask`의 기본값인 `false`를 사용하므로, 메서드 실행이 끝나면 일반 Timer에 횟수와 시간이 기록된다. 강의의 활성 작업 지표와 구분하도록 별도 이름을 사용했다.

```java title="WelcomeService.java"
import io.micrometer.core.annotation.Timed;
import org.springframework.stereotype.Service;

@Service
public class WelcomeService {
    @Timed("users.welcome.completed")
    public String welcome() {
        return "welcome";
    }
}
```

Spring Boot가 자동으로 기록하는 HTTP 서버 요청 메트릭은 별도로 존재한다. HTTP 전체 처리 시간이 목적이라면 먼저 자동 계측된 `http.server.requests`를 확인하고, 별도의 업무 구간을 측정할 때 사용자 정의 이름을 추가한다.

> [!WARNING]
> 강의의 `/health_check` 응답 코드에는 `token.secret`을 응답 문자열에 포함하는 부분이 있다. 상태 확인은 비밀값을 반환할 이유가 없으므로 그대로 재사용하지 않는다. 또한 `beans` 등 관리 정보는 수집에 필요한 범위와 접근 주체를 정해 노출한다.

> 먼저 측정 대상이 완료된 요청인지 진행 중인 작업인지 정해야 한다. 그다음 계측 코드, Registry, Actuator 노출이 이어져야 외부에서 의미 있는 값을 읽을 수 있다.

### 3. Prometheus로 메트릭을 수집하고 시계열로 저장하기

Actuator 응답은 애플리케이션이 현재 제공하는 측정값이다. 시간에 따른 증가·감소와 과거 상태를 비교하려면 이를 주기적으로 가져와 저장하는 시스템이 필요하다.

Prometheus는 수집 대상에 HTTP 요청을 보내 메트릭을 가져오고, 이름과 라벨로 구분한 시계열을 저장한다. 이후 PromQL을 통해 이 기록을 조회한다.

#### 3.1 Pull은 Prometheus가 애플리케이션을 호출하는 방식이다

**스크레이프**는 수집 대상의 메트릭 엔드포인트를 호출해 값을 읽는 작업이다. 강의 구성에서는 User Service가 Prometheus 서버로 값을 전송하는 것이 아니라, Prometheus가 User Service의 노출 주소에 요청한다. [Prometheus의 수집 구조](https://prometheus.io/docs/introduction/overview/)

| 구간 | 요청을 보내는 쪽 | 요청 대상과 목적 |
| --- | --- | --- |
| 메트릭 수집 | Prometheus | 애플리케이션의 메트릭 엔드포인트 읽기 |
| 수집 응답 | 애플리케이션 | 측정값을 Prometheus 요청에 응답 |
| 대시보드 조회 | Grafana 서버 | Prometheus API에 쿼리 실행 |
| 사용자 열람 | 브라우저 | Grafana 화면 확인 |

애플리케이션이 직접 노출하기 어려운 시스템에는 Exporter를 붙일 수 있다. 예를 들어 운영체제 지표는 Node Exporter 같은 도구가 제공하고, 강의의 Spring Boot 애플리케이션은 Actuator와 Registry가 수집 가능한 응답을 제공한다.

#### 3.2 메트릭 이름과 라벨 조합이 하나의 시계열을 만든다

아래는 HTTP 메트릭의 구조를 보여 주기 위한 설명용 샘플이다. `42`는 실제 강의 측정값이 아니다.

```text
http_server_requests_seconds_count{job="user-service",instance="localhost:8000",method="GET",uri="/welcome",status="200"} 42
```

메트릭 이름이 같아도 `method`, `uri`, `status`, `instance` 중 하나가 다르면 별도의 시계열이다. Prometheus는 수집 시각을 함께 저장하므로 같은 시계열의 값이 시간에 따라 어떻게 변했는지 조회할 수 있다.

| 요소 | 의미 | 예시 해석 |
| --- | --- | --- |
| 메트릭 이름 | 무엇을 측정하는가? | 완료된 HTTP 요청 수 |
| 라벨 | 어떤 조건의 측정인가? | GET·`/welcome`·200 응답 |
| 값 | 해당 시점의 측정값 | 해당 조합의 누적 요청 수 |
| 타임스탬프 | 언제 수집한 값인가? | 수집 시각에 대응하는 기록 |

`job`은 보통 같은 수집 목적의 대상 그룹을 뜻하고, `instance`는 기본적으로 수집에 사용한 `host:port`를 나타낸다. `application`은 앞 장의 공통 태그처럼 애플리케이션에서 추가할 수 있으며, `job`과 자동으로 같은 값이 되는 것은 아니다. [Prometheus의 Job과 Instance](https://prometheus.io/docs/concepts/jobs_instances/)

#### 3.3 강의의 수집 설정은 Gateway를 거쳐 User Service를 읽는다

강의 15쪽의 `prometheus.yml` 핵심 설정은 다음과 같다. Prometheus 자신의 `/metrics`와 Gateway 경유 User Service의 메트릭을 각각 수집한다.

```yaml title="prometheus.yml"
scrape_configs:
  - job_name: 'prometheus'
    static_configs:
      - targets: ['localhost:9090']

  - job_name: 'user-service'
    scrape_interval: 15s
    metrics_path: '/user-service/actuator/prometheus'
    static_configs:
      - targets: ['localhost:8000']
```

| 설정 | 역할 | 강의 값의 의미 |
| --- | --- | --- |
| `job_name` | 수집 그룹 이름과 기본 `job` 라벨 | `user-service` 그룹 |
| `scrape_interval` | 해당 Job의 수집 간격 | 15초마다 수집 |
| `metrics_path` | HTTP 요청 경로 | Gateway의 서비스 접두사가 포함된 경로 |
| `static_configs.targets` | 정적으로 지정한 수집 주소 | Gateway의 `localhost:8000` |

주소와 경로를 합치면 `http://localhost:8000/user-service/actuator/prometheus`다. 경로를 생략한 Prometheus 자기 수집 Job은 기본 `/metrics`를 사용한다. [Prometheus 수집 설정](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)

Gateway가 `/user-service`를 제거해 전달하는지, 서비스 자체가 해당 접두사를 사용하는지는 라우트·애플리케이션 설정으로 확인해야 한다. 강의의 URL만 보고 내부 경로 재작성 방식까지 확정할 수는 없다.

#### 3.4 Gateway 주소로 수집하면 실제 인스턴스를 구분하기 어렵다

강의 설정에서 `job="user-service"`는 수집 그룹 이름이다. 하지만 `instance="localhost:8000"`은 수집 접속 대상인 Gateway를 가리키며, User Service의 실제 실행 포트를 식별하지 않는다.

특히 User Service가 여러 인스턴스이고 Gateway가 수집 요청도 분산한다면 문제가 생긴다. 같은 라벨 조합의 값이 이번에는 인스턴스 A, 다음에는 인스턴스 B에서 올 수 있어, 서로 다른 프로세스의 누적 카운터를 하나의 시계열처럼 섞게 된다.

| 수집 방식 | 장점 | 해석 시 주의점 |
| --- | --- | --- |
| Gateway 경유 | 강의의 서비스 접근 경로로 수집 가능 | Gateway와 라우팅에 의존하고 백엔드 식별이 어려울 수 있다. |
| 인스턴스별 직접 수집 | 프로세스별 자원과 카운터 구분 가능 | 수집기가 각 인스턴스에 접근할 주소가 필요하다. |

아래는 서비스 인스턴스가 `8081`, `8082`라고 가정한 설명용 대안이다. 같은 서비스를 두 번 중복 수집하는 추가 Job이 아니라, 직접 수집 방식으로 바꿀 때의 예시다.

```yaml title="prometheus.yml"
scrape_configs:
  - job_name: 'user-service'
    metrics_path: '/actuator/prometheus'
    static_configs:
      - targets: ['localhost:8081', 'localhost:8082']
```

주소가 동적으로 변한다면 정적 목록 대신 적절한 서비스 디스커버리를 사용한다. 애플리케이션이 Eureka에 등록되었다는 사실만으로 Prometheus의 수집 대상까지 자동으로 설정되지는 않는다.

#### 3.5 Counter·Gauge·Histogram·Summary는 해석 방식이 다르다

| 유형 | 값의 성격 | 대표적인 사용 |
| --- | --- | --- |
| Counter | 증가하며 프로세스 재시작 등으로 초기화될 수 있다. | 완료 요청 수, 오류 횟수 |
| Gauge | 현재 상태에 따라 증가하거나 감소한다. | 메모리, 활성 스레드, 활성 작업 수 |
| Histogram | 관측값을 구간별로 집계한다. | 응답 시간 분포와 분위수 계산 |
| Summary | 관측 수·합계와 설정에 따른 분위수를 제공한다. | 애플리케이션에서 계산한 분포 통계 |

Histogram과 Summary의 `_count`·양수 관측값의 `_sum`은 누적값으로 해석하지만, Summary가 직접 계산한 분위수를 인스턴스 간에 단순 합산하거나 평균 내서는 안 된다. 여러 인스턴스를 합친 분위수를 구하려면 집계 가능한 히스토그램 구성이 적합하다. [Prometheus 메트릭 유형](https://prometheus.io/docs/concepts/metric_types/)

강의의 응답에 `# TYPE ... summary`가 보인다고 p95가 자동으로 제공되는 것은 아니다. 또한 구형 LongTaskTimer의 출력 의미는 타입 이름만으로 일반 Timer와 같다고 판단하지 않고 앞 장의 활성 작업 기준을 적용한다.

#### 3.6 라벨 값이 많아지면 저장해야 할 시계열도 늘어난다

라벨별 값의 조합 수가 많아지는 것을 **높은 카디널리티**라고 한다. 사용자 ID·주문 ID·Trace ID처럼 계속 새로운 값이 생기는 정보를 라벨에 넣으면 시계열 수와 저장·조회 비용이 커진다.

HTTP 경로도 `/users/개별-ID`를 모두 다른 라벨로 기록하기보다 `/users/{userId}` 같은 경로 패턴으로 제한하는 것이 적합하다. 개별 요청의 식별 정보는 로그·Trace에 남기고, 메트릭에는 집계에 필요한 제한된 차원을 둔다. [Prometheus의 계측과 라벨 지침](https://prometheus.io/docs/practices/instrumentation/)

#### 3.7 실행 여부와 수집 성공 여부를 따로 확인한다

강의에서는 운영체제에 맞는 배포 파일을 내려받아 압축을 풀고 다음 명령으로 실행한다. 다운로드 화면의 Prometheus `2.25.0`은 강의 당시 버전이며, 설치 시에는 [공식 다운로드](https://prometheus.io/download/)에서 운영체제와 CPU 아키텍처에 맞는 배포본을 선택한다.

```bash
./prometheus --config.file=prometheus.yml
```

Windows에서는 같은 설정 파일을 지정해 `prometheus.exe`를 실행한다. 강의의 웹 UI 주소는 `http://127.0.0.1:9090`이다.

실행 후에는 Targets 화면에서 실제 수집 URL과 오류를 확인한다. 다음은 수집 상태를 확인하기 위한 설명용 PromQL이다.

```text
up{job="user-service"}
```

`up`이 1이면 해당 대상의 최근 스크레이프가 성공했고, 0이면 실패했다는 뜻이다. 결과 자체가 없으면 해당 대상이 설정되지 않았거나 현재 조회 범위에 시계열이 없는 경우 등을 구분해야 한다.

수집 성공은 업무 기능 전체의 정상 동작을 보장하지 않는다. Gateway 경유 구성에서는 그 수집 경로의 성공 여부를 나타내며, 주문 처리나 외부 의존 서비스의 상태까지 검사한 결과가 아니다.

> [!NOTE]
> 강의의 `Level DB → TSDB` 표기는 현재 저장 구조의 설명과 구분한다. 현재 Prometheus는 자체 로컬 TSDB에 시계열을 저장하며, 메모리의 최신 데이터·WAL·디스크 블록을 사용한다. 별도 LevelDB 서버를 설치하는 구성이 아니다. [Prometheus 저장 구조](https://prometheus.io/docs/prometheus/latest/storage/)

> Prometheus가 저장하는 것은 특정 이름과 라벨을 가진 대상의 시간별 측정값이다. 수집 주소와 실제 측정 대상이 일치하는지 확인해야 그래프도 올바르게 해석할 수 있다.

### 4. PromQL로 처리량·오류율·지연 시간 읽기

수집에 성공해도 누적 요청 수만 보면 현재 서비스가 바쁜지, 느린지 판단하기 어렵다. 저장된 메트릭을 질문에 맞게 선택하고 계산하는 언어가 PromQL이다.

강의는 `http_server_requests_seconds_count`를 Table과 Graph로 확인한다. 여기서는 그 조회에서 출발해 운영 상태를 읽는 계산까지 연결한다. 아래 쿼리는 별도 표시가 없는 한 설명용이며, 실제 노출된 메트릭 이름과 라벨을 먼저 확인해야 한다.

#### 4.1 Table은 평가 시점의 값을, Graph는 시간에 따른 변화를 보여 준다

강의 18쪽에서는 다음 메트릭을 조회한다.

```text
http_server_requests_seconds_count
```

Table 화면에는 `method`, `uri`, `status`, `outcome`, `job`, `instance` 등이 다른 여러 결과가 나온다. 한 메트릭이 하나의 숫자만 가지는 것이 아니라, 라벨 조합별 시계열로 나뉘어 있기 때문이다.

강의 19쪽 Graph는 같은 쿼리를 여러 시점에 평가한 선을 보여 준다. 누적 요청 수가 계속 올라가는 것은 처리량이 계속 증가한다는 뜻이 아니다. 일정한 속도로 요청을 받아도 누적값은 계속 증가한다.

#### 4.2 누적 요청 수를 rate로 바꾸면 초당 처리량이 된다

다음 설명용 쿼리는 User Service의 각 시계열에서 최근 5분간 평균 증가율을 구하고 이를 합친다.

```text
sum(rate(http_server_requests_seconds_count{job="user-service"}[5m]))
```

| 표현 | 역할 |
| --- | --- |
| `{job="user-service"}` | 해당 Job의 시계열만 선택한다. |
| `[5m]` | 각 평가 시점에서 직전 5분의 샘플을 사용한다. |
| `rate(...)` | 카운터의 초당 평균 증가율을 구한다. |
| `sum(...)` | 선택한 시계열들의 증가율을 합산한다. |

결과 단위는 초당 요청 수다. 최근 5분 요청 수 자체가 필요하다면 다음처럼 `increase`를 사용한다. 수집 간격과 구간 경계에 대한 보정 때문에 결과가 항상 정수인 것은 아니다.

```text
sum(increase(http_server_requests_seconds_count{job="user-service"}[5m]))
```

`rate`는 수집 구간의 단순 차이만 보는 것이 아니라 재시작에 따른 카운터 초기화도 고려한다. 따라서 각 시계열에 `rate`를 먼저 적용한 뒤 합산해야 하며, 서로 다른 인스턴스의 카운터를 먼저 더하고 변화율을 구하는 방식은 피한다. [Prometheus의 rate·increase](https://prometheus.io/docs/prometheus/latest/querying/functions/)

수집 간격이 15초여도 서비스 상태가 정확히 15초마다 바뀌는 것은 아니다. `rate`에는 여러 샘플이 필요하며, 5분 범위는 단기 흔들림을 완화하는 대신 급격한 변화도 완만하게 보이게 한다.

#### 4.3 오류율은 실패 요청과 전체 요청의 기준을 맞춰 계산한다

여기서는 HTTP 5xx를 서버 오류로 정의한다. 다음 설명용 쿼리는 최근 5분의 서버 오류 요청 비율을 백분율로 계산한다.

```text
100 * (
  sum(rate(http_server_requests_seconds_count{job="user-service",status=~"5.."}[5m]))
  or vector(0)
) / sum(rate(http_server_requests_seconds_count{job="user-service"}[5m]))
```

분자는 5xx 요청의 초당 증가율이고, 분모는 같은 Job·시간 범위의 전체 요청 증가율이다. 이 예시는 전체 합계를 하나의 값으로 만들므로, 아직 5xx 시계열이 없을 때 분자를 0으로 보완한다. 분모도 0이거나 전체 수집이 없으면 정상 오류율이 계산되지 않으므로 `up`과 트래픽을 함께 봐야 한다.

4xx를 서비스 실패로 포함할지, 특정 업무 실패를 어떻게 셀지는 별도의 기준이다. 또한 CircuitBreaker의 fallback이 HTTP 200으로 응답하면 HTTP 오류율에는 실패로 드러나지 않을 수 있으므로, 필요한 경우 fallback 횟수나 업무 실패 지표를 따로 관찰한다.

같은 계측 지점에서 분자·분모를 선택해야 한다. Gateway 요청 수와 백엔드 요청 수를 무작정 더하면 한 사용자 요청을 중복해서 셀 수 있고, 재시도가 있으면 두 계층의 요청 수가 달라질 수도 있다.

#### 4.4 평균 지연 시간은 처리 시간 증가량을 요청 수 증가량으로 나눈다

일반 HTTP Timer의 `_sum`은 누적 처리 시간이고 `_count`는 완료된 요청 수다. 다음 설명용 쿼리는 두 값의 최근 증가율을 나누어 요청당 평균 시간을 구한다.

```text
sum(rate(http_server_requests_seconds_sum{job="user-service"}[5m]))
/
sum(rate(http_server_requests_seconds_count{job="user-service"}[5m]))
```

분자는 초당 누적되는 처리 시간, 분모는 초당 처리한 요청 수이므로 결과 단위는 요청당 초다. 밀리초로 표시하려면 결과에 1000을 곱하거나 Grafana의 단위를 맞춘다.

여러 인스턴스의 평균을 단순 평균 내면 요청이 적은 인스턴스와 많은 인스턴스의 비중이 같아진다. 전체 처리 시간과 전체 요청 수를 각각 합친 뒤 나누는 방식이 요청 수를 반영한 평균이다. [Micrometer의 Prometheus Timer 조회](https://docs.micrometer.io/micrometer/reference/implementations/prometheus.html)

요청이 없는 구간에서는 분모가 0이 되어 유효한 평균이 나오지 않는다. 이를 무조건 0초로 채우면 요청이 없었던 시간을 매우 빠르게 처리한 시간처럼 오해할 수 있다.

#### 4.5 평균에 가려진 느린 요청은 히스토그램과 p95로 본다

평균이 낮아도 일부 요청은 매우 느릴 수 있다. **p95**는 관측된 요청 시간 분포의 95번째 백분위수이며, 소수의 느린 요청이 어느 수준인지 읽는 기준이 된다.

다음은 일반 HTTP Timer의 히스토그램을 활성화하는 설명용 `application.yml` 추가 설정이다. 이미 있는 `management` 설정 안에 병합하며, 같은 키를 중복해서 선언하지 않는다.

```yaml title="application.yml"
management:
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true
```

설정을 적용한 뒤 새 요청이 계측되고 버킷 시계열이 수집되어야 다음 쿼리를 사용할 수 있다. 아래는 고전적 히스토그램의 `_bucket` 출력을 사용하는 설명용 PromQL이다.

```text
histogram_quantile(
  0.95,
  sum by (le) (
    rate(http_server_requests_seconds_bucket{job="user-service"}[5m])
  )
)
```

`le`는 버킷의 상한을 나타내는 라벨이다. `sum by (le)`는 인스턴스 등의 다른 차원은 합치되 버킷 경계는 유지하고, `histogram_quantile`은 합쳐진 분포에서 p95를 추정한다. 버킷 경계를 사용하므로 정확한 개별 요청 목록에서 계산한 값과는 차이가 있을 수 있다. [Prometheus의 histogram_quantile](https://prometheus.io/docs/prometheus/latest/querying/functions/#histogram_quantile)

인스턴스별 p95를 구한 다음 평균 내는 방식은 전체 p95가 아니다. 또한 `_count`와 `_sum`만으로는 분포를 알 수 없으므로 p95를 복원할 수 없다. 히스토그램은 추가 시계열과 메모리를 사용하므로 필요한 측정 대상에 적용한다. [Micrometer의 히스토그램과 분위수](https://docs.micrometer.io/micrometer/reference/concepts/histogram-quantiles.html)

#### 4.6 HTTP 요청 지표와 JVM 자원 지표를 같은 시간대에서 읽는다

요청 지연이 늘 때 JVM 메모리·GC·CPU가 함께 변하는지 확인하면 원인을 좁힐 단서를 얻을 수 있다. 아래는 계측이 제공되는 경우 사용할 수 있는 대표 지표다.

| 메트릭 예시 | 관찰하는 것 | 해석 시 주의점 |
| --- | --- | --- |
| `jvm_memory_used_bytes` | 메모리 영역·풀별 사용량 | `area`, `id` 라벨과 함께 본다. |
| `process_cpu_usage` | 프로세스 CPU 사용 비율 | 비율과 백분율 표시를 구분한다. |
| `jvm_threads_live_threads` | 현재 살아 있는 JVM 스레드 수 | 스레드가 많다는 사실만으로 장애를 확정하지 않는다. |
| `jvm_gc_pause_seconds_count` | 기록된 GC 일시 정지 횟수 | 빈도는 누적값의 증가율로 읽는다. |

같은 시간대에 그래프가 변했다는 사실은 상관관계다. 메모리 누수나 CPU 병목이라고 확정하려면 로그·Trace·추가 진단 근거가 필요하다.

> 쿼리의 핵심은 함수 이름보다 값의 성격과 집계 범위다. 누적값은 변화율로, 현재값은 상태로 읽고, 분자·분모·라벨·시간 범위를 맞춰야 한다.

### 5. Grafana 대시보드와 모니터링 흐름 확인하기

Prometheus에서 필요한 수치를 조회할 수 있으면, Grafana에서 여러 지표를 같은 시간 범위에 배치해 볼 수 있다. Grafana는 Prometheus에 저장된 데이터를 조회하는 쪽이며, 이 구성에서 애플리케이션의 메트릭을 직접 스크레이프하는 주체는 Prometheus다.

마지막 단계에서는 연결 자체의 성공과 패널 내용의 정확성을 구분한다. 강의의 대시보드 결과도 이 기준으로 읽는다.

#### 5.1 Grafana의 데이터 소스는 Prometheus 서버다

강의는 Grafana를 실행하고 `http://127.0.0.1:3000`에 접속한다. 강의에 나온 초기 로그인은 `admin`·`admin`이며, 기본 초기 계정을 사용하는 설치에서는 첫 로그인 후 비밀번호를 변경한다.

강의의 macOS 실행 명령은 다음과 같다. 이는 강의 당시 바이너리 구성의 명령이다.

```bash
./bin/grafana-server web
```

현재 공식 문서의 독립 바이너리 실행 예시는 아래와 같다. 설치 디렉터리에서 실행하며, Homebrew·서비스 설치라면 해당 설치 방식의 실행 명령을 사용한다. Windows 강의의 `grafana-server.exe` 역시 현재 배포본의 실행 파일 이름과 구분한다. [Grafana 서버 실행 문서](https://grafana.com/docs/grafana/latest/setup-grafana/start-restart-grafana/)

```bash
./bin/grafana server
```

데이터 소스 추가에서는 다음 순서로 연결한다.

1. Prometheus 유형의 데이터 소스를 선택한다.
2. Grafana 서버가 접근할 수 있는 Prometheus 기본 주소를 입력한다.
3. 필요한 인증·연결 옵션을 설정한다.
4. `Save & test`로 연결을 확인한다.

강의에서는 `http://127.0.0.1:9090`을 설정하고 연결 성공 메시지를 확인한다. 여기에 `/actuator/prometheus`나 Gateway의 User Service 경로를 넣는 것이 아니다. [Grafana의 데이터 소스 역할](https://grafana.com/docs/grafana/latest/datasources/)

#### 5.2 localhost는 요청을 보내는 프로세스의 실행 환경을 가리킨다

브라우저에서 Prometheus에 접속된다고 Grafana 서버에서도 같은 주소가 통하는 것은 아니다. 특히 컨테이너에서는 `localhost`가 각 컨테이너 자신을 가리킨다.

| 실행 구성 | Grafana에 설정할 주소의 기준 |
| --- | --- |
| 두 서버가 같은 호스트에서 실행 | 로컬 Prometheus의 `http://localhost:9090` 사용 가능 |
| 같은 컨테이너 네트워크의 별도 서비스 | Prometheus 서비스 이름으로 접근 가능한 주소 사용 |
| 서로 다른 서버 | Grafana 서버에서 접근 가능한 Prometheus 호스트 사용 |

예를 들어 같은 컨테이너 네트워크에서 서비스 이름이 `prometheus`라면 `http://prometheus:9090`처럼 연결할 수 있다. 이는 설명용 구성 예시이며 실제 서비스 이름과 네트워크 설정에 맞춰야 한다. Prometheus가 애플리케이션을 수집할 때의 대상 주소도 같은 원칙으로 판단한다. [Grafana의 Prometheus 연결 문제 확인](https://grafana.com/docs/grafana/latest/datasources/prometheus/troubleshooting/)

#### 5.3 대시보드 가져오기는 데이터 소스와 쿼리를 연결하는 작업이다

강의 24~26쪽은 JVM(Micrometer)·Prometheus·Spring Cloud Gateway 대시보드를 찾아 가져오는 과정을 보여 준다. 대시보드는 패널·쿼리·변수·표시 설정의 묶음이며, 가져오는 순간 없던 메트릭이 생성되지는 않는다.

1. 대시보드의 JSON 또는 Grafana.com 식별 정보로 가져오기를 시작한다.
2. 대상 폴더와 이름을 확인한다.
3. 대시보드가 요구하는 Prometheus 데이터 소스를 실제 연결에 매핑한다.
4. 패널 쿼리의 메트릭·라벨·변수가 내 수집 데이터와 일치하는지 확인한다.

가져오기 방법은 [Grafana 대시보드 가져오기 문서](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/import-dashboards/)에서 확인할 수 있다. 오래된 대시보드는 현재 Micrometer의 메트릭 이름이나 라벨과 맞지 않을 수 있으므로 이름이 비슷하다는 이유만으로 호환된다고 판단하지 않는다.

| 대시보드 | 필요한 수집 데이터 | 놓치기 쉬운 조건 |
| --- | --- | --- |
| JVM(Micrometer) | 각 Java 프로세스의 JVM·프로세스 메트릭 | 서비스와 인스턴스 라벨을 맞춰야 한다. |
| Prometheus | Prometheus 자체 `/metrics` | User Service 메트릭만으로 채워지지 않는다. |
| Spring Cloud Gateway | Gateway 자체의 요청·JVM 메트릭 | Gateway를 경유한 User Service 수집과 다르다. |

#### 5.4 Gateway 대시보드에는 Gateway 자신의 계측이 필요하다

강의의 `/user-service/actuator/prometheus`는 라우팅된 User Service의 메트릭을 읽는 경로다. Gateway의 요청 통계를 보려면 Gateway 자체에도 Actuator와 Prometheus Registry를 적용하고 해당 엔드포인트를 노출·수집해야 한다.

아래는 Gateway 자체의 Actuator가 `localhost:8000/actuator/prometheus`에 노출된 경우의 설명용 Job이다. 기존 `prometheus.yml`의 `scrape_configs` 목록에 추가하는 항목이다.

```yaml title="prometheus.yml"
  - job_name: 'api-gateway'
    metrics_path: '/actuator/prometheus'
    static_configs:
      - targets: ['localhost:8000']
```

Spring Cloud Gateway Server WebFlux의 메트릭 필터는 `spring.cloud.gateway.requests`라는 Timer와 `routeId`·`routeUri`·`outcome`·`status`·`httpMethod` 등의 태그를 제공한다. 활성화 조건과 이름은 사용 버전의 문서와 실제 응답을 확인한다. [Gateway 메트릭 필터](https://docs.spring.io/spring-cloud-gateway/reference/spring-cloud-gateway-server-webflux/global-filters.html#_the_gateway_metrics_filter)

다음은 이 Timer가 `spring_cloud_gateway_requests_seconds_count`로 노출되는 환경에서 라우트별 초당 요청 수를 구하는 설명용 쿼리다.

```text
sum by (routeId) (
  rate(spring_cloud_gateway_requests_seconds_count{job="api-gateway"}[5m])
)
```

여기서 보는 것은 Gateway 계층의 요청 통계다. 백엔드 HTTP Timer와 측정 구간이 다르므로 응답 시간이 반드시 같지는 않으며, 사용자가 실제로 경험한 전체 시간과도 구분한다.

#### 5.5 강의 화면의 숫자와 데이터 부재를 구분해 읽는다

강의 27쪽의 Spring Cloud Gateway 대시보드에는 다음 항목이 표시되어 있다. 이 표는 제공된 강의 화면의 내용이며, 별도로 실행해 얻은 결과는 아니다.

| 화면 항목 | 강의에 표시된 내용 | 여기서 알 수 있는 범위 |
| --- | --- | --- |
| Total Requests Served | 181 | 해당 패널 쿼리가 반환한 요청 수다. |
| Total Successful Requests Served | 181 | 해당 패널의 성공 기준에 맞는 요청 수다. |
| Total Unsuccessful Requests Served | N/A | 실패가 정확히 0건이라고 단정할 수 없다. |
| CPU Usage·Memory Used | 시간에 따른 그래프 | 해당 수집·조회 조건의 자원 변화가 표시된다. |
| Live Threads | No data | 해당 패널에 표시할 결과가 없다. |

`N/A`나 `No data`는 정상적인 0과 다르다. 실제로 해당 시계열이 없을 수도 있고, 패널 쿼리·라벨·조회 시간이 맞지 않을 수도 있다. 화면만으로 그 원인을 확정할 수는 없다.

`Total`이라는 제목도 계산 방법을 보장하지 않는다. 패널이 현재 누적 카운터를 보여 주는지, 선택 시간 범위의 `increase`를 보여 주는지 쿼리를 열어 확인해야 한다.

#### 5.6 패널에 데이터가 없으면 계측에서 화면까지 차례로 확인한다

아래는 이 구성에서 사용할 수 있는 확인 기준이다. 실제로 겪고 해결한 오류 기록이 아니라, 어느 구간을 점검할지 구분하기 위한 설명이다.

| 확인 지점 | 확인할 내용 | 다음 판단 |
| --- | --- | --- |
| 애플리케이션 응답 | `/actuator/prometheus`에 원하는 메트릭이 있는가? | 없으면 의존성·계측 조건·요청 발생 여부 확인 |
| HTTP 접근 | 실제 수집 주체가 주소에 접근 가능한가? | 404는 경로·노출, 401·403은 인증·인가 등 확인 |
| Prometheus Targets | URL·상태·최근 수집 오류가 무엇인가? | 연결·타임아웃·응답 형식 문제 구분 |
| Prometheus 쿼리 | 메트릭 이름만 조회해도 결과가 있는가? | 이름·라벨·시간 범위·수집 여부 확인 |
| Grafana 데이터 소스 | 같은 쿼리가 올바른 데이터 소스를 사용하는가? | 연결과 데이터 소스 매핑 확인 |
| Grafana 패널 | 변수·단위·변환·시간 범위가 맞는가? | 표시 설정으로 결과가 가려졌는지 확인 |

요청 기반 메트릭은 첫 요청이 처리된 뒤 생성되는 경우가 있다. `@Timed` 메트릭이 없으면 호출이 실제로 계측 경로를 통과했는지도 확인해야 한다.

Grafana의 자동 새로 고침은 화면 조회 간격이고, Prometheus의 `scrape_interval`은 수집 간격이다. 화면을 더 자주 새로 고쳐도 그 사이에 새로운 스크레이프가 없으면 원본 샘플이 늘어나지 않는다.

`rate` 결과가 비어 있으면 원본 카운터는 있는지, 조회 구간 안에 충분한 샘플이 있는지 나눠 확인한다. Grafana에서는 실제 수집 간격에 맞춘 데이터 소스 설정과 `$__rate_interval`을 활용할 수 있다. [Grafana 쿼리 문제 확인](https://grafana.com/docs/grafana/latest/datasources/prometheus/troubleshooting/)

#### 5.7 대시보드와 알림은 같은 지표를 다른 방식으로 사용한다

대시보드는 사람이 여러 수치를 함께 읽는 화면이다. 알림은 정한 조건이 일정 시간 유지될 때 대응이 필요하다고 알려 주는 장치다.

Prometheus에서는 알림 규칙을 평가하고, Alertmanager는 발생한 알림의 그룹화·중복 제거·전달 등을 담당할 수 있다. Grafana도 별도의 알림 기능을 제공하므로, 대시보드를 가져왔다는 이유만으로 알림까지 설정되었다고 생각하면 안 된다. [Prometheus의 알림 구조](https://prometheus.io/docs/alerting/latest/overview/)

알림 기준은 수집 실패, HTTP 서버 오류율 상승, 지속적인 지연처럼 대응할 수 있는 현상과 연결한다. 임계값과 유지 시간은 서비스 기준으로 정해야 하며, 강의에서 정하지 않은 값을 정답처럼 기록하지 않는다.

> Grafana 연결 성공은 시작점이다. 실제 메트릭이 수집됐는지, 패널이 어떤 범위를 계산하는지, 데이터 부재를 0으로 오해하고 있지 않은지까지 확인해야 화면을 신뢰할 수 있다.

## 🧠 오늘 이해한 핵심

1. **계측·노출·수집·조회·시각화는 서로 다른 단계다.** Micrometer가 측정하고 Actuator가 노출한 값을 Prometheus가 수집·저장하며, Grafana는 쿼리 결과를 보여 준다. 어느 단계의 성공인지 구분해야 빠진 데이터를 찾을 수 있다.
2. **같은 시간 지표라도 완료된 작업과 진행 중인 작업은 의미가 다르다.** 일반 Timer의 누적 횟수·시간으로 처리량과 평균 지연을 구하고, LongTaskTimer로 현재 실행 중인 작업을 관찰한다. 메트릭 이름의 접미사보다 측정 대상과 실제 출력 의미를 먼저 확인한다.
3. **시계열의 신뢰성은 대상 식별과 집계 기준에 달려 있다.** Gateway 주소로 수집한 `instance`는 실제 백엔드 인스턴스를 뜻하지 않을 수 있다. 요청 처리량·오류율·평균·p95도 라벨과 관측 구간을 맞춰 계산해야 한다.
4. **모니터링의 수치는 로그·Trace와 연결할 때 원인 분석으로 이어진다.** 수집 성공이나 HTTP 200만으로 업무 전체의 정상을 보장할 수 없고, `N/A`는 0을 뜻하지 않는다. 전체 변화는 메트릭으로 발견하고 개별 실패의 경로와 문맥은 Trace·로그로 좁힌다.
