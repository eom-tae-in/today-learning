## 1. 추상화와 인터페이스를 통한 표준화

### 개념

추상화는 객체의 세부 구현보다 외부에 필요한 역할과 동작을 먼저 정의하는 것이다.

추상 클래스와 인터페이스는 모두 추상화를 지원하지만 사용하는 목적이 다르다.

|구분|추상 클래스|인터페이스|
|---|---|---|
|주요 목적|공통 상태와 구현을 공유하면서 확장|구현체가 따라야 할 동작 규약 정의|
|적용 방법|`extends`|`implements`|
|다중 적용|하나의 클래스만 상속 가능|여러 인터페이스 구현 가능|
|적합한 경우|관련된 클래스가 공통 기반을 공유할 때|서로 다른 클래스에 같은 역할을 부여할 때|

인터페이스를 사용하면 여러 구현체가 동일한 메서드 구조를 따르도록 표준화할 수 있다.

### 동작 흐름

```text
공통 역할 정의
   ↓
인터페이스에 동작 규약 선언
   ↓
각 클래스가 규약에 맞게 구현
   ↓
호출자는 인터페이스 타입으로 사용
   ↓
구현체가 변경되어도 호출 구조는 유지
```

### 핵심 코드

```java
interface Payment {
    void pay(int amount);
}

final class CardPayment implements Payment {

    @Override
    public void pay(int amount) {
        System.out.println("카드 결제: " + amount);
    }
}

final class CashPayment implements Payment {

    @Override
    public void pay(int amount) {
        System.out.println("현금 결제: " + amount);
    }
}
```

### 핵심 포인트

> 인터페이스는 구현 방법을 통일하는 것이 아니라, 구현체가 지켜야 할 동작의 형태를 표준화한다.

## 2. 객체 은닉화와 느슨한 결합

### 개념

은닉화는 필드를 단순히 `private`으로 선언하는 것에서 끝나지 않는다. 객체가 자신의 상태를 직접 관리하고, 외부에는 허용된 동작만 제공하는 것이 핵심이다.

```java
final class BankAccount {

    private int balance;

    public void deposit(int amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("입금액은 0보다 커야 합니다.");
        }

        balance += amount;
    }

    public int getBalance() {
        return balance;
    }
}
```

외부에서 `balance`를 임의로 변경할 수 없고, 반드시 `deposit()`의 검증 과정을 거쳐야 한다. 이를 통해 객체가 유효한 상태를 스스로 유지할 수 있다.

느슨한 결합은 클래스가 특정 구현체를 직접 생성하거나 의존하지 않고 인터페이스와 같은 추상화에 의존하도록 설계하는 것이다.

### 동작 흐름

```text
외부에서 Payment 구현체 선택
   ↓
생성자를 통해 OrderService에 전달
   ↓
OrderService는 Payment 규약에만 의존
   ↓
실행 시 전달된 구현체의 pay() 호출
```

### 핵심 코드

```java
final class OrderService {

    private final Payment payment;

    OrderService(Payment payment) {
        this.payment = payment;
    }

    public void order(int amount) {
        payment.pay(amount);
    }
}
```

`OrderService` 내부에서 `new CardPayment()`를 직접 호출하지 않으므로 `CashPayment`와 같은 다른 구현체로 교체하기 쉽다.

### 핵심 포인트

> 은닉화는 객체의 상태를 보호하고, 느슨한 결합은 구현 변경이 다른 객체로 퍼지는 범위를 줄인다.

## 3. Factory·Singleton 패턴과 Enum

### 개념

|구분|역할|
|---|---|
|Factory|구체적인 객체를 선택하고 생성하는 책임을 분리한다.|
|Singleton|하나의 클래스에서 하나의 인스턴스만 사용하도록 제어한다.|
|Enum|선택 가능한 상수를 타입으로 묶어 잘못된 값의 사용을 방지한다.|

Enum은 단순한 문자열 상수 모음이 아니라 정해진 값만 가질 수 있는 하나의 타입이다. Factory의 객체 선택 기준으로 사용하면 문자열보다 안전하게 구현체를 구분할 수 있다.

### 객체 생성 흐름

```text
PaymentType 전달
   ↓
PaymentFactory가 타입 확인
   ↓
알맞은 Payment 구현체 생성
   ↓
인터페이스 타입으로 반환
   ↓
OrderService에서 구현체 사용
```

### 핵심 코드

```java
enum PaymentType {
    CARD,
    CASH
}

final class PaymentFactory {

    private PaymentFactory() {
    }

    public static Payment create(PaymentType type) {
        return switch (type) {
            case CARD -> new CardPayment();
            case CASH -> new CashPayment();
        };
    }
}
```

```java
Payment payment = PaymentFactory.create(PaymentType.CARD);
OrderService orderService = new OrderService(payment);

orderService.order(10_000);
```

Singleton은 생성자를 `private`으로 제한하고, 클래스 내부에서 하나의 인스턴스만 생성해 제공한다.

```java
final class AppSettings {

    private AppSettings() {
    }

    private static class Holder {
        private static final AppSettings INSTANCE = new AppSettings();
    }

    public static AppSettings getInstance() {
        return Holder.INSTANCE;
    }
}
```

### 핵심 포인트

> Factory는 객체 생성 위치를 분리하고, Enum은 생성 대상을 안전하게 표현한다. Singleton은 인스턴스가 하나만 필요할 때 사용하지만 전역 상태와 테스트 의존성을 만들 수 있으므로 필요한 경우에만 적용해야 한다.

- 객체가 내부 상태를 스스로 관리하고 호출자가 추상화에 의존하도록 설계하면 변경의 영향 범위를 줄일 수 있다.
- Factory·Singleton·Enum은 모두 객체 생성과 관련되지만 각각 생성 책임 분리, 인스턴스 수 제어, 타입 안전한 값 제한이라는 다른 역할을 가진다.
