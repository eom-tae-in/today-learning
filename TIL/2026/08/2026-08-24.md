## 1. 관계형 데이터베이스 환경 이해

SQL을 작성하기 전에 DBMS, 실제 데이터를 저장하는 스토리지 엔진, 접속 도구의 역할을 구분해야 한다. MariaDB와 HeidiSQL을 같은 프로그램으로 이해하면 서버와 클라이언트의 책임이 섞이기 때문이다.

### DBMS와 RDBMS

DBMS(Database Management System)는 데이터를 저장·조회·변경하고 권한과 동시 접근을 관리하는 소프트웨어다. RDBMS(Relational Database Management System)는 그중 데이터를 행과 열로 구성된 테이블에 저장하고 테이블 간 관계를 이용하는 DBMS다.

| 구성 요소     | 의미            | `TB_STUDENT` 예시 |
| --------- | ------------- | --------------- |
| 행(Row)    | 하나의 데이터 묶음    | 학생 한 명          |
| 열(Column) | 데이터가 가진 속성    | `STUDENT_NAME`  |
| 기본 키(PK)  | 각 행을 유일하게 식별  | `STUDENT_NO`    |
| 외래 키(FK)  | 다른 테이블의 행을 참조 | `DEPARTMENT_NO` |

RDBMS와 Amazon RDS도 구분해야 한다.

| 용어         | 의미                         |
| ---------- | -------------------------- |
| RDBMS      | 관계형 데이터베이스 관리 시스템이라는 기술 분류 |
| Amazon RDS | AWS가 제공하는 관리형 데이터베이스 서비스   |

> RDBMS는 데이터 모델과 관리 방식이고, Amazon RDS는 여러 DBMS를 운영해 주는 클라우드 서비스다.

### MySQL과 MariaDB의 관계

```text
MySQL AB
    ↓ 2008년 인수
Sun Microsystems
    ↓ 2010년 인수
Oracle

MySQL 원 개발자들
    ↓ MySQL을 기반으로 포크
MariaDB
```

포크(Fork)는 기존 오픈소스 프로젝트의 소스 코드를 기반으로 별도의 개발 방향을 이어가는 것이다. MariaDB와 MySQL은 뿌리와 기본 문법이 비슷하지만 현재는 서로 독립적으로 발전하고 있으므로 모든 기능과 버전이 완전히 같지는 않다.

Tibero는 대한민국 기업 티맥스티베로가 개발한 상용 RDBMS다. 국내 기업·공공 환경에서 Oracle Database의 대안으로 사용되는 사례가 있다.

### Oracle Database와 프로그래밍 언어

Java가 Oracle Database와 자주 사용되는 이유는 단순히 두 기술을 Oracle이 보유하고 있기 때문이 아니다. 공식 JDBC 드라이버와 표준 API, Spring·JPA·MyBatis 같은 엔터프라이즈 생태계, 오랜 운영 사례가 함께 존재하기 때문이다.

Python도 Oracle이 관리하는 `python-oracledb` 드라이버를 통해 Oracle Database에 연결할 수 있다. 언어와 DB의 조합은 소유 회사보다 드라이버, 프레임워크, 팀 역량과 업무 목적을 기준으로 선택해야 한다.

### HeidiSQL의 역할

HeidiSQL은 DB 서버가 아니라 DB에 접속해 SQL을 실행하고 구조와 데이터를 확인하는 GUI 클라이언트다.

```text
사용자
    ↓ SQL 작성·실행
HeidiSQL
    ↓ 네트워크 연결
MariaDB Server
    ↓ 데이터 처리
데이터베이스와 테이블
```

- MariaDB/MySQL 외에도 PostgreSQL, Microsoft SQL Server, SQLite 등을 지원한다.
- 과거에는 Windows 중심 도구로 알려졌지만 현재는 Windows·Linux·macOS용 공식 빌드가 제공된다.
- 설치 가능 여부와 교육 환경에서 자동 설치되는지는 별개의 문제다.

### RDBMS와 Python DataFrame

| 비교 기준 | RDBMS                   | DataFrame                |
| ----- | ----------------------- | ------------------------ |
| 주된 목적 | 영구 저장과 다중 사용자 데이터 관리    | 메모리상의 데이터 가공과 분석         |
| 핵심 기능 | 트랜잭션, 권한, 제약조건, 동시성, 복구 | 열 단위 연산, 통계, 정제, 시각화 전처리 |
| 처리 위치 | DB 서버                   | Python 프로세스              |
| 대표 사용 | 업무 데이터 저장·조회            | 탐색적 분석과 추가 가공            |

```text
RDBMS에 원본 데이터 저장
    ↓ SQL로 필요한 행·열을 필터링하고 집계
필요한 결과만 Python으로 전달
    ↓
DataFrame으로 분석·가공·시각화
```

RDBMS도 `GROUP BY`, `SUM`, `AVG`로 열을 기준으로 분석할 수 있고 DataFrame도 행 단위로 처리할 수 있다. 둘의 차이를 단순히 “행 중심 대 열 중심”으로만 설명하기보다 저장 목적, 트랜잭션, 동시성, 실행 위치로 구분해야 한다.

> 데이터베이스, 스토리지 엔진, 접속 도구와 분석 도구는 서로 대체 관계가 아니라 각기 다른 책임을 맡는다.

## 2. MariaDB의 시스템 데이터베이스와 InnoDB

MariaDB 서버에 접속하면 사용자가 만든 DB 외에도 여러 시스템 DB가 보인다. 이들은 업무 데이터를 저장하는 곳이 아니라 서버 구조, 권한과 실행 상태를 관리하거나 조회하기 위한 영역이다.

### 기본 데이터베이스의 역할

| 데이터베이스               | 역할                               | 주의점                                |
| -------------------- | -------------------------------- | ---------------------------------- |
| `information_schema` | 데이터베이스·테이블·컬럼·인덱스 등 구조 정보 제공     | 일반 업무 데이터를 저장하는 DB가 아니다.           |
| `mysql`              | 계정, 인증, 권한과 서버 운영 정보 관리          | 내부 테이블을 직접 수정하지 않고 계정·권한 명령을 사용한다. |
| `performance_schema` | SQL 실행, 대기, 메모리, I/O, 연결 등 성능 계측 | 서버 내부 상태를 분석할 때 사용한다.              |
| `sys`                | 성능 관련 원시 정보를 읽기 쉬운 View로 가공      | 느린 쿼리와 인덱스 상태 점검에 활용한다.            |
| `test`               | 간단한 테스트와 연습                      | 핵심 시스템 DB가 아니며 설치 환경에 따라 없을 수 있다.  |
| `lgcns`              | 사용자가 생성한 실습용 DB                  | 실제 SQL 실습 대상을 저장한다.                |

구조 정보는 다음처럼 조회할 수 있다.

```sql
SELECT TABLE_SCHEMA,
       TABLE_NAME
FROM information_schema.TABLES;
```

`information_schema`, `mysql`, `performance_schema`, `sys`는 서버 운영에 필요한 영역이므로 실습 중 임의로 삭제하거나 내부 데이터를 직접 변경하지 않는다.

### InnoDB란

스토리지 엔진은 DBMS 내부에서 데이터를 저장하고 읽는 방식, 인덱스, 잠금, 트랜잭션과 복구를 담당한다. InnoDB는 MariaDB의 기본 스토리지 엔진이다.

```sql
CREATE TABLE ACCOUNT (
    ACCOUNT_ID BIGINT PRIMARY KEY,
    BALANCE DECIMAL(15, 2) NOT NULL
) ENGINE = InnoDB;
```

| 기능      | 역할                                               |
| ------- | ------------------------------------------------ |
| 트랜잭션    | 여러 SQL을 하나의 작업 단위로 묶고 `COMMIT`·`ROLLBACK`을 지원한다. |
| ACID    | 원자성·일관성·격리성·지속성을 지켜 데이터 신뢰성을 높인다.                |
| 행 단위 잠금 | 필요한 행을 중심으로 잠가 동시 작업의 충돌을 줄인다.                   |
| MVCC    | 여러 버전의 데이터를 이용해 읽기와 쓰기의 불필요한 충돌을 줄인다.            |
| 외래 키    | 부모·자식 테이블의 참조 무결성을 검사한다.                         |
| 장애 복구   | 로그를 이용해 비정상 종료 뒤 일관된 상태로 복구한다.                   |
| 인덱스 저장  | 기본 키를 중심으로 행을 배치하고 보조 인덱스에서 기본 키를 참조한다.          |

```text
SQL 실행
    ↓
MariaDB가 구문 분석·실행 계획 수립
    ↓
InnoDB가 데이터와 인덱스 접근
    ↓
트랜잭션·잠금·로그 처리
    ↓
결과 반환 또는 변경 내용 저장
```

> InnoDB는 파일 형식 하나가 아니라 데이터 저장, 트랜잭션, 동시성, 인덱스와 복구를 함께 책임지는 핵심 엔진이다.

## 3. SQL의 논리적 실행 순서

SQL은 `SELECT`부터 작성하지만 DB가 결과를 논리적으로 만드는 순서는 다르다. 이 차이를 알아야 별칭 사용 위치와 `WHERE`·`HAVING`의 역할을 정확히 이해할 수 있다.

### 작성 순서와 논리적 처리 순서

| 단계  | 작성 순서         | 논리적 처리 순서     |
| --- | ------------- | ------------- |
| 1   | `SELECT`      | `FROM / JOIN` |
| 2   | `FROM`        | `ON`          |
| 3   | `JOIN ... ON` | `WHERE`       |
| 4   | `WHERE`       | `GROUP BY`    |
| 5   | `GROUP BY`    | `HAVING`      |
| 6   | `HAVING`      | `SELECT`      |
| 7   | `ORDER BY`    | `DISTINCT`    |
| 8   | `LIMIT`       | `ORDER BY`    |
| 9   | -             | `LIMIT`       |

다음 쿼리는 재학생을 학과별로 묶고, 학생이 5명 이상인 학과 중 상위 3개를 조회한다.

```sql
SELECT DEPARTMENT_NO,
       COUNT(*) AS STUDENT_COUNT
FROM TB_STUDENT
WHERE ABSENCE_YN = 'N'
GROUP BY DEPARTMENT_NO
HAVING COUNT(*) >= 5
ORDER BY STUDENT_COUNT DESC
LIMIT 3;
```

```text
TB_STUDENT에서 행을 가져온다.
    ↓ WHERE
재학생만 남긴다.
    ↓ GROUP BY
학과 번호별 그룹을 만든다.
    ↓ HAVING
학생이 5명 이상인 그룹만 남긴다.
    ↓ SELECT
학과 번호와 학생 수를 출력 형태로 만든다.
    ↓ ORDER BY
학생 수가 많은 순서로 정렬한다.
    ↓ LIMIT
상위 3개 행만 반환한다.
```

### 실행 순서로 이해하는 주의점

#### `WHERE`에서 SELECT 별칭을 사용하기 어려운 이유

`WHERE`가 실행될 때는 아직 `SELECT`에서 별칭을 만들기 전이기 때문이다.

```sql
-- 잘못된 예
SELECT CAPACITY * 2 AS DOUBLE_CAPACITY
FROM TB_DEPARTMENT
WHERE DOUBLE_CAPACITY >= 60;

-- 조건식을 직접 사용
SELECT CAPACITY * 2 AS DOUBLE_CAPACITY
FROM TB_DEPARTMENT
WHERE CAPACITY * 2 >= 60;
```

#### `WHERE`와 `HAVING`

| 구분       | 필터링 대상      | 실행 시점         |
| -------- | ----------- | ------------- |
| `WHERE`  | 그룹화 전의 개별 행 | `GROUP BY` 이전 |
| `HAVING` | 그룹화된 결과     | `GROUP BY` 이후 |

#### 결과 순서

`ORDER BY`가 없으면 조회 결과의 순서는 보장되지 않는다. DB는 실행 계획과 데이터 상태에 따라 다른 순서로 행을 읽을 수 있다.

위 순서는 SQL을 이해하기 위한 논리적 순서다. 실제로는 옵티마이저가 같은 결과를 더 빠르게 만들기 위해 조인 순서, 인덱스와 조건 적용 방법을 변경할 수 있다.

> SQL의 작성 순서는 문법이고, 논리적 실행 순서는 결과가 만들어지는 사고 과정이며, 물리적 실행 계획은 옵티마이저가 선택한 실제 처리 방법이다.

## 4. NULL과 인덱스의 관계

SELECT 조건을 작성하려면 값의 부재를 표현하는 NULL과 검색 범위를 줄이는 인덱스를 함께 이해해야 한다. 특히 “NULL이 있으면 인덱스가 풀린다”는 표현은 MariaDB/MySQL 기준으로 정확하지 않다.

### NULL의 의미

NULL은 숫자 0이나 빈 문자열 `''`이 아니다. 값이 없거나 아직 알려지지 않은 상태다.

```sql
-- 잘못된 비교
SELECT STUDENT_NAME
FROM TB_STUDENT
WHERE DEPARTMENT_NO = NULL;

-- NULL인 행
SELECT STUDENT_NAME
FROM TB_STUDENT
WHERE DEPARTMENT_NO IS NULL;

-- NULL이 아닌 행
SELECT STUDENT_NAME
FROM TB_STUDENT
WHERE DEPARTMENT_NO IS NOT NULL;
```

NULL과 일반 비교 연산을 수행하면 결과는 참이나 거짓이 아니라 `UNKNOWN`이 된다. `WHERE`는 결과가 참인 행만 남기므로 `= NULL`로는 원하는 행을 찾을 수 없다.

| 표현              | 결과 또는 의미              |
| --------------- | --------------------- |
| `NULL = NULL`   | `UNKNOWN`             |
| `NULL <> NULL`  | `UNKNOWN`             |
| `10 + NULL`     | `NULL`                |
| `COUNT(*)`      | NULL 여부와 관계없이 행을 센다.  |
| `COUNT(COLUMN)` | 해당 컬럼이 NULL인 행을 제외한다. |

### 인덱스의 역할

인덱스는 테이블 전체를 처음부터 읽지 않고 조건에 맞는 행의 위치를 빠르게 찾도록 돕는 별도의 자료구조다.

```sql
CREATE INDEX IDX_STUDENT_DEPARTMENT
    ON TB_STUDENT (DEPARTMENT_NO);

SELECT STUDENT_NAME
FROM TB_STUDENT
WHERE DEPARTMENT_NO = '001';
```

```text
검색 조건 확인
    ↓
B-Tree 인덱스에서 값의 범위 탐색
    ↓
일치하는 기본 키 또는 행 위치 확인
    ↓
필요한 행만 조회
```

인덱스는 읽기 성능을 높일 수 있지만 저장 공간을 사용하고, `INSERT`, `UPDATE`, `DELETE` 때 함께 갱신해야 한다. 따라서 인덱스가 많을수록 항상 좋은 것은 아니다.

### NULL이 있으면 인덱스를 사용할 수 없는가?

MariaDB/MySQL의 일반 InnoDB B-Tree 인덱스는 NULL을 허용하는 컬럼에도 만들 수 있고, `IS NULL` 조건에서도 인덱스를 사용할 수 있다.

- NULL이 존재한다고 인덱스가 삭제되거나 무효화되지 않는다.
- `IS NULL`, `IS NOT NULL`에서도 인덱스를 사용할 가능성이 있다.
- 조건에 맞는 행이 대부분이면 옵티마이저가 전체 테이블 스캔이 더 저렴하다고 판단할 수 있다.
- 이 경우는 인덱스가 “풀린 것”이 아니라 해당 실행 계획에서 선택되지 않은 것이다.

Oracle의 일반 B-Tree 인덱스는 모든 인덱스 컬럼이 NULL인 행을 저장하지 않는 특성이 있다. 따라서 특정 DBMS의 특성을 다른 DBMS에 그대로 적용하지 않아야 한다.

### 인덱스 사용에 유리하거나 불리한 조건

| 조건                       | 일반적인 영향      | 이유                           |
| ------------------------ | ------------ | ---------------------------- |
| `COLUMN = VALUE`         | 유리           | 특정 값을 바로 탐색할 수 있다.           |
| `IN (...)`               | 유리할 수 있음     | 여러 개의 동등 조건을 탐색한다.           |
| `BETWEEN`, `>=`, `<`     | 유리           | 정렬된 인덱스에서 범위를 찾을 수 있다.       |
| `LIKE '전주%'`             | 유리할 수 있음     | 문자열 시작 지점을 기준으로 범위를 정할 수 있다. |
| `SUBSTRING(COLUMN, ...)` | 불리           | 저장된 원본 값이 아닌 함수 결과를 비교한다.    |
| `LIKE '%전주%'`            | 불리           | 검색 시작 위치를 정할 수 없다.           |
| 암시적 형 변환                 | 불리할 수 있음     | 비교 과정에서 컬럼 값의 변환이 필요할 수 있다.  |
| 전체의 대부분을 반환              | 사용하지 않을 수 있음 | 테이블 전체를 읽는 비용이 더 낮을 수 있다.    |

복합 인덱스 `(DEPARTMENT_NO, ABSENCE_YN)`는 왼쪽의 `DEPARTMENT_NO`부터 조건에 사용해야 인덱스의 정렬 구조를 효과적으로 활용할 수 있다.

### 실행 계획 확인

인덱스 사용 여부는 추측하지 않고 `EXPLAIN`으로 확인한다.

```sql
EXPLAIN
SELECT STUDENT_NAME
FROM TB_STUDENT
WHERE DEPARTMENT_NO = '001';
```

| 항목              | 확인 내용             |
| --------------- | ----------------- |
| `type`          | 테이블에 접근한 방식       |
| `possible_keys` | 사용할 수 있었던 후보 인덱스  |
| `key`           | 실제 선택한 인덱스        |
| `rows`          | 읽을 것으로 예상한 행 수    |
| `Extra`         | 추가 정렬·필터링 등 실행 정보 |

> 인덱스의 존재와 실제 사용은 다르다. 옵티마이저는 조건과 데이터 분포를 바탕으로 인덱스 접근과 전체 스캔 중 비용이 낮은 방법을 선택한다.

## 5. Basic SELECT 문법을 쿼리에 적용

Basic SELECT 1~10번을 풀며 출력 형태 지정, 문자열 결합, 여러 조건의 조합, 범위와 NULL 검색, 중복 제거와 날짜 조건을 확인했다.

### 사용한 문법

| 문법                      | 역할                | 적용 문제   |
| ----------------------- | ----------------- | ------- |
| `AS`                    | 출력 컬럼의 별칭 지정      | 1, 2    |
| `CONCAT`                | 문자열과 컬럼 값 연결      | 2       |
| `JOIN`·서브쿼리             | 다른 테이블의 값을 조건에 활용 | 3       |
| `SUBSTRING`             | 문자열의 일부 추출        | 3       |
| `IN`                    | 여러 후보 값 중 하나인지 검사 | 3, 4    |
| `BETWEEN`               | 양 끝을 포함하는 범위 검색   | 5       |
| `IS NULL`·`IS NOT NULL` | 값의 부재 여부 검사       | 6, 7, 8 |
| `DISTINCT`              | SELECT 결과의 중복 제거  | 9       |
| `LIKE`                  | 문자열 패턴 검색         | 10      |
| `>=`·`<`                | 반열린 구간으로 날짜 범위 검색 | 10      |

### 1~2번: 출력 형태 만들기

```sql
-- 1. 학과 이름과 계열에 출력 별칭 지정
SELECT DEPARTMENT_NAME AS `학과 명`,
       CATEGORY AS `계열`
FROM TB_DEPARTMENT;

-- 2. 학과 이름과 정원을 한 문장으로 연결
SELECT CONCAT(
           DEPARTMENT_NAME,
           '의 정원은 ',
           CAPACITY,
           ' 명 입니다.'
       ) AS `학과별 정원`
FROM TB_DEPARTMENT;
```

MariaDB에서는 공백이 포함된 식별자 별칭을 백틱으로 감싸는 것이 안전하다. `CONCAT`은 인수 중 하나가 NULL이면 전체 결과가 NULL이 될 수 있으므로 필요하면 `COALESCE(CAPACITY, 0)`처럼 기본값을 지정한다.

### 3번: 다른 테이블의 값과 여러 조건 연결

문제에서는 국어국문학과의 학과 코드를 `TB_DEPARTMENT`에서 조회하도록 요구했다. 따라서 `DEPARTMENT_NO = '001'`로 직접 고정하기보다 두 테이블을 연결하는 편이 문제 의도에 맞다.

```sql
SELECT S.STUDENT_NAME
FROM TB_STUDENT AS S
JOIN TB_DEPARTMENT AS D
  ON D.DEPARTMENT_NO = S.DEPARTMENT_NO
WHERE D.DEPARTMENT_NAME = '국어국문학과'
  AND S.ABSENCE_YN = 'Y'
  AND SUBSTRING(S.STUDENT_SSN, 8, 1) IN ('2', '4');
```

```sql
학생과 학과를 학과번호로 연결
    ↓
국어국문학과 학생만 선택
    ↓
휴학생만 선택
    ↓
주민번호 구분 값이 2 또는 4인 학생만 선택
    ↓
학생 이름 반환
```

### 4~5번: 여러 값과 범위 검색

```sql
-- 4. 지정된 학번 중 하나에 해당하는 학생 조회
SELECT STUDENT_NAME
FROM TB_STUDENT
WHERE STUDENT_NO IN (
    'A513079',
    'A513090',
    'A513091',
    'A513110',
    'A513119'
);

-- 5. 정원이 20명 이상 30명 이하인 학과 조회
SELECT DEPARTMENT_NAME,
       CATEGORY
FROM TB_DEPARTMENT
WHERE CAPACITY BETWEEN 20 AND 30;
```

`IN`은 같은 컬럼을 여러 번 `OR`로 비교하는 조건을 간결하게 표현한다. `BETWEEN 20 AND 30`은 20과 30을 모두 포함한다.

4번 문제는 정렬을 요구하지 않으므로 `ORDER BY STUDENT_NAME DESC`를 추가할 필요가 없다. 정렬이 필요하다면 요구사항에 맞는 방향을 명시해야 하며, `ORDER BY`가 없으면 결과 순서는 보장되지 않는다.

### 6~9번: NULL 검사와 중복 제거

```sql
-- 6. 소속 학과가 없는 교수 조회
SELECT PROFESSOR_NAME
FROM TB_PROFESSOR
WHERE DEPARTMENT_NO IS NULL;

-- 7. 학과가 지정되지 않은 학생 조회
SELECT STUDENT_NAME
FROM TB_STUDENT
WHERE DEPARTMENT_NO IS NULL;

-- 8. 선수과목이 존재하는 과목의 과목번호 조회
SELECT CLASS_NO
FROM TB_CLASS
WHERE PREATTENDING_CLASS_NO IS NOT NULL;

-- 9. 학과에 존재하는 계열의 종류 조회
SELECT DISTINCT CATEGORY
FROM TB_DEPARTMENT;
```

7번은 데이터 품질 점검의 의미도 있다. Workbook의 테이블 구조대로 `TB_STUDENT.DEPARTMENT_NO`에 `NOT NULL` 제약조건이 실제 적용되어 있다면 결과가 0건이어야 정상이다.

`DISTINCT`는 특정 컬럼 하나가 아니라 `SELECT`에 작성한 컬럼 조합 전체를 기준으로 중복을 제거한다. 9번에서는 `CATEGORY` 하나만 선택하므로 계열 종류만 한 번씩 반환한다.

### 10번: 날짜와 문자열 검색

처음 작성한 `ENTRANCE_DATE LIKE '2002%'`도 형 변환을 통해 결과가 나올 수 있지만, `ENTRANCE_DATE`가 DATE 타입이라면 날짜 범위로 비교하는 것이 의미가 명확하고 일반 인덱스 활용에도 유리하다.

```sql
SELECT STUDENT_NO,
       STUDENT_NAME,
       STUDENT_SSN
FROM TB_STUDENT
WHERE ENTRANCE_DATE >= '2002-01-01'
  AND ENTRANCE_DATE <  '2003-01-01'
  AND STUDENT_ADDRESS LIKE '%전주%'
  AND ABSENCE_YN = 'N';
```

```text
2002-01-01 이상
    ↓ AND
2003-01-01 미만
    ↓
2002년의 모든 날짜·시각 포함
```

`YEAR(ENTRANCE_DATE) = 2002`는 읽기 쉽지만 컬럼을 함수로 가공하므로 일반 `ENTRANCE_DATE` 인덱스의 범위 검색에 불리할 수 있다.

`STUDENT_ADDRESS LIKE '%전주%'`는 문자열 중간에 전주가 포함된 행을 찾지만 앞에 `%`가 있어 일반 B-Tree 인덱스로 검색 시작 위치를 정하기 어렵다.

> SQL은 결과만 맞추는 데서 끝나지 않는다. 데이터 타입, 문제의 요구사항, NULL의 의미와 인덱스 사용 가능성까지 고려해 조건을 작성해야 한다.

문제 문장의 대상이 애매함

## 문제 1. 8번에서 어떤 과목번호를 출력해야 하는가?

### 원인

`PREATTENDING_CLASS_NO`가 선수과목의 번호이기 때문에 이 값을 출력해야 하는지, 선수과목을 가진 현재 과목의 `CLASS_NO`를 출력해야 하는지 헷갈릴 수 있었다.

### 해결

문제는 “선수과목이 존재하는 과목들의 과목번호”를 요구한다. 따라서 `PREATTENDING_CLASS_NO IS NOT NULL`로 조건을 검사하고 현재 과목의 `CLASS_NO`를 출력한다.

```sql
SELECT CLASS_NO
FROM TB_CLASS
WHERE PREATTENDING_CLASS_NO IS NOT NULL;
```

### 배운 점

> 조건을 검사하는 컬럼과 최종 출력하는 컬럼은 서로 다를 수 있다.

## 문제 2. 9번에서 왜 DISTINCT가 필요한가?

### 원인

`TB_DEPARTMENT`에는 같은 계열에 속한 여러 학과가 있으므로 `CATEGORY`를 그대로 조회하면 같은 계열이 반복된다.

### 해결

문제는 학과 목록이 아니라 계열의 “종류”를 요구하므로 `DISTINCT`로 중복을 제거한다.

```sql
SELECT DISTINCT CATEGORY
FROM TB_DEPARTMENT;
```

### 배운 점

> 요구사항의 “어떤 종류가 있는가”는 중복을 제거해야 한다는 신호가 될 수 있다.

## 문제 3. 인덱스 컬럼에 NULL이 있으면 인덱스가 풀리는가?

### 원인

Oracle의 일반 B-Tree 인덱스 특성이나 옵티마이저가 인덱스를 선택하지 않은 상황을 MariaDB/MySQL의 인덱스 자체가 무효화된 것으로 혼동했다.

### 해결

MariaDB/MySQL의 InnoDB에서는 NULL을 허용하는 컬럼에도 인덱스를 만들 수 있고 `IS NULL` 검색에 인덱스를 사용할 수 있다. 다만 조회 대상이 너무 많으면 옵티마이저가 전체 스캔을 선택할 수 있으므로 실제 사용 여부는 `EXPLAIN`으로 확인해야 한다.

### 배운 점

> 인덱스가 존재하는 것과 특정 쿼리에서 인덱스가 선택되는 것은 별개의 문제다.

---

# 🧠 오늘 이해한 핵심

- MariaDB 서버, HeidiSQL 클라이언트와 InnoDB 스토리지 엔진은 하나의 도구가 아니라 서로 다른 계층에서 접속·SQL 실행·데이터 저장을 담당한다.
- SQL은 작성 순서와 논리적 실행 순서가 다르며, 이 차이로 `WHERE`에서 SELECT 별칭을 바로 사용할 수 없는 이유와 `WHERE`·`HAVING`의 차이를 설명할 수 있다.
- NULL이 포함되어 있다는 이유로 인덱스가 무효화되는 것은 아니며, 옵티마이저가 데이터 분포와 조건의 형태를 보고 인덱스 사용 여부를 결정한다.
- 조회 쿼리는 결과만 맞는지보다 문제의 요구사항, 컬럼 타입, 정렬 보장과 인덱스 사용 가능성까지 함께 검토해야 한다.
