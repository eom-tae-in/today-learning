## 1. Stream API로 마무리한 `Post` CRUD

### CRUD와 Stream의 역할

CRUD는 데이터를 생성하고(Create), 조회하고(Read), 수정하고(Update), 삭제하는(Delete) 기본 작업이다. 메모리의 `List<Post>`를 데이터 저장소로 사용하면 Stream API로 목록을 선언적으로 조회하고 조건에 맞는 데이터를 찾을 수 있다.

다만 Stream은 컬렉션 자체를 저장하거나 수정하는 자료구조가 아니다. **원본 컬렉션을 순회하여 원하는 결과를 만드는 처리 흐름**이므로, 작업의 목적에 따라 Stream과 컬렉션 메서드를 구분해야 한다.

| 작업       | 적합한 방식                          | 이유                               |
| -------- | ------------------------------- | -------------------------------- |
| 생성       | `List.add()`                    | 원본 컬렉션에 새 요소를 추가해야 한다.           |
| 전체·조건 조회 | `stream()`, `filter()`, `map()` | 순회·선별·변환을 선언적으로 표현할 수 있다.        |
| 단건 조회    | `filter()` → `findFirst()`      | 조건에 맞는 첫 요소를 `Optional`로 표현한다.   |
| 수정       | 조회 후 객체의 변경 메서드 호출              | 대상을 찾는 과정과 상태를 바꾸는 책임을 분리할 수 있다. |
| 삭제       | `removeIf()`                    | 원본 컬렉션에서 조건에 맞는 요소를 직접 제거한다.     |

### 처리 흐름

```text
Controller가 CRUD 요청을 받음
        ↓ 요청 값 전달
Service가 처리할 작업을 결정
        ↓
List<Post>에서 추가·조회·수정·삭제
        ↓ 조회 시 Stream으로 조건 처리
Post 또는 결과 목록 반환
        ↓
Controller가 응답 생성
```

### 복습용 예시 코드

아래 코드는 오늘 실습한 범위를 다시 확인하기 위한 대표 예시다. 실제 수업 코드와 세부 클래스 구조는 다를 수 있다.

```java
public class PostService {

    private final List<Post> posts = new ArrayList<>();
    private long sequence = 1L;

    public Post create(String title, String content) {
        Post post = new Post(sequence++, title, content);
        posts.add(post);
        return post;
    }

    public List<Post> findAll() {
        return posts.stream()
                .toList();
    }

    public Post findById(long id) {
        return posts.stream()
                .filter(post -> post.getId() == id)
                .findFirst()
                .orElseThrow(() -> new IllegalArgumentException("게시글이 없습니다."));
    }

    public Post update(long id, String title, String content) {
        Post post = findById(id);
        post.update(title, content);
        return post;
    }

    public void delete(long id) {
        boolean removed = posts.removeIf(post -> post.getId() == id);

        if (!removed) {
            throw new IllegalArgumentException("게시글이 없습니다.");
        }
    }
}
```

### 중간 연산과 최종 연산

```text
posts.stream()
        ↓ 스트림 생성
filter(...)
        ↓ 조건 등록: 아직 순회하지 않음
findFirst()
        ↓ 최종 연산 호출
실제 데이터 처리 시작
        ↓
Optional<Post> 반환
```

- `filter()`는 조건을 등록하는 **중간 연산**이다.
- `findFirst()`와 `toList()`는 처리를 시작하고 결과를 만드는 **최종 연산**이다.
- `findFirst()`는 결과가 없을 가능성을 `Optional<Post>`로 표현한다.
- Java 16 이상에서 `Stream.toList()`가 반환한 목록은 요소를 추가·삭제할 수 없다. 수정 가능한 새 목록이 필요하면 `Collectors.toCollection(ArrayList::new)` 등을 사용한다.

> Stream은 조회와 데이터 가공의 흐름을 표현한다. 원본 컬렉션의 구조를 바꾸는 생성·삭제와 객체 상태를 바꾸는 수정까지 무조건 Stream으로 해결하려 하지 않는다.

## 2. 메모리 CRUD에서 데이터베이스 영속화로 이어지는 ORM

### ORM이 필요한 이유

`List<Post>`에 저장한 데이터는 애플리케이션이 종료되면 사라진다. 데이터를 계속 보관하려면 관계형 데이터베이스에 저장해야 하지만, Java 객체와 관계형 테이블은 데이터를 표현하는 방식이 다르다.

| Java 객체 | 관계형 데이터베이스      |
| ------- | --------------- |
| 클래스     | 테이블             |
| 필드      | 컬럼              |
| 객체 참조   | 외래 키와 조인        |
| 상속·캡슐화  | 행과 열 중심의 데이터 구조 |

ORM(Object-Relational Mapping)은 이 차이를 매핑 정보로 연결한다. 개발자는 객체를 중심으로 저장·조회하고, ORM 구현체는 객체의 변경과 조회 요청을 SQL로 변환하여 데이터베이스와 통신한다.

### Spring Boot에서의 일반적인 데이터 접근 흐름

```text
HTTP 요청
        ↓
Controller
        ↓ 요청 처리 위임
Service
        ↓ 비즈니스 규칙·트랜잭션
Repository
        ↓ 객체 단위 저장·조회
JPA
        ↓ 표준 명세에 따른 처리
Hibernate
        ↓ SQL 생성·JDBC 사용
관계형 데이터베이스
```

- **JPA**는 Java ORM 사용 방법을 정의한 표준 명세다.
- **Hibernate**는 JPA 명세를 실제로 구현한 대표적인 ORM 프레임워크다.
- **Spring Data JPA**는 Repository 인터페이스를 중심으로 반복적인 데이터 접근 코드를 줄여 준다.

### 복습용 매핑 예시

```java
@Entity
@Table(name = "posts")
public class Post {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;

    private String content;

    protected Post() {
    }
}
```

```java
public interface PostRepository extends JpaRepository<Post, Long> {
}
```

`Post` 객체와 `posts` 테이블의 대응 관계를 선언하면 Repository는 객체 단위의 저장·조회 인터페이스를 제공한다. 그러나 ORM을 사용해도 데이터베이스와 SQL이 사라지는 것은 아니다. 생성되는 SQL, 연관관계, 트랜잭션 범위와 조회 횟수를 함께 이해해야 한다.

> ORM의 목적은 SQL을 몰라도 되게 만드는 것이 아니라, 객체와 테이블 사이의 반복적인 변환을 맡아 애플리케이션을 객체 중심으로 설계하도록 돕는 것이다.

## 3. I/O Stream으로 애플리케이션 외부의 데이터 다루기

### I/O Stream의 기준

I/O에서 방향은 항상 **프로그램을 기준**으로 판단한다.

```text
파일·네트워크·키보드
        ↓ 데이터가 프로그램으로 들어옴
Input
        ↓ 프로그램 내부에서 처리
Output
        ↓ 데이터가 프로그램 밖으로 나감
파일·네트워크·화면
```

Java의 I/O Stream은 데이터를 연속적인 흐름으로 읽거나 쓰는 API다. 데이터의 종류에 따라 바이트 기반과 문자 기반 스트림을 선택한다.

| 구분      | 입력            | 출력             | 적합한 데이터                      |
| ------- | ------------- | -------------- | ---------------------------- |
| 바이트 스트림 | `InputStream` | `OutputStream` | 이미지, 영상, 압축 파일 등 모든 바이너리 데이터 |
| 문자 스트림  | `Reader`      | `Writer`       | 문자 인코딩을 해석해야 하는 텍스트 데이터      |

### 보조 스트림과 버퍼

파일에 직접 연결되는 스트림에 `BufferedReader`나 `BufferedOutputStream` 같은 보조 스트림을 연결하면 데이터를 일정 크기만큼 모아 처리할 수 있다. 작은 단위로 저장 장치에 반복 접근하는 횟수를 줄여 입출력 효율을 높이고, `readLine()` 같은 편의 기능도 사용할 수 있다.

```text
파일
  ↓ 실제 데이터 연결
File 기반 스트림
  ↓ 버퍼 기능 추가
Buffered 스트림
  ↓ read()·readLine()·write()
프로그램
```

### 복습용 텍스트 파일 입출력 예시

```java
Path path = Path.of("posts.txt");

try (BufferedWriter writer = Files.newBufferedWriter(
        path,
        StandardCharsets.UTF_8
)) {
    writer.write("1|Stream API로 Post 조회하기");
    writer.newLine();
    writer.write("2|ORM의 역할 이해하기");
}

try (BufferedReader reader = Files.newBufferedReader(
        path,
        StandardCharsets.UTF_8
)) {
    String line;

    while ((line = reader.readLine()) != null) {
        System.out.println(line);
    }
}
```

### 반드시 함께 기억할 점

- `try-with-resources`는 `AutoCloseable`을 구현한 자원을 블록 종료 시 자동으로 닫는다.
- 텍스트 파일은 같은 바이트라도 문자 인코딩에 따라 다르게 해석될 수 있으므로 `UTF-8`처럼 인코딩을 명시하는 편이 안전하다.
- 출력 스트림의 버퍼에 남은 데이터는 `flush()`로 내보낼 수 있다. `close()`가 호출될 때도 flush가 수행되므로, 정상적으로 자원을 닫는 것이 중요하다.
- 바이너리 데이터를 문자 스트림으로 읽으면 데이터가 손상될 수 있다. 데이터 성격에 맞는 스트림 계층을 선택해야 한다.

> Input과 Output은 파일의 입장이 아니라 프로그램의 입장이다. 텍스트는 `Reader`·`Writer`, 바이너리는 `InputStream`·`OutputStream`을 기준으로 선택한다.

## 4. Serializable과 객체 직렬화

### 개념

메모리의 객체는 JVM이 실행되는 동안만 존재한다. 객체의 현재 상태를 파일에 저장하거나 다른 시스템으로 전달하려면 객체를 연속된 바이트 형태로 바꾸어야 한다.

- **직렬화(Serialization)**: 객체를 바이트 스트림으로 변환한다.
- **역직렬화(Deserialization)**: 바이트 스트림으로부터 객체를 복원한다.
- `**Serializable**`: 해당 클래스의 객체를 Java 직렬화 대상으로 사용할 수 있음을 표시하는 마커 인터페이스다.

### 동작 흐름

```text
Java 객체
        ↓ ObjectOutputStream.writeObject()
바이트 데이터로 직렬화
        ↓ 파일 저장·네트워크 전송
바이트 스트림
        ↓ ObjectInputStream.readObject()
Java 객체로 역직렬화
```

### 복습용 예시 코드

```java
public class Post implements Serializable {

    @Serial
    private static final long serialVersionUID = 1L;

    private Long id;
    private String title;
    private String content;
}
```

```java
Path path = Path.of("post.dat");

try (ObjectOutputStream output = new ObjectOutputStream(
        Files.newOutputStream(path)
)) {
    output.writeObject(post);
}

try (ObjectInputStream input = new ObjectInputStream(
        Files.newInputStream(path)
)) {
    Post restoredPost = (Post) input.readObject();
}
```

### 직렬화 시 주의할 점

| 항목                 | 핵심 내용                                                       |
| ------------------ | ----------------------------------------------------------- |
| 객체 그래프             | 직렬화 대상이 참조하는 객체도 직렬화할 수 있어야 한다.                             |
| `serialVersionUID` | 직렬화한 클래스와 역직렬화할 클래스의 버전 호환 여부를 판단한다.                        |
| `transient`        | 민감 정보나 복원할 필요가 없는 필드를 직렬화 대상에서 제외한다.                        |
| `static` 필드        | 객체가 아니라 클래스에 속하므로 객체 상태로 직렬화되지 않는다.                         |
| 신뢰할 수 없는 데이터       | 역직렬화 과정에서 보안 문제가 생길 수 있으므로 임의의 외부 데이터를 Java 객체로 역직렬화하지 않는다. |

Java 기본 직렬화는 JVM 객체를 그대로 복원하는 데 초점을 둔다. 장기간 저장하거나 서로 다른 언어·시스템 사이에서 데이터를 주고받을 때는 구조가 명시적인 JSON 같은 형식이 더 적합한 경우가 많다.

> `Serializable`은 객체를 영구적으로 안전하게 보관해 주는 저장 기술 자체가 아니다. 객체를 바이트로 바꿀 수 있게 하는 규약이며, 호환성과 보안을 함께 고려해야 한다.

## 5. 정규표현식으로 문자열 패턴 검증하기

### 정규표현식이 필요한 이유

파일이나 요청에서 읽은 문자열은 형식이 일정하지 않을 수 있다. 정규표현식(Regular Expression)은 문자열의 규칙을 하나의 패턴으로 표현하여 이메일·전화번호 같은 형식을 검증하거나, 긴 문자열에서 원하는 부분을 탐색·추출하게 한다.

### 핵심 문법

| 표현              | 의미                        | 예시                              |
| --------------- | ------------------------- | ------------------------------- |
| `^`, `$`        | 문자열의 시작과 끝                | `^010-...$`는 전체 형식을 제한한다.       |
| `.`             | 줄바꿈을 제외한 임의의 한 문자         | `a.c`는 `abc`, `a1c` 등에 일치한다.    |
| `\d`            | 숫자 한 문자                   | Java 문자열에서는 `"\\d"`로 작성한다.      |
| `[abc]`         | 대괄호 안 문자 중 하나             | `[YN]`은 `Y` 또는 `N`이다.           |
| `[^abc]`        | 대괄호 안 문자를 제외한 하나          | `[^0-9]`는 숫자가 아닌 문자다.           |
| `*`, `+`, `?`   | 각각 0회 이상, 1회 이상, 0회 또는 1회 | `\d+`는 숫자가 한 개 이상이다.            |
| `{n}`, `{n,m}`  | 정확히 n회, n회 이상 m회 이하       | `\d{4}`는 숫자 네 자리다.              |
| `()`            | 패턴을 그룹으로 묶음               | 추출할 부분을 그룹으로 지정한다.              |
| <code>\|</code> | OR 조건                     | <code>cat\|dog</code>는 둘 중 하나다. |

### Java 문자열에서의 이스케이프

정규표현식에서 숫자를 뜻하는 문법은 `\d`지만, Java 문자열에서도 역슬래시가 이스케이프 문자로 사용된다. 따라서 Java 코드에서는 역슬래시를 한 번 더 작성해야 한다.

```text
정규표현식에서 원하는 패턴: \d{4}
        ↓ Java 문자열 문법 적용
Java 코드에 작성할 값: "\\d{4}"
        ↓ Pattern이 문자열을 해석
실제 정규표현식: \d{4}
```

### `matches()`와 `find()`의 차이

| 메서드         | 검사 범위                     | 적합한 상황               |
| ----------- | ------------------------- | -------------------- |
| `matches()` | 문자열 전체가 패턴과 일치하는지 검사      | 전화번호·이메일 등 전체 형식 검증  |
| `find()`    | 문자열 안에서 일치하는 부분을 차례로 탐색   | 문장 속 번호·날짜·이메일 추출    |
| `group()`   | 가장 최근에 찾은 일치 문자열 또는 그룹 반환 | `find()`로 찾은 실제 값 사용 |

### 더미 데이터 검증용 예시

아래 코드는 더미 데이터에 패턴을 적용하는 과정을 복습하기 위한 예시다. 이메일 패턴은 학습용으로 단순화한 것이며 모든 국제 이메일 형식을 완전히 검증하지는 않는다.

```java
private static final Pattern EMAIL_PATTERN = Pattern.compile(
        "^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,}$"
);

List<String> dummyEmails = List.of(
        "taein@example.com",
        "wrong-email",
        "spring@boot.dev"
);

List<String> validEmails = dummyEmails.stream()
        .map(String::trim)
        .filter(email -> EMAIL_PATTERN.matcher(email).matches())
        .toList();
```

문장 안에서 전화번호를 찾으려면 전체 일치가 아닌 `find()`를 사용한다.

```java
Pattern phonePattern = Pattern.compile("010-\\d{4}-\\d{4}");
Matcher matcher = phonePattern.matcher(
        "문의: 010-1234-5678, 예비 연락처: 010-9876-5432"
);

while (matcher.find()) {
    System.out.println(matcher.group());
}
```

반복해서 많은 데이터를 검사한다면 매번 `String.matches()`를 호출하기보다 `Pattern`을 한 번 컴파일해 재사용할 수 있다.

> 검증은 문자열 전체가 규칙에 맞는지를 보는 `matches()`, 추출은 문자열 안의 일치 구간을 찾는 `find()`로 구분한다. Java 코드에서는 정규식의 역슬래시를 이중으로 이스케이프해야 한다.

# 🔄 함께 복습한 내용

## 1. 직접 만든 구조와 Spring MVC 구성 요소 비교

| 직접 만든 구성 요소      | Spring MVC 구성 요소     | 공통 역할                      | Spring이 추가로 제공하는 범위                                                    |
| ---------------- | -------------------- | -------------------------- | ---------------------------------------------------------------------- |
| Front Controller | `DispatcherServlet`  | 요청을 한곳에서 받아 적절한 처리 흐름으로 연결 | `HandlerMapping`, `HandlerAdapter`, 예외 처리, 뷰 처리 등과 협력해 전체 요청 처리를 조정한다. |
| `BeanFactory`    | `ApplicationContext` | 필요한 객체를 생성·보관하고 조회         | Bean 생명주기, 의존성 주입, 이벤트, 환경 설정 등 애플리케이션 전반의 기능을 제공한다.                   |

직접 만든 Front Controller와 `BeanFactory`는 Spring MVC의 핵심 원리를 단순화해 확인하는 구조다. 실제 Spring에서는 한 객체가 모든 책임을 맡지 않고 여러 구성 요소가 협력한다.

> `DispatcherServlet`은 요청 처리의 지휘자이고, `ApplicationContext`는 애플리케이션 객체를 관리하는 컨테이너다.

## 2. 요청 매핑 책임과 Bean 조회 책임

```text
HTTP 요청
        ↓
DispatcherServlet
        ↓ 어떤 Handler가 처리하는지 조회
HandlerMapping
        ↓ 실행할 Controller 정보 반환
HandlerAdapter
        ↓ Controller 메서드 호출
Controller Bean
        ↑ 생성·보관·의존성 주입
ApplicationContext
```

- **요청 매핑**은 URL과 HTTP 메서드에 맞는 Handler를 찾는 책임이며 `HandlerMapping`이 담당한다.
- **Bean 관리**는 객체를 생성·보관하고 의존성을 연결하는 책임이며 `ApplicationContext`가 담당한다.
- `DispatcherServlet`은 두 책임을 직접 모두 구현하지 않고, 필요한 구성 요소에 요청한 뒤 전체 흐름을 조정한다.

## 3. Controller와 Service의 경계

| 계층         | 남겨야 할 책임                                       | 피해야 할 책임                         |
| ---------- | ---------------------------------------------- | -------------------------------- |
| Controller | HTTP 요청 값 수신, 검증 결과 처리, Service 호출, HTTP 응답 변환 | 핵심 비즈니스 규칙, 직접적인 데이터 접근, 긴 조건 분기 |
| Service    | 유스케이스 실행, 비즈니스 규칙, 여러 작업의 순서 결정, 트랜잭션 경계       | HTTP 요청·응답 객체에 종속된 처리            |

Controller는 웹 요청을 애플리케이션이 이해할 입력으로 바꾸고, Service는 실제 업무 규칙을 수행한다. 같은 기능을 HTTP가 아닌 다른 방식으로 호출해도 재사용해야 하는 로직이라면 Service에 둘 가능성이 높다.

> Controller는 요청과 응답을 번역하고, Service는 무엇을 어떤 규칙으로 처리할지를 결정한다.

## 4. Stream 연산과 `orElse()`·`orElseGet()`의 평가 시점

```text
Stream 중간 연산 등록
        ↓ 최종 연산 호출 전에는 실행되지 않음
최종 연산 호출
        ↓
요소 순회·결과 생성
```

| 구분                        | 평가 시점                            | 핵심 주의점                                |
| ------------------------- | -------------------------------- | ------------------------------------- |
| `filter()`, `map()`       | 최종 연산이 호출될 때                     | 중간 연산만 선언하면 실제 순회가 시작되지 않는다.          |
| `findFirst()`, `toList()` | 호출되는 즉시                          | 스트림을 소비하고 결과를 만든다.                    |
| `orElse(value)`           | `Optional`에 값이 있어도 인자를 먼저 평가     | 대체값 생성에 비용이나 부작용이 있으면 불필요하게 실행될 수 있다. |
| `orElseGet(supplier)`     | `Optional`이 비어 있을 때만 Supplier 실행 | 대체값을 늦게 만들고 싶을 때 적합하다.                |

```java
Post post = optionalPost.orElse(createDefaultPost());
// 값이 있어도 createDefaultPost()가 먼저 실행된다.

Post lazyPost = optionalPost.orElseGet(this::createDefaultPost);
// 값이 없을 때만 createDefaultPost()가 실행된다.
```

> Stream의 지연 처리는 최종 연산 호출 여부로 판단하고, `Optional`의 대체값은 생성 비용과 부작용을 기준으로 `orElse()`와 `orElseGet()`을 구분한다.
