# 📚 학습 내용

## 1. Front Controller로 요청의 공통 진입점 만들기

Controller마다 요청을 직접 받도록 구성하면 요청 분석, 공통 로깅, 인증 확인과 같은 진입 로직이 여러 곳에 반복될 수 있다. Front Controller는 이 문제를 줄이기 위해 모든 요청을 먼저 받는 하나의 진입점을 둔다.

### 역할과 책임

| 구성 요소            | 맡는 책임                                                  |
| ---------------- | ------------------------------------------------------ |
| Front Controller | 요청을 가장 먼저 받고 공통 처리를 수행한 뒤 실제 처리기로 위임한다.                |
| 요청 매핑            | 경로, HTTP Method 또는 명령을 기준으로 처리할 Controller와 메서드를 결정한다. |
| 개별 Controller    | 자신에게 위임된 기능의 입력을 받고 처리 흐름을 시작한다.                       |

Front Controller가 직접 게시글을 저장하거나 조회하는 것은 아니다. 어떤 요청인지 판별하고, 그 요청을 처리할 객체로 연결하는 **조정자** 역할을 한다.

### 요청 위임 흐름

```text
HTTP 요청
   ↓
Front Controller
   ↓ 공통 처리
요청 경로·HTTP Method·명령 확인
   ↓
처리할 Controller와 메서드 결정
   ↓
Controller에 요청 위임
   ↓
처리 결과를 HTTP 응답으로 변환
```

### Front Controller와 Session Facade 구분

두 패턴 모두 복잡한 내부 구조 앞에 단순한 창구를 제공한다는 공통점은 있지만, 적용 위치와 목적은 다르다.

| 비교 기준 | Front Controller        | Session Facade                    |
| ----- | ----------------------- | --------------------------------- |
| 적용 위치 | 웹 계층의 요청 진입부            | 비즈니스 계층의 경계                       |
| 주된 목적 | 요청을 공통으로 받아 알맞은 처리기로 위임 | 여러 비즈니스 객체의 기능을 하나의 단순한 인터페이스로 제공 |
| 주된 대상 | HTTP 요청과 Controller     | 여러 Service 또는 비즈니스 객체             |
| 핵심 질문 | “이 요청을 누가 처리할 것인가?”     | “여러 비즈니스 기능을 어떤 창구로 제공할 것인가?”     |

따라서 오늘의 요청 처리 구조와 직접 연결되는 패턴은 **Front Controller**다. `Session Facade`를 Front Controller의 다른 이름으로 보지는 않는다.

> Front Controller는 모든 기능을 처리하는 객체가 아니라, 공통 요청을 받아 실제 처리기로 연결하는 웹 계층의 진입점이다.

## 2. BeanFactory로 객체 생성과 조회 책임 분리하기

Front Controller가 요청을 받을 때마다 `new PostController()`를 직접 실행하면 요청 전달 코드가 구체적인 객체 생성 방식까지 알아야 한다. Controller의 생성자나 의존 객체가 바뀔 때 Front Controller도 함께 수정될 수 있으므로 두 책임을 분리해야 한다.

### `BeanFactory`가 필요한 이유

| 직접 생성할 때의 문제                  | `BeanFactory`로 분리한 결과                       |
| ----------------------------- | ------------------------------------------- |
| 요청 처리 코드가 구현 클래스와 생성자를 직접 안다. | 이름이나 타입을 통해 필요한 객체를 조회한다.                   |
| 여러 위치에서 객체가 중복 생성될 수 있다.      | 생성과 재사용 정책을 한곳에서 관리할 수 있다.                  |
| 의존 관계가 변경되면 호출부까지 수정될 수 있다.   | 객체 구성 변경을 관리 영역에 모을 수 있다.                   |
| 요청 위임과 객체 생성 책임이 섞인다.         | Front Controller는 위임, Factory는 객체 제공에 집중한다. |

### 객체 조회 흐름

```text
애플리케이션 시작
   ↓
BeanFactory가 객체를 생성하거나 등록
   ↓
클라이언트 요청 도착
   ↓
Front Controller가 처리 대상 식별
   ↓ bean 이름 또는 타입으로 요청
BeanFactory가 등록된 객체 조회
   ↓
Controller 인스턴스 반환
   ↓
Front Controller가 요청 처리 위임
```

### 개념 연결용 예제

다음 코드는 오늘 학습한 역할을 단순화해 표현한 예제다. 실제 수업 코드의 세부 구현을 그대로 재현한 것은 아니다.

```java
public final class BeanFactory {
    private final Map<String, Object> beans = new HashMap<>();

    public BeanFactory() {
        beans.put("postController", new PostController());
    }

    public <T> T getBean(String name, Class<T> requiredType) {
        Object bean = beans.get(name);

        if (bean == null) {
            throw new IllegalArgumentException("등록되지 않은 Bean: " + name);
        }

        return requiredType.cast(bean);
    }
}
```

```java
PostController controller = beanFactory.getBean(
        "postController",
        PostController.class
);
```

이 구조에서 `Map`은 객체를 보관하고, `getBean()`은 이름에 맞는 객체를 조회한다. 제네릭 타입과 `Class#cast()`를 사용하면 호출부가 원하는 타입을 명시할 수 있지만, 잘못된 타입을 요청하면 `ClassCastException`이 발생할 수 있다.

### Spring의 컨테이너와 연결

직접 만든 단순 `BeanFactory`와 Spring 컨테이너의 역할 범위는 같지 않다.

| 구분    | 단순 실습용 `BeanFactory` | Spring 컨테이너                                    |
| ----- | -------------------- | ---------------------------------------------- |
| 주된 역할 | 미리 등록한 객체를 이름으로 조회   | Bean 생성, 의존 관계 주입, 생명주기와 설정 관리                 |
| 관리 대상 | 예제에서는 주로 Controller  | Controller, Service, Repository 등 애플리케이션 객체    |
| 대표 타입 | 직접 작성한 클래스           | `BeanFactory`, 일반적으로 사용하는 `ApplicationContext` |

Spring에서 `BeanFactory`는 IoC 컨테이너의 기본 기능을 정의하는 핵심 인터페이스다. 실제 애플리케이션에서는 이 기능에 이벤트, 메시지 처리 등 부가 기능을 더한 `ApplicationContext`를 주로 사용한다.

또한 **요청에 맞는 Controller를 찾는 일**과 **그 Controller 객체를 생성·관리하는 일**은 개념적으로 다른 책임이다. 단순 실습에서는 두 과정이 가까이 보일 수 있지만, Spring MVC에서는 요청 매핑과 Bean 관리가 각각의 구성 요소로 나뉜다.

> Front Controller는 “누구에게 요청을 위임할지”를 조정하고, BeanFactory는 “그 객체를 어떻게 만들고 제공할지”를 관리한다.

## 3. Post CRUD Controller로 기능별 요청 나누기

처리할 `PostController` 인스턴스를 얻었다면 다음 단계는 요청의 목적에 맞는 CRUD 메서드를 실행하는 것이다. CRUD는 데이터를 생성하고 읽고 수정하고 삭제하는 네 가지 기본 작업을 뜻한다.

### CRUD와 요청의 대응

아래 HTTP Method와 경로는 Spring MVC에서 일반적으로 사용하는 대응 예시다. 실제 수업의 명령 이름이나 경로가 다르더라도 각 기능의 책임은 동일하다.

| 기능     | 의미     | 일반적인 요청 예시                             | Controller의 책임            |
| ------ | ------ | -------------------------------------- | ------------------------- |
| Create | 게시글 생성 | `POST /posts`                          | 입력값을 받아 생성 처리를 요청한다.      |
| Read   | 게시글 조회 | `GET /posts`, `GET /posts/{id}`        | 전체 또는 조건에 맞는 게시글을 반환한다.   |
| Update | 게시글 수정 | `PUT /posts/{id}`, `PATCH /posts/{id}` | 식별자와 변경값을 받아 수정 처리를 요청한다. |
| Delete | 게시글 삭제 | `DELETE /posts/{id}`                   | 식별자에 해당하는 게시글의 삭제를 요청한다.  |

### 전체 요청 처리 흐름

```text
게시글 HTTP 요청
   ↓
Front Controller
   ↓ 요청 매핑
Post Controller의 대상 메서드
   ├─ create()  → 게시글 생성
   ├─ findAll()→ 게시글 목록 조회
   ├─ findById()→ 게시글 단건 조회
   ├─ update()  → 게시글 수정
   └─ delete()  → 게시글 삭제
        ↓
처리 결과 반환
   ↓
Front Controller가 응답 구성
```

### Controller와 하위 계층의 책임

오늘은 Controller 구현을 중심으로 학습했지만, 실제 Spring 애플리케이션에서는 모든 로직을 Controller에 넣지 않고 계층별 책임을 나눈다.

| 계층         | 핵심 책임                                     |
| ---------- | ----------------------------------------- |
| Controller | 요청 입력을 받고 필요한 형식으로 변환한 뒤 애플리케이션 로직을 호출한다. |
| Service    | 비즈니스 규칙을 적용하고 하나의 작업 흐름을 조정한다.            |
| Repository | 데이터 저장소에 접근해 조회·저장·수정·삭제를 수행한다.           |

### 개념 연결용 예제

다음 코드는 CRUD 메서드와 반환 형태의 관계를 보여 주는 예제다. 실제 실습에서 작성한 세부 저장 로직을 재현한 코드는 아니다.

```java
public final class PostController {
    private final PostService postService;

    public PostController(PostService postService) {
        this.postService = postService;
    }

    public Post create(Post post) {
        return postService.create(post);
    }

    public List<Post> findAll() {
        return postService.findAll();
    }

    public Optional<Post> findById(Long id) {
        return postService.findById(id);
    }

    public Post update(Long id, Post post) {
        return postService.update(id, post);
    }

    public void delete(Long id) {
        postService.delete(id);
    }
}
```

Controller는 어떤 요청인지 구분해 적절한 기능을 호출하지만, 실제 비즈니스 규칙과 데이터 접근까지 모두 책임지지는 않는다.

> CRUD 메서드는 기능별 진입점을 만들고, Controller는 요청과 애플리케이션 로직 사이의 경계를 담당한다.

## 4. Stream과 Optional로 조회 결과 안전하게 표현하기

CRUD 중 Read는 조건에 맞는 데이터가 하나도 없을 수 있다. 이때 `null`을 반환하면 호출자가 매번 `null` 검사를 해야 하고, 검사를 놓치면 `NullPointerException`이 발생한다. 조회 개수에 맞는 반환 타입을 사용하면 “결과 없음”도 정상적인 상태로 표현할 수 있다.

### 다건 조회: 빈 리스트 반환

```text
게시글 컬렉션
   ↓ stream()
Stream 생성
   ↓ filter()
조건에 맞는 요소만 통과
   ↓ toList()
결과 List 생성
   ├─ 일치하는 요소 있음 → 요소가 담긴 List
   └─ 일치하는 요소 없음 → 빈 List
```

```java
public List<Post> findByTitle(String keyword) {
    return posts.stream()
            .filter(post -> post.getTitle().contains(keyword))
            .toList();
}
```

`filter()`를 통과한 요소가 없어도 `toList()`는 `null`이 아니라 빈 리스트를 반환한다. 호출자는 별도의 `null` 검사 없이 `isEmpty()`, `size()` 또는 반복문을 사용할 수 있다.

Java 16부터 `Stream#toList()`가 반환하는 리스트에는 요소를 추가하거나 삭제할 수 없다. 결과를 수정해야 한다면 변경 가능한 컬렉션으로 수집해야 한다.

```java
public List<Post> findMutableResult(String keyword) {
    return posts.stream()
            .filter(post -> post.getTitle().contains(keyword))
            .collect(Collectors.toCollection(ArrayList::new));
}
```

### 단건 조회: `Optional<Post>` 반환

단건 조회는 결과가 정확히 하나이거나 없다는 의미가 자연스럽다. `findFirst()`는 첫 번째 결과를 직접 반환하지 않고 `Optional<T>`로 감싸서 반환한다.

```java
public Optional<Post> findById(Long id) {
    return posts.stream()
            .filter(post -> post.getId().equals(id))
            .findFirst();
}
```

```text
단건 조회
   ↓ findFirst()
Optional<Post>
   ├─ 값 존재 → Post 사용
   └─ 값 없음
        ├─ 기본값이 정상적인 경우 → orElse() 또는 orElseGet()
        ├─ 동작만 분기하는 경우 → ifPresentOrElse()
        └─ 반드시 존재해야 하는 경우 → orElseThrow()
```

### `Optional`의 값 부재 처리

| 메서드                                    | 값이 없을 때              | 실행 시점과 사용 기준                                        |
| -------------------------------------- | -------------------- | --------------------------------------------------- |
| `orElse(value)`                        | 미리 전달한 값을 반환         | Optional에 값이 있어도 인수 표현식이 먼저 평가된다. 값 생성이 단순할 때 적합하다. |
| `orElseGet(supplier)`                  | `Supplier`가 만든 값을 반환 | 값이 없을 때만 `Supplier`를 실행한다. 대체 값 생성 비용이 있을 때 적합하다.   |
| `orElseThrow(supplier)`                | 지정한 예외를 발생           | 값 부재를 정상 결과로 허용할 수 없을 때 사용한다.                       |
| `ifPresentOrElse(action, emptyAction)` | 존재·부재에 맞는 동작 실행      | 값을 반환하는 대신 두 경우의 동작을 나눌 때 사용한다.                     |

```java
Post post = findById(id)
        .orElseThrow(() -> new NoSuchElementException("게시글이 없습니다: " + id));
```

```java
Post post = findById(id)
        .orElseGet(this::loadDefaultPost);
```

`loadDefaultPost()`처럼 대체 값을 만드는 과정에 비용이 있다면, 값이 없을 때만 실행되는 `orElseGet()`이 적합하다.

```java
findById(id).ifPresentOrElse(
        post -> System.out.println(post.getTitle()),
        () -> System.out.println("게시글이 없습니다.")
);
```

### 조회 개수에 따른 반환 타입 선택

| 조회 상황              | 권장 반환 형태         | “결과 없음”의 표현            |
| ------------------ | ---------------- | ---------------------- |
| 여러 건 조회            | `List<Post>`     | 빈 리스트                  |
| 한 건이 있을 수도 있는 조회   | `Optional<Post>` | `Optional.empty()`     |
| 반드시 한 건이 있어야 하는 처리 | `Post` 또는 예외 처리  | 의미 있는 예외               |
| 피해야 할 일반적인 표현      | `null`           | 호출자마다 별도의 `null` 검사 필요 |

다건 조회를 `Optional<List<Post>>`로 감싸면 `Optional.empty()`와 “비어 있는 List”라는 두 종류의 빈 상태가 생긴다. 두 상태를 구분해야 하는 특별한 요구가 없다면 다건 조회는 빈 리스트 하나로 표현하는 편이 단순하다.

> 여러 건의 부재는 **빈 리스트**, 한 건의 부재 가능성은 **Optional**로 표현하면 반환 타입만 보고도 조회 의도를 이해할 수 있다.

## 오늘 수행한 내용

- 하나의 공통 진입점이 요청을 분석하고 Controller로 위임하는 흐름 확인
- `BeanFactory`에서 Controller 인스턴스를 관리하고 조회하는 구조 작성
- 게시글의 생성·조회·수정·삭제를 담당하는 Post CRUD Controller 작성
- Stream API를 이용한 조건별 게시글 조회
- 조건을 만족하는 게시글이 없을 때 빈 리스트가 반환되는 결과 확인
- `Optional`을 이용한 값 존재·부재 분기 처리

구체적인 실습 소스가 제공되지 않았으므로 본문의 코드는 학습한 구조를 연결하기 위한 예제로 구분했다.

## 통합 실행 흐름

```text
요청 수신
   ↓
Front Controller가 요청 분석
   ↓
처리할 Post Controller 식별
   ↓
BeanFactory에서 Controller 인스턴스 조회
   ↓
CRUD 메서드 실행
   ├─ 변경 요청 → 생성·수정·삭제 결과 반환
   └─ 조회 요청 → Stream으로 조건 처리

                         └─ 단건 → Optional<Post>
                                      ↓
                              값 부재 처리
   ↓
응답 반환
```

# 🔄 함께 복습한 내용

## 1. MVC 패턴과 서버 계층 구조

| 구분       | 구성                            | 책임을 나누는 기준                        |
| -------- | ----------------------------- | --------------------------------- |
| MVC 패턴   | Model·View·Controller         | 사용자 입력, 상태, 화면 표현의 역할을 분리한다.      |
| 서버 계층 구조 | Controller·Service·Repository | 요청 처리, 비즈니스 로직, 데이터 접근의 책임을 분리한다. |

두 구조에 모두 `Controller`가 등장하지만 분류 기준이 다르다. MVC는 애플리케이션의 표현 구조를 설명하고, Controller–Service–Repository는 서버 내부에서 작업 책임을 나누는 계층 구조다.

> 같은 `Controller`라는 이름이 보여도 MVC의 세 요소와 서버 내부의 세 계층을 하나의 구조로 섞어 설명하지 않는다.

## 2. Servlet, DispatcherServlet, Controller

```text
HTTP 요청
   ↓ 서블릿 컨테이너가 전달
DispatcherServlet
   ↓ 요청과 매핑된 처리기 탐색·호출
Controller
   ↓ 애플리케이션 로직 실행 요청
응답 데이터 또는 View 정보 반환
```

- Servlet은 Java 웹 환경에서 요청과 응답을 처리하는 기본 컴포넌트다.
- `DispatcherServlet`은 Servlet이면서 Spring MVC의 Front Controller 역할을 한다.
- Controller는 매핑된 요청의 입력을 받고 Service 등을 호출한 뒤 처리 결과를 반환한다.

> `DispatcherServlet`이 모든 비즈니스 로직을 처리하는 것이 아니라, 알맞은 Controller를 찾아 호출 흐름을 조정한다.

## 3. `throw`, `throws`와 예외 종류

| 구분                  | 핵심 의미                       | 확인할 점                             |
| ------------------- | --------------------------- | --------------------------------- |
| `throw`             | 예외 객체를 현재 코드에서 직접 발생시킨다.    | 메서드 내부의 실행문이다.                    |
| `throws`            | 메서드 밖으로 전달될 수 있는 예외를 선언한다.  | 메서드 선언부에 작성한다.                    |
| Checked Exception   | 컴파일러가 처리 여부를 확인한다.          | `catch`로 처리하거나 `throws`로 전파해야 한다. |
| Unchecked Exception | `RuntimeException` 계열의 예외다. | 컴파일러가 처리나 선언을 강제하지 않는다.           |

> `throw`는 예외를 **발생**시키고, `throws`는 메서드가 예외를 **전파할 가능성**을 선언한다.

## 4. 바이트 스트림과 문자 스트림

| 구분      | 대표 추상 타입                      | 처리 단위  | 주로 사용하는 데이터               |
| ------- | ----------------------------- | ------ | ------------------------- |
| 바이트 스트림 | `InputStream`, `OutputStream` | `byte` | 이미지, 영상, 압축 파일 등 바이너리 데이터 |
| 문자 스트림  | `Reader`, `Writer`            | `char` | 문자 인코딩을 고려해야 하는 텍스트 데이터   |

```text
원본 바이트
   ↓ InputStreamReader와 문자 인코딩
문자로 해석
   ↓ Reader
텍스트 처리
```

바이트 스트림은 원본 바이트를 그대로 처리한다. 문자 스트림은 바이트와 문자 사이를 변환하므로 올바른 문자 인코딩을 지정해야 글자가 깨지지 않는다.

> 바이너리는 바이트 스트림, 텍스트는 문자 인코딩을 고려한 문자 스트림을 기준으로 선택한다.
