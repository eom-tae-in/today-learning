## 1. 서브쿼리: 다른 조회 결과를 현재 쿼리의 조건으로 사용하기

### 개념과 필요한 이유

서브쿼리(Subquery)는 하나의 SQL문 안에 포함된 다른 `SELECT`문이다. 평균 급여처럼 먼저 계산해야 하는 값이나, 특정 조건을 만족하는 복수의 키를 바깥 쿼리에서 다시 사용하고 싶을 때 조회를 단계별로 표현할 수 있다.

```text
안쪽 서브쿼리가 값 또는 행 집합을 구함
    ↓ 결과 반환
바깥쪽 메인 쿼리가 그 결과를 조건에 사용
    ↓
최종 행 집합 조회
```

이는 비상관 서브쿼리를 이해하기 위한 논리적 흐름이다. 실제 물리적 실행 순서는 DB 옵티마이저가 쿼리를 변환하거나 통합할 수 있으므로 실행 계획으로 확인해야 한다.

### 반환 결과에 따른 구분

| 구분       | 결과 형태        | 주로 사용하는 연산자                     | 핵심 주의점                               |
| -------- | ------------ | ------------------------------- | ------------------------------------ |
| 단일행 서브쿼리 | 최대 1행        | `=`, `<>`, `>`, `<`, `>=`, `<=` | 두 행 이상이 반환되면 단일행 비교에서 오류가 발생한다.      |
| 다중행 서브쿼리 | 여러 행         | `IN`, `ANY`, `ALL`, `EXISTS`    | 하나의 값과 여러 결과를 어떻게 비교할지 정해야 한다.       |
| 상관 서브쿼리  | 바깥 행과 연관된 결과 | 비교 연산자, `EXISTS` 등              | 바깥쪽 쿼리의 현재 행을 참조하므로 독립적인 완성 쿼리가 아니다. |

### 설명용 예제: 단일행 서브쿼리

안쪽 쿼리는 전체 사원의 평균 급여라는 하나의 값을 반환하고, 바깥 쿼리는 그보다 높은 급여를 필터링한다.

```sql
SELECT employee_name, salary
FROM employee
WHERE salary > (
    SELECT AVG(salary)
    FROM employee
);
```

### 설명용 예제: 상관 서브쿼리

각 사원의 부서를 기준으로 평균 급여를 계산해, 자신이 속한 부서의 평균보다 많이 받는 사원을 조회한다. `e2.department_id = e.department_id`가 안쪽 쿼리와 바깥 행을 연결한다.

```sql
SELECT e.employee_name, e.department_id, e.salary
FROM employee AS e
WHERE e.salary > (
    SELECT AVG(e2.salary)
    FROM employee AS e2
    WHERE e2.department_id = e.department_id
);
```

### 서브쿼리를 사용하는 위치

| 위치       | 역할                      | 이름·조건                                            |
| -------- | ----------------------- | ------------------------------------------------ |
| `WHERE`  | 조회 조건의 비교값을 제공한다.       | 단일행과 다중행 모두 사용 가능하다.                             |
| `HAVING` | 그룹화된 결과에 조건을 적용한다.      | 집계 결과를 다른 값과 비교할 때 유용하다.                         |
| `FROM`   | 서브쿼리 결과를 임시 테이블처럼 사용한다. | 인라인 뷰 또는 파생 테이블이라고 하며, MariaDB/MySQL에서는 별칭을 붙인다. |
| `SELECT` | 바깥 행마다 표시할 하나의 값을 계산한다. | 스칼라 서브쿼리로, 각 평가 결과가 하나의 값이어야 한다.                 |

`FROM`절의 서브쿼리로 부서별 평균 급여를 먼저 만든 뒤 400만 원 이상인 부서만 조회할 수 있다.

```sql
SELECT department_id, avg_salary
FROM (
    SELECT department_id, AVG(salary) AS avg_salary
    FROM employee
    GROUP BY department_id
) AS department_salary
WHERE avg_salary >= 4000000;
```

### 핵심 포인트

> 서브쿼리를 선택했다면 먼저 예상 반환 행 수를 확인하고, 그 결과와 호환되는 비교 연산자를 사용해야 한다.

## 2. 다중행 서브쿼리: `IN`, `ANY`, `ALL`, `EXISTS`

단일행 비교 연산자는 하나의 값만 비교할 수 있다. 서브쿼리가 여러 행을 반환하면, 값 일치·일부 조건 충족·전체 조건 충족·행 존재 중 어느 의미인지에 따라 연산자를 골라야 한다.

### 연산자 비교

| 연산자      | 참이 되는 조건               | 주로 사용하는 상황                                      |
| -------- | ---------------------- | ----------------------------------------------- |
| `IN`     | 반환된 값 중 같은 값이 하나라도 있다. | 여러 식별자·카테고리 중 하나에 포함되는지 확인한다.                   |
| `ANY`    | 여러 비교 중 하나라도 조건을 만족한다. | `>`, `<` 등과 함께 범위를 비교한다. `= ANY`는 `IN`과 같은 의미다. |
| `ALL`    | 모든 비교가 조건을 만족한다.       | 결과 전체보다 크거나 작은지 확인한다.                           |
| `EXISTS` | 서브쿼리 결과 행이 하나라도 존재한다.  | 값 자체보다 조건을 만족하는 행의 존재 여부가 중요할 때 사용한다.           |

### `ANY`와 `ALL`의 경계 판단

비교 집합이 `{300, 400, 500}`이라고 가정하면 다음과 같다. 아래 단순화는 집합이 비어 있지 않고 `NULL`이 없는 경우를 전제로 한다.

| 조건                        | 의미            | 경계값으로 단순화              |
| ------------------------- | ------------- | ---------------------- |
| `x > ANY (300, 400, 500)` | 하나보다만 크면 된다.  | `x > 300`, 즉 최솟값보다 크다. |
| `x < ANY (300, 400, 500)` | 하나보다만 작으면 된다. | `x < 500`, 즉 최댓값보다 작다. |
| `x > ALL (300, 400, 500)` | 전부보다 커야 한다.   | `x > 500`, 즉 최댓값보다 크다. |
| `x < ALL (300, 400, 500)` | 전부보다 작아야 한다.  | `x < 300`, 즉 최솟값보다 작다. |

숫자들의 최솟값과 최댓값을 박스의 경계로 보면 `ANY`는 하나만 만족하므로 범위가 넓고, `ALL`은 모두 만족해야 하므로 박스의 바깥 경계까지 넘어야 한다. 다만 박스는 암기법일 뿐이며, 최종 판단은 **`ANY = 하나라도`, `ALL = 모두`**라는 정의로 해야 한다.

### 설명용 예제

개발부와 영업부 중 하나에 속한 사원은 `IN`으로 조회한다.

```sql
SELECT employee_name, department_id
FROM employee
WHERE department_id IN (
    SELECT department_id
    FROM department
    WHERE department_name IN ('개발부', '영업부')
);
```

개발부 사원 중 누군가 한 명보다만 급여가 높으면 `> ANY`, 개발부의 모든 사원보다 높으면 `> ALL`이다.

```sql
SELECT employee_name, salary
FROM employee
WHERE salary > ANY (
    SELECT salary
    FROM employee
    WHERE department_id = 10
);

SELECT employee_name, salary
FROM employee
WHERE salary > ALL (
    SELECT salary
    FROM employee
    WHERE department_id = 10
);
```

### `NOT IN`과 `NULL` 주의

SQL에서 `NULL`은 알 수 없는 값이므로 `NULL`과의 비교는 `TRUE`나 `FALSE`가 아닌 `UNKNOWN`이 된다. `NOT IN` 목록이나 서브쿼리 결과에 `NULL`이 포함되면 조건 전체가 예상과 다르게 평가될 수 있다. 따라서 비교 대상에서 `NULL`을 제거해야 한다.

```sql
SELECT employee_name
FROM employee
WHERE department_id NOT IN (
    SELECT department_id
    FROM excluded_department
    WHERE department_id IS NOT NULL
);
```

### 핵심 포인트

> `ANY`와 `ALL`은 박스의 안쪽·바깥쪽을 외우기 전에, 각각 “하나라도”와 “모두”라는 논리를 모든 비교값에 적용해 판단한다.

## 3. Top-N Query와 순위 분석

다중행 조회로 원하는 대상을 찾았다면, 다음으로는 정렬된 결과 중 가장 높거나 낮은 일부만 선택할 수 있다. Top-N Query는 이를 위한 SQL 작성 방식이고, Top-N 분석은 상위·하위·그룹별 순위 데이터를 해석하는 목적까지 포함한다.

### 전체 결과의 Top-N

MariaDB/MySQL에서는 정렬 후 `LIMIT`로 필요한 개수만 가져온다.

```sql
SELECT employee_name, salary
FROM employee
ORDER BY salary DESC
LIMIT 3;
```

```text
salary 내림차순 정렬
    ↓
결과의 첫 3행 선택
    ↓
급여 상위 3명 반환
```

하위 3명은 `ORDER BY salary ASC LIMIT 3`으로 조회한다. `LIMIT 3, 3`은 0부터 세는 인덱스 3, 즉 정렬 결과의 네 번째 행부터 3개를 의미한다.

```sql
SELECT employee_name, salary
FROM employee
ORDER BY salary DESC
LIMIT 3, 3;
```

`LIMIT`만 사용하고 `ORDER BY`를 생략하면 어떤 행이 상위인지를 정의할 수 없다. 또한 정렬 값이 같을 때 항상 같은 행 순서가 필요하면 PK처럼 유일한 2차 정렬 기준을 추가한다.

```sql
ORDER BY salary DESC, employee_id ASC
```

### 순위 함수의 차이

단순히 N개만 잘라내는 것이 아니라 각 행의 순위나 그룹별 Top-N이 필요하면 윈도우 함수를 사용한다. 점수가 `100, 90, 90, 80`일 때의 차이는 다음과 같다.

| 함수             | 순위 결과        | 동점 처리                          |
| -------------- | ------------ | ------------------------------ |
| `ROW_NUMBER()` | `1, 2, 3, 4` | 동점이어도 서로 다른 번호를 부여한다.          |
| `RANK()`       | `1, 2, 2, 4` | 동점에 같은 순위를 주고 다음 순위를 건너뛴다.     |
| `DENSE_RANK()` | `1, 2, 2, 3` | 동점에 같은 순위를 주고 다음 순위를 이어서 부여한다. |

### 설명용 예제: 부서별 급여 상위 2명

`PARTITION BY department_id`는 부서별로 순위 계산 범위를 나누고, 각 범위 안에서 급여 내림차순으로 번호를 매긴다. 순위는 윈도우 함수가 계산된 후에 필터링해야 하므로 인라인 뷰로 한 번 감싼다.

```sql
SELECT department_id, employee_name, salary
FROM (
    SELECT department_id,
           employee_name,
           salary,
           ROW_NUMBER() OVER (
               PARTITION BY department_id
               ORDER BY salary DESC
           ) AS salary_rank
    FROM employee
) AS ranked_employee
WHERE salary_rank <= 2;
```

### 핵심 포인트

> Top-N의 출발점은 N이 아니라 순위를 결정할 `ORDER BY` 기준이다. 전체 N개는 `LIMIT`, 그룹별 순위는 윈도우 함수를 우선 검토한다.

## 4. Driving Table과 Driven Table: 조인의 탐색 기준 이해하기

여러 테이블을 조인할 때는 모든 행을 같은 비용으로 읽는 것이 아니다. 특히 Nested Loop Join은 한쪽에서 기준 행을 가져온 뒤 다른 테이블을 반복 탐색하므로, 어느 테이블이 기준이 되는지와 반복 탐색을 얼마나 빠르게 할 수 있는지가 중요하다.

### 역할 비교

| 구분            | 다른 이름       | 역할                                       |
| ------------- | ----------- | ---------------------------------------- |
| Driving Table | Outer Table | 조인을 시작할 때 먼저 기준 행을 만든다.                  |
| Driven Table  | Inner Table | Driving Table의 각 기준 행에 대해 조인 키로 반복 탐색된다. |

```text
Driving Table에 필터 조건 적용
    ↓
조건을 만족한 기준 행과 조인 키 확보
    ↓ 기준 행마다 반복
Driven Table에서 조인 키가 일치하는 행 탐색
    ↓
두 테이블의 행을 결합해 반환
```

### 설명용 예제

아래 쿼리에서 `department_name = '개발부'`가 소수의 `department` 행을 먼저 만든다면, `department`가 Driving Table이 되고 `employee`가 Driven Table이 되는 실행 방식을 생각할 수 있다.

```sql
SELECT e.employee_name, e.salary
FROM department AS d
JOIN employee AS e
  ON e.department_id = d.department_id
WHERE d.department_name = '개발부';
```

Driven Table인 `employee`를 조인 키로 반복 탐색한다면 `employee.department_id`의 인덱스가 탐색 비용을 줄일 수 있다. 다만 InnoDB는 외래 키 생성 시 필요한 인덱스가 없으면 지원 인덱스를 자동으로 만들 수 있으므로, 실제로는 기존 인덱스를 먼저 확인해 중복 생성을 피한다.

```sql
CREATE INDEX idx_employee_department_id
ON employee (department_id);
```

### 실행 순서를 단정하지 않기

SQL의 `FROM`절에 먼저 쓴 테이블이 항상 Driving Table이 되는 것은 아니다. DB 옵티마이저는 통계 정보, 조건 선택도, 인덱스, 예상 비용을 바탕으로 조인 순서와 방식을 선택한다. 따라서 실제 기준·탐색 테이블은 `EXPLAIN`을 포함한 실행 계획으로 확인해야 한다.

일반적인 설계 방향은 다음과 같다.

- Driving Table에 조건을 적용한 후의 행 수가 작을수록 유리한 경우가 많다.
- Driven Table의 조인 키에 적절한 인덱스가 있으면 반복 탐색 비용을 줄일 수 있다.
- 위 원칙은 절대 규칙이 아니며, 최종 판단은 실제 실행 계획과 데이터 분포를 기준으로 한다.

### 핵심 포인트

> Driving/Driven은 SQL 작성 순서를 암기하는 개념이 아니라, 기준 행 수와 반복 탐색 비용을 이해하기 위한 실행 관점이다.

## 5. DDL과 제약조건: 구조와 데이터 무결성 정의하기

질의를 올바르게 작성하려면 그 대상인 테이블의 구조와 관계가 먼저 정의되어야 한다. DDL(Data Definition Language)은 테이블·뷰·인덱스·시퀀스 같은 데이터베이스 객체의 구조를 생성·변경·삭제하는 SQL이다.

### DDL 명령어와 데이터 조작의 구분

| 구분                       | 역할                         | 대표 문법                          |
| ------------------------ | -------------------------- | ------------------------------ |
| `CREATE`                 | 테이블·인덱스 등의 객체를 생성한다.       | `CREATE TABLE`, `CREATE INDEX` |
| `ALTER`                  | 존재하는 객체의 구조를 변경한다.         | `ADD`, `MODIFY`, `DROP COLUMN` |
| `DROP`                   | 객체의 구조와 저장된 데이터를 함께 삭제한다.  | `DROP TABLE`                   |
| `INSERT INTO ... VALUES` | 이미 생성된 테이블에 행을 추가하는 DML이다. | `INSERT INTO employee ...`     |
| `SELECT ... FROM`        | 저장된 데이터를 조회한다.             | `SELECT * FROM employee`       |

### 설명용 통합 예제: 관계와 규칙을 포함한 테이블

테이블을 다시 만들 때는 외래 키로 부모를 참조하는 자식 테이블 `employee`를 먼저 삭제한다. `IF EXISTS`는 대상이 없을 때의 오류를 방지하지만, 존재하는 테이블의 데이터와 구조가 삭제되는 위험은 그대로이다.

```sql
DROP TABLE IF EXISTS employee;
DROP TABLE IF EXISTS department;

CREATE TABLE department (
    department_id   BIGINT,
    department_name VARCHAR(50) NOT NULL,

    CONSTRAINT pk_department
        PRIMARY KEY (department_id),

    CONSTRAINT uq_department_name
        UNIQUE (department_name)
);

CREATE TABLE employee (
    employee_id   BIGINT,
    employee_name VARCHAR(50) NOT NULL,
    salary        DECIMAL(12, 2) NOT NULL,
    job_role      VARCHAR(30) DEFAULT '사원',
    department_id BIGINT NOT NULL,
    created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT pk_employee
        PRIMARY KEY (employee_id),

    CONSTRAINT chk_employee_salary
        CHECK (salary >= 0),

    CONSTRAINT fk_employee_department
        FOREIGN KEY (department_id)
        REFERENCES department(department_id)
);
```

`VARCHAR(n)`은 길이가 달라지는 문자열을, `DATE`는 날짜를, `DATETIME`은 날짜와 시간을 저장할 때 사용한다. `CURRENT_TIMESTAMP`는 현재 날짜와 시간을 생성 시각의 기본값으로 주로 사용하며, `SYSDATE()`도 현재 날짜와 시간을 반환하는 함수다.

### 제약조건의 역할

제약조건(Constraint)은 잘못된 값, 중복 값, 존재하지 않는 참조값이 저장되는 것을 DB 자체에서 막아 데이터 무결성을 지킨다.

| 제약조건·속성       | 보장하는 규칙                               | 핵심 주의점                                                              |
| ------------- | ------------------------------------- | ------------------------------------------------------------------- |
| `PRIMARY KEY` | 각 행을 유일하게 식별하며 중복과 `NULL`을 허용하지 않는다.  | 테이블당 하나만 만들 수 있지만 여러 컬럼을 묶은 복합 PK는 가능하다.                            |
| `FOREIGN KEY` | 다른 테이블의 PK 또는 고유 키를 참조해 참조 무결성을 보장한다. | 부모에 없는 키를 자식에 저장할 수 없다.                                             |
| `NOT NULL`    | 해당 컬럼의 `NULL` 저장을 금지한다.               | 반드시 값이 필요한 컬럼에 사용하며 컬럼 레벨에 작성한다.                                    |
| `UNIQUE`      | `NULL`이 아닌 값의 중복을 금지한다.               | MariaDB/MySQL에서는 일반적으로 여러 `NULL`을 허용하므로 필수 고유값이면 `NOT NULL`을 함께 쓴다. |
| `CHECK`       | 입력값이 지정한 조건을 만족하는지 검사한다.              | `CHECK (salary >= 0)`만으로는 `NULL`을 금지하지 않으므로 필수값이면 `NOT NULL`을 추가한다. |
| `DEFAULT`     | `INSERT`에서 컬럼을 생략했을 때 사용할 기본값을 정의한다.  | 명시적인 `NULL`을 무조건 대체하는 기능은 아니며, 유효성을 검사하는 제약조건과 역할이 다르다.             |

### 컬럼 레벨과 테이블 레벨

| 구분     | 작성 위치                     | 적합한 상황                                                                             |
| ------ | ------------------------- | ---------------------------------------------------------------------------------- |
| 컬럼 레벨  | 컬럼 정의 뒤에 바로 작성한다.         | 하나의 컬럼에 적용되는 간단한 `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `CHECK`, `DEFAULT` 표현에 적합하다. |
| 테이블 레벨 | 모든 컬럼 정의 뒤에 별도 항목으로 작성한다. | 제약조건 이름 지정, 복합 키, 외래 키를 명확히 표현할 때 유용하다.                                            |

`NOT NULL`과 `DEFAULT`는 해당 컬럼 정의에 작성한다. 제약조건에 `pk_employee`, `fk_employee_department`처럼 이름을 붙이면 오류나 구조 변경 시 대상을 식별하기 쉬워진다.

복합 기본 키는 테이블 레벨에서 여러 컬럼을 함께 지정한다.

```sql
CREATE TABLE enrollment (
    student_id BIGINT NOT NULL,
    course_id  BIGINT NOT NULL,

    CONSTRAINT pk_enrollment
        PRIMARY KEY (student_id, course_id)
);
```

### 외래 키와 부모 행 삭제

| 옵션                   | 부모 행을 삭제했을 때의 동작        | 조건                                   |
| -------------------- | ----------------------- | ------------------------------------ |
| `ON DELETE CASCADE`  | 연결된 자식 행도 함께 삭제한다.      | 자식 데이터가 부모의 생명주기에 완전히 종속되는지 판단해야 한다. |
| `ON DELETE SET NULL` | 자식의 외래 키를 `NULL`로 변경한다. | 해당 외래 키 컬럼이 `NULL`을 허용해야 한다.         |

### `ALTER TABLE`로 구조 변경하기

이미 생성된 테이블에도 컬럼이나 제약조건을 추가·변경·삭제할 수 있다. 아래는 MariaDB/MySQL 기준의 설명용 문법이며, DBMS마다 세부 문법이 다를 수 있다.

```sql
ALTER TABLE employee
ADD COLUMN email VARCHAR(100);

ALTER TABLE employee
MODIFY COLUMN employee_name VARCHAR(100) NOT NULL;

ALTER TABLE employee
ADD CONSTRAINT uq_employee_email UNIQUE (email);

ALTER TABLE employee
DROP COLUMN email;
```

### DDL 실행 전 주의할 점

- MariaDB/MySQL의 대부분 DDL은 암시적 커밋을 발생시킬 수 있으므로 실행 전에 대상과 영향을 확인한다.
- `DROP TABLE`은 `DELETE`처럼 행만 지우는 명령이 아니라 테이블 구조와 데이터를 모두 삭제한다.
- 외래 키가 있는 경우 부모·자식 관계와 삭제 순서를 확인한다.
- 제약조건은 애플리케이션 검증을 대체하기 위한 것이 아니라, 어떤 경로로 데이터가 들어와도 DB가 최종 무결성을 보장하기 위한 규칙이다.

### 핵심 포인트

> DDL은 데이터를 담는 구조를 정의하고, 제약조건은 그 구조에 저장될 수 있는 값의 규칙을 강제한다.

# 🧠 오늘 이해한 핵심

- 서브쿼리에서 가장 먼저 확인할 것은 문법이 아니라 **안쪽 쿼리가 몇 행을 반환하는지**이며, 이 결과가 `=`, `IN`, `ANY`, `ALL` 등의 선택을 결정한다.
- `ANY`와 `ALL`의 차이는 최솟값·최댓값 암기법보다 **하나라도 만족하는지, 모두 만족하는지**로 판단해야 대소 비교의 방향을 실수하지 않는다.
- Top-N과 조인 성능은 모두 데이터의 순서와 탐색 기준에 의존한다. Top-N은 `ORDER BY`, 조인은 조건 적용 후의 행 수·인덱스·실행 계획을 확인해야 한다.
- DDL과 제약조건은 단순히 테이블을 만드는 문법이 아니라, PK로 행을 식별하고 FK로 관계를 연결하며 나머지 규칙으로 잘못된 데이터를 차단하는 무결성 설계다.
