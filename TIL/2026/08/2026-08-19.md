## 1. Servlet·JSP에서 Spring MVC까지

### Java 웹 컴포넌트의 역할

Servlet과 JSP는 모두 Java 기반 웹 애플리케이션을 구성하는 기술이지만 담당 역할이 다르다.


| 구분      | 주요 역할             | 중심 내용               |
| ------- | ----------------- | ------------------- |
| Servlet | HTTP 요청 수신과 응답 제어 | Java 코드, 요청 처리 로직   |
| JSP     | 동적인 화면 생성         | HTML 안에서 서버 데이터를 표현 |

Servlet만으로 화면까지 만들면 Java 코드 안에 HTML이 섞이고, JSP에 처리 로직까지 넣으면 화면과 비즈니스 로직이 뒤섞인다. 이를 분리하기 위해 요청 처리와 화면 표현의 책임을 나누는 MVC 패턴을 사용한다.

```text
Client 요청
    ↓
Servlet이 요청 처리
    ↓
Model에 결과 저장
    ↓
JSP가 화면 생성
    ↓
Client 응답
```

### Spring MVC와 DispatcherServlet

Spring MVC에서는 `DispatcherServlet`이 모든 요청을 먼저 받는 **Front Controller** 역할을 한다. 요청마다 공통 처리를 반복하는 대신, 하나의 진입점이 적절한 Controller를 찾아 처리를 위임한다.

```text
HTTP 요청
    ↓
DispatcherServlet
    ↓ 요청을 처리할 Controller 탐색
Controller
    ↓ 처리 결과 반환
DispatcherServlet
    ↓
View 렌더링 또는 응답 데이터 변환
    ↓
HTTP 응답
```

> Servlet은 Java 웹 요청을 처리하는 기반 기술이고, `DispatcherServlet`은 그 Servlet을 이용해 Spring MVC의 공통 요청 흐름을 관리한다.

## 2. MVC와 계층형 아키텍처의 연결

### 서로 다른 분리 기준

MVC와 `Controller–Service–Repository` 구조는 같은 개념이 아니다.


| 구분       | 분리 기준         | 주요 구성                           |
| -------- | ------------- | ------------------------------- |
| MVC 패턴   | 사용자 요청과 화면 표현 | Model, View, Controller         |
| 계층형 아키텍처 | 애플리케이션 내부 책임  | Controller, Service, Repository |

- `Controller`는 HTTP 요청을 받고 입력을 해석한 뒤 적절한 Service를 호출한다.
- `Service`는 비즈니스 규칙과 작업의 흐름을 담당한다.
- `Repository`는 데이터베이스 접근을 담당한다.

### React에서 데이터베이스까지의 요청·응답 흐름

React가 화면을 담당하는 구조에서는 서버가 JSP 같은 View를 반환하기보다 주로 JSON 데이터를 응답한다. 그래도 서버 내부에서는 Spring MVC의 요청 처리 구조와 계층 분리가 그대로 사용된다.

```text
React
  ↓ HTTP 요청
DispatcherServlet
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Database
  ↓ 조회·저장 결과
Repository → Service → Controller
  ↓ JSON 응답
React 화면 갱신
```

> MVC는 요청과 표현을 분리하는 패턴이고, 계층형 아키텍처는 서버 내부의 책임을 나누는 구조다.

## 3. Java 예외 처리와 Spring 전역 예외 처리

### 예외 처리 문법


| 구분        | 역할                                   |
| --------- | ------------------------------------ |
| `try`     | 예외가 발생할 수 있는 코드를 실행한다.               |
| `catch`   | 발생한 예외를 받아 처리한다.                     |
| `finally` | 예외 발생 여부와 관계없이 마무리 작업을 수행한다.         |
| `throw`   | 코드에서 예외 객체를 직접 발생시킨다.                |
| `throws`  | 메서드가 처리하지 않은 예외를 호출한 쪽으로 전달한다고 선언한다. |

```java
public User findUser(long id) {
    return userRepository.findById(id)
            .orElseThrow(() -> new IllegalArgumentException("사용자를 찾을 수 없습니다."));
}
```

위 코드는 설명용 예제로, 조회 결과가 없을 때 `throw`가 포함된 `orElseThrow`를 통해 예외를 발생시킨다.

### Checked Exception과 Unchecked Exception

| 구분                  | 기준                                             | 처리 방식                 |
| ------------------- | ---------------------------------------------- | --------------------- |
| Checked Exception   | `Exception`을 상속하지만 `RuntimeException`은 상속하지 않음 | 컴파일 시점에 처리 또는 전파가 요구됨 |
| Unchecked Exception | `RuntimeException` 상속                          | 컴파일러가 처리나 선언을 강제하지 않음 |

### Spring에서 HTTP 오류 응답으로 변환되는 흐름

Controller마다 같은 `try-catch`를 반복하면 예외 처리 코드가 분산된다. Spring에서는 `@RestControllerAdvice`와 `@ExceptionHandler`를 사용해 여러 Controller의 예외를 한곳에서 처리할 수 있다.

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<String> handleIllegalArgument(
            IllegalArgumentException exception
    ) {
        return ResponseEntity
                .badRequest()
                .body(exception.getMessage());
    }
}
```

```text
요청 처리 중 예외 발생
        ↓
호출 스택을 따라 예외 전파
        ↓
전역 예외 처리기가 예외 포착
        ↓
예외에 맞는 HTTP 상태와 응답 본문 생성
        ↓
Client에 오류 응답 반환
```

> Java 예외 처리는 실패를 처리하고 전파하는 기반이며, Spring 전역 예외 처리는 그 예외를 일관된 HTTP 응답으로 바꾸는 계층이다.

## 4. 웹 서버를 이해하기 위한 Java 기반 개념

### 바이트 스트림과 문자 스트림

| 구분        | 대표 추상 클래스                      | 처리 대상                |
| --------- | ------------------------------ | -------------------- |
| 바이트 입력·출력 | `InputStream` / `OutputStream` | 이미지, 영상, 일반 바이너리 데이터 |
| 문자 입력·출력  | `Reader` / `Writer`            | 문자 데이터               |

`Reader`와 `Writer`는 고정된 2바이트 단위 스트림이 아니라 **문자 단위 스트림**이다. 실제 문자 인코딩에서는 문자마다 필요한 바이트 수가 달라질 수 있다.

`Scanner`는 바이트·문자 스트림 자체의 종류라기보다, 입력 데이터를 토큰이나 기본 타입으로 편리하게 읽도록 돕는 고수준 도구다.

```java
try (BufferedReader reader = new BufferedReader(
        new InputStreamReader(System.in)
)) {
    String input = reader.readLine();
    System.out.println(input);
}
```

위 코드는 바이트 기반 표준 입력을 `InputStreamReader`로 문자 스트림에 연결한 설명용 예제다.

### 웹 서버의 스레드 기반 요청 처리

웹 서버는 여러 요청을 동시에 처리하기 위해 스레드를 사용한다. 일반적인 Servlet 기반 서버에서는 요청이 들어오면 준비된 스레드가 요청 하나를 맡아 애플리케이션 코드를 실행한다.

```text
여러 HTTP 요청 도착
        ↓
서버의 스레드 풀
        ↓ 각 요청에 작업 스레드 할당
Servlet · Spring MVC 코드 실행
        ↓
응답 반환
        ↓
스레드를 풀에 반납
```

스레드를 요청마다 무제한 생성하면 생성 비용과 메모리 사용량이 커질 수 있으므로, 서버는 보통 일정 수의 스레드를 미리 관리하는 스레드 풀을 사용한다.

### DI와 DL

| 구분  | 의미                   | 핵심                          |
| --- | -------------------- | --------------------------- |
| DI  | Dependency Injection | 필요한 의존 객체를 외부에서 주입받는다.      |
| DL  | Dependency Lookup    | 필요한 객체를 사용자가 컨테이너에서 직접 찾는다. |

Spring에서는 컨테이너가 객체를 생성하고 관계를 구성한 뒤 필요한 위치에 주입하는 DI 방식을 주로 사용한다. 객체가 의존 대상을 직접 생성하거나 찾는 책임을 줄일 수 있다.

### Facade와 Front Controller

두 패턴 모두 복잡한 내부 구조 앞에 하나의 진입점을 둔다는 공통점이 있지만 목적은 다르다.

| 패턴               | 목적                           | Spring MVC에서의 연결                            |
| ---------------- | ---------------------------- | ------------------------------------------- |
| Facade           | 여러 객체와 서브시스템의 복잡한 사용 절차를 단순화 | Service가 여러 작업을 묶어 단순한 기능을 제공하는 형태에서 볼 수 있음 |
| Front Controller | 웹 요청의 공통 진입점을 하나로 통합         | `DispatcherServlet`                         |

> Facade는 복잡한 기능 사용을 단순화하고, Front Controller는 여러 웹 요청의 진입과 공통 처리를 통합한다.
