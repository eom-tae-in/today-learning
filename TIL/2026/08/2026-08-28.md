## 1. 테이블 제약조건과 참조 무결성

애플리케이션에서 값을 검사하더라도 다른 프로그램이나 SQL 도구가 DB에 직접 접근할 수 있다. 따라서 데이터가 최종적으로 저장되는 DB에서도 잘못된 값을 막아야 한다.

제약조건은 테이블에 저장할 수 있는 데이터의 규칙을 DB가 직접 강제하는 장치다.

### 주요 제약조건

|제약조건|역할|대표적인 적용 대상|
|---|---|---|
|`PRIMARY KEY`|각 행을 유일하게 식별하고 `NULL`과 중복을 막는다.|회원 ID, 상품 ID|
|`FOREIGN KEY`|부모 테이블에 존재하는 값만 참조하도록 제한한다.|상품의 카테고리 ID|
|`NOT NULL`|반드시 값이 존재하도록 제한한다.|상품명, 가격|
|`UNIQUE`|컬럼 또는 컬럼 조합의 중복을 막는다.|이메일, 상품 코드|
|`CHECK`|저장할 값이 지정한 조건을 만족하는지 검사한다.|가격 0 이상, 수량 1 이상|
|`DEFAULT`|값을 생략했을 때 사용할 기본값을 지정한다.|상태, 생성 시각|

`DEFAULT`는 다른 제약조건처럼 잘못된 값을 거부하기보다, 값이 생략됐을 때 대신 사용할 값을 제공하는 속성에 가깝다.

### 컬럼 수준과 테이블 수준 제약조건

하나의 컬럼에만 적용하는 간단한 제약조건은 컬럼 선언과 함께 작성할 수 있다.

```sql
CREATE TABLE member (
    member_id BIGINT PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE
);
```

제약조건의 이름을 지정하거나 여러 컬럼을 묶어야 한다면 테이블 수준으로 선언한다.

```sql
CREATE TABLE course_registration (
    student_id BIGINT NOT NULL,
    course_id BIGINT NOT NULL,
    registered_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT pk_course_registration
        PRIMARY KEY (student_id, course_id)
);
```

테이블 수준 선언은 제약조건의 의미와 이름이 명확하고, 이후 `ALTER TABLE`로 관리하기도 쉽다.

### 부모 테이블과 자식 테이블

외래 키 관계에서는 참조되는 테이블이 부모이고, 외래 키를 가진 테이블이 자식이다.

```text
category.category_id
        부모 PK
           ↑ 참조
product.category_id
        자식 FK
```

자식 테이블에 `category_id = 1`을 저장하려면 부모 테이블에 `category_id = 1`인 행이 먼저 존재해야 한다.

### 설명용 테이블 예제

아래 SQL은 제약조건과 외래 키 동작을 연결해서 확인하기 위한 설명용 예제다.

```sql
CREATE TABLE category (
    category_id BIGINT NOT NULL AUTO_INCREMENT,
    category_name VARCHAR(50) NOT NULL,

    CONSTRAINT pk_category
        PRIMARY KEY (category_id),

    CONSTRAINT uq_category_name
        UNIQUE (category_name)
);

CREATE TABLE product (
    product_id BIGINT NOT NULL AUTO_INCREMENT,
    category_id BIGINT NOT NULL,
    sku VARCHAR(30) NOT NULL,
    product_name VARCHAR(100) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'SALE',

    CONSTRAINT pk_product
        PRIMARY KEY (product_id),

    CONSTRAINT uq_product_sku
        UNIQUE (sku),

    CONSTRAINT chk_product_price
        CHECK (price >= 0),

    CONSTRAINT fk_product_category
        FOREIGN KEY (category_id)
        REFERENCES category(category_id)
        ON DELETE RESTRICT
);
```

### 제약조건에 따른 저장 흐름

```text
INSERT 또는 UPDATE 요청
    ↓
NOT NULL·CHECK·UNIQUE 검사
    ↓
외래 키 값에 해당하는 부모 행 확인
    ↓
모든 조건 만족
    ↓
데이터 저장
```

하나라도 만족하지 못하면 DB는 데이터 저장을 거부한다.

### 설명용 제약조건 검증 예제

```sql
-- 정상 데이터
INSERT INTO category (category_name)
VALUES ('신선식품');

INSERT INTO product (
    category_id,
    sku,
    product_name,
    price
) VALUES (
    1,
    'APL-001',
    '사과 1kg',
    5900
);

-- UNIQUE 위반: 같은 SKU가 이미 존재
INSERT INTO product (
    category_id,
    sku,
    product_name,
    price
) VALUES (
    1,
    'APL-001',
    '다른 사과 상품',
    6900
);

-- CHECK 위반: 가격이 음수
INSERT INTO product (
    category_id,
    sku,
    product_name,
    price
) VALUES (
    1,
    'BAD-PRICE',
    '잘못된 가격 상품',
    -100
);

-- FOREIGN KEY 위반: 999번 카테고리가 존재하지 않음
INSERT INTO product (
    category_id,
    sku,
    product_name,
    price
) VALUES (
    999,
    'BAD-FK',
    '부모 없는 상품',
    1000
);
```

> 애플리케이션 검증은 사용자에게 빠른 피드백을 제공하고, DB 제약조건은 잘못된 데이터 저장을 막는 마지막 방어선이 된다.

## 2. CASCADE와 RESTRICT

외래 키를 선언하면 부모 데이터가 삭제되거나 참조 키가 변경될 때 자식 데이터를 어떻게 처리할지 정해야 한다.

### 동작 비교

|참조 동작|부모 삭제 시 결과|적합한 상황|
|---|---|---|
|`CASCADE`|관련 자식 데이터도 자동으로 삭제한다.|부모 없이는 의미가 없는 종속 데이터|
|`RESTRICT`|자식 데이터가 있으면 부모 삭제를 거부한다.|자식 데이터를 보존하거나 먼저 직접 처리해야 하는 경우|

### RESTRICT 동작

상품이 카테고리를 참조하고 있고 외래 키에 `ON DELETE RESTRICT`가 적용되어 있다고 가정한다.

```text
카테고리 삭제 요청
    ↓
해당 카테고리를 참조하는 상품 조회
    ↓
참조 상품 존재
    ↓
카테고리 삭제 거부
```

```sql
DELETE FROM category
WHERE category_id = 1;
```

`category_id = 1`을 참조하는 상품이 존재하면 부모 카테고리는 삭제되지 않는다.

`RESTRICT`는 다음과 같은 상황에 적합하다.

- 상품이 남아 있는 카테고리를 실수로 삭제하면 안 되는 경우
- 주문 이력이 있는 회원이나 상품의 삭제를 막아야 하는 경우
- 자식 데이터를 어떤 방식으로 처리할지 명시적으로 결정해야 하는 경우

### CASCADE 동작

상품 이미지가 특정 상품에 완전히 종속된 데이터라고 가정한다.

```sql
CREATE TABLE product_image (
    image_id BIGINT NOT NULL AUTO_INCREMENT,
    product_id BIGINT NOT NULL,
    image_url VARCHAR(500) NOT NULL,

    CONSTRAINT pk_product_image
        PRIMARY KEY (image_id),

    CONSTRAINT fk_product_image_product
        FOREIGN KEY (product_id)
        REFERENCES product(product_id)
        ON DELETE CASCADE
);
```

```text
상품 삭제 요청
    ↓
상품을 참조하는 상품 이미지 확인
    ↓
부모 상품 삭제
    ↓
관련 상품 이미지 자동 삭제
```

```sql
DELETE FROM product
WHERE product_id = 1;
```

`product_id = 1`과 연결된 `product_image` 행도 함께 삭제된다.

### CASCADE 사용 시 주의점

`CASCADE`는 편리하지만 부모 행 하나를 삭제했을 때 예상보다 많은 자식 행이 사라질 수 있다.

특히 다음 데이터에는 신중하게 적용해야 한다.

- 주문 및 결제 이력
- 감사 로그
- 법적 보존 의무가 있는 기록
- 여러 단계의 테이블이 연속으로 연결된 구조

부모가 삭제돼도 기록을 남겨야 한다면 물리 삭제보다 상태값이나 삭제 시각을 이용한 논리 삭제를 고려할 수 있다.

> `CASCADE`는 자식을 자동으로 처리하고, `RESTRICT`는 자식이 있을 때 부모 작업을 차단한다.

## 3. DEFAULT와 날짜 기본값

`DEFAULT`는 `INSERT`에서 특정 컬럼을 생략했을 때 DB가 대신 넣을 값을 정의한다.

### DEFAULT 적용 흐름

```text
INSERT 실행
    ↓
특정 컬럼의 값이 생략됨
    ↓
DEFAULT 선언 여부 확인
    ↓
DEFAULT 값 저장
```

```sql
CREATE TABLE sample_default (
    sample_id BIGINT NOT NULL AUTO_INCREMENT,
    status VARCHAR(20) NOT NULL DEFAULT 'READY',
    quantity INT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT pk_sample_default
        PRIMARY KEY (sample_id)
);
```

```sql
INSERT INTO sample_default (sample_id)
VALUES (NULL);
```

저장되는 값은 다음과 같다.

|컬럼|저장되는 값|
|---|---|
|`sample_id`|자동 생성된 번호|
|`status`|`'READY'`|
|`quantity`|`0`|
|`created_at`|`INSERT`가 실행된 시각|

### DEFAULT와 NULL의 차이

`DEFAULT`가 있다고 해서 명시적으로 전달한 `NULL`이 항상 기본값으로 바뀌는 것은 아니다.

```sql
-- status 컬럼을 생략했으므로 DEFAULT 사용
INSERT INTO sample_default (quantity)
VALUES (10);

-- DEFAULT 키워드를 명시했으므로 DEFAULT 사용
INSERT INTO sample_default (status, quantity)
VALUES (DEFAULT, 10);

-- NOT NULL 컬럼에 NULL을 직접 전달
INSERT INTO sample_default (status, quantity)
VALUES (NULL, 10);
```

마지막 SQL은 정상적인 엄격 모드에서 `NOT NULL` 위반 오류가 발생한다.

### 동적 날짜와 고정 날짜

날짜 기본값은 값이 변한다는 이유만으로 위험한 것이 아니다. 해당 컬럼의 업무상 의미와 맞는지가 판단 기준이다.

|컬럼의 의미|적합한 기본값|이유|
|---|---|---|
|행 생성 시각|`CURRENT_TIMESTAMP` 또는 `SYSDATE`|행마다 생성된 실제 시각이 달라야 한다.|
|최종 수정 시각|현재 시각 기반 갱신 값|수정 시점마다 값이 바뀌어야 한다.|
|행사 기준일|고정 날짜 또는 명시적 입력|등록 날짜와 무관하게 정해진 날짜를 유지해야 한다.|
|정책 적용일|고정 날짜 또는 명시적 입력|실행하는 날마다 값이 달라지면 의미가 변한다.|

```sql
CREATE TABLE event (
    event_id BIGINT NOT NULL AUTO_INCREMENT,
    event_name VARCHAR(100) NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    event_base_date DATE NOT NULL DEFAULT '2026-08-28',

    CONSTRAINT pk_event
        PRIMARY KEY (event_id)
);
```

- `created_at`은 행을 생성할 때마다 달라지는 것이 정상이다.
- `event_base_date`는 업무상 정해진 날짜이므로 고정된 값을 사용한다.

### DBMS별 현재 날짜 표현

```sql
-- MySQL/MariaDB
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
```

```sql
-- Oracle
created_at DATE DEFAULT SYSDATE NOT NULL
```

Oracle의 `SYSDATE`는 DB 서버 기준의 현재 날짜와 시각을 반환한다. MySQL/MariaDB에서는 생성 시각 기본값으로 `CURRENT_TIMESTAMP`를 사용하는 것이 일반적이다.

서버와 애플리케이션의 시간대가 다르면 저장된 시간의 해석이 달라질 수 있으므로 시간대 기준도 함께 정해야 한다.

> 날짜 기본값의 선택 기준은 “값이 변하는가?”가 아니라 “컬럼의 의미상 변해야 하는가?”이다.

## 4. ALTER TABLE과 DML

제약조건과 기본값으로 테이블의 초기 구조를 만들었다면, 이후에는 `ALTER TABLE`로 구조를 변경하고 DML로 실제 데이터를 다룬다.

### DDL과 DML 비교

|구분|목적|대표 명령어|
|---|---|---|
|DDL|테이블과 제약조건 등 DB 구조 정의·변경|`CREATE`, `ALTER`, `DROP`|
|DML|테이블 안의 데이터 조작|`INSERT`, `UPDATE`, `DELETE`|
|조회|테이블의 데이터 조회|`SELECT`|

`SELECT`는 교재나 분류 기준에 따라 DML에 포함하거나 별도의 DQL로 구분하기도 한다.

### ALTER TABLE

`ALTER TABLE`은 이미 존재하는 테이블의 컬럼이나 제약조건을 변경한다.

```sql
-- 컬럼 추가
ALTER TABLE product
ADD COLUMN stock INT NOT NULL DEFAULT 0;

-- 컬럼의 길이와 제약조건 변경
ALTER TABLE product
MODIFY COLUMN product_name VARCHAR(150) NOT NULL;

-- CHECK 제약조건 추가
ALTER TABLE product
ADD CONSTRAINT chk_product_stock
CHECK (stock >= 0);

-- 컬럼 삭제
ALTER TABLE product
DROP COLUMN stock;
```

### ALTER TABLE 실행 흐름

```text
기존 테이블 확인
    ↓
변경할 컬럼·제약조건 결정
    ↓
ALTER TABLE 실행
    ↓
테이블 구조 확인
    ↓
기존 데이터와 애플리케이션 영향 확인
```

테이블 구조는 다음 명령으로 확인할 수 있다.

```sql
SHOW CREATE TABLE product;
```

### ALTER 사용 시 주의점

- DBMS와 버전에 따라 세부 문법이 다를 수 있다.
- 큰 테이블을 변경하면 긴 실행 시간이나 잠금이 발생할 수 있다.
- 외래 키 컬럼을 변경할 때는 부모와 자식 컬럼의 타입을 함께 확인해야 한다.
- 컬럼을 삭제하기 전에 애플리케이션, 인덱스, 제약조건의 참조 여부를 확인해야 한다.
- MySQL/MariaDB의 많은 DDL은 암시적 커밋을 발생시키므로 일반적인 DML처럼 쉽게 되돌릴 수 있다고 가정하면 안 된다.

### DML

#### INSERT

```sql
INSERT INTO product (
    category_id,
    sku,
    product_name,
    price
) VALUES (
    1,
    'APL-001',
    '사과 1kg',
    5900
);
```

컬럼 목록을 명시하면 어떤 값이 어느 컬럼에 들어가는지 분명해지고, 테이블 구조가 변경됐을 때 발생할 수 있는 실수를 줄일 수 있다.

#### SELECT

```sql
SELECT product_id, product_name, price
FROM product
WHERE price >= 5000
ORDER BY price DESC;
```

#### UPDATE

```sql
UPDATE product
SET price = 4900
WHERE sku = 'APL-001';
```

#### DELETE

```sql
DELETE FROM product
WHERE sku = 'APL-001';
```

`UPDATE`와 `DELETE`는 `WHERE`를 빠뜨리면 모든 행에 영향을 줄 수 있다. 따라서 먼저 같은 조건으로 대상을 조회하는 습관이 안전하다.

```text
변경할 조건 작성
    ↓
같은 WHERE 조건으로 SELECT
    ↓
대상 행 확인
    ↓
UPDATE 또는 DELETE 실행
    ↓
변경 결과 다시 SELECT
```

```sql
SELECT *
FROM product
WHERE sku = 'APL-001';

UPDATE product
SET price = 4900
WHERE sku = 'APL-001';

SELECT *
FROM product
WHERE sku = 'APL-001';
```

> `ALTER TABLE`은 테이블의 구조를 바꾸고, DML은 그 구조 안에 저장된 데이터를 바꾼다.

## 5. PRIMARY KEY와 자동 번호 생성

`PRIMARY KEY`, `AUTO_INCREMENT`, `SEQUENCE`는 함께 사용되는 경우가 많지만 역할은 서로 다르다.

### 역할 비교

|구분|역할|테이블과의 관계|유일성 제약|
|---|---|---|---|
|`PRIMARY KEY`|각 행을 식별한다.|테이블의 제약조건|중복과 `NULL`을 막는다.|
|`AUTO_INCREMENT`|`INSERT` 시 다음 숫자를 자동 생성한다.|특정 테이블 컬럼에 종속|그 자체가 PK는 아니다.|
|`SEQUENCE`|호출할 때 다음 숫자를 생성한다.|독립된 DB 객체|그 자체가 PK는 아니다.|

### AUTO_INCREMENT

MySQL/MariaDB에서 숫자형 식별자를 자동으로 생성할 때 주로 사용한다.

```sql
CREATE TABLE auto_product (
    product_id BIGINT NOT NULL AUTO_INCREMENT,
    product_name VARCHAR(100) NOT NULL,

    CONSTRAINT pk_auto_product
        PRIMARY KEY (product_id)
);
```

```sql
INSERT INTO auto_product (product_name)
VALUES ('사과');

INSERT INTO auto_product (product_name)
VALUES ('바나나');
```

```text
INSERT 실행
    ↓
AUTO_INCREMENT가 다음 숫자 생성
    ↓
생성된 값을 product_id에 저장
    ↓
PRIMARY KEY가 중복과 NULL 여부 검사
```

번호 생성은 `AUTO_INCREMENT`가 담당하고, 행의 유일성 보장은 `PRIMARY KEY`가 담당한다.

### SEQUENCE 객체

`SEQUENCE`는 테이블과 독립적으로 다음 숫자를 발급하는 DB 객체다.

```sql
-- MariaDB 예시
CREATE SEQUENCE product_seq
START WITH 1
INCREMENT BY 1;

SELECT NEXT VALUE FOR product_seq;
```

```sql
CREATE TABLE sequence_product (
    product_id BIGINT PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL
);

INSERT INTO sequence_product (
    product_id,
    product_name
) VALUES (
    NEXT VALUE FOR product_seq,
    '노트북'
);
```

Oracle에서는 다음과 같이 `NEXTVAL`을 사용한다.

```sql
CREATE SEQUENCE product_seq
START WITH 1
INCREMENT BY 1
NOCYCLE;

INSERT INTO product (
    product_id,
    product_name
) VALUES (
    product_seq.NEXTVAL,
    '노트북'
);
```

### 자동 생성 번호의 공백

자동 생성 번호는 중복 없는 식별자 후보를 만드는 것이 주된 목적이다. 항상 빈틈없는 연속 번호를 보장하지는 않는다.

번호가 비는 대표적인 상황은 다음과 같다.

- 발급한 번호를 사용한 작업이 실패한 경우
- 트랜잭션이 취소된 경우
- 행을 삭제한 경우
- 시퀀스가 미리 확보한 번호가 사용되지 않은 경우

따라서 삭제된 PK 번호를 억지로 다시 사용하거나, PK가 반드시 연속되어야 한다고 가정하면 안 된다.

> PK는 행의 유일성을 보장하고, `AUTO_INCREMENT`와 `SEQUENCE`는 PK에 사용할 수 있는 번호를 생성한다.

## 6. DB 캐시

DB는 데이터를 디스크에 저장하지만 매번 디스크에서 직접 읽으면 속도가 느리다. 이를 줄이기 위해 자주 사용하는 데이터와 인덱스 페이지를 메모리에 보관한다.

MySQL/MariaDB의 InnoDB에서는 대표적으로 Buffer Pool이 이 역할을 담당한다.

### 기본 조회 흐름

```text
SELECT 요청
    ↓
필요한 데이터 페이지가 Buffer Pool에 있는지 확인
    ↓
있음 ──→ 메모리에서 읽기
    ↓ 없음
디스크에서 페이지 읽기
    ↓
Buffer Pool에 적재
    ↓
조회 결과 반환
```

### 주요 용어

|용어|의미|
|---|---|
|Cache Hit|필요한 페이지가 메모리에 존재하는 상태|
|Cache Miss|필요한 페이지가 메모리에 없어 디스크 읽기가 필요한 상태|
|Cold Cache|필요한 페이지가 메모리에 충분히 올라오지 않은 상태|
|Warm Cache|자주 사용하는 페이지가 메모리에 올라온 상태|

같은 데이터를 다시 조회할 때 필요한 페이지가 Buffer Pool에 남아 있다면 디스크 접근을 줄일 수 있다.

### DB 내부 캐시와 애플리케이션 캐시

|구분|DB 내부 캐시|Redis 같은 애플리케이션 캐시|
|---|---|---|
|저장 대상|데이터·인덱스 페이지|조회 결과·계산 결과|
|요청 위치|SQL 요청이 DB까지 도달한다.|캐시 적중 시 DB 요청을 줄일 수 있다.|
|관리 주체|DBMS|애플리케이션|
|주요 고려사항|메모리 크기, 페이지 교체|TTL, 무효화, DB와의 정합성|

DB 내부 캐시가 존재하더라도 SQL 요청 자체는 DB에 도달한다. Redis 같은 애플리케이션 캐시는 캐시 적중 시 DB 조회 자체를 생략할 수 있다는 차이가 있다.

### Query Cache와 Buffer Pool

Buffer Pool은 데이터와 인덱스 페이지를 메모리에 보관한다. 과거의 Query Cache처럼 SQL 문자열에 대응하는 완성된 결과 전체를 저장하는 기능과는 다르다.

따라서 같은 `SELECT`의 두 번째 실행이 빨라졌다고 해서 완성된 쿼리 결과가 그대로 캐시됐다고 단정하면 안 된다.

### 설명용 관찰 SQL

```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';

SHOW GLOBAL STATUS
LIKE 'Innodb_buffer_pool_read_requests';

SHOW GLOBAL STATUS
LIKE 'Innodb_buffer_pool_reads';
```

|상태값|의미|
|---|---|
|`Innodb_buffer_pool_read_requests`|Buffer Pool에 요청한 논리 읽기 횟수|
|`Innodb_buffer_pool_reads`|메모리에 없어 디스크에서 읽은 횟수|

동일한 조회를 반복하면서 전후 값을 비교할 수 있다.

```sql
SELECT *
FROM product
WHERE sku = 'APL-001';

SELECT *
FROM product
WHERE sku = 'APL-001';
```

단, 상태값은 서버 전체의 누적 통계이므로 다른 세션의 요청이 함께 반영될 수 있다. 작은 테이블에서는 차이가 분명하게 나타나지 않을 수도 있다.

> DB 캐시는 디스크 접근을 줄이는 장치이며, 인덱스와 애플리케이션 캐시를 대체하는 동일한 개념은 아니다.

- DB Buffer Pool은 데이터 페이지를 메모리에 보관하고, Redis는 애플리케이션 수준에서 DB 요청 자체를 줄일 수 있다.

## 1. ANY와 ALL의 비교 기준

비교 대상이 `{300, 400, 500}`이고 `NULL`이 없다고 가정하면 `ANY`와 `ALL`은 최솟값 또는 최댓값 조건으로 바꿔 생각할 수 있다.

|조건|단일 비교로 변환|의미|
|---|---|---|
|`x > ANY (300, 400, 500)`|`x > 300`|하나보다만 크면 된다.|
|`x < ANY (300, 400, 500)`|`x < 500`|하나보다만 작으면 된다.|
|`x > ALL (300, 400, 500)`|`x > 500`|모든 값보다 커야 한다.|
|`x < ALL (300, 400, 500)`|`x < 300`|모든 값보다 작아야 한다.|

```text
ANY
    ↓ 하나라도 만족
비교가 가장 쉬운 경계값 사용

ALL
    ↓ 모두 만족
비교가 가장 엄격한 경계값 사용
```

- `> ANY`는 최솟값보다 크면 된다.
- `< ANY`는 최댓값보다 작으면 된다.
- `> ALL`은 최댓값보다 커야 한다.
- `< ALL`은 최솟값보다 작아야 한다.

> `ANY`는 하나만 만족하면 되고, `ALL`은 가장 까다로운 값까지 모두 만족해야 한다.

## 2. NOT IN과 NULL

SQL은 조건 결과를 `TRUE`, `FALSE`, `UNKNOWN`으로 평가한다.

다음 조건을 생각해 볼 수 있다.

```sql
WHERE department_id NOT IN (10, NULL)
```

이는 개념적으로 다음과 비슷하다.

```sql
department_id <> 10
    AND
department_id <> NULL
```

어떤 값을 `NULL`과 비교한 결과는 `TRUE`나 `FALSE`가 아니라 `UNKNOWN`이다.

```sql
department_id <> 10
    ↓ TRUE라고 가정
department_id <> NULL
    ↓ UNKNOWN
TRUE AND UNKNOWN
    ↓
UNKNOWN
```

`WHERE`는 결과가 `TRUE`인 행만 반환하므로 `UNKNOWN`이 된 행은 조회되지 않는다.

서브쿼리에서 `NULL`을 제거하면 이를 방지할 수 있다.

```sql
SELECT *
FROM employee
WHERE department_id NOT IN (
    SELECT department_id
    FROM excluded_department
    WHERE department_id IS NOT NULL
);
```

상관 조건을 사용한 `NOT EXISTS`도 대안이 될 수 있다.

```sql
SELECT e.*
FROM employee e
WHERE NOT EXISTS (
    SELECT 1
    FROM excluded_department d
    WHERE d.department_id = e.department_id
);
```

> `NOT IN`을 사용할 때는 서브쿼리 결과에 `NULL`이 포함될 가능성을 먼저 확인해야 한다.

## 3. ROW_NUMBER, RANK, DENSE_RANK

세 함수는 모두 정렬된 결과에 순위를 부여하지만 동점 데이터를 처리하는 방식이 다르다.

점수가 `100, 100, 90`인 경우 결과는 다음과 같다.

|점수|`ROW_NUMBER()`|`RANK()`|`DENSE_RANK()`|
|---|---|---|---|
|100|1|1|1|
|100|2|1|1|
|90|3|3|2|

|함수|동점 처리|다음 순위|
|---|---|---|
|`ROW_NUMBER()`|동점이어도 서로 다른 번호를 부여한다.|항상 1씩 증가한다.|
|`RANK()`|동점에 같은 순위를 부여한다.|동점 수만큼 건너뛴다.|
|`DENSE_RANK()`|동점에 같은 순위를 부여한다.|순위를 건너뛰지 않는다.|

그룹별 Top-N은 `PARTITION BY`로 그룹을 나눈 뒤 순위를 계산한다.

```sql
WITH ranked_employee AS (
    SELECT
        employee_id,
        department_id,
        employee_name,
        salary,
        ROW_NUMBER() OVER (
            PARTITION BY department_id
            ORDER BY salary DESC, employee_id
        ) AS row_num
    FROM employee
)
SELECT
    employee_id,
    department_id,
    employee_name,
    salary
FROM ranked_employee
WHERE row_num <= 3;
```

선택 기준은 다음과 같다.

- 그룹마다 정확히 N개 행이 필요하면 `ROW_NUMBER()`를 사용한다.
- 동점자를 같은 순위로 처리하고 순위 간격을 유지하려면 `RANK()`를 사용한다.
- 동점자를 같은 순위로 처리하면서 순위를 연속시키려면 `DENSE_RANK()`를 사용한다.
- `RANK()`나 `DENSE_RANK()`로 `순위 <= N`을 적용하면 동점자 때문에 N개보다 많은 행이 나올 수 있다.

> Top-N에서는 동점자를 포함할지와 정확히 N개 행만 가져올지를 먼저 결정해야 한다.

## 4. Driving Table과 Driven Table

조인에서 먼저 읽어 기준이 되는 테이블을 Driving Table, 그 결과를 바탕으로 반복 조회되는 테이블을 Driven Table이라고 한다.

```text
Driving Table에서 조건에 맞는 행 조회
    ↓
Driving Table의 조인 키 추출
    ↓
Driven Table에서 일치하는 행 조회
    ↓
두 테이블의 결과 결합
```

일반적으로 Driving Table에서 먼저 추려지는 행이 적을수록 Driven Table을 반복 조회하는 횟수도 줄어든다.

Driven Table의 조인 키에 인덱스가 없다면 반복 조회마다 넓은 범위를 탐색할 수 있다.

```sql
EXPLAIN
SELECT
    d.department_name,
    e.employee_name
FROM department d
JOIN employee e
    ON e.department_id = d.department_id
WHERE d.department_name = '개발';
```

`EXPLAIN`에서 확인할 주요 항목은 다음과 같다.

|항목|확인할 내용|
|---|---|
|`table`|어떤 테이블에 접근하는가|
|`type`|테이블 접근 방식이 전체 탐색인지 인덱스 탐색인지|
|`possible_keys`|사용할 수 있는 인덱스 후보|
|`key`|실제로 선택한 인덱스|
|`rows`|탐색할 것으로 예상하는 행 수|
|`Extra`|추가 필터링이나 처리 정보|

위 쿼리에서는 `department_name` 조건으로 부서가 먼저 좁혀지고, `employee.department_id`로 직원을 찾는 계획을 생각할 수 있다.

이때 Driven Table이 된 `employee`의 `department_id`에 인덱스가 있으면 반복 조인의 탐색 비용을 줄일 수 있다.

```sql
CREATE INDEX idx_employee_department_id
ON employee (department_id);
```

단, SQL에 작성한 테이블 순서가 실제 접근 순서를 보장하지는 않는다. 옵티마이저는 통계와 인덱스를 바탕으로 실행 계획을 선택하므로 실제 역할은 `EXPLAIN`으로 확인해야 한다.

> Driving Table은 SQL 작성 순서로 단정하지 않고 실행 계획으로 확인하며, Driven Table의 조인 키 인덱스 사용 여부를 함께 살펴봐야 한다.
