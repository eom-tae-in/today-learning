## 1. 요청을 처리할 Controller 메서드 찾기

### Controller와 DispatcherServlet의 관계

Controller는 HTTP 요청을 받아 필요한 처리를 Service에 요청하고, 그 결과를 HTTP 응답으로 표현하는 역할을 맡는다. 모든 요청 처리 코드와 SQL을 한곳에 넣지 않도록 책임을 나누는 출발점이다.

Spring MVC에서는 `DispatcherServlet`이 공통 진입점 역할을 한다. 요청에 맞는 핸들러를 찾고 호출하는 작업을 관련 구성 요소에 위임하여 개별 Controller 메서드로 연결한다. [Spring MVC 공식 문서](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet.html)

내장 Tomcat을 사용하는 구성을 기준으로 역할을 구분하면 다음과 같다.

|구성 요소|역할|
|---|---|
|Spring Boot|애플리케이션 구성과 실행을 지원한다. 내장 서버를 포함하는 방식으로 실행할 수 있다.|
|Tomcat|HTTP 요청을 받아 웹 애플리케이션의 서블릿으로 연결한다.|
|Catalina|Tomcat의 서블릿 컨테이너 구성 요소다.|
|DispatcherServlet|서블릿 컨테이너 안에서 실행되는 Spring MVC의 공통 요청 처리 진입점이다.|
|Controller|매핑된 메서드에서 요청값을 사용하고 응답을 구성한다.|

`Spring Boot → Tomcat → Catalina → DispatcherServlet`은 구성 관계를 떠올리는 데 도움이 되지만, 네 요소를 차례로 호출한다는 뜻의 실행 순서는 아니다. [Tomcat Catalina 공식 API](https://tomcat.apache.org/tomcat-10.1-doc/api/org/apache/catalina/package-summary.html)

### 요청 매핑과 응답 본문

|애노테이션|역할|예시|
|---|---|---|
|`@RestController`|`@Controller`와 `@ResponseBody`의 기능을 함께 적용한다.|REST API Controller 선언|
|`@RequestMapping`|경로·HTTP 메서드 등의 조건으로 요청을 매핑한다.|클래스에 `@RequestMapping("/products")`|
|`@GetMapping`|GET 요청을 처리할 메서드를 지정한다.|메서드에 `@GetMapping("/{id}")`|
|`@PostMapping`|POST 요청을 처리할 메서드를 지정한다.|메서드에 `@PostMapping`|

클래스의 `/products`와 메서드의 `/{id}`를 조합하면 `GET /products/10`을 처리할 수 있다. `@RequestMapping`에서 HTTP 메서드를 제한하지 않으면 GET 전용이 아니므로, 동작에 맞는 매핑을 명시한다. [Spring 요청 매핑 공식 문서](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-requestmapping.html)

`@RestController`에서 반환한 객체는 `HttpMessageConverter`를 통해 응답 본문으로 작성된다. JSON 변환기가 구성된 일반적인 REST API에서는 DTO를 JSON으로 변환하지만, `**@RestController**`**가 모든 반환값을 무조건 JSON으로 만드는 것은 아니다.** 문자열이나 다른 미디어 타입도 반환할 수 있다. [Spring 응답 본문 공식 문서](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/responsebody.html)

> 요청 매핑은 호출할 메서드를 결정하고, 응답 본문 처리는 그 메서드의 반환값을 클라이언트에게 전달할 형태로 변환한다.

## 2. 요청값의 위치와 형태에 맞춰 받기

요청을 처리할 메서드를 정했다면, 다음은 HTTP 요청의 데이터를 Java 메서드 인자로 옮기는 단계다. **요청값을 어디에서 읽는지**와 **어떤 객체에 담는지**를 나누어 보면 구분이 쉬워진다.

### 수신 방식 비교

아래는 Spring MVC 기준이다.

|방식|주로 읽는 데이터|사용하는 상황|
|---|---|---|
|`@PathVariable`|URL 경로의 `{변수}` 부분|`/products/10`에서 특정 상품의 ID를 받는다.|
|`@RequestParam`|쿼리 파라미터 또는 폼 파라미터|`?keyword=keyboard`처럼 개별 검색 조건을 받는다.|
|`@ModelAttribute` + DTO|쿼리·폼 등의 이름 있는 요청값|여러 검색 조건을 하나의 객체로 묶는다.|
|`@RequestBody` + DTO|HTTP 요청 본문|JSON 같은 본문을 메시지 변환기로 읽어 객체로 만든다.|

`@RequestParam`은 Servlet 요청 파라미터를 읽으므로 쿼리와 폼 값 모두를 받을 수 있다. `@ModelAttribute`도 쿼리 전용 기능은 아니며, 요청 파라미터 외에 경로 변수 등의 바인딩을 지원한다. [RequestParam 공식 문서](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/requestparam.html), [ModelAttribute 공식 문서](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/modelattrib-method-args.html)

DTO는 **Data Transfer Object**, 즉 데이터를 전달하기 위한 객체다. `@RequestParam`, `@PathVariable`과 나란히 놓고 세 가지 독립적인 전송 방식으로 외우면 혼동하기 쉽다. 동일한 DTO도 어떤 애노테이션으로 받는지에 따라 바인딩 방식이 달라진다.

### Request Body와 RequestParam은 반대 개념이 아니다

다음은 설명용 폼 요청이다.

```http
POST /product-search/keyword HTTP/1.1
Content-Type: application/x-www-form-urlencoded

keyword=keyboard
```

`keyword=keyboard`는 실제 HTTP **본문에 들어 있다.** 하지만 이 폼 값은 서버에서 `@RequestParam("keyword")`로 받을 수 있다.

반면 JSON 본문은 일반적으로 `@RequestBody`와 JSON 메시지 변환기를 통해 읽는다. **본문이 존재한다는 사실**과 **Spring의** `**@RequestBody**`**를 사용한다는 사실**을 구분해야 한다. [Spring 요청 본문 공식 문서](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/requestbody.html)

### 같은 DTO를 쿼리와 JSON으로 받는 예제

검색 조건 두 개를 담는 DTO다. `minPrice`는 값이 생략된 상태를 표현할 수 있도록 `Integer`를 사용한다.

```java
// 설명용 ProductSearchRequest.java
public class ProductSearchRequest {
    private String keyword;
    private Integer minPrice;

    public String getKeyword() { return keyword; }
    public void setKeyword(String keyword) { this.keyword = keyword; }
    public Integer getMinPrice() { return minPrice; }
    public void setMinPrice(Integer minPrice) { this.minPrice = minPrice; }
}
```

다음 Controller는 바인딩된 값을 돌려주는 설명용 코드다. 실제 상품 검색이나 DB 조회는 수행하지 않는다. Spring Web 애노테이션의 import는 생략했다.

```java
@RestController
@RequestMapping("/product-search")
public class ProductSearchController {

    @GetMapping
    public ProductSearchRequest fromQuery(
            @ModelAttribute ProductSearchRequest request) {
        return request;
    }

    @PostMapping(consumes = "application/json")
    public ProductSearchRequest fromJson(
            @RequestBody ProductSearchRequest request) {
        return request;
    }

    @PostMapping(value = "/keyword",
                 consumes = "application/x-www-form-urlencoded")
    public String fromForm(
            @RequestParam("keyword") String keyword) {
        return keyword;
    }
}
```

첫 번째 메서드는 다음 요청의 검색 조건을 DTO에 바인딩한다.

```http
GET /product-search?keyword=keyboard&minPrice=10000 HTTP/1.1
```

두 번째 메서드는 같은 의미의 조건을 JSON 본문으로 받는다.

```json
POST /product-search HTTP/1.1
Content-Type: application/json

{
  "keyword": "keyboard",
  "minPrice": 10000
}
```

|비교 기준|`@ModelAttribute` 예제|`@RequestBody` 예제|
|---|---|---|
|입력|이름과 값으로 구성된 요청 파라미터|JSON 본문|
|객체 구성|이름을 기준으로 바인딩하고 필요한 타입 변환 수행|메시지 변환기로 JSON 역직렬화|
|결과|`ProductSearchRequest` 객체|`ProductSearchRequest` 객체|

DTO에 담긴 최종 값이 같더라도 HTTP 입력 형태와 객체를 만드는 과정은 다르다.

### 기본값·필수값·타입 변환

|선언 또는 조건|동작|
|---|---|
|`@RequestParam("keyword") String keyword`|기본적으로 필수다. 파라미터가 빠지면 기본 예외 처리에서 400 응답이 된다.|
|`@RequestParam(name = "keyword", required = false) String keyword`|생략할 수 있으며, 일반적으로 `null`을 받는다.|
|`@RequestParam(name = "page", defaultValue = "1") int page`|값이 없거나 비어 있으면 기본값 `1`을 사용한다.|
|`@PathVariable("id") Long id`|경로에서 읽은 값을 `Long`으로 변환한다.|
|숫자 자리에 `abc` 전달|숫자로 변환할 수 없어 기본 예외 처리에서 400 응답이 된다.|

위 표의 필수 여부·기본값은 애노테이션 설정, 400 응답은 Spring MVC의 기본 예외 처리 기준이다. [RequestParam API](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/bind/annotation/RequestParam.html), [기본 예외 처리 API](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/servlet/mvc/support/DefaultHandlerExceptionResolver.html)

파라미터가 존재한다는 것과 내용이 유효하다는 것은 다르다. 필수 문자열이라고 해서 공백·빈 문자열 검증까지 자동으로 끝나는 것은 아니다. 또한 DTO를 받는 애노테이션과 입력값 검증은 별개의 역할이다.

> 먼저 요청값의 위치와 형식을 결정하고 수신 애노테이션을 선택한다. DTO는 그렇게 읽은 값을 묶어 전달할 그릇이다.

## 3. Service·Mapper·MyBatis로 데이터 접근 연결하기

Controller가 값을 받는 것만으로 DB 조회가 이루어지지는 않는다. 요청 처리와 데이터 접근을 연결하면서 각 계층의 책임을 나눠야 한다.

### 계층별 역할

|구성 요소|책임|상품 단건 조회에서 하는 일|
|---|---|---|
|Controller|HTTP 요청·응답 처리|경로의 상품 ID를 받고 조회 결과에 맞는 응답 구성|
|Service|업무 규칙과 처리 흐름 조합|상품 조회 기능을 제공하고 Mapper 호출|
|Mapper 인터페이스|데이터 접근 메서드 정의|`selectById(id)`라는 호출 지점 제공|
|MyBatis|메서드와 SQL 연결, 파라미터 바인딩, 결과 매핑|JDBC를 통해 SQL을 실행하고 조회 결과를 객체로 변환|
|DB|데이터 저장과 SQL 처리|조건에 맞는 행 조회|

이 예제의 데이터 접근 계층은 Mapper다. 앞서 Repository를 사용한 구조에서 살펴본 데이터 접근 책임을 이 위치에서 맡는다.

### 상품 조회 예제의 데이터 객체와 Service

이하 예제는 `com.example.product` 패키지가 Spring의 스캔 범위에 있고, MyBatis Spring Boot Starter와 DB 연결이 구성된 상황을 가정한다. 실제 수업 프로젝트의 코드나 설정값을 나타내지는 않는다.

`ProductDto`는 DB 조회 결과와 응답 데이터를 담는다. 여기서는 학습용으로 하나의 DTO를 공유한다.

```java
package com.example.product;

public class ProductDto {
    private Long productId;
    private String productName;
    private Integer price;

    public Long getProductId() { return productId; }
    public void setProductId(Long productId) { this.productId = productId; }
    public String getProductName() { return productName; }
    public void setProductName(String productName) { this.productName = productName; }
    public Integer getPrice() { return price; }
    public void setPrice(Integer price) { this.price = price; }
}
```

Service는 Mapper를 생성자로 주입받는다. 단순 조회 예제라 처리 내용은 짧지만, 업무 규칙이 생기면 그 규칙을 조합할 위치가 된다.

```java
package com.example.product;

import org.springframework.stereotype.Service;

@Service
public class ProductService {
    private final ProductMapper productMapper;

    public ProductService(ProductMapper productMapper) {
        this.productMapper = productMapper;
    }

    public ProductDto findById(Long id) {
        return productMapper.selectById(id);
    }
}
```

### Mapper는 인터페이스인데 어떻게 호출되는가?

```java
package com.example.product;

import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;

@Mapper
public interface ProductMapper {
    ProductDto selectById(@Param("id") Long id);
}
```

MyBatis와 Spring의 연동 구성이 Mapper 프록시를 만들어 빈으로 등록한다. Service에 주입되는 것은 이 프록시이며, 인터페이스 메서드 호출을 대응하는 SQL 실행으로 연결한다. XML 방식에서는 `ProductMapperImpl`을 직접 작성할 필요가 없다. [MyBatis Mapper 주입 공식 문서](https://mybatis.org/spring/mappers.html)

`@Param("id")`는 Java 인자를 SQL에서 `id`라는 이름으로 참조하도록 한다. HTTP 파라미터를 읽는 Spring의 `@RequestParam`과 역할이 다르다. [MyBatis Java API 공식 문서](https://mybatis.org/mybatis-3/java-api.html)

### mybatis-config.xml과 Mapper XML의 차이

파일 이름에 모두 MyBatis가 관련되어 있어도 담당하는 설정은 다르다.

|파일|역할|
|---|---|
|`application.yml`|Spring Boot 설정과 MyBatis 설정 파일·Mapper XML의 위치 지정|
|`mybatis-config.xml`|MyBatis 동작 옵션과 타입 별칭 같은 전역 설정|
|`ProductMapper.java`|데이터 접근 메서드와 반환 타입 정의|
|`ProductMapper.xml`|메서드에 연결할 SQL과 결과 매핑 정의|

다음은 설명용 `src/main/resources/mybatis-config.xml`이다.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE configuration PUBLIC "-//mybatis.org//DTD Config 3.0//EN"
        "https://mybatis.org/dtd/mybatis-3-config.dtd">
<configuration>
    <settings>
        <setting name="mapUnderscoreToCamelCase" value="true"/>
    </settings>
    <typeAliases>
        <typeAlias alias="ProductDto"
                   type="com.example.product.ProductDto"/>
    </typeAliases>
</configuration>
```

|설정|예제에서의 효과|구분할 점|
|---|---|---|
|`mapUnderscoreToCamelCase`|`product_id`를 `productId`, `product_name`을 `productName`에 자동 매핑|MyBatis 기본값은 `false`이며, DB 컬럼명 자체를 바꾸는 설정은 아니다.|
|`typeAlias`|XML에서 긴 클래스명 대신 `ProductDto` 사용|Java 클래스를 새로 만들거나 Spring 빈으로 등록하는 기능은 아니다.|

컬럼명과 프로퍼티명의 대응이 자동 규칙으로 해결되지 않으면 SQL 별칭이나 명시적인 `resultMap`을 사용할 수 있다. [MyBatis 설정 공식 문서](https://mybatis.org/mybatis-3/configuration.html)

다음은 해당 파일을 연결하는 `application.yml`의 MyBatis 설정 부분이다.

```yml
mybatis:
  config-location: classpath:mybatis-config.xml
  mapper-locations: classpath:/mappers/*.xml
```

`config-location`은 전역 설정 파일, `mapper-locations`는 SQL을 작성한 Mapper XML을 가리킨다. 파일을 만들었다는 것과 애플리케이션이 그 파일을 읽도록 연결했다는 것을 구분해야 한다.

Spring Boot에서는 `mybatis.configuration.*`로 동작 옵션을 설정하는 방법도 있어 별도 설정 XML이 항상 필요한 것은 아니다. `**mybatis.config-location**`**과** `**mybatis.configuration.***`**는 함께 사용할 수 없으므로 설정 방식을 선택한다.** [MyBatis Spring Boot Starter 공식 문서](https://mybatis.org/spring-boot-starter/mybatis-spring-boot-autoconfigure/)

### 메서드와 SQL을 연결하는 Mapper XML

다음은 `src/main/resources/mappers/ProductMapper.xml` 예제다. `products` 테이블의 `product_id`가 상품을 유일하게 식별한다고 가정한다.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "https://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.example.product.ProductMapper">
    <select id="selectById" resultType="ProductDto">
        SELECT product_id, product_name, price
        FROM products
        WHERE product_id = #{id}
    </select>
</mapper>
```

|연결 요소|맞아야 하는 대상|
|---|---|
|`namespace`|Mapper 인터페이스의 전체 이름 `com.example.product.ProductMapper`|
|`<select id="selectById">`|인터페이스 메서드명 `selectById`|
|`#{id}`|`@Param("id")`로 지정한 SQL 파라미터 이름|
|`resultType="ProductDto"`|앞서 등록한 타입 별칭과 조회 결과를 담을 타입|
|`product_name` → `productName`|설정한 자동 매핑 규칙과 DTO 프로퍼티|

`#{id}`는 값을 PreparedStatement의 파라미터로 바인딩한다. `${id}`처럼 문자열을 SQL에 그대로 끼워 넣는 방식과 다르며, 사용자 입력값을 직접 치환하면 SQL Injection 위험이 생긴다. [MyBatis Mapper XML 공식 문서](https://mybatis.org/mybatis-3/sqlmap-xml.html)

### 하나의 조회 요청이 실행되는 순서

```text
GET /products/10
    ↓ 경로 변수를 Long으로 변환
Controller: id = 10
    ↓ 조회 기능 호출
ProductService.findById(10L)
    ↓ 데이터 접근 메서드 호출
ProductMapper.selectById(10L)
    ↓ Mapper 프록시가 대응 SQL 선택
ProductMapper.xml의 selectById
    ↓ id를 바인딩하여 JDBC로 실행
DB에서 product_id = 10인 행 조회
    ↓ 컬럼을 Java 프로퍼티에 매핑
ProductDto 반환
    ↓ Service를 거쳐 Controller로 전달
조회 결과에 맞는 상태 코드와 응답 본문 구성
```

조회 결과 객체를 만드는 것은 MyBatis의 결과 매핑이고, 그 객체를 JSON 응답으로 쓰는 것은 Spring MVC의 메시지 변환이다. **DB 행 → Java 객체 → JSON은 서로 다른 변환 단계다.**

### 의존 객체를 선택하는 @Qualifier

Service가 Mapper를 주입받듯이, 필요한 객체를 외부에서 전달받는 것이 의존성 주입이다. `@Qualifier`는 같은 타입의 주입 후보를 한정하는 데 사용한다. 빈 이름을 선택 기준으로 활용할 수도 있다. 정확한 표기는 **`@Qualifier`**다. [Spring Qualifier 공식 문서](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired-qualifiers.html)

예를 들어 생성자 파라미터에 `@Qualifier("productMapper") ProductMapper productMapper`를 선언하면 해당 타입의 후보 중 지정한 조건에 맞는 빈을 주입받는다. 위 예제처럼 주입 후보가 명확하게 하나라면 이를 추가할 필요는 없다.

|비슷해 보이는 이름|실제 역할|
|---|---|
|`@RequestParam`|HTTP 요청 파라미터를 Controller 인자로 받는다.|
|`@Param`|Mapper 인자를 SQL에서 참조할 이름을 지정한다.|
|`@Parameter`|API 입력 파라미터를 문서화한다.|
|`@Qualifier`|의존성 주입 대상 빈 후보를 한정한다.|

> Controller는 HTTP, Service는 업무 처리, Mapper는 데이터 접근을 담당한다. MyBatis 설정과 SQL 매핑이 연결되어야 Mapper 호출이 실제 DB 작업으로 이어진다.

## 4. Swagger로 API의 요청·응답 계약 명세하기

요청을 받아 DB 결과를 반환하는 흐름을 만들었다면, API를 사용하는 사람이 같은 코드를 읽지 않아도 호출 방법을 알 수 있어야 한다. API 문서는 경로, 입력값, 응답 형태를 공유하는 기준이 된다.

### OpenAPI·Swagger UI·springdoc의 관계

|구성 요소|역할|
|---|---|
|OpenAPI|API 경로, 요청값, 응답 등을 기술하는 명세 형식|
|Swagger UI|OpenAPI 명세를 읽어 사람이 확인하고 요청을 보낼 수 있는 화면으로 표현|
|springdoc-openapi|Spring의 Controller 정보와 애노테이션 등을 분석해 OpenAPI 명세 생성|

springdoc-openapi를 사용하는 경우 기본 설정에서 `/v3/api-docs`는 명세 JSON, `/swagger-ui.html`은 Swagger UI에 접근하는 경로다. 실제 경로는 애플리케이션 설정에 따라 달라질 수 있다. [springdoc 공식 문서](https://springdoc.org/)

### 애노테이션별 명세 대상

|애노테이션|설명하는 대상|대표 작성 위치|주요 속성|
|---|---|---|---|
|`@Tag`|상품·회원 등 API 그룹|Controller 클래스|`name`, `description`|
|`@Operation`|개별 API의 기능|Controller 메서드|`summary`, `description`|
|`@Parameter`|경로·쿼리 등 입력 파라미터|메서드 파라미터 등|`description`, `example`, `required`|
|`@ApiResponse`|상태 코드별 응답|메서드 또는 `@ApiResponses` 내부|`responseCode`, `description`, `content`|

이 애노테이션들은 `io.swagger.v3.oas.annotations` 계열을 사용한다. DTO 구조나 필드 설명에는 `@Schema`, 응답의 미디어 타입과 스키마에는 `@Content`를 함께 사용할 수 있다. [Swagger 애노테이션 공식 문서](https://github.com/swagger-api/swagger-core/wiki/Swagger-2.X---Annotations)

### 상품 조회 Controller와 명세를 함께 읽기

다음은 앞의 `ProductService`와 연결하는 설명용 Controller다. `package`와 import는 생략했다.

```java
@RestController
@RequestMapping("/products")
@Tag(name = "상품", description = "상품 조회 API")
public class ProductController {
    private final ProductService productService;

    public ProductController(ProductService productService) {
        this.productService = productService;
    }

    @GetMapping(value = "/{id}", produces = "application/json")
    @Operation(summary = "상품 단건 조회",
               description = "상품 ID로 한 개의 상품을 조회한다.")
    @ApiResponses({
        @ApiResponse(
            responseCode = "200",
            description = "상품 조회 성공",
            content = @Content(
                mediaType = "application/json",
                schema = @Schema(implementation = ProductDto.class)
            )
        ),
        @ApiResponse(
            responseCode = "404",
            description = "해당 상품 없음",
            content = @Content
        )
    })
    public ResponseEntity<ProductDto> findById(
            @Parameter(description = "상품 ID", example = "10", required = true)
            @PathVariable("id") Long id) {

        ProductDto product = productService.findById(id);

        if (product == null) {
            return ResponseEntity.notFound().build();
        }

        return ResponseEntity.ok(product);
    }
}
```

이 코드에서 실제 반환 분기와 문서의 대응은 다음과 같다.

|조건|실제 반환 코드|명세|
|---|---|---|
|상품을 찾음|`ResponseEntity.ok(product)`|200, `ProductDto` 형태의 JSON|
|상품을 찾지 못함|`ResponseEntity.notFound().build()`|404, 본문 없음|

예를 들어 DB에 상품 ID `10`, 상품명 `Keyboard`, 가격 `30000`이 있다면 성공 응답 본문은 다음 형태다. 실제 조회 결과를 기록한 것은 아니다.

```json
{
  "productId": 10,
  "productName": "Keyboard",
  "price": 30000
}
```

### 명세 작성과 실제 동작을 구분하기

`@ApiResponse(responseCode = "404")`는 404 응답을 **설명**한다. 실제 404는 Controller의 `notFound()` 반환처럼 구현에서 만들어야 한다. `@Parameter(required = true)`도 문서상의 필수 여부를 설명하므로 실제 값 수신과 검증을 대신하지 않는다.

JSON 본문 전체는 OpenAPI의 `requestBody` 항목으로 표현한다. 이를 설명하는 Swagger의 `@RequestBody`와 실제 본문을 읽는 Spring의 `@RequestBody`는 이름이 같아 import를 구분해야 한다.

|전체 이름|역할|
|---|---|
|`org.springframework.web.bind.annotation.RequestBody`|HTTP 본문을 읽어 Controller 인자로 변환|
|`io.swagger.v3.oas.annotations.parameters.RequestBody`|OpenAPI의 요청 본문 명세 설명|

Swagger 화면에서는 상품 그룹과 API 설명, `id`의 위치·자료형·예시, 상태 코드별 응답 구조를 읽는다. `Try it out`으로 요청을 보내는 경우에는 문서에 표시된 예시와 서버가 실제 반환한 상태 코드·본문을 대조한다.

> API 문서는 호출 방법과 응답 계약을 설명한다. 명세의 정확성은 실제 바인딩·검증·반환 로직과 일치하는지에 달려 있다.

# 🐛 문제 해결

## 요청 파라미터로 값을 받으면 동기 방식인가?

**질문**: 파라미터로 API 요청값을 받는 것을 동기 방식이라고 하는가? Request Body와는 어떤 관계인가?

혼동을 풀려면 서로 다른 분류 기준을 나누어야 한다.

|구분 기준|확인할 질문|예시|
|---|---|---|
|데이터 전달 위치·형식|요청값이 어디에 어떤 형태로 들어 있는가?|경로, 쿼리, 폼 본문, JSON 본문|
|서버의 수신 방식|그 데이터를 어떤 방식으로 읽는가?|`@RequestParam`, `@PathVariable`, `@ModelAttribute`, `@RequestBody`|
|동기·비동기|호출한 작업의 완료와 후속 실행을 어떻게 연결하는가?|완료 후 다음 단계 진행, 완료를 별도로 전달받아 처리|

**정리**: 쿼리 파라미터나 JSON 본문을 사용한다는 사실만으로 동기·비동기가 결정되지는 않는다. 두 기준 사이에 필연적인 인과관계는 없다.

브라우저의 `fetch()`는 Promise를 반환한다. 다음처럼 값을 URL의 쿼리에 넣어도 비동기로 HTTP 요청을 보낼 수 있다. [MDN Fetch 공식 문서](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)

```js
// 설명용: 쿼리 파라미터를 사용하는 비동기 HTTP 호출
async function searchProducts() {
    const response = await fetch(
        "/product-search?keyword=keyboard&minPrice=10000"
    );
    return response.json();
}
```

여기서 `await`는 해당 비동기 함수의 후속 실행을 기다리게 한다. 브라우저 전체를 멈추는 동기 호출로 바꾸는 것은 아니다. 또한 클라이언트가 비동기로 요청했다는 사실만으로 서버의 Controller나 DB 처리까지 비동기가 되는 것은 아니다.

> 요청값의 위치, Spring의 수신 애노테이션, 동기·비동기는 각각 나누어 판단한다. 폼 값은 본문에 있으면서도 `@RequestParam`으로 받을 수 있다.

# 🧠 오늘 이해한 핵심

- **HTTP 데이터와 Java 객체는 다른 관점이다.** 쿼리·폼·JSON은 전달 형식이고, DTO는 읽어 들인 데이터를 묶는 구조다. 동기·비동기는 이와 별도로 판단한다.
- **Mapper 호출과 객체 반환 사이에는 연결 규칙이 있다.** 인터페이스·메서드명·SQL 파라미터·결과 매핑·설정 파일이 맞물려 데이터 접근이 이루어진다.
- **API의 구현과 명세는 같은 계약을 가리켜야 한다.** Spring 애노테이션과 반환 코드가 실제 동작을 만들고, Swagger 애노테이션은 그 동작을 사용하는 방법을 설명한다.

# 🔄 함께 복습한 내용

## 1. Spring Boot·Tomcat·Catalina·DispatcherServlet의 관계

|구성 요소|핵심 역할과 관계|
|---|---|
|Spring Boot|애플리케이션 설정과 내장 Tomcat의 구성·실행을 지원한다.|
|Tomcat|HTTP 요청을 받아 서블릿을 실행할 환경을 제공한다.|
|Catalina|Tomcat의 서블릿 컨테이너로, 서블릿의 실행과 생명주기를 관리한다.|
|DispatcherServlet|컨테이너에 등록된 Spring MVC 서블릿으로, 요청에 맞는 Controller에 처리를 위임한다.|

**구성 요소의 포함·관리 관계와 요청 처리 순서를 구분한다.** Spring Boot를 요청마다 통과하는 처리 단계로 보지 않는다. [Spring MVC](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet.html), [Tomcat Catalina](https://tomcat.apache.org/tomcat-10.1-doc/api/org/apache/catalina/package-summary.html)

## 2. React에서 DB 조회 후 JSON을 받기까지

```text
React: 상품 조회 요청
    ↓
Controller: 요청값 수신
    ↓
Service: 업무 처리
    ↓
Repository 또는 Mapper: DB에서 상품 조회
    ↓
조회 결과가 Service를 거쳐 Controller로 반환
    ↓
Spring MVC: Java 객체를 JSON으로 변환
    ↓
React: 응답 데이터로 화면 갱신
```

JPA 기반 구조에서는 Repository, 이번 MyBatis 예제에서는 Mapper가 데이터 접근을 맡는다. **DB 조회 결과를 Java 객체로 매핑하는 단계와 그 객체를 JSON 응답으로 변환하는 단계는 다르다.** [Spring 응답 본문 처리](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/responsebody.html)

## 3. React 기반 REST API와 JSP 방식 비교

React가 브라우저에서 화면을 구성하는 **CSR 방식**을 기준으로 비교한다.

|비교 기준|React CSR + REST API|JSP 방식|
|---|---|---|
|화면 생성 위치|브라우저|서버|
|서버의 주요 응답|JSON 데이터|서버에서 생성한 HTML|
|Controller의 대표 반환|DTO 또는 `ResponseEntity`|뷰 이름과 `Model` 데이터|
|Jasper 사용|JSP를 사용하지 않으면 필요하지 않음|JSP를 서블릿으로 변환·컴파일할 때 사용|

Jasper는 Tomcat의 JSP 엔진이다. JSON 응답을 만드는 역할은 맡지 않는다. [Spring JSP 지원](https://docs.spring.io/spring-framework/reference/web/webmvc-view/mvc-jsp.html), [Tomcat Jasper](https://tomcat.apache.org/tomcat-10.1-doc/jasper-howto.html)

## 4. DB·SQL을 역할별로 다시 분류하기

|분류 기준|관련 문법·개념|핵심 역할|
|---|---|---|
|데이터 조회·변경|`SELECT`, `INSERT`, `UPDATE`, `DELETE`|저장된 행을 조회·추가·수정·삭제|
|구조 정의|`CREATE`, `ALTER`, `DROP`|테이블 등 DB 객체의 구조 생성·변경·삭제|
|무결성 보장|`PRIMARY KEY`, `FOREIGN KEY`, `NOT NULL`, `UNIQUE`, `CHECK`|식별·참조 관계와 저장 가능한 값의 규칙 보장|
|데이터 결합·추출|`JOIN`, `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`, 서브쿼리|데이터 연결·필터링·집계·정렬과 조건 구성|

`WHERE`는 그룹화 전의 행을, `HAVING`은 그룹화된 결과를 조건으로 걸러낸다. 제약조건은 `CREATE`·`ALTER`로 정의하며, API를 거치지 않고 데이터를 변경해도 DB에서 적용된다. [Oracle SQL 문장 분류](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Types-of-SQL-Statements.html), [SELECT](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/SELECT.html), [데이터 무결성](https://docs.oracle.com/en/database/oracle/oracle-database/21/cncpt/data-integrity.html)
