## 1. JOIN 결과를 게시글·댓글 객체로 연결하기 — MyBatis 관계 매핑

### 개념

관계형 DB의 조회 결과는 행과 열로 구성되지만, Java에서는 게시글 객체 안에 댓글 목록을 담아 표현할 수 있다. 따라서 SQL을 올바르게 작성하는 것과 조회 결과를 원하는 객체 구조로 만드는 것은 별개의 작업이다.

|구성 요소|역할|
|---|---|
|JOIN|게시글과 댓글의 데이터를 하나의 조회 결과로 가져온다.|
|`resultMap`|조회 컬럼을 Java 객체의 속성에 연결한다.|
|`<id>`|중첩 결과 매핑에서 같은 객체를 식별하는 기준을 지정한다. DB의 PK를 생성하는 설정은 아니다.|
|`<association>`|다른 객체 하나를 속성에 연결한다.|
|`<collection>`|여러 자식 객체를 목록 등의 컬렉션에 연결한다.|
|`ofType`|컬렉션 자체가 아니라 그 안에 들어갈 원소의 타입을 지정한다.|

부모와 자식의 식별 컬럼을 명확하게 지정하면 반복되는 JOIN 행을 올바른 객체 구조로 묶는 데 도움이 된다. [MyBatis 관계 매핑 문서](https://mybatis.org/mybatis-3/sqlmap-xml.html)

### 댓글 유무에 따른 JOIN 결과

게시글 10에는 댓글이 두 개 있고, 게시글 11에는 댓글이 없다고 가정한다. 각 게시글을 `LEFT JOIN`으로 조회했을 때 주요 컬럼은 다음처럼 나타난다.

|post_id|post_title|comment_id|comment_content|
|---|---|---|---|
|10|첫 번째 게시글|101|첫 댓글|
|10|첫 번째 게시글|102|두 번째 댓글|
|11|두 번째 게시글|NULL|NULL|

- 게시글 10이 두 행에 나타나는 것은 댓글이 두 개이기 때문이다. 게시글 두 개를 뜻하지 않는다.
- `LEFT JOIN`은 댓글이 없는 게시글도 남긴다. 대응하는 댓글 컬럼에는 `NULL`이 들어간다.
- 같은 조건을 `INNER JOIN`으로 조회하면 댓글이 없는 게시글은 결과에서 제외된다.
- 오른쪽 테이블에 대한 조건을 `WHERE`에 추가해 `NULL` 행을 제거하면, `LEFT JOIN`이어도 댓글 없는 게시글이 사라질 수 있다.

### 동작 흐름

```text
LEFT JOIN으로 게시글·댓글 조회
    ↓ 게시글 컬럼은 댓글 개수만큼 반복될 수 있음
부모의 post_id를 기준으로 게시글 객체 식별
    ↓ 댓글 식별 컬럼 확인
유효한 comment_id를 가진 댓글 객체 구성
    ↓ 부모 객체의 collection에 연결
게시글 객체와 댓글 목록 완성
```

### 핵심 코드

조회 결과를 담는 Java 객체의 예시다. 두 클래스는 각각 별도 파일에 둔다.

```java
@Getter
@Setter
@NoArgsConstructor
public class PostData {
    private Long id;
    private String title;
    private List<CommentData> comments = new ArrayList<>();
}

@Getter
@Setter
@NoArgsConstructor
public class CommentData {
    private Long id;
    private Long postId;
    private String content;
}
```

다음은 Mapper XML의 핵심 부분이다. Mapper 메서드는 `findWithComments(@Param("postId") Long postId)`처럼 파라미터 이름을 연결한다고 가정한다.

```xml
<mapper namespace="com.example.board.mapper.PostMapper">
    <resultMap id="postWithCommentsMap"
               type="com.example.board.model.PostData">
        <id property="id" column="post_id" />
        <result property="title" column="post_title" />

        <collection property="comments"
                    ofType="com.example.board.model.CommentData"
                    notNullColumn="comment_id">
            <id property="id" column="comment_id" />
            <result property="postId" column="comment_post_id" />
            <result property="content" column="comment_content" />
        </collection>
    </resultMap>

    <select id="findWithComments" resultMap="postWithCommentsMap">
        SELECT p.id      AS post_id,
               p.title   AS post_title,
               c.id      AS comment_id,
               c.post_id AS comment_post_id,
               c.content AS comment_content
        FROM posts p
        LEFT JOIN comments c ON c.post_id = p.id
        WHERE p.id = #{postId}
        ORDER BY c.id
    </select>
</mapper>
```

`notNullColumn="comment_id"`는 댓글 식별값이 있을 때 자식 객체를 구성하도록 기준을 명시한다. `id`라는 동명 컬럼도 `post_id`·`comment_id`로 구분해 매핑의 모호함을 줄인다. [MyBatis 중첩 결과 매핑](https://mybatis.org/mybatis-3/sqlmap-xml.html)

### 없는 게시글과 댓글 없는 게시글은 다르다

|상황|객체·API에서 구분할 의미|
|---|---|
|게시글이 있고 댓글도 있음|게시글 객체와 댓글 원소가 있는 목록|
|게시글은 있지만 댓글이 없음|게시글 객체와 빈 댓글 목록 `[]`|
|게시글 자체가 없음|단건 조회 결과가 없음. Service·Controller에서 별도의 없음 처리 필요|

MyBatis의 단건 조회는 결과 객체가 없으면 `null`을 반환할 수 있다. 이것을 댓글 목록이 비었다는 의미와 혼동하지 않는다. 위 예제는 목록을 초기화하고, 응답 계약에서도 댓글 없음이 `[]`로 표현되도록 구성하는 방식이다. [MyBatis 단건·목록 조회](https://mybatis.org/mybatis-3/java-api.html)

`mapUnderscoreToCamelCase`는 `post_id`와 `postId` 같은 이름 대응을 돕는 설정이다. 이것만 켠다고 JOIN 결과가 자동으로 부모·자식 목록 구조가 되는 것은 아니다. [MyBatis 설정 문서](https://mybatis.org/mybatis-3/configuration.html)

### 핵심 포인트

> JOIN은 데이터를 가져오고, 관계 매핑은 그 데이터를 객체 구조로 연결한다. 댓글 목록이 잘못되면 SQL 결과와 부모·자식 식별 컬럼을 먼저 대조한다.

## 2. 객체 생성과 데이터 변환의 경계 나누기 — DTO·Lombok·Jackson

### 개념

DB에서 객체를 만들었다고 바로 브라우저에 JSON이 전달되는 것은 아니다. 조회 객체를 응답 DTO로 바꾸는 단계와, 그 DTO를 JSON으로 쓰는 단계가 이어진다.

DTO는 계층이나 시스템 사이에서 전달할 데이터를 담는 객체다. 요청 DTO와 응답 DTO를 구분하면 입력받을 값과 외부에 공개할 값을 각각 관리할 수 있다.

|단계|입력 → 출력|주요 담당|
|---|---|---|
|DB 결과 매핑|SQL 조회 결과 → Java 객체|MyBatis|
|요청 역직렬화|요청 JSON → 요청 DTO|Spring의 메시지 컨버터와 Jackson|
|애플리케이션 내부 변환|조회·처리 객체 → 응답 DTO|생성자, 정적 팩터리 메서드, Builder 등의 변환 코드|
|응답 직렬화|응답 DTO → JSON 본문|Spring의 메시지 컨버터와 Jackson|
|브라우저 JSON 파싱|응답 본문 → JavaScript 값|`response.json()` 등|

Spring MVC의 `HttpMessageConverter`는 요청·응답 본문을 읽고 쓰는 역할을 한다. JSON 처리에는 Jackson 기반 컨버터 등을 사용한다. [Spring HTTP 메시지 변환](https://docs.spring.io/spring-framework/reference/web/webmvc/message-converters.html)

### 요청과 응답의 동작 흐름

```text
React가 JSON 요청 본문 전송
    ↓ @RequestBody 인자 해석
JSON을 요청 DTO로 역직렬화
    ↓
Controller가 Service 호출
    ↓
Service·Mapper에서 필요한 처리 수행
    ↓ 애플리케이션 내부 변환
응답 DTO 구성
    ↓ Controller 반환값 처리
응답 DTO를 JSON으로 직렬화
    ↓ 브라우저가 본문 파싱
JavaScript 데이터로 사용
```

`@RequestBody`는 요청 본문을 메서드 인자로 변환하는 데 사용하고, `@ResponseBody`는 반환값을 응답 본문에 쓰도록 한다. `@RestController`에는 `@ResponseBody`의 의미가 포함된다. [Spring 요청 본문 처리](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/requestbody.html), [Spring 응답 본문 처리](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/responsebody.html)

### Lombok 애너테이션별 역할

|애너테이션|제공하는 코드|구분할 점|
|---|---|---|
|`@NoArgsConstructor`|매개변수가 없는 생성자|Getter·Setter를 함께 만드는 것은 아니다.|
|`@AllArgsConstructor`|일반적으로 각 인스턴스 필드를 인자로 받는 생성자|JSON 속성과 생성자 인자를 자동으로 연결해 주는 설정은 아니다.|
|`@Builder`|값을 지정한 뒤 `build()`로 객체를 만드는 Builder API|DTO 자체의 Getter·Setter나 JSON 변환 기능을 보장하지 않는다.|
|`@Getter`|필드 값을 읽는 접근자|일반적인 Jackson 응답 직렬화에서 속성을 읽는 통로가 된다.|
|`@Setter`|필드 값을 변경하는 접근자|기본 생성자와 함께 요청 DTO의 값을 채우는 방식에 사용할 수 있다.|

생성자 애너테이션과 Builder는 객체 생성 방식을 돕는 도구다. 클래스 수준 `@Builder`와 다른 생성자를 함께 사용할 때는 Builder가 호출할 생성자 구성이 맞는지 확인한다. 명시적인 생성자에 `@Builder`를 붙이는 방법도 있다. [Lombok 생성자 문서](https://projectlombok.org/features/constructor), [Lombok Builder 문서](https://projectlombok.org/features/Builder)

### 핵심 코드

요청 DTO는 기본 생성자로 객체를 만들고 Setter로 값을 채울 수 있도록 구성한 예시다.

```java
@Getter
@Setter
@NoArgsConstructor
public class CommentCreateRequest {
    private String content;
}
```

응답 DTO는 애플리케이션이 직접 생성한다. Builder를 적용할 생성자를 명시하고, `from()`에서 내부 객체를 응답 형태로 변환한다.

```java
@Getter
public class CommentResponse {
    private final Long id;
    private final Long postId;
    private final String content;

    @Builder
    public CommentResponse(Long id, Long postId, String content) {
        this.id = id;
        this.postId = postId;
        this.content = content;
    }

    public static CommentResponse from(CommentData data) {
        return CommentResponse.builder()
                .id(data.getId())
                .postId(data.getPostId())
                .content(data.getContent())
                .build();
    }
}
```

`CommentResponse.from()`은 Java 객체를 다른 Java 객체로 바꾸는 코드다. JSON 직렬화는 이 메서드가 아니라 이후의 응답 처리에서 수행한다.

### 요청 DTO와 응답 DTO에서 확인할 것이 다른 이유

- 요청 역직렬화에서는 Jackson이 객체를 **어떻게 생성하고 값을 넣을지** 확인한다.
- 응답 직렬화에서는 이미 존재하는 객체에서 **어떤 속성을 읽어 JSON으로 내보낼지** 확인한다.
- 기본 생성자와 Setter는 요청 DTO를 구성하는 한 가지 방법이지 절대적인 필수 조건은 아니다. `@JsonCreator` 등으로 다른 생성 방식을 지정할 수도 있다.
- 응답 객체를 JSON으로 쓰는 데 기본 생성자가 반드시 필요한 것은 아니다. Getter·필드 접근 설정·직렬화 설정을 확인해야 한다. [Jackson 생성 방식과 속성 접근 문서](https://github.com/FasterXML/jackson-annotations)

### 핵심 포인트

> 객체 생성 문제와 JSON 변환 문제는 구분해야 한다. 생성자 애너테이션을 무조건 추가하기보다, 실패한 단계가 객체 생성인지·값 주입인지·속성 읽기인지 먼저 확인한다.

## 3. 비즈니스 로직에 공통 처리를 적용하기 — Spring AOP와 트랜잭션

### 개념과 필요한 이유

댓글 등록의 핵심은 입력에 맞게 댓글을 저장하는 것이다. 실행 시간 측정이나 트랜잭션 처리처럼 여러 기능에 반복되는 작업을 각 메서드에 직접 넣으면 비즈니스 코드와 공통 코드가 섞인다.

AOP는 이런 공통 관심사를 분리하고, 선택한 실행 지점에 부가 기능을 적용하는 방식이다.

|용어|의미|예시|
|---|---|---|
|Aspect|공통 관심사를 모아 놓은 단위|Service 실행 시간 측정|
|Join Point|부가 기능을 적용할 수 있는 실행 지점|Spring AOP에서는 메서드 실행|
|Pointcut|적용할 Join Point를 고르는 조건|특정 패키지의 Service 메서드|
|Advice|선택한 지점에서 실행할 처리와 실행 시점|호출 전 로그, 호출 전후 시간 측정|
|Target|실제 비즈니스 로직을 가진 대상 객체|`CommentService`|
|Proxy|대상 호출을 받아 부가 기능을 적용하는 대리 객체|Spring이 제공하는 Service 프록시|

Pointcut은 **어디에**, Advice는 **무엇을 언제**, Aspect는 **어떤 공통 관심사로 묶을지**에 해당한다. [Spring AOP 핵심 개념](https://docs.spring.io/spring-framework/reference/core/aop/introduction-defn.html)

### Advice 실행 시점

|Advice|실행 시점|주의점|
|---|---|---|
|`@Before`|대상 실행 전|반환값을 바꿔 전달하는 Advice는 아니다.|
|`@AfterReturning`|대상이 정상 반환했을 때|DB 커밋 성공이나 HTTP 응답 성공을 자동으로 의미하지 않는다.|
|`@AfterThrowing`|대상이 예외를 던지며 종료했을 때|작성했다고 예외가 자동으로 해결되는 것은 아니다.|
|`@After`|대상 종료 시, 정상·예외 모두|`finally`와 같은 성격의 후처리다.|
|`@Around`|대상 실행을 감싸는 위치|`proceed()` 호출, 반환값, 예외 전달을 제어할 수 있다.|

여러 Aspect가 함께 적용되면 순서 설정도 확인해야 한다. 따라서 일반적인 `@AfterReturning`을 무조건 커밋 이후의 콜백으로 해석하면 안 된다. [Spring Advice 문서](https://docs.spring.io/spring-framework/reference/core/aop/ataspectj/advice.html)

### 핵심 코드 — 실행 시간 측정

```java
@Slf4j
@Aspect
@Component
public class ServiceTimingAspect {

    @Pointcut("execution(* com.example.board.service..*.*(..))")
    public void serviceMethods() {
    }

    @Around("serviceMethods()")
    public Object measure(ProceedingJoinPoint joinPoint) throws Throwable {
        long startedAt = System.nanoTime();

        try {
            return joinPoint.proceed();
        } finally {
            long elapsed = System.nanoTime() - startedAt;
            log.info("{} elapsedNs={}",
                    joinPoint.getSignature().toShortString(), elapsed);
        }
    }
}
```

- Pointcut은 `com.example.board.service`와 하위 패키지의 메서드를 대상으로 한다.
- `proceed()`는 다음 Advice 또는 대상 메서드로 호출을 진행한다.
- 반환값을 그대로 반환하고, 예외도 삼키지 않아 원래 호출의 결과를 보존한다.
- `finally`에서 시간을 기록하므로 호출이 정상 종료되거나 예외로 종료되어도 측정한다.

이 예제는 Aspect 빈 등록과 AOP 프록시 지원이 활성화되어 있다는 전제다. `@Aspect`만 적는 것으로 모든 설정이 끝나는 것은 아니다. [Spring Pointcut 문서](https://docs.spring.io/spring-framework/reference/core/aop/ataspectj/pointcuts.html)

### 프록시 기반 동작과 내부 호출

```text
호출자가 Spring이 주입한 객체의 메서드 호출
    ↓ 프록시 경유
적용 대상에 맞는 Advice 실행
    ↓
실제 Target 메서드 실행
    ↓ 정상 반환 또는 예외 전달
Advice의 후처리를 거쳐 호출자에게 복귀
```

Spring AOP는 JDK 동적 프록시 또는 CGLIB 기반 프록시를 사용한다. JDK 방식은 인터페이스를 기반으로 하고, CGLIB 방식은 클래스를 상속하는 방식이다. CGLIB에서는 상속·오버라이딩할 수 없는 `final` 클래스·메서드와 `private` 메서드 등에 제약이 있다.

같은 객체 안에서 `this.method()`를 호출하면 프록시를 다시 거치지 않는다. 이 호출에는 해당 메서드의 Advice가 새로 적용되지 않는다. `new`로 직접 만든 객체 역시 Spring이 제공한 프록시가 아니다. [Spring 프록시 동작 문서](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html)

### `@Transactional`은 프록시를 통한 트랜잭션 처리다

트랜잭션은 관련 DB 작업을 하나의 성공·실패 단위로 묶는다. 기본 프록시 방식에서는 트랜잭션 인터셉터가 메서드 호출을 감싸며 트랜잭션 시작·참여·완료를 처리한다.

```text
외부에서 @Transactional 메서드의 프록시 호출
    ↓ 전파 설정과 기존 트랜잭션 확인
새 트랜잭션 시작 또는 기존 트랜잭션 참여
    ↓
Service의 DB 작업과 메서드 본문 실행
    ↓ 반환값 또는 예외가 프록시에 전달됨
롤백 규칙·rollback-only 상태·트랜잭션 소유 범위에 따라 완료 처리
    ↓
호출자에게 반환값 또는 예외 전달
```

기본 전파 방식은 `REQUIRED`다. 기존 트랜잭션이 없으면 시작하고, 있으면 참여한다. 기존 트랜잭션에 참여한 메서드가 반환됐다고 그 자리에서 물리적 커밋이 완료되는 것은 아니다. [Spring](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html) `[@Transactional](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)` [설정](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html), [Spring 트랜잭션 전파](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html)

### 내부 호출이면 항상 트랜잭션이 없는가?

아니다. **내부 메서드의 애너테이션이 새로 적용되는지**와 **이미 시작된 트랜잭션 안에서 실행되는지**를 구분해야 한다.

|호출 상황|트랜잭션 해석|
|---|---|
|기존 트랜잭션 없이 외부에서 `@Transactional` 메서드를 프록시로 호출|기본 `REQUIRED`라면 새 트랜잭션 시작|
|기존 트랜잭션이 있는 상태에서 다른 Bean의 `REQUIRED` 메서드를 프록시로 호출|기존 트랜잭션 참여|
|기존 트랜잭션 없이 같은 객체의 `@Transactional` 메서드를 직접 호출|그 애너테이션에 의한 트랜잭션 시작은 일어나지 않음|
|외부에서 시작된 트랜잭션 안에서 같은 객체의 메서드를 직접 호출|기존 트랜잭션 안에서 실행될 수 있지만 내부 메서드의 별도 설정은 적용되지 않음|

위 비교는 같은 스레드에서 같은 트랜잭션 자원을 사용하는 일반적인 호출을 전제로 한다.

```java
@Service
public class CommentWorkflow {

    public void withoutTransaction() {
        this.saveInNewTransaction();
    }

    @Transactional
    public void withTransaction() {
        this.saveInNewTransaction();
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveInNewTransaction() {
        // 설명용: DB 작업이 수행되는 위치
    }
}
```

외부 트랜잭션이 없는 호출자가 각 진입 메서드를 프록시로 호출한다고 가정하면 다음과 같다.

- `withoutTransaction()`의 내부 호출은 `REQUIRES_NEW`를 적용하지 못한다.
- `withTransaction()`의 내부 호출은 바깥에서 시작된 트랜잭션 안에서 실행되지만, 별도 새 트랜잭션으로 분리되지 않는다.
- 내부 작업에 독립적인 트랜잭션 경계가 필요하다면 별도 Bean으로 책임을 분리해 프록시를 경유하도록 설계할 수 있다. [Spring 내부 호출과 프록시](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html)

### 예외와 롤백 판단

다음은 별도의 전역·개별 롤백 규칙을 바꾸지 않은 기본 설정을 기준으로 한다.

|상황|판단 기준|
|---|---|
|`RuntimeException`·`Error`가 트랜잭션 경계 밖으로 전달됨|기본 롤백 대상|
|Checked Exception이 전달됨|기본 롤백 대상이 아님. 필요하면 `rollbackFor` 지정|
|Service 내부에서 예외를 잡고 정상 반환함|프록시가 그 예외를 보지 못하므로 해당 예외만으로는 롤백을 판단할 수 없음|
|안쪽 트랜잭션 참여 범위에서 이미 rollback-only로 표시됨|바깥에서 예외를 잡더라도 커밋되지 않을 수 있음|
|프록시를 빠져나온 예외를 Controller에서 처리함|응답 방식은 바뀌어도 이미 수행된 트랜잭션 판단을 되돌리지는 않음|

예외를 잡았다는 사실만으로 커밋 여부를 단정하지 않는다. 예외가 어느 경계를 통과했는지와 rollback-only 상태를 함께 확인한다. [Spring 롤백 규칙](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html), [Spring 트랜잭션 참여와 rollback-only](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html)

MyBatis-Spring의 DB 작업도 Spring 트랜잭션에 참여할 수 있다. 이때 트랜잭션 매니저와 `SqlSessionFactory`가 같은 `DataSource`를 사용해야 한다. 트랜잭션 밖에서 실행한 Mapper 호출이 저장되지 않는다고 생각해서도 안 된다. MyBatis-Spring은 트랜잭션 밖의 Mapper 작업을 자동 커밋할 수 있다. [MyBatis-Spring 트랜잭션 문서](https://mybatis.org/spring/transactions.html)

### 핵심 포인트

> 트랜잭션은 애너테이션의 존재만으로 판단하지 않는다. 프록시 경유 여부, 기존 트랜잭션, 전파 설정, 예외가 전달된 경계와 롤백 상태를 함께 확인한다.

## 4. HTTP 요청과 메서드 호출의 개입 지점 구분하기 — Filter·Interceptor·AOP

### 개념과 비교

AOP가 메서드 호출에 공통 처리를 적용한다면, Filter와 Interceptor는 웹 요청의 처리 흐름에 관여한다. 모두 전후 처리가 가능하다는 공통점이 있지만 같은 위치에서 동작하는 것은 아니다.

`DispatcherServlet`은 Spring MVC의 중앙 진입점인 Front Controller다. 요청에 맞는 핸들러를 찾고, 그 핸들러를 실행할 어댑터와 응답 처리 흐름을 조정한다.

|구분|Filter|Interceptor|Spring AOP|
|---|---|---|---|
|기반|Servlet API|Spring MVC|Spring의 프록시 기반 메서드 호출|
|적용 대상|등록 조건에 맞는 서블릿 요청·응답|매핑된 MVC 핸들러 실행 흐름|Pointcut에 맞고 프록시로 호출되는 Bean 메서드|
|주요 개입 지점|다음 Filter·서블릿으로 전달하기 전후|핸들러 실행 전·정상 처리 후·완료 시|대상 메서드 실행 전후|
|대표 API|`doFilter`, `FilterChain`|`preHandle`, `postHandle`, `afterCompletion`|`@Before`, `@Around` 등|
|대표 용도|요청 공통 로깅, 인코딩, 요청·응답 래핑|핸들러 관련 공통 검사·로깅|실행 시간 측정, 트랜잭션 등|
|범위 기준|URL 패턴·서블릿 매핑·디스패치 유형 등|HandlerMapping·경로 등록 등|메서드 조건과 프록시 경유 여부|

Filter의 실행 위치가 DispatcherServlet 바깥이라는 말은, Filter를 Spring Bean으로 관리할 수 없다는 뜻이 아니다. Spring Boot의 내장 서블릿 컨테이너에서는 Filter Bean을 등록하는 방식도 사용할 수 있다. [Spring Boot Filter 등록](https://docs.spring.io/spring-boot/reference/web/servlet.html)

Interceptor는 MVC 핸들러에 적용되므로 무조건 Controller 메서드만 대상으로 한다고 단정하지 않는다.

### 핵심 코드 — Filter의 전달과 후처리

Spring Boot의 서블릿 환경에서 Filter를 Bean으로 등록한 예시다.

```java
@Slf4j
@Component
public class RequestTraceFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request,
                         ServletResponse response,
                         FilterChain chain)
            throws IOException, ServletException {
        log.info("filter before");

        try {
            chain.doFilter(request, response);
        } finally {
            log.info("filter after");
        }
    }
}
```

`chain.doFilter()`를 호출하면 다음 Filter 또는 대상 서블릿으로 진행한다. 호출하지 않고 반환하면 다음 단계로 넘어가지 않으므로, 중단하는 Filter가 응답을 적절하게 구성해야 한다. 예외가 발생해도 수행할 후처리는 단순히 호출문 아래에 두지 말고 `finally`의 의미를 고려한다. [Jakarta Servlet Filter API](https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/filter)

### 핵심 코드 — Interceptor의 세 시점

```java
@Slf4j
@Component
public class HandlerTraceInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) {
        log.info("interceptor preHandle");
        return true;
    }

    @Override
    public void postHandle(HttpServletRequest request,
                           HttpServletResponse response,
                           Object handler,
                           ModelAndView modelAndView) {
        log.info("interceptor postHandle");
    }

    @Override
    public void afterCompletion(HttpServletRequest request,
                                HttpServletResponse response,
                                Object handler,
                                Exception ex) {
        log.info("interceptor afterCompletion");
    }
}
```

Interceptor는 Bean으로 만드는 것뿐 아니라 MVC 처리 경로에 등록해야 한다.

```java
@Configuration
@RequiredArgsConstructor
public class InterceptorConfig implements WebMvcConfigurer {
    private final HandlerTraceInterceptor handlerTraceInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(handlerTraceInterceptor)
                .addPathPatterns("/api/**");
    }
}
```

|메서드|동작과 조건|
|---|---|
|`preHandle`|핸들러가 선택된 뒤 실행 전 호출. `true`면 진행하고, `false`면 체인을 중단한다.|
|`postHandle`|HandlerAdapter의 정상 처리 후 호출. 일반적인 View 렌더링보다 앞이지만, REST 응답 본문 쓰기보다 항상 앞인 것은 아니다.|
|`afterCompletion`|MVC 요청 처리 완료 시 호출. 자신의 `preHandle`이 정상적으로 `true`를 반환한 경우에만 대상이 된다.|

여러 Interceptor의 `postHandle`·`afterCompletion`은 적용된 체인의 역순으로 호출된다. 예외가 처리기에 의해 해결되었다면 `afterCompletion`의 `ex`가 반드시 그 예외를 담는 것도 아니다. [Spring HandlerInterceptor API](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/servlet/HandlerInterceptor.html)

### 동작 흐름 — 정상적인 동기식 REST 요청

아래는 Service가 최상위 트랜잭션을 시작하고, 요청이 정상적으로 끝나는 경우다. AOP를 Service에 적용한 예이며 모든 AOP의 위치가 Service로 고정된다는 뜻은 아니다.

```text
Filter 전처리
    ↓ chain.doFilter()
DispatcherServlet이 HandlerMapping으로 핸들러 선택
    ↓
Interceptor.preHandle()
    ↓ true
HandlerAdapter에서 요청 인자 변환 후 Controller 실행
    ↓
Service 프록시에서 트랜잭션 시작
    ↓
Service → Mapper → DB 작업
    ↓
Service 본문 반환 후 트랜잭션 프록시에서 커밋
    ↓
Controller가 응답 DTO 반환
    ↓ HandlerAdapter 내부 반환값 처리
HttpMessageConverter가 JSON 직렬화·응답 쓰기
    ↓
Interceptor.postHandle()
    ↓
Interceptor.afterCompletion()
    ↓ DispatcherServlet 호출에서 복귀
Filter 후처리
```

`@ResponseBody`·`ResponseEntity` 응답은 HandlerAdapter 내부에서 본문이 쓰이고 응답이 커밋된 뒤 `postHandle`이 호출된다. 따라서 `postHandle`을 JSON 변환 전 시점으로 생각하거나 여기서 응답 헤더·본문을 자유롭게 바꾸려 해서는 안 된다. 응답 본문을 쓰기 직전의 공통 변환은 `ResponseBodyAdvice` 같은 별도의 지점을 검토한다. [Spring MVC Interception 문서](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet/handlermapping-interceptor.html)

여기서 **HTTP 응답 커밋**은 상태·헤더 등이 확정되어 전송되는 의미다. **DB 트랜잭션 커밋**과는 다른 사건이다.

### 요청이 중단되거나 예외가 발생하면

|상황|실행 범위|
|---|---|
|Filter가 `chain.doFilter()`를 호출하지 않음|이후 Filter·서블릿·Controller로 진행하지 않는다.|
|Interceptor가 `preHandle()`에서 `false` 반환|이후 Interceptor·핸들러는 실행하지 않는다. 먼저 `true`를 반환한 Interceptor에는 완료 처리가 적용될 수 있다.|
|Controller 처리 또는 JSON 쓰기 중 예외가 전파됨|정상 후처리인 `postHandle`은 건너뛸 수 있다. 조건을 충족한 Interceptor의 완료 처리는 별도로 진행된다.|
|서버의 `afterCompletion`이 호출됨|브라우저의 JSON 파싱이나 React 렌더링 성공까지 증명하지는 않는다.|

이 흐름은 동기식 요청 기준이다. 비동기 처리나 에러 재디스패치에서는 호출 시점·횟수가 달라질 수 있으므로 같은 순서를 기계적으로 적용하지 않는다. [Spring Interceptor 실행 조건](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/servlet/HandlerInterceptor.html)

### 핵심 포인트

> Filter는 서블릿 호출 체인, Interceptor는 MVC 핸들러 처리, AOP는 프록시 기반 메서드 호출을 기준으로 구분한다. 서버의 후처리 완료와 클라이언트의 화면 반영 완료도 서로 다르다.

## 5. 댓글 등록부터 화면 갱신까지 연결하기 — API 계약·CORS·실패 단계

### 개념

앞에서 구분한 처리 단계는 React가 댓글 등록 요청을 보낼 때 하나의 흐름으로 연결된다. 연동의 출발점은 프론트와 백엔드가 URL·HTTP 메서드·입력 위치·응답 구조를 동일하게 이해하는 것이다.

다음은 흐름을 설명하기 위한 API 계약 예시다.

|작업|요청|입력|성공 응답 예시|
|---|---|---|---|
|댓글 등록|`POST /api/posts/{postId}/comments`|경로의 게시글 ID, JSON의 `content`|`201 Created`와 생성된 댓글 객체|
|댓글 목록 재조회|`GET /api/posts/{postId}/comments`|경로의 게시글 ID|`200 OK`와 댓글 배열|

`postId`는 `@PathVariable`로 받고, JSON 본문의 `content`는 `@RequestBody` DTO로 받는다. 입력 위치는 API 계약의 문제이며, 요청의 동기·비동기 여부를 결정하는 기준은 아니다.

### 핵심 코드 — Controller와 트랜잭션 Service 연결

아래 예제는 핵심 호출 구조만 나타낸다. 입력 검증, 게시글 존재·권한 확인, 상세한 예외 응답 정책은 생략했다.

```java
@RestController
@RequestMapping("/api/posts/{postId}/comments")
@RequiredArgsConstructor
public class CommentController {
    private final CommentService commentService;

    @PostMapping
    public ResponseEntity<CommentResponse> create(
            @PathVariable("postId") Long postId,
            @RequestBody CommentCreateRequest request) {
        CommentResponse response = commentService.create(postId, request);
        return ResponseEntity.status(HttpStatus.CREATED).body(response);
    }

    @GetMapping
    public List<CommentResponse> findAll(
            @PathVariable("postId") Long postId) {
        return commentService.findAll(postId);
    }
}

@Service
@RequiredArgsConstructor
public class CommentService {
    private final CommentMapper commentMapper;

    @Transactional
    public CommentResponse create(Long postId, CommentCreateRequest request) {
        CommentData data = new CommentData();
        data.setPostId(postId);
        data.setContent(request.getContent());

        if (commentMapper.insert(data) != 1) {
            throw new IllegalStateException("댓글 저장 결과가 올바르지 않습니다.");
        }

        return CommentResponse.from(data);
    }

    public List<CommentResponse> findAll(Long postId) {
        return commentMapper.findByPostId(postId).stream()
                .map(CommentResponse::from)
                .toList();
    }
}
```

Mapper는 `insert(CommentData data)`와 `findByPostId(@Param("postId") Long postId)`를 제공하는 Spring 관리 Mapper라고 가정한다. 댓글 ID가 DB에서 자동 생성되는 테이블의 XML 예시는 다음과 같다.

```xml
<mapper namespace="com.example.board.mapper.CommentMapper">
    <insert id="insert"
            useGeneratedKeys="true"
            keyProperty="id"
            keyColumn="id">
        INSERT INTO comments (post_id, content)
        VALUES (#{postId}, #{content})
    </insert>

    <select id="findByPostId"
            resultType="com.example.board.model.CommentData">
        SELECT id, post_id AS postId, content
        FROM comments
        WHERE post_id = #{postId}
        ORDER BY id
    </select>
</mapper>
```

`insert()`의 반환값은 생성된 ID가 아니라 영향받은 행 수다. 생성 키는 지원하는 DB·JDBC 드라이버에서 `keyProperty`에 지정한 `data.id`로 전달받는다. INSERT 성공이나 ID 할당 자체를 커밋 완료로 해석하지 않는다. [MyBatis Mapper XML](https://mybatis.org/mybatis-3/sqlmap-xml.html), [MyBatis Java API](https://mybatis.org/mybatis-3/java-api.html)

이 예제에서는 `CommentResponse.from(data)`가 트랜잭션 메서드 본문 안에서 실행된다. 반면 DTO를 JSON으로 쓰는 처리는 Controller 반환 이후다. **Java 객체 간 변환과 JSON 직렬화를 구분해야 실패 시 트랜잭션 영향도 판단할 수 있다.**

### CORS와 사전 요청

Origin은 스킴·호스트·포트의 조합이다. 예를 들어 `http://localhost:5173`과 `http://localhost:8080`은 포트가 달라 서로 다른 Origin이다.

CORS는 서버가 허용 조건을 응답하고, 브라우저가 이를 검사해 다른 Origin의 응답을 JavaScript에서 사용할 수 있게 하는 방식이다. 서버의 인증·인가를 대신하는 기능은 아니다.

다른 Origin으로 `Content-Type: application/json`인 POST를 보내면 일반적으로 사전 요청 대상이 된다. 브라우저는 `OPTIONS`로 실제 사용할 메서드·헤더의 허용 여부를 먼저 확인한다. 사전 요청 허용 결과가 캐시되어 있으면 매번 OPTIONS가 보이지 않을 수 있다. [MDN CORS 문서](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS), [MDN 사전 요청 문서](https://developer.mozilla.org/en-US/docs/Glossary/Preflight_request)

```text
React에서 다른 Origin으로 JSON POST 요청
    ↓ 필요한 경우 브라우저가 먼저 OPTIONS 전송
서버가 Origin·요청 메서드·요청 헤더의 허용 조건 응답
    ↓ 사전 확인 통과
브라우저가 실제 POST 전송
    ↓
서버가 댓글 처리 후 실제 응답 전송
    ↓ 실제 응답에도 CORS 조건 적용
브라우저가 허용 여부를 확인하고 JavaScript에 응답 제공
```

사전 요청이 필요 없는 요청도 실제 응답의 CORS 검사는 받는다. 또한 사전 요청이 통과했다는 사실만으로 실제 API 응답의 CORS 처리가 올바르다고 단정할 수 없다.

### 핵심 코드 — 예제 API에 대한 CORS 설정

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("http://localhost:5173")
                .allowedMethods("GET", "POST")
                .allowedHeaders("Content-Type");
    }
}
```

위 예제는 쿠키 인증이나 Authorization 헤더를 사용하지 않는 요청을 기준으로 한다. 실제 요청에 추가 헤더·인증 정보가 있으면 해당 조건에 맞춰 설정해야 한다. 쿠키 등을 포함하는 교차 Origin 요청에는 자격 증명 허용 조건이 추가되며, 허용 Origin을 단순한 `*`로 지정할 수 없다. [Spring MVC CORS 설정](https://docs.spring.io/spring-framework/reference/web/webmvc-cors.html)

앞단의 Filter·Spring Security가 사전 요청을 먼저 막는 경우에는 MVC 설정만 확인해서는 부족하다. 요청이 어느 계층까지 도달했는지도 함께 확인한다. [Spring Security의 CORS 통합](https://docs.spring.io/spring-security/reference/servlet/integrations/cors.html)

### 핵심 코드 — 등록 요청과 목록 갱신을 나눠 처리하기

다음은 `postId`와 댓글 입력·목록·안내 메시지 상태를 가진 React 컴포넌트의 제출 처리 부분이다. 등록 응답을 확인한 뒤 목록을 재조회하는 방식을 사용한다.

```js
async function handleSubmit(event) {
    event.preventDefault();
    setMessage("");

    const url = `http://localhost:8080/api/posts/${postId}/comments`;

    try {
        const response = await fetch(url, {
            method: "POST",
            headers: { "Content-Type": "application/json" },
            body: JSON.stringify({ content })
        });

        if (!response.ok) {
            throw new Error(`등록 응답 오류: HTTP ${response.status}`);
        }

        const created = await response.json();
        if (created.id == null) {
            throw new Error("등록 응답 구조가 예상과 다릅니다.");
        }
        setContent("");
    } catch {
        setMessage("등록 성공 여부를 확인하지 못했습니다. 재등록 전에 목록을 재조회하세요.");
        return;
    }

    try {
        const response = await fetch(url);
        if (!response.ok) {
            throw new Error(`목록 조회 오류: HTTP ${response.status}`);
        }

        const latestComments = await response.json();
        if (!Array.isArray(latestComments)) {
            throw new Error("댓글 목록 응답이 배열이 아닙니다.");
        }
        setComments(latestComments);
    } catch {
        setMessage("등록 응답은 확인했지만 목록 갱신에 실패했습니다. 목록을 다시 조회하세요.");
    }
}
```

`fetch()`는 HTTP 400·500을 받았다는 이유만으로 Promise가 거부되는 것은 아니므로 `response.ok` 등을 확인해야 한다. `response.json()`도 별도의 비동기 파싱 단계이며, 비어 있거나 올바르지 않은 JSON 본문이면 실패할 수 있다. [MDN Fetch 사용법](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)

실제 화면에는 위에서 갱신한 `comments` 상태가 렌더링에 사용되어야 한다. 다른 변수나 이전 props를 출력하고 있으면 상태를 갱신해도 기대한 목록이 보이지 않을 수 있다.

|목록 갱신 방식|특징|
|---|---|
|등록 응답을 상태에 추가|추가 GET 요청 없이 반영할 수 있지만 서버의 정렬·필터 조건과 일치하는지 고려해야 한다.|
|목록을 재조회한 뒤 상태 교체|서버 조회 결과를 기준으로 반영한다. 등록 성공과 재조회 성공은 별도로 확인해야 한다.|

기존 배열을 직접 `push()`하기보다 새 배열로 상태를 갱신한다. 응답 추가 방식이라면 `setComments(prev => [...prev, created])`처럼 작성할 수 있다. 상태 설정은 다음 렌더링을 요청하는 동작이므로, 바로 다음 줄에서 읽는 기존 상태 값이 즉시 바뀌었다고 가정하지 않는다. [React 배열 상태 갱신](https://react.dev/learn/updating-arrays-in-state), [React 상태의 스냅샷](https://react.dev/learn/state-as-a-snapshot)

### DB 저장 성공과 응답·화면 성공 분리하기

다음은 특정 오류가 실제 발생했다는 기록이 아니라, 오늘 학습한 흐름에 따른 판단 기준이다.

|실패 지점|DB 작업에 대해 판단할 수 있는 것|
|---|---|
|사전 요청이 차단되어 실제 POST가 전송되지 않음|해당 시도의 실제 POST를 통한 댓글 저장은 수행되지 않는다.|
|SQL 실행 또는 트랜잭션 처리 중 실패|트랜잭션 범위·롤백 규칙·실제 DB 결과를 확인해야 한다.|
|Service 내부 DTO 변환에서 예외 발생|아직 트랜잭션 안이라면 예외 전달과 롤백 규칙에 따라 DB 작업도 롤백될 수 있다.|
|DB 커밋 완료 후 JSON 직렬화·응답 쓰기 실패|이미 커밋된 데이터는 이 실패만으로 자동 롤백되지 않는다.|
|실제 요청 전송 후 네트워크 오류·CORS 응답 차단|브라우저에서 결과를 읽지 못해도 서버는 저장을 완료했을 수 있다.|
|브라우저 JSON 파싱 또는 React 화면 처리 실패|서버 저장의 성공 여부와 별개다. 저장 결과를 재확인해야 한다.|
|등록 응답 확인 후 목록 재조회 실패|등록을 다시 시도하기보다 목록 조회 실패를 따로 점검해야 한다.|

Service 트랜잭션이 끝난 뒤 JSON 응답을 쓰는 앞선 예제에서는, **직렬화 오류가 발생해도 이미 저장된 댓글이 남을 수 있다**는 결론이 나온다. 이는 트랜잭션 완료 시점과 응답 쓰기 시점을 연결한 판단이다. [Spring 트랜잭션 경계](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html), [Spring REST 응답 쓰기 시점](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet/handlermapping-interceptor.html)

### 연동 결과를 점검하는 순서

1. **Network:** 실제 요청 URL·메서드·본문이 맞는지, OPTIONS와 POST 중 어디까지 전송되었는지 확인한다.
2. **서버 로그:** Filter·Interceptor·Controller·Service 중 어디까지 도달했는지와 예외의 원인 체인을 확인한다.
3. **DB 재조회:** 댓글 ID·게시글 ID·내용을 기준으로 저장 결과를 확인한다. INSERT 로그만으로 커밋 성공을 단정하지 않는다.
4. **응답:** 상태 코드·CORS 헤더·Content-Type·JSON 구조를 대조한다. `{ "comments": [...] }`와 `[...]`는 사용하는 방식이 다르다.
5. **React:** 응답 파싱, 상태 변경, 실제 렌더링 데이터, 목록의 `key`가 올바른지 확인한다.

> 화면에서 실패했다고 곧바로 같은 등록 요청을 반복하면 중복 저장될 수 있다. 먼저 서버의 저장 결과와 응답·화면 처리 결과를 분리해서 확인한다.

### 핵심 포인트

> 댓글 기능의 완료는 요청 전송 하나로 결정되지 않는다. DB 작업, 응답 생성·전달, JSON 파싱, 상태 갱신과 화면 반영이 각각 의도대로 이루어졌는지 확인해야 한다.

# 🧠 오늘 이해한 핵심

- **데이터가 바뀌는 경계와 작업을 맡는 도구가 다르다.** MyBatis의 행→객체 매핑, 애플리케이션의 객체→DTO 변환, Jackson의 DTO→JSON 직렬화를 구분하면 확인할 위치가 선명해진다.
- **부가 기능은 애너테이션 이름보다 호출 경로와 실행 경계가 중요하다.** 내부 호출의 Advice 우회, 기존 트랜잭션 참여, Filter·Interceptor의 실행 조건을 함께 보아야 한다.
- **서버와 브라우저는 하나의 성공·실패 단위가 아니다.** DB 커밋 이후 응답이나 화면 처리만 실패할 수 있으므로, 클라이언트 오류만으로 저장 실패를 단정할 수 없다.

# 🔍 복습할 부분

- 댓글 0개·1개·여러 개의 JOIN 결과를 직접 적고, 부모·자식 `<id>`와 `notNullColumn`이 객체 및 목록 구성에 어떻게 연결되는지 확인하기.
- 외부 호출과 내부 호출을 기존 트랜잭션 유무별로 나누고, `REQUIRED`·`REQUIRES_NEW` 적용 여부와 예외를 잡는 위치에 따른 롤백 판단 설명하기.
- 정상 REST 응답, `preHandle=false`, Controller 예외, JSON 직렬화 예외를 비교해 `postHandle`·`afterCompletion`·Filter 후처리 중 무엇이 실행되는지 구분하기.
- 댓글 등록 실패 메시지가 보이는 상황을 요청 전송·DB 처리·응답 변환·상태 갱신으로 나누고, 각 단계에서 Network·로그·DB 중 어떤 근거를 확인할지 정리하기.

# 🔄 함께 복습한 내용

- **JOIN과 관계 매핑:** 같은 게시글이 여러 JOIN 행에 반복되는 것은 댓글과 결합된 결과다. 부모·자식 식별 정보를 구분하고, 댓글 없음은 게시글 없음과 다르게 빈 목록으로 표현한다.
- **프록시와 트랜잭션:** 내부 호출은 해당 메서드의 트랜잭션 설정을 새로 적용하지 않지만, 이미 시작된 트랜잭션 안에서는 실행될 수 있다. 롤백은 예외 종류뿐 아니라 전달된 경계와 rollback-only 상태까지 확인한다.
- **생성자·Builder·JSON:** 생성자와 Builder는 객체 생성, Getter·접근 설정은 속성 읽기와 관련된다. 요청 DTO를 만드는 문제와 이미 만들어진 응답 DTO를 직렬화하는 문제를 구분한다.
- **댓글 등록과 화면 반영:** 사전 요청, 실제 요청, 서버 처리, 응답 파싱, 상태 갱신은 서로 다른 단계다. 커밋 이후 응답·화면 실패가 발생할 수 있으므로 재등록 전에 저장 여부를 확인한다.
